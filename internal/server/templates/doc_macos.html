macOS agents (Apple silicon)

The macOS agent backs up the files and folders of a Mac with Apple silicon. It runs as a service from the first boot, reads every backup of the startup disk from an APFS local snapshot and keeps the Mac's file metadata. A menu bar app shows its state and guides the user through the permissions only he can grant.

Preview. The macOS agent is new in 0.59. It was written and tested on Macs by a contributor; our own tests of it run on macOS in the build pipeline. Please report what does not work in GitHub Issues.

Requirements

  • A Mac with Apple silicon (M1 and newer, arm64) and macOS 13 or newer. Intel Macs get no package.
  • An administrator account on the Mac, for the installation and the enrollment.
  • The user of the Mac, to grant Full Disk Access: macOS lets nobody else do it, neither a script nor the console.
  • Like every agent, the Mac must reach the console's agent address (usually port 8443) and the storage.

Installing

  1. On the Agents page, download macOS agent — Apple silicon (backupzit-agent_version_darwin_arm64.pkg). The console package carries it, like the Windows and Linux installers.
  2. Open the .pkg on the Mac and follow the installer. A package that is not signed with an Apple Developer ID makes macOS ask for confirmation first: right-click it and choose Open (on newer macOS: System Settings → Privacy & Security → Open Anyway).
  3. The installer's last page explains the permissions to grant, and the menu bar app opens.

The package installs:

WhatWhere
The agent program/Library/BackupZit/bin/backupzit-agent
The uninstaller/Library/BackupZit/uninstall.sh
The menu bar app/Applications/BackupZit.app
The agent service (LaunchDaemon: runs as root, starts at boot, restarted when it stops)/Library/LaunchDaemons/com.backupzit.agent.plist
The menu bar app at login (LaunchAgent)/Library/LaunchAgents/com.backupzit.tray.plist
Configuration (root only, created at enrollment)/Library/Application Support/BackupZit/agent.json
Log/Library/Logs/BackupZit/agent.log

The program is not added to the PATH: in Terminal, call it with its full path.

Enrolling

The service is installed and running even before the Mac is enrolled; it starts working as soon as it is. On the Agents page, Create enrollment token shows the code and the commands for macOS next to those for Windows and Linux. Choose one of four ways:

  1. In the menu bar app, after the installation (the usual way, agents 0.60 and newer): while the Mac is not enrolled, the BackupZit menu bar app asks for the code right after the installation. Paste it, click Enroll and enter an administrator's name and password when macOS asks. The app then says whether the enrollment worked, and why not. Later, or after Later, choose Enroll this Mac… in its menu; the item is there while the Mac is not enrolled.
  2. In Terminal, after the installation: 
    sudo /Library/BackupZit/bin/backupzit-agent enroll --code "BZ1-..."
  3. With an MDM (Jamf, Intune, Mosyle…): before the package is installed, a script writes the code to a file owned by root: 
    echo "BZ1-..." | sudo sh -c 'umask 077; mkdir -p "/Library/Application Support/BackupZit"; cat > "/Library/Application Support/BackupZit/enroll-code"'
    Then deploy the package. Its installation enrolls the Mac with the code and deletes the file. A file not owned by root is ignored. This is also the way to move an enrolled Mac to another console.
  4. A file next to the package: backupzit-enroll.txt with the code, in the same folder as the .pkg on the Mac's startup disk (for example in /Users/Shared; copy both from a USB stick or a network share first: on such a volume any file can claim to belong to root). It is used only while the Mac is not enrolled yet, and only if nobody else could have written it: the file belongs to root or an administrator of the Mac, has one name and only its owner may change it, and its folder belongs to root or an administrator and is not writable by other users (or has the sticky bit, like /Users/Shared).

If the console cannot be reached during the installation, the agent keeps the code and retries. If the enrollment fails, the reason is in /Library/Application Support/BackupZit/enroll-error.log; enroll from the menu bar app or in Terminal afterwards. Upgrades and reinstallations keep the enrollment.

Permissions

macOS protects some data from every program, also from one running as root, until the user allows it in System Settings. Only the user at the Mac can grant these permissions; the installer's last page and the menu bar app walk him through them.

Full Disk Access for the agent

Without it, backups miss the folders macOS protects, and no APFS snapshot is taken (see What is backed up).

  1. Open System Settings → Privacy & Security → Full Disk Access.
  2. Click + below the list and enter your password.
  3. Press Command-Shift-G, type /Library/BackupZit/bin/backupzit-agent, press Return and click Open.
  4. Check that the switch next to backupzit-agent is on.

Instead of +, you can drag the file into the list: in the Finder choose Go → Go to Folder…, type /Library/BackupZit/bin and drag backupzit-agent onto the list.

The agent in the background

After the installation macOS shows Background Items Added. In System Settings → General → Login Items & Extensions, under Allow in the Background, backupzit-agent and BackupZit must stay on: switched off, the agent does not run and no backup starts.

Notifications and open at login

  • Notifications: allow them when the menu bar app asks, or later in System Settings → Notifications → BackupZit (Allow notifications). The app tells the user there when a backup fails.
  • Open at login: the menu bar app opens at every login while BackupZit is on under Login Items & Extensions → Allow in the Background.

The menu bar app and its assistant

The BackupZit icon in the menu bar shows the agent's state; its menu has Back up now for each job of the Mac, Open console in browser and Hide this icon (until the next login; backups continue). Its Permissions section lists the agent in the background, Full Disk Access, notifications and open at login, each with ✅ or ❌. Click an item to open its page of System Settings; a missing permission is also explained once per login in a dialog with the steps to take. While something is missing, it checks again by itself every few seconds, so ✅ appears as soon as the permission is granted. The agent also reports a missing Full Disk Access to the console, in the run report.

Checking in Terminal

/Library/BackupZit/bin/backupzit-agent status

It works as a normal user and shows the console, the jobs and full disk access: granted or denied (with the program to switch on).

Full Disk Access after an update

macOS ties Full Disk Access to the program's signature. Packages signed with an Apple Developer ID keep it across updates. A package built without one (signed ad hoc) loses it with each self-update: backups then warn again, and the menu bar app says that Full Disk Access is gone since the update. Grant it again: in the Full Disk Access list select backupzit-agent, click − to remove it (switching it off and on is not enough), then add it again with + as above.

What is backed up

A Mac agent runs files and folders jobs like any agent: paths such as /Users, /Applications or /, {users} paths (/Users/<name>/Documents) and wildcards, also in a job for several agents with All macOS agents.

APFS local snapshot

Every files backup of the startup disk's data volume is read from an APFS local snapshot, the macOS counterpart of VSS on Windows: the backup sees every file as of one moment, also those a program keeps writing. The agent takes the snapshot (tmutil localsnapshot), mounts it read-only, reads the files from it and unmounts and deletes it after the backup. Snapshots left by a crash are cleaned up at the next start; Time Machine's own snapshots are never touched. The run report says Read from an APFS local snapshot of /System/Volumes/Data.

The snapshot needs the service (root) and Full Disk Access. Without Full Disk Access, and for paths on other volumes (/Volumes: external disks, network shares), the files are read without a snapshot, and the run report says so.

Metadata

Kept with every file and folder: owner and group, permissions, extended attributes (except com.apple.provenance, which macOS manages itself), hard links, symbolic links, BSD file flags (hidden, locked, nodump, append-only…; the system flags only when the agent runs as root, as the service does), the creation time and modification times to the nanosecond. Sparse files stay sparse: their holes are punched again on APFS.

Folders kept empty

Some system folders below a backed up folder are kept as empty folders: other volumes (/Volumes), swap (/System/Volumes/VM, /private/var/vm), the support volumes in /System/Volumes, /dev, temporary files (/private/tmp, /private/var/folders), caches (/Library/Caches, /System/Library/Caches, ~/Library/Caches), the Trash (~/.Trash, .Trashes), Spotlight, FSEvents, document versions and local and HFS+ Time Machine backups. With / as a source, the data volume's folders that / already shows (/Users, /Applications…) are not read twice. A folder named as a source of the job is always read, e.g. /Volumes/USB or ~/.Trash.

Warnings in the run report

Without Full Disk Access the folders macOS protects cannot be read: Mail, Messages, Safari, Desktop and Documents, other apps' data, removable and network volumes. A backup whose sources reach /Users (except /Users/Shared), /Library or /Volumes, or a folder above them such as /, then ends with the warning Full Disk Access is not granted to the BackupZit agent. Backups of other folders (e.g. /opt/data) do not warn.

Files in iCloud Drive

With Desktop & Documents in iCloud Drive and Optimize Mac Storage on, macOS keeps the content of files not used for a while only in iCloud. The file stays in the Finder with its name and size, but its data is not on the Mac (a "dataless" file, shown with the iCloud download arrow). A backup cannot read such a file: an APFS snapshot does not hold its content, and a read on the live disk would have iCloud download it in its owner's session, which fails while that user is not signed in. Since 0.60 the agent never opens these files and never makes iCloud download one:

  • A file that was in the previous backup and has not changed since (same size and modification time) keeps its content from there, so a file freed up after a backup stays in the backups.
  • Any other such file is left out of the backup and counted apart from the read errors. The run ends with a warning such as 3360 files (1.2 GiB) are in iCloud Drive but not downloaded on this Mac, and the run page lists them per folder (e.g. /Users/anna/Documents) with the number of files and their size.

To have them backed up, download them on the Mac before the backup: in the Finder, right-click the folder → Download Now, or in Terminal as that user find ~/Documents -type f -exec brctl download {} \;. To keep them on the Mac for good, turn off Optimize Mac Storage in System Settings → your name → iCloud. Files of a user who is not signed in to the Mac can only be downloaded once that user signs in.

Restoring

Files of a Mac are restored like all file backups: the whole backup or only some paths, into a folder or to the original location, on the Mac or on another agent; single files can be downloaded from the console. A restore on a Mac sets the metadata above again. Like on Windows and Linux, it writes only through the folders it opened, never by path, so a link put in the way during the restore is not followed. A restore over locked files clears their locked and append-only flags first and sets the stored ones again (system flags cannot be cleared on a running Mac).

Updating and uninstalling

The Agents page offers Update to version for a Mac like for other agents (see Agents). The agent downloads the .pkg from the console, checks it against the signed list of agent installers and its SHA-256 checksum, installs it with Apple's installer in a one-shot launchd job and restarts with the new version. If launchd refuses that job, the update run fails with launchd's message. The installer log is in /Library/Application Support/BackupZit/updates. Check Full Disk Access after an update of an unsigned package.

Remove on the Agents page with Uninstall the agent from the computer removes the program, the menu bar app, the LaunchDaemon and LaunchAgent and the package receipt; the configuration and the log stay. To uninstall by hand:

sudo /Library/BackupZit/uninstall.sh            # keeps configuration and log
sudo /Library/BackupZit/uninstall.sh --purge    # deletes them too

Without --purge the enrollment is set aside (agent.json.removed-date), so a new installation asks for a code again. After uninstalling, remove backupzit-agent from Privacy & Security → Full Disk Access by hand: macOS does not let a program do it.

What a Mac agent cannot do

Not on a MacInstead
Linux system / bare-metal backupsThe console refuses a system job for a Mac (is a Mac: back it up with a files job): its system volume is sealed and signed by Apple and is reinstalled, not restored. Back up the data with a files job.
Disk imagesWindows only.
Hyper-V, Proxmox VE hosts and VMware ESXi proxyAgents on the Hyper-V host (Windows), the Proxmox node (Linux) or a Linux proxy agent.
NAS / file share jobs (SMB, NFS)A Windows or Linux agent for now: the Mac agent does not mount shares yet.
PostgreSQL / MySQL jobsNot validated on macOS yet: use them on a Mac only after testing a restore.

Microsoft 365 jobs run on any agent with internet access, a Mac too.

Then check the network path to the console as for any agent (Troubleshooting).
"Full Disk Access is not granted to the BackupZit agent", full disk access: deniedGrant it as in Full Disk Access.

The run says the files were read "without a snapshot""No APFS local snapshot … was taken": grant Full Disk Access. "Not on the startup disk's data volume": the path is on an external disk or a share, which APFS local snapshots do not cover; it is backed up all the same. Any other reason is in the message.
An update run failedThe run shows the reason, e.g. launchd's refusal of the installer job. The installer's output is in /Library/Application Support/BackupZit/updates (Get log on the Agents page includes it). Installing the newer .pkg by hand also works; the enrollment is kept.

"… are in iCloud Drive but not downloaded on this Mac"Their content is only in iCloud (Optimize Mac Storage). Download them on the Mac or turn the option off: see Files in iCloud Drive.

Logs

  • Agent: /Library/Logs/BackupZit/agent.log (also listed in Console.app); a crash trace goes to /Library/Logs/BackupZit/launchd.log.
  • Enrollment by the installer: /Library/Application Support/BackupZit/enroll-error.log and the installer log /var/log/install.log.
  • Updates: /Library/Application Support/BackupZit/updates.
  • Get log on the Agents page fetches the end of the log from the console (see Logs).
