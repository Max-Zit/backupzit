Ransomware protection

Attackers try to delete or encrypt backups before they encrypt production data. BackupZit offers storage where backups cannot be destroyed, even with stolen credentials.

The layers

LayerProtects against
Encryption (AES-256)Reading or tampering with backups on the storage. Every change is detected.
Immutable S3 (Object Lock, compliance mode)Deleting or overwriting backups — by an attacker with the keys, a rogue admin, or a mistake.
Hardened repositoryThe same, on your own Linux server: files are write-once and get the filesystem immutable flag.
Off-site copyFire, theft, total site loss.

Automatic detection of suspicious backups

Every backup is compared with the recent history of its job. It is marked suspicious when it shows the traces of ransomware or mass deletion:

  • far more files changed than usual (e.g. 95 % instead of the usual 1 %),
  • the new data no longer compresses — encrypted files look like random data,
  • the number of files suddenly dropped by a third or more,
  • a sudden jump in the amount of new data (also for disk images, Linux systems and VMs).

Then BackupZit sends an alert email (with failure notifications on), shows the backup on the dashboard as suspicious backups to review, and pauses the job's retention: no older backup is deleted, so the last clean backups stay restorable even if the damaged backups keep coming. After checking the machine, click Reviewed — resume retention on the job page.

Immutable S3 with Object Lock

  1. Create a bucket with Object Lock enabled (AWS, Wasabi, Backblaze B2, MinIO: mc mb --with-lock).
  2. Add a lifecycle rule that deletes noncurrent versions after 1 day (MinIO: mc ilm rule add --noncurrent-expire-days 1 --expire-delete-marker).
  3. Add the S3 target and tick Immutable backups for N days. Choose N at least as long as your longest retention you need protected, e.g. 30.

Each restore point stays locked for at least N days after it was created; data shared with newer backups is extended automatically.

Hardened repository

A dedicated Linux server running backupzit-repo:

  • Agents and the console can only add files; existing files are never overwritten.
  • Every file gets the chattr +i attribute for the period set on that server. Not even root can delete it without removing the flag first.
  • Deletes from clients only hide files until their period ends.
  • The service runs as an unprivileged user; its only privilege is setting the immutable flag.
apt install ./backupzit-repo_*.deb
vi /etc/backupzit-repo/repo.env        # BACKUPZIT_REPO_LOCK_DAYS=30
systemctl start backupzit-repo
backupzit-repo add-key office-console
backupzit-repo fingerprint

After setup, disable SSH and other remote access on the repository server and protect its local console / iDRAC / iLO / hypervisor access. The protection is only as strong as that machine's root account.

Recovering after an attack

If an attacker deleted or overwrote backups, read the storage as it was before the attack — this is read-only and changes nothing:

backupzit-agent snapshots --repo <repository> --as-of 2026-10-01T14:30
backupzit-agent restore   --repo <repository> --as-of 2026-10-01T14:30 --target D:\Restore latest

On a hardened repository the administrator can also bring hidden files back so backups continue normally:

backupzit-repo status
backupzit-repo undelete --since 2026-10-01T14:00

Recommendations

  • Use a separate account for the storage that is not part of your Windows domain.
  • Keep at least one immutable copy (S3 Object Lock or hardened repository).
  • Keep the recovery sheets offline (printed, in a safe).
  • Enable email alerts — a sudden change in failures or in uploaded data volume is often the first sign of an attack.
