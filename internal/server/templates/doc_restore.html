Restoring

Every successful backup can be restored: completely or only selected folders, to the same machine, to another agent, or as a new virtual machine.

The restore wizard

Click Restore in the menu. The wizard asks four questions:

  1. What do you want to restore?
    • a whole virtual machine
    • files from a virtual machine
    • files and folders
    • a disk image / bare metal
    • files from a disk image
    • a database (to a point in time)
    • a whole Linux system
    • Microsoft 365 mail, OneDrive, calendars and contacts and SharePoint files (see Microsoft 365)
    Each choice shows how many restore points exist for it.
  2. Source: the virtual machine (across all hypervisors and jobs), or the backup job and its machine.
  3. Restore point: the backup to restore from, newest first, with its status, storage and size.
    • Backups flagged as suspicious (possible ransomware) are marked.
    • Copies on secondary storage made by a backup copy job are listed as copy (file and VM backups).
  4. Options: where and how to restore. A summary of what you chose is shown above the options.

The steps at the top are links, so you can go back to any earlier step. Every step has its own address, so you can bookmark or share a step.

The options are the same as on a backup's page in Activity, where you can also start a restore directly. Only users whose role may restore see the wizard.

Restore from a file backup

  1. Choose Files and folders in the restore wizard, then the job and the restore point. Alternatively, open the backup in Activity or on the job page.
  2. Under Restore files from this backup choose the agent that should receive the files. It can be a different machine than the one that was backed up — for example a replacement PC.
  3. Choose where:
    • Restore into a folder (recommended) — e.g. D:\Restore. The original structure is recreated below it: D:\Restore\C\Users\ana\Documents\…. Nothing existing is touched.
    • Restore to original location — writes the files back where they were, overwriting current versions. For a NAS share the agent connects the share again, writable. Sparse files (VM images, databases) come back sparse. On Windows only a file that was sparse is marked sparse again; others, such as VHD/VHDX disks (Hyper-V refuses sparse ones), come back as normal files, and so do all files of backups made with agents before 0.57, which did not record the attribute. A symbolic link or junction in the way is never written through: restoring into a folder replaces it with a folder, and every restore writes only into the folders it opened, even when a link appears while it runs (0.58: also for file backups and at the original location; a volume root such as / or C: cannot be chosen as the folder for files from VM and image backups). At the original location only links of the system are followed (owned by root or the agent's user on Linux, by SYSTEM, TrustedInstaller or an administrator on Windows, and nobody else may change or replace them: the old compatibility links in user profiles such as Application Data are not followed); a link to a folder that does not exist is an error, nothing is created where it points. Owner, permissions and attributes are set on the restored file itself, never through a link put in its place. Since 0.59 such a link must also have a single name: a hard link of it, which another user could make, is not followed.
  4. Optionally limit to Only these paths, one per line, e.g. C:\Users\ana\Documents\Contracts — or pick them in the file browser (below).
  5. Keep Verify restored files on: each file is read back and compared with the checksum in the backup.
  6. Click Start restore. Progress and results appear on the restore run's page.

File times, Windows attributes (hidden, read-only, …) and Linux owners, permissions (including setuid bits), ACLs, extended attributes (SELinux labels, file capabilities), symbolic and hard links are restored too. On macOS also the BSD file flags (hidden, locked…), the creation time and the extended attributes (see macOS agents). Owners are set only when the agent runs as root/administrator.

While a restore runs, a folder it creates is open only to its owner (0700 on Linux and macOS, also for files from virtual machines) and gets its own permissions once its contents are written: the files of a private folder such as /root are not readable by others in the meantime. A restore that stops halfway leaves such folders private.

Browse, download and pick files

On the backup run, Browse files shows the backed up folders as they were (also for NAS shares and Linux system backups). Open folders, tick files and folders, then:

  • Download — one file comes as it is, several files or folders as a ZIP archive, straight in the browser. Downloads are recorded in the audit log.
  • Restore them on an agent — into a folder or to the original location, like a restore with Only these paths.

Top of the backup at the start of the path goes back to the first level, and the .. row at the top of the list one folder up; browsing files inside a VM disk works the same way.

A symbolic link to a file (e.g. /etc/os-release) is downloaded as the file it points to, when that file is in the backup; links to folders are left out of ZIP archives. The same applies to files downloaded from virtual machine backups (ext4, XFS, btrfs). A restore on an agent recreates links as links.

The console reads the backup from the storage itself, so browsing works for backups on network storage (SFTP, S3, SMB, Azure, hardened repository); for storage reachable by agents only it reads through an agent that uses the storage (agents 0.61 and newer). For a local disk or a USB disk of an agent, restore with the paths. Users with a restore role may browse and download.

Finding the right backup: use the Calendar to see which backups ran on which day, or the job page's history.

Restore single files from a disk image

For image backups, click Browse files on the backup run. You can navigate the NTFS file system inside the image directly in the console, tick files and folders, and restore them to any agent — without restoring the whole disk. Restored into a folder, the files get the same layout as from a file backup: the drive letter becomes the first folder (D:\Restore\C\Users\…).

Download the ticked files straight to your browser instead: one file comes as it is, several files or folders as a ZIP archive — handy for a single document from a large image backup. Like browsing, it works for image backups on network storage, needs the Restore permission, and the audit log records which paths were downloaded.

Restore single files from a VM (Proxmox VE, Hyper-V, VMware)

In a VM backup run click Browse files next to the guest. The console shows the partitions and LVM volumes of its disks and lets you browse NTFS, ext4, XFS and btrfs file systems. Download the ticked files (several as a ZIP archive) or restore them on any agent. See Proxmox VE, Hyper-V and VMware ESXi. Files restored on an agent keep the Unix permissions they had in the VM (ext4, XFS, btrfs), so restored secrets such as /etc/shadow stay private; files from NTFS volumes are readable only by their owner on Linux. Restored on a Windows agent, names with : from Linux guests (ext4, XFS, btrfs) are skipped and listed: Windows would read the part after the colon as a stream of another file. NTFS alternate data streams are restored as streams.

Sparse files of the guest stay sparse: runs of zeros are not written, so a file such as /var/log/lastlog, whose apparent size can reach terabytes, takes only the space of its data. On a Windows agent a file is marked sparse only when it holds a run of at least 64 MiB of zeros (Hyper-V refuses sparse virtual disks); other files are written in full there.

btrfs is shown the way it looks with the top-level subvolume mounted: subvolumes and snapshots are folders where they are linked (in a snapshot, a subvolume that was inside the original is an empty folder, as on Linux). Files compressed with zstd, LZO or zlib are read like any other. Only btrfs on one disk can be browsed: for a file system spread over several disks (btrfs RAID or added devices) the console shows an error; start the VM with instant recovery and copy the files from there.

Restore whole machines

  • Windows disk images: onto a disk or bare metal, also onto different hardware — Disk images.
  • Linux systems: onto a disk or bare metal, or as a new Proxmox VM — Linux system backup.
  • Proxmox VMs and containers: as a new guest or in place — Proxmox VE. Proxmox VMs can also run instantly from the backup and be moved to storage while they run (instant recovery).
  • Databases (SQL Server, PostgreSQL, MySQL/MariaDB): under a new name or in place, to a point in time — Databases.
  • Hyper-V VMs: as a new VM or in place (keeps ID and MAC addresses) — Hyper-V.
  • VMware ESXi VMs: as a new VM or in place (keeps UUID and MAC addresses), on any ESXi host and datastore — VMware ESXi; also instantly from the backup through a Linux proxy agent, then copied to a datastore (instant recovery).

Recovery ISOs

Bare-metal restores boot the machine from a recovery ISO (on a USB stick or attached to a VM), see Recovery media:

  • Linux recovery ISO — published with every release (backupzit-recovery-linux.iso); the Recovery media page links it from the update source.
  • Windows recovery ISO — Windows PE may not be redistributed, so it is built once on any Windows 10/11 or Server PC:
    1. Install the free Windows ADK (feature Deployment Tools) and the Windows PE add-on from Microsoft.
    2. Download build-winpe.ps1 from the release (next to the agent packages) and take backupzit-agent.exe from C:\Program Files\backupzit Agent of a machine with the agent.
    3. In an administrator PowerShell: .\build-winpe.ps1 -AgentExe .\backupzit-agent.exe -Out .\backupzit-recovery.iso. Add -DriverDir C:\Drivers for storage or network drivers (e.g. VirtIO for Proxmox VMs) and -RecoveryJson .\recovery.json so it connects without typing.
    4. At start the ISO looks for \backupzit\recovery.json on every drive. With it, the recovery agent connects to this console and the restore is started here, so someone on site only boots the stick. Without it, the graphical recovery program opens (backupzit-recovery.exe, installed next to the agent): restore a disk image or single partitions, also to a smaller or larger disk, repair the boot, load drivers. The command prompt of the medium starts the other one (backupzit-recovery or backupzit-agent recovery). With -AccessPackage .\backupzit.bzaccess (created under Recovery media) the program opens the backups without this console; only the passphrase is needed. Its passphrase needs 12 characters of three kinds (16 of two, 20 of one), and common passwords are refused; the page offers a generated one that types the same on QWERTY, QWERTZ and AZERTY keyboards.
    5. Language and keyboard of Windows PE are those of the PC that builds the ISO, like the time zone (-Language de-de, -KeyboardLayout, -TimeZone choose others), so a server address or passphrase types as on that PC. The recovery program speaks the console's 14 languages. -NoUi builds the console agent only. The medium carries the license texts and SOURCE-CODE.txt in \backupzit\.
    6. Before it writes, the program checks the target disk again by size, model, serial number and partition table ID: a disk that got the chosen number in the meantime (a USB disk plugged in again) is refused, and so are the disks with the backups, the recovery medium and an access package. A restore onto the original disk keeps the layout of the backup when it fits (no partition grows into a gap); Fit to the target disk is proposed for a smaller disk or when chosen. A disk converted to GPT or MBR cannot stay offline. If the backed up disk is still in the computer (another disk with the same disk ID), the program and image-restore warn before writing: Windows keeps the copy offline while both disks are in, so a partition that grows is extended only after the old disk is removed (in Disk Management); tick Leave the target disk offline. Where a partition cannot be made smaller (for example a copy that was not shut down cleanly), the sizes page and the messages about a too small disk say why. Boot repair saves the boot data to \backupzit on another drive first.
    7. The program works with the keyboard alone (Tab, Enter, Space, Esc) and on screens down to 800×600, where its pages scroll. The summary names the disk that will be erased in red (number, model, size); the restore starts only after that number is typed. An SFTP location without an access package shows the server's host key and asks before trusting it: compare it with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the server.
    8. Optionally copy the ISO into the console's /var/lib/backupzit/dist; it is then offered on the Recovery media page.

Browsing files in the console works for backups on network storage (SFTP, S3, SMB, Azure, hardened repository): the console reads them directly or, for storage reachable by agents only, through an agent that uses it (also with an SSH key; agents 0.61 and newer). For backups on a local disk of an agent or on SFTP with an SSH key, a restore with Only these paths still works from the console; to look into them, use the command line.

Restore without the console

If the console itself is lost, any machine with the agent installed can restore directly from the storage using the recovery sheet of the storage target:

set BACKUPZIT_PASSWORD=<recovery key>
set BACKUPZIT_SFTP_PASSWORD=...           (or the S3/SMB/hardened credentials)
set BACKUPZIT_SFTP_HOSTKEY=SHA256:...      (the SFTP host key, on the recovery sheet)
backupzit-agent snapshots --repo sftp://backup@nas:22/backups/pc1_1a2b3c4d
backupzit-agent restore   --repo sftp://backup@nas:22/backups/pc1_1a2b3c4d --target D:\Restore latest

latest is the newest backup of any job of that computer; to restore a particular job, use a snapshot ID from snapshots. See Command line reference.

Automatic restore tests

BackupZit proves your backups regularly without you doing anything: weekly (configurable under Settings → Restore tests) the agent of each job restores a random sample of files from the newest backup into a temporary folder, verifies every byte against the stored checksums and deletes it again. For disk images, random blocks are read and verified. This exercises the whole chain — storage access, credentials, encryption key and data integrity.

  • Results appear in Activity and the job history as Restore test runs, and per job in Reports (column Restore test).
  • A failed test is a failure like any other and triggers an email alert.
  • Test restore on a job's page starts a test immediately.
  • The sample size limits how much is read from the storage — keep it small for cloud storage with download fees.

Boot test for Proxmox VMs

Readable blocks do not prove that a VM still starts. With Boot test for Proxmox VM backups on (Settings → Restore tests), the restore test of a Proxmox VM job also starts every VM of the newest backup on the job's node, one after the other, with instant recovery: it runs from the backup with a new ID, its network cards disconnected (so it cannot conflict with the original), and is deleted again right afterwards. The test passes when the VM's QEMU guest agent answers within the configured time, which means the operating system booted. VMs without the guest agent pass when they keep running for a minute; the run page shows them as running rather than booted. The copy also leaves out settings that reach outside the VM: a hook script, raw QEMU arguments (args), passed-through PCI and USB devices, host shares (virtiofs) and serial or parallel ports on host devices; the run page names what was left out. A VM that cannot start without them fails its boot test.

  • The node needs free memory for one more VM while the test runs.
  • Install the QEMU guest agent in the VMs (qemu-guest-agent on Linux, the VirtIO guest tools on Windows) and enable it in the VM options, so the test can confirm the boot.
  • The run page lists each VM with its result and how long the boot took.

Checks inside the VM (agents 0.61 and newer): a VM that boots can still be broken, or already compromised when the backup was made. In a Proxmox VM job, Boot test checks lists what must work in the booted copy, one per line: service sshd (the service runs), file /var/www/index.html (the file exists), port 443 (a program listens on the TCP port) or command … (your own command ends with exit code 0; sh on Linux, cmd on Windows). Start a line with a VM ID and a colon, e.g. 101: service nginx, for that VM only. The checks run through the QEMU guest agent as root or SYSTEM inside the isolated copy and are tried again until they pass or the boot test's wait ends; the run page shows each one. Only users who may change commands set them.

Also boot-test the oldest backup the job keeps starts the VMs of the oldest kept restore point too, so you know that the point you would fall back to after an unnoticed compromise still boots. A VM backup whose VMs booted and passed their checks is marked verified on its run page, where it is restored from.

Check of all stored data

Restore tests read a sample. On top of that, an agent reads every piece of data in each repository, verifies it against its checksum and checks that every backup's folders and data are present — monthly by default (Settings → Restore tests: Check the stored data: monthly, every three months or never). This finds damage on the storage itself, such as a failing disk in a NAS or bit rot, before you need the backup. Each repository is checked once (the jobs of one agent on one storage share it), by the agent that writes it. The check reads as much as the repository holds, so on cloud storage (S3, Azure) it runs only with Also on cloud storage on. Problems make the Data check run fail and send a failure notification; Check data on a job's page starts a check at once. Needs agents 0.39.0 or newer. On S3, Azure and hardened storage the check reads several data packs at once (agents 0.54.2 and newer). While a check runs, Activity and its run page show how many of the repository's data packs it has checked so far. A check that finds damaged data packs offers Repair on its run page (Troubleshooting).

Additionally, restore a real folder by hand from time to time (e.g. quarterly) and open a few files — it also trains the people who will need to do it in an emergency.
