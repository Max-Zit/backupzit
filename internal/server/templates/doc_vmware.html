VMware ESXi virtual machines

BackupZit backs up the virtual machines of VMware ESXi hosts without installing anything on ESXi or inside the VMs. A BackupZit agent on any machine in the network works as the host's proxy. It takes snapshots, reads only the changed blocks of the virtual disks and writes them to your storage.

Requirements

  • ESXi 6.7, 7 or 8 connected directly, or vCenter Server 7 or 8 with its ESXi hosts (see vCenter Server).
  • A user with administrator rights on the host, usually root.
  • SSH enabled on hosts with the free license: Host → Actions → Services → Enable Secure Shell. The free ESXi license makes the API read-only, so snapshots and restores go over SSH. Licensed hosts are changed through the vSphere API and need no SSH.
  • A proxy agent: any Windows or Linux agent that reaches the host on port 443 (and 22 when SSH is used). The backup data flows through it, so put it on a fast network close to the host and the storage.
  • Free space on the VM's datastore while a running VM is backed up. BackupZit copies the disk there for a moment (see below). The copy is thin, so it needs as much space as the disk actually uses. With hot-add no copy is made.

Adding a host

  1. Open Agents → VMware ESXi hosts → Add an ESXi host or vCenter Server.
  2. Enter the address, the user, the password and the proxy agent.
  3. The console connects once to check them. It reads the VM list and the license, and pins the host's HTTPS certificate and SSH host key. If the host is later replaced by another machine with the same address, BackupZit refuses to connect instead of sending it the password. If the certificate changes for a reason you know — the host was reinstalled, got a new certificate, or was added to vCenter (which replaces the certificates of its hosts) — the host shows the new fingerprint with an Accept the new certificate button on the Agents page. Compare the fingerprint with the host before accepting it. Since 0.62 the console shows the certificate and SSH host key fingerprints before it sends the password (also through a proxy agent of 0.62 or newer, which reads them for it), and connects only after you confirmed them.

The password is stored encrypted, like all other secrets. The console itself connects to the host (HTTPS 443, and SSH 22 on the free license) when it is added, on Refresh and every 10 minutes to refresh the VM list, unless the host is reached through the proxy agent. Remove deletes the host together with its backup jobs; the backups stay on the storage. The table shows each host's mode:

  • vSphere API (licensed host, SSH not needed): snapshots, disk copies, restores and instant recovery go through the API.
  • vCenter Server (vSphere API): a vCenter with its ESXi hosts; everything goes through the vCenter API.
  • free license: snapshots and restores over SSH: the host's API is read-only, so these steps go over SSH.
  • SSH (chosen for this host): the host is changed over SSH even though its API could do it (Always SSH when adding the host).

Through the proxy agent (agent 0.56 or newer): tick Connect through the proxy agent when adding the host, or Connect through the proxy in its row, and the console never connects to the host itself. The proxy agent checks the address and password, reads the VM list, version and license, and reports the HTTPS certificate and SSH host key it saw; the console pins them the first time, as it does for a direct connection, and from then on the proxy refuses a host that presents another certificate (the host's row then offers Accept the new certificate). Refresh and the VM list every 10 minutes come from the proxy too; these checks do not show in Activity. Only the proxy needs to reach the host, exactly as for backups and restores, so the console can be on another network, behind NAT or in an overlapping address range. A wrong address or password shows as the host's error after the proxy's first check: remove the host and add it again. While the proxy is offline or busy, the last VM list stays.

The console chooses by itself with Automatic, so a host that gets a license later switches to the API without further setup. How the host is changed in the host's row (and when adding it) can force Always SSH or Always vSphere API; the change is checked at once. Earlier backups and their restore points are not affected by the method.

vCenter Server

Add a vCenter Server like a host: its address, administrator@vsphere.local (or a user with the Administrator role) and a proxy agent. BackupZit then sees the VMs of all ESXi hosts and clusters of the datacenter through this one connection; nothing is changed over SSH and no host password is needed.

  • A VM moved to another host with vMotion keeps being backed up: VMs are recognised by their instance UUID, not by their host.
  • A restore can choose the ESXi host that runs the VM (default: the host of the original VM) and the datastore.
  • Instant recovery starts the VM on the chosen host; Finish moves it to a datastore with Storage vMotion while it keeps running, without downtime.
  • A vCenter with several datacenters cannot be added yet; add the hosts of the other datacenters directly.

Do not add the same ESXi host both directly and through vCenter: each connection has its own repository, so its VMs would be backed up twice. If a host that BackupZit backs up directly is later added to vCenter, accept its new certificate on the Agents page; its jobs keep working — vCenter gives VMs that were created on the standalone host a new ID, and BackupZit moves the jobs to it at the next refresh.

Backup jobs

In Backup jobs, choose the ESXi host (listed under VMware ESXi hosts in the agent list) and Virtual machines. Back up all VMs of the host (VMs created later are included automatically) or tick individual ones. The job runs on the host's proxy agent. If you change the proxy, the existing jobs follow.

To leave out single VMs, e.g. the VM of the BackupZit console, choose All VMs (and containers) on the host except the ticked ones and tick them.

How a VM is backed up

  1. Changed block tracking (CBT) is switched on for the VM if it is off.
    • On licensed hosts this happens automatically.
    • On free hosts CBT can only be switched on while the VM is turned off. BackupZit does it at the first backup that finds the VM off. Until then, every backup reads the whole disks and the run shows a warning.
  2. A snapshot backupzit_… is taken. When VMware Tools run in the guest, the snapshot is quiesced: applications and file systems are flushed first, which makes the backup application-consistent. Without VMware Tools it is crash-consistent. Install open-vm-tools in Linux VMs and VMware Tools in Windows VMs. For a guest whose quiescing fails or misbehaves, tick Crash-consistent snapshots (no VMware Tools quiescing) in the job: its backups are then crash-consistent, like after a power cut (agent 0.58). On some hosts (ESXi 6.7) the disk of a quiesced snapshot is a small delta that the quiescing itself wrote; the agent reads it with the snapshot (agent 0.58; older agents refused it as a snapshot delta disk).
  3. CBT reports which blocks to read:
    • for the first backup, only the blocks in use;
    • after that, only the blocks changed since the previous backup.
  4. A running VM keeps its disks locked. Its disks are therefore copied on the datastore (thin) and the snapshot is removed right away, usually after seconds. The copy is then read over HTTPS and deleted. VMs that are turned off are read directly. With hot-add the disks of running VMs are read through the proxy's own VM instead, without a copy.
  5. The VM's configuration (.vmx) and NVRAM are stored with the backup.

Example from the test lab: a Debian VM with an 8 GB disk, 1.6 GB of it in use. The first backup read 1.6 GB. The next one, after 50 MB of new data, read 70 MB and took 23 seconds.

Hot-add: no copy on the datastore

Copying the disks of a running VM costs time and I/O on the production datastore at every backup, incremental ones too, and needs free space for the disks' used blocks. With large VMs on slow disks that matters. With Hot-add (Agents → VMware ESXi hosts, the checkbox under the proxy agent) the proxy reads them in place instead:

  • Requirements: the proxy is a Linux agent in a VM that sees the VM's datastores (on the same host, or on a host of the same vCenter with access to them), and the host is changed through the vSphere API (vCenter or a licensed host). The proxy finds its own VM by its BIOS UUID.
  • How: while the snapshot exists, each disk is attached to the proxy's VM independent-nonpersistent. The proxy opens it read-only; anything written to it would go to a redo log that vSphere discards when the disk is detached, so the VM's disk is never changed. The proxy reads only the blocks changed block tracking reports, detaches the disk, and then the snapshot is removed.
  • What it saves: no temporary copy and no extra space on the datastore. An incremental backup of a 2 TB VM with 20 GB of changes reads 20 GB. The snapshot stays for as long as the disks are read (instead of only for the copy), so the VM writes into the snapshot a little longer.
  • Fallback: if the proxy is not a VM of the host, or attaching or reading a disk fails, that disk is copied on the datastore as before, and the run shows a warning with the reason. Hot-add is off by default; agents before 0.54 ignore it. The run page shows how many disks were read through hot-add.
  • On the proxy VM: keep LVM from activating volumes of the attached disks, with LVM's devices file (use_devicesfile = 1 in /etc/lvm/lvm.conf, the proxy's own disks listed with lvmdevices). Volumes it activates anyway are removed before the disk is detached. Do not attach disks of other VMs to the proxy by hand: an independent-nonpersistent disk from another VM's folder is taken for one an interrupted backup left behind, and detached.

Several proxies (vCenter)

One proxy reads one disk after the other, and through hot-add only on the hosts whose datastores it sees. With a vCenter connection, add a Linux agent in a VM on each ESXi host as a further proxy (Agents → VMware ESXi hosts, Further proxies under the proxy agent; agents 0.55 or newer):

  • Split by host: every backup of the job is split. Each VM goes to the proxy on the ESXi host it runs on (as the last VM list shows it), every other VM to the connection's proxy. Each proxy backs up its share as a run of its own, at the same time as the others, through hot-add on its own host. Only proxies that are online take part: the VMs of a proxy that is off go to the connection's proxy. The first backup into a new repository, and backups to a local or USB target, are not split.
  • One start: the job shows the parts of a start as one: running while a part runs, failed if a part failed. RPO alerts and the dashboard count a backup once all parts succeeded; a chained job or an "after each backup" copy starts once, after the last part.
  • No overlap: backups and restores of the connection on different proxies do not run at the same time (only the parts of one start do), so a VM that moved between hosts is never handled by two proxies at once.
  • Retention per proxy: each part keeps the job's number of backups of its VMs, and copy jobs copy and keep them per part too. Backups from before the job was split, and those of a proxy that was removed, stay as they are: they remain restore points of their VMs. A VM moved to another host (vMotion) goes to that host's proxy from the next VM list refresh on.
  • The proxy's host is found by the BIOS UUID its agent reports; the Agents page shows it next to each agent. ESXi host not found: the agent is not a VM of this vCenter, or the VM list is older than the agent (click Refresh).

Cancelling a VMware backup (Activity → Cancel) also stops a disk copy running on the datastore and deletes the partial copy; the snapshot is removed as after every backup. A snapshot still being created when the backup is cancelled is waited for (up to five minutes) and removed too.

Snapshots that stay behind. The proxy records every snapshot and temporary disk copy before it creates it, and drops the record only once it sees the object gone: after the removal it lists the VM's snapshots again, tries up to three times over about ten minutes, signs in again when the vSphere session has ended (also before each VM, so one lost session does not fail the VMs after it), and consolidates the disks when vSphere reports that they need it; a VM without snapshots whose disks still need consolidation from an earlier removal is consolidated before its next backup. If the agent stops in the middle (crash, power loss) or a removal keeps failing, the record stays:

  • The console queues a clean-up run on the proxy (only the proxy has the host's credentials), and the proxy also removes such leftovers after each backup of the connection. VMs a backup or restore of the proxy works on are left alone. A record that an agent reports for a connection it is not a proxy of (for example a former proxy) is listed without a clean-up run; the snapshot then shows up from the VM list, as described below.
  • The dashboard lists every leftover under Attention (VM, since when, why) with Remove now, and a notification (email, chat) goes out once per leftover that stays.
  • The console also looks for backupzit_… snapshots older than six hours in the VM list it refreshes every 10 minutes, while no backup of the connection runs, so leftovers of older agents show up too. Only snapshots named backupzit_… are ever removed; the VM's own snapshots are never touched. A record of a VM that is missing from the VM list (its datastore is down, it was moved to another host) stays on the proxy for seven days, so its snapshot is still removed when the VM comes back (agents 0.63 and newer).

Restoring a VM

Use the restore wizard (Whole virtual machine) or the backup's page in Activity. Choose:

  • As a new VM next to the original: a copy with a new name, UUID and MAC addresses. The default name is the original's plus -restored- and the date. Guest network settings tied to the old MAC addresses, such as netplan match: macaddress in cloud images, do not apply to the copy.
  • In place of the original VM: with turn it off and replace its disks, BackupZit:
    • turns the VM off and deletes its snapshots;
    • renames the current disks to ….replaced-DATE.vmdk (delete them once the restored VM works);
    • writes the backup into new disks with the original names, and sets CPU and memory as in the backup.
    The VM keeps its UUID, network adapters and MAC addresses. If the VM was deleted, it is recreated with its original identity.
  • ESXi host and datastore: another host, or another datastore of the same host.
  • Start the VM after the restore.

Disks are restored thin, and only blocks with data are written. ISO images that were connected to CD/DVD drives are not part of the backup, so those drives are left empty.

Instant recovery

Choose Instantly, running from the backup to start a VM within seconds, without copying its disks first. The host's proxy agent — it must be a Linux agent — serves the VM's disks straight from the backup over NFS; the host mounts that as the datastore backupzit-<agent> and runs the VM from it. Changes the VM makes are kept on the agent (/var/lib/backupzit/instant-esxi, so it needs free space for them); the backup itself is never changed, and retention keeps it while the VM runs from it. If the original VM still exists, the instant VM gets a new UUID and new MAC addresses.

On the run's page, when the VM works as it should:

  • Finish copies it to a datastore of the host: the VM is shut down (through VMware Tools if they run), its disks are copied thin (through the API on licensed hosts, with vmkfstools over SSH on the free license), it is registered from the datastore and started again. A standalone host has no Storage vMotion, so this needs a short downtime that grows with the disk size. If the copy fails, the VM keeps running from the backup.
  • Discard stops and deletes the VM with all its changes.

The agent answers NFS on port 2049 (and registers it with the machine's rpcbind on port 111, or answers port 111 itself) only for the ESXi host's address; open these ports from the host to the agent if a firewall is in between. When the last instant VM is finished or discarded, the datastore is removed and the NFS server stops.

Single files

Browse files on the backup's page (or Files from a virtual machine in the restore wizard) opens the VM's disks. You can browse NTFS, ext2/3/4, XFS and btrfs, also on LVM, and download files or restore them to any agent.

Command line

These commands run on any agent. Set the ESXi password in BACKUPZIT_VMWARE_PASSWORD:

backupzit-agent vmware list    --host 192.168.1.20 [--user root]
backupzit-agent vmware backup  --host … --repo … [--vmid N,N]
backupzit-agent vmware restore --host … --repo … --vmid N [--new] [--name NAME] [--datastore DS] [--overwrite] [--start] SNAPSHOT|latest

vmware list shows the host's certificate and SSH key fingerprints. Pass them with --thumbprint and --ssh-host-key to pin them on the command line too.

Not yet included

  • vCenter with several datacenters. Only a vCenter with one datacenter can be added; add the hosts of the others directly.
  • VMs with snapshots of their own. Their disks are deltas; delete or consolidate the snapshots first. (The small delta a quiesced snapshot writes is the backup's own and is read with it.)
  • Some disk types. Raw device mappings (RDM) and independent disks.
  • Instant recovery through a Windows proxy agent. Instant recovery needs a Linux proxy agent.
