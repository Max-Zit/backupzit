Security & best practices

How BackupZit protects your data and the console, and what you should do on your side.

Built-in protection

  • Encryption at the source — AES-256-GCM in the agent; the storage only sees encrypted data. Keys are derived with Argon2id.
  • Pinned connections — agents pin the console certificate; SFTP host keys and hardened repository certificates are pinned too. No certificate authority can be abused to impersonate them.
  • Secrets at rest — storage passwords and keys, recovery keys, SMTP/LDAP passwords and two-factor secrets are encrypted in the database with a key kept outside it (secrets.key).
  • Agent secrets — each agent has its own secret, stored only as a hash on the console and in a file only administrators can read on the agent.
  • Web console — HttpOnly, SameSite=Strict session cookies; protection against cross-site requests and clickjacking; strict Content-Security-Policy; passwords hashed with bcrypt; sensitive pages are never cached.
  • Brute-force protection — addresses that fail to sign in too often are blocked: passwords, two-factor codes and API tokens. Blocks survive restarts, repeat offenders are blocked longer, and administrators get an email. See below.
  • Accounts — roles with least privilege, optional two-factor authentication (TOTP) and LDAPS sign-in; API tokens with their own, lower role and expiry.
  • Audit trail — sign-ins, failed sign-ins, user and role changes, jobs, storage targets, restores, displayed recovery keys, settings changes and API actions are recorded in the audit log; deletions on a hardened repository are logged on that server.
  • Agent updates — agents download new versions only from their console over the pinned connection and install them only if the SHA-256 checksum matches.
  • Local status channel — the tray app talks to the agent service over a local named pipe (Windows) or a root-only socket (Linux). Signed-in users of the machine can read the status and start the machine's own backup jobs; nothing else (jobs, schedules, storage and restores are managed only in the console).
  • Hypervisor backups — the agent on a Proxmox or Hyper-V host uses the host's own tools; no hypervisor passwords or API tokens are stored in the console.
  • Backup integrity — every chunk is verified by its SHA-256 hash on restore; automatic restore tests and ransomware detection watch the backups continuously.

Brute-force protection

Configure it under Settings → Sign-in & security. The defaults are safe for most installations:

SettingDefaultMeaning
Failed attempts per address5Failed sign-ins from one IP address within the counting period block that address. This counts wrong passwords, wrong two-factor codes and invalid API tokens.
Counting period15 minutesFailures older than this are forgotten.
Block for30 minutesA blocked address cannot sign in, not even with the right password. The sign-in page answers "Too many failed sign-ins" and the API answers HTTP 429.
Block repeat offenders longeronEach further block of an address within a day lasts twice as long: 30 minutes, 1 hour, 2 hours, … up to 7 days.
Failed attempts per username20Failures for one username, from any addresses, pause sign-in for that username until the counting period has passed. This stops guessing that spreads over many addresses. Accounts are never locked permanently, so an attacker cannot lock the administrator out.
Never block these networksnoneOptional networks, e.g. the administrators' subnet, that are never blocked. The per-username limit still applies to them.
Reverse proxiesnoneIf the console runs behind nginx, Traefik or another proxy, enter its address. The client address is then taken from X-Forwarded-For; otherwise all clients would look like the proxy. The header is ignored from any other address, so it cannot be forged.
Email when an address is blockedonSent to the recipients in the email settings.

The same page lists the blocked addresses, with the reason and how long each block lasts, and lets you lift a block. Blocks and unblocks are recorded in the audit log.

If you locked yourself out, sign in from another address, or run this on the server with the same database options as the service:

backupzit-server --unblock-ip all

To lift a single block, give the address instead of all.

Recommendations

Console

  • Keep the console on an internal network; do not publish port 8443 to the internet. Use a VPN for remote administration.
  • Use a long, unique admin password and change the initial one.
  • Require two-factor authentication for administrators (Settings → Sign-in & security).
  • Give every person their own account with the lowest role that works; use API tokens with the Viewer role for monitoring.
  • Back up secrets.key separately from the database (Installing the server).
  • Choose a sign-in session length under Settings → Sign-in & security that suits you (shorter is safer).
  • Keep the server updated (apt upgrade / dnf upgrade), including PostgreSQL.

Storage

  • Give each storage target its own account with access only to the backup folder or bucket.
  • Do not join backup storage to the Windows domain; use credentials that are not used anywhere else.
  • Keep at least one immutable copy (S3 Object Lock or hardened repository) and one off-site copy.

Keys

  • Store recovery sheets offline. Without them, encrypted backups cannot be restored if the console is lost.
  • Test a restore from the command line with only the recovery sheet once, so you know the procedure works.
  • Treat a USB stick with recovery.json like a key: until the recovery code expires (30 days) it lets a machine join the console as a recovery agent. Create a new code when you need one instead of keeping old sticks around.
  • Recovery ISOs give a root / administrator command line to whoever boots them — as any boot medium does. Protect servers with a firmware (BIOS/UEFI) password and secure boot settings.

Agents and hypervisors

  • The console can install software on agents (agent updates) and restore data onto them. Protect the administrator accounts accordingly: two-factor authentication, few administrators.
  • Files from VM disks are parsed by the console and agents when you browse them; damaged or hostile file system data produces an error, not a crash.

Reporting a security issue

Please report vulnerabilities privately to the BackupZit maintainers instead of opening a public issue.
