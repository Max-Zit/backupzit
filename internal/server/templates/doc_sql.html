Databases: SQL Server, PostgreSQL, MySQL

BackupZit backs up databases with the database server's own tools, from the agent on the database machine: Microsoft SQL Server on Windows, PostgreSQL and MySQL/MariaDB on Linux. Full backups run on the job's schedule; log backups every few minutes make it possible to restore a single database to any point in time — for example to one minute before a wrong DELETE.

Creating a job

Under Backup jobs create a job of the kind Databases, on the agent of the database machine, and choose:

  • Database server: Microsoft SQL Server, PostgreSQL or MySQL/MariaDB. It cannot be changed later.
  • Instance or port: the SQL Server instance (empty for the default instance, e.g. SQLEXPRESS) or the PostgreSQL port (empty for 5432). MySQL/MariaDB is reached over the local socket.
  • Databases: one name per line, or empty for all user databases — databases created later are included automatically.
  • Back up the logs every … minutes: e.g. 15 — transaction logs (SQL Server), archived WAL (PostgreSQL) or binary logs (MySQL). Leave empty if restoring to the time of a full backup is enough.
  • The schedule is that of the full backups, e.g. daily at 22:00.

Backups are deduplicated — unchanged data is not uploaded again — and encrypted like every backup. Retention counts the full backups; log backups are kept as long as the full backup they build on. The run page lists what each backup holds.

Microsoft SQL Server

  1. Install the agent on the Windows machine that runs SQL Server (any edition from 2012 on, including Express).
  2. The agent runs as NT AUTHORITY\SYSTEM and connects with Windows authentication. Give that account the sysadmin role, once per instance: 
    sqlcmd -S .\SQLEXPRESS -E -Q "ALTER SERVER ROLE sysadmin ADD MEMBER [NT AUTHORITY\SYSTEM]"
  • Each run writes one backup file per database (BACKUP DATABASE / BACKUP LOG … WITH CHECKSUM) into the instance's default backup folder, stores the files and deletes them. The folder needs free space for the largest database while the run lasts.
  • With log backups on, the full backups start the log chain. Without them, full backups are taken COPY_ONLY, so they do not disturb other backup or maintenance plans.
  • Log backups are taken for databases in the full or bulk-logged recovery model; databases in the simple model only get full backups. Tick system databases to add master, model and msdb.

PostgreSQL

The agent works as the postgres account over the local socket — nothing to configure for backups. A full backup stores the whole cluster (pg_basebackup), the roles (pg_dumpall --globals-only) and a pg_dump of each database.

Point-in-time recovery needs WAL archiving. With log backups on, the first full backup sets it up with ALTER SYSTEM: archive_mode = on and an archive_command that copies finished WAL segments into /var/lib/backupzit-pg/wal; the log backups store and remove them there. archive_mode takes effect after one restart of PostgreSQL (systemctl restart postgresql) — the run tells you. If another tool already uses archive_command, BackupZit leaves it alone and backs up without point-in-time recovery. If the log backups stop (job disabled or deleted), switch archiving off again (ALTER SYSTEM RESET archive_mode, restart) so the folder does not fill up.

  • Restore a database as of the full backup: from its pg_dump into the running server, under a new name or replacing the database.
  • At a point in time (or latest): the agent unpacks the cluster backup into a temporary instance on a free port (socket only, no network, no archiving), replays the WAL up to that time, dumps the database from it into the running server and removes the temporary instance. The machine needs free space for the cluster for a while.
  • Whole cluster: restored the same way as a separate instance that keeps running on a free port; the run tells you its port and data directory (below /var/lib/backupzit-pg) and how to connect and stop it.

MySQL and MariaDB

The agent connects as root over the local socket (socket authentication, the default on Debian and Ubuntu), or with the credentials in /root/.my.cnf. A full backup stores a mysqldump of each database (consistent, with routines, events and triggers) together with the binary log position it matches.

Point-in-time recovery needs the binary log. Enable it once in the server configuration and restart the server, e.g. /etc/mysql/mariadb.conf.d/60-binlog.cnf:

[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin
binlog_format = ROW
expire_logs_days = 7

(create the folder for the log, owned by the mysql account). The log backups then store each closed binary log. Keep the server's own expiry longer than the log backup interval; a gap is reported, and restores cannot cross it.

  • Restore a database: its dump is loaded into a new database (or replaces an existing one). At a point in time or latest, the changes of that database recorded in the binary logs after the dump are replayed up to that time — also when the database gets a new name. The replay is not written to the server's binary log.
  • Users and privileges (the mysql system database) are not part of the dumps.

Restoring

Open a full backup run (or use the restore wizard → Database) and choose the database, the machine to restore on (the same server or another one with the same database server) and:

  • As a new database named e.g. sales_restored — the original stays untouched and you can copy rows back — or under its original name; tick replace it to overwrite an existing database (its users are disconnected first).
  • State: as of the full backup; the latest state (the full backup and every log backup after it); or a point in time between the full backup and the newest usable log backup, as the table shows. Enter the time as shown in the console, in the console server's time zone (see Time zone); the agent converts it to the database server's time zone.

Command line

backupzit-agent sql list    [--instance SQLEXPRESS]
backupzit-agent sql backup  --repo ... [--instance I] [--db a,b] [--system] [--log] [--copy-only]
backupzit-agent sql restore --repo ... [--instance I] --db NAME [--as NEW] [--replace] [--at "2026-10-04 14:59:00"] SNAPSHOT|latest
backupzit-agent pg list     [--port 5432]
backupzit-agent pg backup   --repo ... [--port P] [--db a,b] [--pitr | --wal]
backupzit-agent pg restore  --repo ... --db NAME|"(cluster)" [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest
backupzit-agent mysql list
backupzit-agent mysql backup  --repo ... [--db a,b] [--binlog]
backupzit-agent mysql restore --repo ... --db NAME [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest

Not included

  • SQL Server differential backups and Always On availability groups; remote database servers — the agent backs up servers on its own machine.
  • Restoring single tables: restore the database under a new name and copy the rows.
