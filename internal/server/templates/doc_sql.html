Microsoft SQL Server

BackupZit backs up SQL Server databases with SQL Server's own BACKUP statement, from the agent on the SQL Server machine. Full backups run on the job's schedule; transaction log backups every few minutes make it possible to restore a single database to any point in time — for example to one minute before a wrong DELETE.

Setup

  1. Install the BackupZit agent on the Windows machine that runs SQL Server (any edition from 2012 on, including Express).
  2. The agent runs as NT AUTHORITY\SYSTEM and connects to the instance with Windows authentication. Give that account the sysadmin role, once per instance, e.g. in SQL Server Management Studio or with: 
    sqlcmd -S .\SQLEXPRESS -E -Q "ALTER SERVER ROLE sysadmin ADD MEMBER [NT AUTHORITY\SYSTEM]"
  3. Create a job of the kind SQL Server databases under Backup jobs:
    • Instance: empty for the default instance (MSSQLSERVER), otherwise its name, e.g. SQLEXPRESS.
    • Databases: one name per line, or empty for all user databases — databases created later are included automatically. Tick system databases to add master, model and msdb.
    • Back up the transaction logs every … minutes: e.g. 15. Leave empty if restoring to the time of a full backup is enough.
    • The schedule is that of the full backups, e.g. daily at 22:00.

How it works

  • Each run writes one backup file per database into the instance's default backup folder (SQL Server's service account can write there), stores the files in the repository and deletes them. The folder needs free space for the largest database while the run lasts.
  • Backups are deduplicated: unchanged pages of the database are not uploaded again, so daily full backups of a large database cost little space. They are encrypted like every backup.
  • With log backups on, the full backups start the log chain (normal full backups). Without them, full backups are taken COPY_ONLY, so they do not disturb other backup or maintenance plans of the instance.
  • Log backups are taken for databases in the full or bulk-logged recovery model; databases in the simple model only get full backups. Log backups also keep the transaction log from growing.
  • Retention counts the full backups; log backups are kept as long as the full backup they build on.
  • Every run is checked with CHECKSUM; the run page lists each database with its recovery model, size and LSN range.

Restoring a database

Open a full backup run (or use the restore wizard → SQL Server database) and choose:

  • Database, and the machine and instance to restore on — the same server or another one with SQL Server.
  • As a new database named e.g. sales_restored — the original stays untouched and you can copy rows back — or under its original name. To overwrite an existing database tick replace it: its users are disconnected first.
  • State: as of the full backup; the latest state (the full backup and every log backup after it); or a point in time between the full backup and the newest log backup, as the table shows. Times are the local time of the SQL Server machine.

The agent restores the needed files into the instance's backup folder, runs RESTORE DATABASE and RESTORE LOG … STOPAT and deletes the files again. A database with a new name gets its own data and log files in the instance's default folders.

Command line

backupzit-agent sql list    [--instance SQLEXPRESS]
backupzit-agent sql backup  --repo ... [--instance I] [--db a,b] [--system] [--log] [--copy-only]
backupzit-agent sql show    --repo ...
backupzit-agent sql restore --repo ... [--instance I] --db NAME [--as NEW] [--replace] [--at "2026-10-04 14:59:00"] SNAPSHOT|latest

Not included

  • Differential backups, Always On availability groups and remote instances — the agent backs up instances on its own machine.
  • Restoring single tables: restore the database under a new name and copy the rows.
