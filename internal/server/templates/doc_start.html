Getting started

BackupZit protects Windows and Linux machines with file and disk-image backups that you manage from one web console running on your own network.

How BackupZit works

  • Management console (this web application) — runs on a Linux server in your network. It stores configuration, schedules jobs, collects results and shows reports. It never needs to be reachable from the internet.
  • Agents — a small service installed on every machine you protect (Windows MSI, Linux deb/rpm). Agents contact the console over HTTPS, receive jobs, and send the backup data directly to the storage.
  • Storage targets — where backups are kept: an SFTP server, S3-compatible object storage (AWS, Wasabi, Backblaze B2, MinIO…), an SMB share/NAS, a local or mounted disk, or a BackupZit hardened repository.

Backup data never passes through the console. The console only coordinates, so it can run on a small virtual machine.

First steps

  1. Add a storage target under Storage. Keep Encrypt backups enabled and save the recovery sheet that is shown afterwards in a safe place. See Storage targets.
  2. Install agents: under Agents click Create enrollment token and run the shown command on each machine. See Agents.
  3. Create a backup job under Backup jobs: choose the agent, the storage, what to back up (folders or a whole disk), when to run and how many backups to keep. See Backup jobs & schedules.
  4. Run it once manually with Run backup now on the job page and check the result under Activity.
  5. Test a restore — a backup is only as good as its restore. See Restoring files.
  6. Set up email alerts under Settings so you hear about failures, and optionally a weekly report.

Key concepts

Snapshots and deduplication

Every backup creates a snapshot: a complete, browsable picture of the data at that moment. Data is split into variable-size chunks, and each chunk is stored only once, so the second and later backups only upload what changed — yet every snapshot can be restored on its own. There is no "full vs. incremental chain" to manage.

Repositories

Each agent writes into its own repository below the storage target location (<location>/<hostname>_<id>). A repository is self-contained: with the location, the storage credentials and the recovery key, it can be restored even if the console is gone.

Retention

Each job keeps a number of recent, daily, weekly and monthly backups. Older snapshots are removed after each run and the space they used is freed.
