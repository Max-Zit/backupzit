Getting started

BackupZit protects Windows and Linux machines and Proxmox VE, Hyper-V and VMware ESXi virtual machines — files, whole disks and whole systems — from one web console that runs on your own network.

How BackupZit works

  • Management console (this web application) — runs on a Linux server in your network. It stores configuration, schedules jobs, collects results and shows reports. It never needs to be reachable from the internet.
  • Agents — a small service on every protected machine (Windows MSI, Linux deb/rpm) and on Proxmox and Hyper-V hosts; VMware ESXi hosts are reached through an agent working as proxy. Agents contact the console over HTTPS, receive jobs, and send the backup data directly to the storage. On Windows the agent shows its state next to the clock.
  • Storage targets — where backups are kept: SFTP, S3-compatible object storage (AWS, Wasabi, Backblaze B2, MinIO, Google Cloud…), Azure Blob Storage, an SMB share/NAS, rotating USB disks, a local or mounted disk, or a BackupZit hardened repository.

Backup data never passes through the console. The console only coordinates, so it can run on a small virtual machine.

First steps

To set up a new console, install the BackupZit appliance ISO in a small VM. It installs everything without questions; see Installing the server.

  1. Add a storage target under Storage. Keep Encrypt backups enabled and save the recovery sheet that is shown afterwards in a safe place. See Storage targets.
  2. Install agents: under Agents click Create enrollment token, download the installer from the same page and paste the enrollment code when the Windows installer asks for it (Linux: backupzit-agent enroll --code …). For VMs install the agent on the Proxmox or Hyper-V host; add VMware ESXi hosts under Agents → VMware ESXi hosts. See Agents.
  3. Create a backup job under Backup jobs: choose the agent, the storage, what to back up (files, a disk image, the whole Linux system or the VMs of a Proxmox, Hyper-V or VMware ESXi host), when to run and how many backups to keep. See Backup jobs & schedules.
  4. Run it once manually with Run backup now on the job page and check the result under Activity.
  5. Test a restore — a backup is only as good as its restore. Automatic restore tests run weekly; restore something by hand once too, with the restore wizard. See Restoring.
  6. Prepare for disasters: download the recovery ISOs and create a recovery code under Recovery media.
  7. Set up email alerts under Settings → Email notifications so you hear about failures, and optionally a weekly report.

Key concepts

Snapshots and deduplication

Every backup creates a snapshot: a complete, browsable picture of the data at that moment. Files are split into variable-size chunks and disks into blocks, and each piece is stored only once, so the second and later backups only upload what changed — yet every snapshot can be restored on its own. There is no "full vs. incremental chain" to manage.

Repositories

Each agent writes into its own repository below the storage target location (<location>/<hostname>_<id>). A repository is self-contained: with the location, the storage credentials and the recovery key, it can be restored even if the console is gone.

Retention

Each job keeps a number of recent, daily, weekly and monthly backups. Older snapshots are removed after each run and the space they used is freed.

What BackupZit checks for you

  • Restore tests — every job's newest backup is partly restored and verified weekly (Restoring).
  • Ransomware detection — unusual backups (mass changes, encrypted data, mass deletion, sudden data volume jumps) are flagged and retention is paused (Ransomware protection).
  • Alerts and reports — emails for failures and a daily summary; scheduled reports for management (Email notifications, Monitoring).
