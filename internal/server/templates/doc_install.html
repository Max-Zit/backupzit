Installing the server

The console runs on Linux (Debian, Ubuntu, AlmaLinux, Rocky Linux) with PostgreSQL. Each organization runs its own console on its own network.

Requirements

  • A Linux VM or server: 2 vCPU, 2–4 GB RAM, 20 GB disk is plenty for hundreds of agents (backup data is not stored on it).
  • PostgreSQL 13 or newer (local or on another server).
  • Network: agents must reach the console on TCP 8443 (HTTPS). Agents must also reach the storage directly.

1. Ready-made VM image

A finished appliance (Debian, PostgreSQL, the console, automatic security updates) that starts in under a minute and needs no internet access:

HypervisorHow
VMware ESXiHost client: Create / Register VM → Deploy a virtual machine from an OVF or OVA file, choose backupzit-appliance.ova. vSphere: Deploy OVF Template. Workstation and VirtualBox: File → Open / Import.
Proxmox VECopy backupzit-appliance.qcow2 to the node, create a VM without a disk (2 vCPU, 2–4 GB RAM, VirtIO network), then
qm importdisk <vmid> backupzit-appliance.qcow2 local-lvm
attach the imported disk as SCSI, make it the boot disk and enable the QEMU guest agent.
Hyper-VUnzip backupzit-appliance-vhdx.zip, then New → Virtual Machine, generation 1, 2–4 GB RAM, Use an existing virtual hard disk: the VHDX.

Start the VM. Its screen shows the address of the web console and the initial password of admin (see First sign-in). Give the VM 2 vCPU and 2–4 GB RAM; you can enlarge the 16 GB disk at any time. At the first start every copy creates its own SSH keys, database password and secrets key, so one image can be deployed many times. The network adapter gets its address by DHCP.

2. Appliance ISO

The appliance ISO installs everything without questions: Debian, PostgreSQL, the console and automatic security updates.

  1. Create a VM (or use a server) with 2 vCPU, 2–4 GB RAM and a 16 GB or larger disk. Use VirtIO or the hypervisor's default devices, BIOS or UEFI.
  2. Boot it from backupzit-appliance.iso. After 5 seconds the installation starts by itself, erases the first disk and installs. It downloads the operating system packages, so the server needs internet access during installation. This takes about 10–20 minutes, and the server then restarts.
  3. The server's screen shows the address of the web console and the initial password of admin. Open the address, sign in and change the password.

The appliance (image or ISO)

The appliance has two separate accounts:

  • admin in the web console (https://<address>:8443) for everyday work. Its initial password is shown on the server's screen after the first start; change it under My account.
  • bzadmin on the server itself (its screen in the hypervisor console, or SSH), initial password backupzit. You must change it at the first sign-in; the user can use sudo. Root cannot sign in.

Updates of BackupZit and of the operating system are managed from the console (see below). VMware Tools and the QEMU guest agent are included, so hypervisors show the appliance's address.

Setup menu on the server's screen

When bzadmin signs in on the server's own screen (not over SSH), a menu opens:

ItemWhat it does
1 NetworkDHCP or a static address with prefix length (e.g. 192.168.1.20/24), gateway and up to three DNS servers.
2 Server nameThe host name (letters, digits and -).
3 SSHSwitch the SSH server on or off and change its port. The ports of the console (80, 443, 8443), PostgreSQL (5432) and instant recovery (111, 2049) cannot be used.
4 Reset the password of "admin"For a forgotten web console password; also lifts sign-in blocks.
5 Lift sign-in blocks and web console limitsWhen too many failed sign-ins blocked an address, or the web console is limited to addresses you can no longer use (see Security).

The same network, server name and SSH settings are under Settings → Network in the web console (administrators only). There, a static address whose gateway does not answer within half a minute is undone automatically, so a typo cannot cut the appliance off the network; if the console still cannot be reached, use the menu on the server's screen, which works even with SSH off.

Agents remember the console's certificate, not its address. If they reach the console by its IP address and the address changes, point them at the new one with backupzit-agent set-server (see Agents), or use a DNS name from the start. With DHCP, reserve the appliance's address in the DHCP server so it does not change.

The appliance's SSH server offers only AES-GCM/CTR ciphers and SHA-2 MACs (no chacha20-poly1305 or 64-bit MACs, which vulnerability scanners report as weak).

3. Install script

On an existing server with Debian 12+, Ubuntu 22.04+, AlmaLinux or Rocky Linux 9+ (x86-64), as root:

curl -fsSL https://github.com/Max-Zit/backupzit/releases/latest/download/install.sh | sudo sh

The script installs PostgreSQL, downloads the newest release, checks its signature with the BackupZit release key and the package checksum, installs the console, creates the database with a random password, writes /etc/backupzit/server.env, switches on automatic security updates, opens port 8443 in firewalld or ufw if they are active, starts the console and prints its address and the initial admin password. Options (after sh -s --):

OptionEffect
--version 0.32.0install this release instead of the newest
--db postgres://user:pw@host:5432/dbuse an existing PostgreSQL database instead of a local one
--hosts backup.example.local,10.0.0.10names and addresses for the console's certificate (default: the server's address and name)
--no-auto-updatesleave automatic security updates as they are

Example: curl -fsSL …/install.sh | sudo sh -s -- --hosts backup.example.local. Running the script again on an installed console updates BackupZit and keeps the configuration and data. To read the script before running it, download it first: curl -fsSLO …/install.sh; less install.sh; sudo sh install.sh.

4. Packages by hand

Debian / Ubuntu

apt install postgresql
apt install ./backupzit-server_*.deb

AlmaLinux / Rocky Linux

dnf install postgresql-server && postgresql-setup --initdb && systemctl enable --now postgresql
dnf install ./backupzit-server-*.rpm

On AlmaLinux and Rocky Linux, change ident to scram-sha-256 for the 127.0.0.1 and ::1 lines in /var/lib/pgsql/data/pg_hba.conf and restart PostgreSQL, so the console can sign in with a password.

Create the database

sudo -u postgres psql -c "SET password_encryption = 'scram-sha-256'; CREATE USER backupzit WITH PASSWORD 'choose-a-strong-password'"
sudo -u postgres psql -c "CREATE DATABASE backupzit OWNER backupzit"

Put the connection string into /etc/backupzit/server.env:

BACKUPZIT_DB=postgres://backupzit:choose-a-strong-password@localhost:5432/backupzit?sslmode=disable
BACKUPZIT_PUBLIC_URL=https://backup.example.local:8443
BACKUPZIT_TLS_HOSTS=backup.example.local,10.0.0.10
systemctl start backupzit-server

First sign-in

Open https://<server>:8443. The initial administrator is admin; the password is in /var/lib/backupzit/initial-admin-password.txt (or set BACKUPZIT_ADMIN_PASSWORD before the first start). Change it after signing in. To reset a forgotten password on the server:

set -a; . /etc/backupzit/server.env; set +a
backupzit-server --set-admin-password 'NEW-PASSWORD'

The certificate

On first start the console creates a self-signed certificate. Your browser will warn about it once; agents do not rely on certificate authorities at all — they pin the certificate fingerprint shown on the Agents page when they enroll. That protects agents against a fake server even on an untrusted network.

Do not replace that certificate (cert.pem/key.pem in the data directory): agents enrolled earlier would refuse to connect until they are enrolled again. For browsers, add a trusted certificate as described below instead.

A trusted certificate for browsers

To avoid the browser warning, open Settings → Certificate. The console then also answers at a DNS name, for example https://backup.example.com on port 443, with a trusted certificate. Agents keep using port 8443 and the pinned certificate, so they are not affected.

  • Upload a certificate from your company CA or a public CA, also a wildcard certificate such as *.example.com. Paste the certificate (with its intermediate certificates) and the private key as PEM, or choose the files. The console checks that the key belongs to the certificate, that it is valid now and that it covers the DNS name. Without internal DNS, enter the console's IP address instead and use a certificate issued for that IP address (subject alternative name IP:192.168.1.20); give the console a fixed address then. You get an email 21 days before it expires.
  • Let's Encrypt: free certificates, renewed automatically 30 days before they expire. Let's Encrypt has to verify that you control the name, in one of two ways:
    • DNS check via Cloudflare, recommended for consoles that are not reachable from the internet. BackupZit creates a temporary TXT record with a Cloudflare API token. In Cloudflare, go to My Profile → API Tokens → Create Token, use the template Edit zone DNS and limit it to your zone.
    • HTTP check: port 80 of the console must be reachable from the internet under the DNS name. This is rarely wanted for a backup server.
    Try the setup first with Use the Let's Encrypt test system. Its certificates are not trusted by browsers, but it has no rate limits.
  • Serve port 80 redirects http:// to https://.

The DNS name must point to the console's IP address, usually through an A record in your internal DNS. The certificate files are kept in /var/lib/backupzit/web, and the key is readable only by the service. On Linux the service may use ports 80 and 443 (CAP_NET_BIND_SERVICE); open them in the firewall if browsers connect from other networks.

Updating BackupZit

By default the console takes updates from the official BackupZit releases on GitHub (https://github.com/Max-Zit/backupzit/releases). Under Settings → Updates you can enter another update source instead — your own HTTPS mirror or a folder on the server. Whatever the source, every release must carry a valid BackupZit signature. The console checks every day for new releases and emails the administrators when one is available. To install it, click Install:

  1. The console checks the release signature and the package checksum, and waits until no backup or restore is running.
  2. A system service (backupzit-update, running as root) checks the signature again with the release keys built into BackupZit. Even a compromised console cannot get any other package installed.
  3. It backs up the database (pg_dump), keeps the current program, installs the package and restarts the console.
  4. If the new version does not answer within two minutes, the previous program and the database as it was are restored automatically. The result, with the log of the failed start, is shown on the Updates page, recorded in the audit log and emailed.
  5. After a successful update the agents are updated too: each one installs the new version when it is idle. Turn this off on the same page if you prefer to update them yourself.

The console is unavailable for about a minute. The database backups and previous programs of the last three updates are kept in /var/lib/backupzit-update.

Without internet access: download the release files (manifest.json, manifest.json.sig and the server package) on another computer. Then upload them under Install an update from files, or copy them into a folder on the server and use that folder as the update source.

You can still update with the package manager (apt install ./backupzit-server_….deb); the database is migrated when the new version starts.

Operating system updates

The same page (Settings → Updates) shows the operating system of the console server: how many updates are available, how many of them are security fixes, whether a restart is needed, and whether automatic security updates are on. The status is refreshed daily, or with Check now. You can:

  • Switch on automatic security updates (recommended). The system's own tool installs only security fixes, daily: unattended-upgrades on Debian and Ubuntu, dnf-automatic on AlmaLinux and Rocky Linux.
  • Install all updates now. Services such as PostgreSQL may restart briefly, and the console reconnects by itself.
  • Restart the server, for example after a kernel update. The console refuses while backups or restores are running. Agents keep their jobs and report the results when the console is back.

These tasks run through the same root service as console updates. They are recorded in the audit log, and the output of the last task is shown on the page.

Backing up the console itself

Backups on your storage stay readable without the console, using the recovery sheets. To also get back the console itself after losing its server, switch on Settings → Console backup. That includes jobs, schedules, agents, users, settings, run history and stored credentials. The console then backs itself up every day to a network storage target, into the folder backupzit-console.

A console backup holds:

  • the whole database, exported table by table, so no particular pg_dump version is needed;
  • the secrets key that decrypts the stored credentials;
  • the console's certificate, which agents pin.

It is encrypted with the target's recovery key and deduplicated. The newest backups are kept: 14 by default.

Restoring the console

  1. Install a new console with the same or a newer version, for example from the appliance ISO.
  2. On the new server, as root, run the following. The credentials are the ones from the storage target's recovery sheet, and the repository address is shown on the Console backup page. 
    systemctl stop backupzit-server
set -a; . /etc/backupzit/server.env; set +a
export BACKUPZIT_PASSWORD='<recovery key>'
export BACKUPZIT_SFTP_PASSWORD='…' BACKUPZIT_SFTP_HOSTKEY='SHA256:…'   # or BACKUPZIT_S3_ACCESS_KEY/_SECRET_KEY, _SMB_PASSWORD, _AZURE_KEY, _HARDENED_KEY/_FINGERPRINT
backupzit-server --restore-console --repo 'sftp://backup@nas:22/backups/backupzit-console'
systemctl start backupzit-server
  3. Give the new server the old server's IP address or DNS name. The agents trust the restored certificate and reconnect by themselves.

The restore replaces the new console's database with the backup and brings the database up to the installed version. --snapshot ID restores an older backup instead of the newest one.

Also keep a copy of the recovery sheets and of secrets.key outside the server, for example in your password manager.
