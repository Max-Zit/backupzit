Installing the server

The console runs on Linux (Debian, Ubuntu, AlmaLinux, Rocky Linux) with PostgreSQL. Each organization runs its own console on its own network.

Requirements

  • A Linux VM or server: 2 vCPU, 2–4 GB RAM, 20 GB disk is plenty for hundreds of agents (backup data is not stored on it).
  • PostgreSQL 13 or newer (local or on another server).
  • Network: agents must reach the console on TCP 8443 (HTTPS). Agents must also reach the storage directly.

Install

Debian / Ubuntu

apt install postgresql
apt install ./backupzit-server_*.deb

AlmaLinux / Rocky Linux

dnf install postgresql-server && postgresql-setup --initdb && systemctl enable --now postgresql
dnf install ./backupzit-server-*.rpm

Create the database

sudo -u postgres psql -c "CREATE USER backupzit WITH PASSWORD 'choose-a-strong-password'"
sudo -u postgres psql -c "CREATE DATABASE backupzit OWNER backupzit"

Put the connection string into /etc/backupzit/server.env:

BACKUPZIT_DB=postgres://backupzit:choose-a-strong-password@localhost:5432/backupzit?sslmode=disable
BACKUPZIT_PUBLIC_URL=https://backup.example.local:8443
BACKUPZIT_TLS_HOSTS=backup.example.local,10.0.0.10
systemctl start backupzit-server

First sign-in

Open https://<server>:8443. The initial administrator is admin; the password is in /var/lib/backupzit/initial-admin-password.txt (or set BACKUPZIT_ADMIN_PASSWORD before the first start). Change it after signing in. To reset a forgotten password on the server:

set -a; . /etc/backupzit/server.env; set +a
backupzit-server --set-admin-password 'NEW-PASSWORD'

The certificate

On first start the console creates a self-signed certificate. Your browser will warn about it once; agents do not rely on certificate authorities at all — they pin the certificate fingerprint shown on the Agents page when they enroll. That protects agents against a fake server even on an untrusted network.

Do not replace that certificate (cert.pem/key.pem in the data directory): agents enrolled earlier would refuse to connect until they are enrolled again. For browsers, add a trusted certificate as described below instead.

A trusted certificate for browsers

To avoid the browser warning, open Settings → Certificate. The console then also answers at a DNS name, for example https://backup.example.com on port 443, with a trusted certificate. Agents keep using port 8443 and the pinned certificate, so they are not affected.

  • Upload a certificate from your company CA or a public CA, also a wildcard certificate such as *.example.com. Paste the certificate (with its intermediate certificates) and the private key as PEM, or choose the files. The console checks that the key belongs to the certificate, that it is valid now and that it covers the DNS name. You get an email 21 days before it expires.
  • Let's Encrypt: free certificates, renewed automatically 30 days before they expire. Let's Encrypt has to verify that you control the name, in one of two ways:
    • DNS check via Cloudflare, recommended for consoles that are not reachable from the internet. BackupZit creates a temporary TXT record with a Cloudflare API token. In Cloudflare, go to My Profile → API Tokens → Create Token, use the template Edit zone DNS and limit it to your zone.
    • HTTP check: port 80 of the console must be reachable from the internet under the DNS name. This is rarely wanted for a backup server.
    Try the setup first with Use the Let's Encrypt test system. Its certificates are not trusted by browsers, but it has no rate limits.
  • Serve port 80 redirects http:// to https://.

The DNS name must point to the console's IP address, usually through an A record in your internal DNS. The certificate files are kept in /var/lib/backupzit/web, and the key is readable only by the service. On Linux the service may use ports 80 and 443 (CAP_NET_BIND_SERVICE); open them in the firewall if browsers connect from other networks.

The console also connects to the storage itself to let you browse files inside disk images and VM backups (and download them), so it needs the same storage access as the agents.

Backing up the console itself

Back up the PostgreSQL database (for example with a nightly pg_dump to a file that a BackupZit agent on the same machine backs up) and the data directory /var/lib/backupzit: the certificate and secrets.key, the key that encrypts all stored passwords, storage keys and recovery keys in the database. Keep a copy of secrets.key outside the server (e.g. in your password manager); without it the stored credentials in a restored database cannot be read. Alternatively provide the key in BACKUPZIT_SECRETS_KEY (base64). Keep the recovery sheets of your storage targets separately — with them, backups can be restored even without the console.
