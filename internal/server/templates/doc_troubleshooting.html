Troubleshooting & FAQ

An agent shows as offline

  • Is the machine on and the service running? Windows: Get-Service backupzit-agent; Linux: systemctl status backupzit-agent.
  • Can the machine reach the console? Test-NetConnection backup-server -Port 8443 or curl -k https://backup-server:8443/login.
  • Agent log: C:\ProgramData\backupzit\agent.log, on Linux /var/log/backupzit/agent.log or journalctl -u backupzit-agent. "fingerprint mismatch" means the console certificate changed — enroll the agent again.

A backup failed

Open the run in Activity; the message names the cause. Common ones:

Message containsFix
host key mismatch / fingerprintThe SFTP server's key changed or the fingerprint was entered wrongly. Check with ssh-keygen -lf on the server.
permission denied / access deniedStorage credentials or folder permissions. Test the login with an SFTP/SMB client.
no space left / quotaStorage is full. Reduce retention or add space; expired backups free space after the next run.
repository is lockedAnother operation (e.g. cleanup) is running on the same repository; the run retries for 30 minutes. Stale locks expire automatically.
wrong password / recovery keyThe repository was created with a different key — check that the job uses the right storage target.
bucket has no Object Lock enabledImmutability was requested on a bucket created without Object Lock. Create a new bucket with Object Lock.
S3 / Azure: "the clock of this computer differs from the storage's by more than 15 minutes" (RequestTimeTooSkewed, Request date header too old)Cloud storage signs every request with the time and refuses it when the clock is more than about 15 minutes off. Correct the time of the computer named in the run (the agent; for Test connection the console) and turn on time synchronization: Windows Settings → Time & language → Set time automatically; Linux timedatectl set-ntp true or chrony. Virtual machines may get a wrong time after being off for a long time or across a daylight saving change.

Other messages

SituationWhat to do
"no matching backup disk is connected"Plug in one of the rotating USB disks (the message lists the label it needs and which labeled disks are connected). A restore needs exactly the disk shown in the backup run.
"several backup disks are connected"Connect only one of the rotating disks at a time.
Restore test failedOpen the run: the message names the damaged file or block or the reason (e.g. backup deleted on the storage). Run backupzit-agent check --read-data against the repository, check the storage, and start a new backup. If backups were deleted on immutable storage, see Ransomware protection.
Data check found damaged data packsThe storage lost or changed data (for example a fault at the provider). As long as the damaged packs are in the index, new backups keep reusing their data. Click Repair: take the damaged data out of the index on the run page of the check, or run backupzit-agent repair --repo … (--dry-run only lists): the storage is read again under an exclusive lock, the damaged packs leave the index, and the run lists the backups that need the lost data. They stay and restore what is left; tick Also remove the backups that need the lost data to remove them, so that later data checks and freeing space after retention work again. Removing them asks for your password or two-factor code, needs a second user's approval when four-eyes approval is on, keeps backups a VM runs from (instant recovery), and is refused while retention is paused after a suspicious backup. The next backups store that data again. Agents 0.55 and newer. Since 0.55 only packs proven damaged are taken out: missing, or not matching their content when read whole. A pack that only arrives short on this agent while the storage holds it whole is read again with a pause, then listed and left alone; check the network path (proxy, firewall, IPS, NAT). The pack files themselves go with the next cleanup. Backups whose folder lists cannot be read from this agent are kept, never removed as affected. When 20 packs in a row cannot be read, the check stops with "the storage stopped answering" and judges nothing: check the storage and the network path, then run it again. Since 0.56 a pack missing from the storage's file listing is looked up on its own, with several tries, before it counts as missing; a listing that is empty, or that misses most packs at once, gives no verdict and the check fails with the reason, so a storage hiccup never takes data out of the index.
Backup marked suspiciousCheck the machine for ransomware or a mass deletion (e.g. a synced folder emptied). If everything is fine (e.g. a planned migration), click Reviewed — resume retention on the job page.
Let's Encrypt: "could not verify … is port 80 … reachable"The HTTP check needs port 80 reachable from the internet. Use the DNS check via Cloudflare for internal consoles.
Let's Encrypt: "no Cloudflare zone … is accessible with this token"The token must have the permission Zone → DNS → Edit for the zone that holds the console's name.
"HTTPS port 443: … permission denied" or "address already in use"Another program uses the port, or the service may not bind ports below 1024 (run it with CAP_NET_BIND_SERVICE, as the package does). Choose another port in Settings → Certificate.
Updates: "updates from the console need the Linux package of the console"The console was not installed from the deb/rpm package (for example the evaluation mode). Update it the way it was installed.
Updates: "the release is not signed with a BackupZit release key"The update source does not hold an official release, or the files were changed on the way. Download them again from the official address.
Updates: status rolled-backThe new version did not start, so the previous one and its database were restored. The log of the failed start is on the Updates page; send it to support.
"The agent is no longer running this"The agent was restarted or stopped during the run (for example a reboot or a service restart), or could not deliver the result. Agents 0.52.0 and newer report the runs they work on, so the console fails such a run within about two minutes instead of showing it as running until someone stops it; with older agents, stop it on its page. Get log on the Agents page shows what happened. The next scheduled run starts as usual. If the agent shuts down normally (service stop, a reboot for updates), the run ends with "The agent was stopped during the run" instead.
"agent stopped responding while the run was in progress"The agent did not contact the console for more than 10 minutes during the run (a network outage, or the agent machine stopped). Time while the console itself was down does not count. The agent keeps trying to deliver its result for two hours; when it arrives, the run shows the real result and its backup can be restored.
Operating system: "no supported package manager"Updates of the operating system are supported on Debian, Ubuntu (apt) and AlmaLinux, Rocky Linux, RHEL (dnf).
Console backup: "the backup was made by a newer BackupZit"Install the version that made the backup, or a newer one, on the new console before restoring.
Console backup: "console backups need network storage"Choose an SFTP, S3, SMB, Azure or hardened repository target; a local path of an agent is not reachable from the console.
"Too many failed sign-ins"Your address was blocked after repeated wrong passwords: by default for 30 minutes, longer for repeated blocks. An administrator can lift the block under Settings → Sign-in & security. On the server, backupzit-server --unblock-ip all lifts all blocks. Accounts are never locked permanently.
Lost phone for two-factor sign-inUse one of the recovery codes; otherwise an administrator resets two-factor on your user page. If no administrator can sign in any more, run backupzit-server --reset-two-factor USER on the server (Docker: docker compose exec backupzit backupzit-server --reset-two-factor USER): it turns two-factor sign-in off for that user, signs the user out and is written to the audit log; then sign in with the password and set it up again.
"your directory account is not in any BackupZit group"Add the user to one of the groups mapped under Settings → LDAP / Active Directory, or map more groups. Use Test there to see the groups found for a user.
API returns 401 / 403401: token missing, revoked, expired or its owner disabled. 403: the token's role is too low for the request.
Azure: AuthenticationFailed / AuthorizationPermissionMismatchWrong account key, or the SAS token lacks read, write, delete or list permission or has expired.
A restored Windows Server 2012 R2 / Windows 8.1 VM does not boot on Hyper-V Gen 2 ("hash was denied (DBX)")Microsoft revoked the old boot loader for Secure Boot. Turn off Secure Boot for that VM, or update the system before backing it up.

Virtual machines, Linux systems and new hardware

SituationWhat to do
Proxmox: "the guest is running and one of its disks is on storage without snapshot support"Running guests need LVM-thin, ZFS, Ceph RBD or qcow2 disks. Move the disk (Disk Action → Move Storage) or back the guest up while it is stopped.
Proxmox: "container volumes that are directories on dir storage are not supported yet"The container's volume is a directory on directory, NFS or btrfs storage. Only directories on ZFS (subvolumes) are backed up file by file; move the volume to ZFS, LVM-thin or Ceph RBD (Volume Action → Move Storage).
Hyper-V: the run says "crash-consistent"The guest could not prepare for the checkpoint. In Windows guests check that the Hyper-V integration services (Backup (volume shadow copy)) are enabled in the VM settings. In Linux guests install hyperv-daemons (RHEL) or linux-cloud-tools / hyperv-daemons (Debian/Ubuntu).
VMware: "SSH off" or "SSH to …: connection refused"Enable SSH on the ESXi host: Host → Actions → Services → Enable Secure Shell (and set its policy to start with the host). Restores, and backups on the free license, need it.
VMware: "changed block tracking is off and can be enabled … only while the VM is off"Free ESXi license: shut the VM down once, then run the job; BackupZit enables changed block tracking and later backups read only changed blocks.
VMware: "copy the disk on the datastore (needs free space …)"Running VMs are copied briefly on their datastore. Free up space there (as much as the disk uses), or back up the VM while it is off.
VMware: "… is a snapshot delta disk"The VM has snapshots of its own. Delete or consolidate them in the ESXi host client (Snapshots → Delete all).
Dashboard: "backup snapshot … left on …", "backup checkpoint …", "temporary disk copy …" or "backup lock"A backup could not remove what it created on the hypervisor (the agent was stopped in the middle, or the removal failed); while it stays, the VM's disks grow or, with the lock, the guest cannot start. The agent tries again by itself (Proxmox VE and Hyper-V every 15 minutes, VMware at the next backup of the connection). Click Remove now to have it try at once; the clean-up run on the Activity page shows what was removed and why the rest failed (for example a datastore or storage that is busy, a file locked by another program). If it keeps failing, remove it in the hypervisor's own tools: vSphere Client (Snapshots → Delete, then Consolidate), Proxmox VE (qm delsnapshot ID NAME --force, qm unlock ID), Hyper-V Manager (Checkpoints → Delete). See VMware, Proxmox VE and Hyper-V.
Proxmox: "guest … already has the backup lock"Another backup of the guest runs (BackupZit or vzdump), or an interrupted run left the lock. The agent removes a lock it set itself within 15 minutes; any other lock, once no backup runs, is removed with qm unlock ID (containers: pct unlock ID).
VMware: "the ESXi certificate changed"The host was reinstalled or another machine answers at its address. If that is expected, check the fingerprint and click Accept the new certificate next to the host on the Agents page.
VMware: *.replaced-DATE.vmdk files next to VM disksThe old disks of a VM restored in place. Delete them in the datastore browser once the restored VM works.
Hyper-V: old VHDX files left after an in-place restoreThe restore detaches the VM's old disks and leaves them where they were (the run lists each one: old disk kept at …); the restored disks are in a backupzit-restore-… subfolder. Delete the old files once the restored VM works.
Proxmox instant recovery: the VM does not boot or hangsCheck the disk server: systemctl status backupzit-instant-ID and journalctl -u backupzit-instant-ID on the node. It needs the backup storage to stay reachable; when the repository cannot be read, the VM's disk reads stall.
Proxmox instant recovery: "efidisk0 stays on storage backupzit-instant"QEMU cannot move the EFI variable store while the VM runs. Shut the VM down and run qm disk move ID efidisk0 STORAGE --delete 1; it does not depend on the backup.
Proxmox: "runs on node X; install the BackupZit agent on X"The guest was migrated. Install the agent on every node and back up each node's guests with that node's agent.
Proxmox backups or restores slow, SFTP "connection lost", "message authentication code incorrect" on the storage serverKnown problem of Intel e1000e network cards on Proxmox hosts (log: "Detected Hardware Unit Hang", "Reset adapter unexpectedly"). Turn off offloading: ethtool -K eno1 tso off gso off gro off and add it as post-up line to the interface in /etc/network/interfaces.
Browse files: "stored on a local path of the agent"The console can only read backups on network storage. Use backupzit-agent pve ls/extract or image-ls/image-extract on the agent.
Linux system restore: "missing programs …"Install the named packages on the restoring machine, or boot the BackupZit Linux recovery ISO, which has them.
Restored Linux machine has no networkThe network settings were bound to the old MAC address (netplan match: macaddress). Restore with Different hardware, or remove the match lines in /etc/netplan/.
Restored Windows stops with INACCESSIBLE_BOOT_DEVICERestore again with Restore to different hardware, or boot the recovery ISO and run backupzit-agent prepare-hardware --disk 0 [--drivers E:\Drivers].
A restored copy of a machine shows up as the original agentA Linux system restored as a new VM is unenrolled automatically. For other copies (a VM restored as a new VM, instant recovery, a replica, a cloned disk) the console holds the agent's runs and shows two machines; enroll the copy as a new machine (see Two machines using one agent).
Agent update does not finishSee the installer log in C:\ProgramData\backupzit\updates or /var/lib/backupzit-agent/updates; agents before 0.21 must be updated once by hand.
The tray icon is missingClick the ^ arrow next to the clock and drag the BackupZit icon onto the taskbar, or start BackupZit Agent from the Start menu.

A backup ends with "warning"

Some files could not be read — usually files locked by an application while VSS is not available, or files the agent has no permission for. The list is on the run page. Everything else is backed up.

Backups are slow

  • The first backup reads and uploads everything; later ones read only changed files and upload only new data.
  • Check the network path to the storage (Wi-Fi, VPN, internet upload speed for cloud storage).
  • Exclude caches, temporary files and media you do not need.

A recovery system prints its log on its screen. To report a bug, click Report a bug at the bottom of the menu: it opens the bug report form on GitHub with the console version filled in — no support contract is needed. Attach the diagnostics zip if it helps. With a MaxZit support plan, Contact support (the gold button above it) opens a new ticket in the customer portal at portal.maxzit.com, with the product and version filled in.

FAQ

Can I use NFS?

To back up an NFS (or SMB) share, create a NAS / file share job; a Linux agent mounts the export for each run. To store backups on NFS, mount the export on the agent (Linux: /etc/fstab) and use a Local / mounted path target such as /mnt/nfs-backup; for Windows machines an SMB target is the better choice.

Can I move backups to another storage?

Copy the repository folder (or bucket prefix) as is — it is self-contained — and add a storage target pointing to the new location with the same recovery key.

Does deleting a job delete the backups?

No. Backups stay on the storage and remain restorable from Activity or the command line. Copy jobs of the deleted job are deleted with it; the copies they made stay on their storage.

What happens if the console is down?

No new scheduled backups start until it is back; then each job whose scheduled time passed runs once (unless its backup window is over), and queued runs continue. Restores are always possible from the command line with the recovery sheet.

How much space will backups need?

Roughly the size of the data after compression for the first backup, plus the daily changes for each kept day. The Reports page shows how much was uploaded per job.
