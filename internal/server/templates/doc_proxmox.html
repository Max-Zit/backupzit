Proxmox VE virtual machines

BackupZit backs up Proxmox VE virtual machines (QEMU) and containers (LXC) without installing anything inside the guests. The agent runs on the Proxmox host, takes a snapshot of each guest, reads its disks and stores them deduplicated on any storage target. VM disks are stored as disk images; containers on ZFS are backed up file by file (see Containers (LXC) on ZFS).

Setup

  1. Install the Linux agent — Debian / Ubuntu package from Agents on each Proxmox node (Proxmox VE 7, 8 and 9 are Debian based): 
    apt install ./backupzit-agent_*.deb
backupzit-agent enroll --code "BZ1-..."
systemctl enable --now backupzit-agent
  2. Within a minute the node appears on the Agents page with the badge Proxmox VE · N guests.
  3. In Backup jobs select that agent and choose Virtual machines (Proxmox VE, Hyper-V, VMware). Then choose All VMs (and containers) on the host (guests created later are included automatically) or tick individual ones.

To leave out single guests, e.g. the VM of the BackupZit console, choose All VMs (and containers) on the host except the ticked ones and tick them.

The agent uses the node's own tools (qm, pct, pvesm, LVM, ZFS, Ceph); no API token or password is stored in the console.

How a guest is backed up

  1. A temporary Proxmox snapshot is taken (backupzit_…, visible under Snapshots for a few seconds to minutes). The guest keeps running.
  2. If the QEMU guest agent runs in the VM (and is enabled in the VM options), Proxmox freezes the file systems for the snapshot — the backup is then application consistent. Without it, the backup is crash consistent, like a power loss. Install qemu-guest-agent in Linux VMs and the VirtIO guest tools in Windows VMs.
  3. Every disk is read from the snapshot in 1 MiB blocks. Empty blocks are not stored and blocks already in the repository are not uploaded again, so after the first backup only changed data is transferred. Running VMs with disks on LVM-thin, ZFS, Ceph RBD or qcow2 files also get changed block tracking (QEMU dirty bitmaps): from the second backup on, only the areas written since the previous backup are read, which takes seconds instead of minutes. After the VM was stopped, restarted or moved to another node, or a disk was resized, the next backup reads its disks completely once; the run page shows which disks were read as changed blocks only. This is the default block size; a job can use 256 or 512 KiB instead (see Jobs).
  4. The snapshot is removed. The guest configuration (CPU, memory, network, disks) is stored with the backup.

The run page lists each guest, its disks and how it was captured. Restore tests check random blocks of VM backups like disk images and, with the boot test on, start each VM from the backup isolated from the network to prove that it boots. Containers on ZFS are tested by restoring random files.

Disks marked Backup: no (backup=0) in Proxmox, passed-through physical disks and bind mounts are skipped and listed as warnings. Cloud-init drives are not stored; they are recreated from the configuration on restore. A stopped guest whose disks are read without a snapshot carries Proxmox VE's backup lock meanwhile, as with vzdump: it cannot be started (also not by HA) until its disks are read.

Snapshots and locks that stay behind. The agent records each backup snapshot before it takes it, and the backup lock of a stopped guest once it is set, and drops the record only when the guest's configuration shows it gone (a snapshot is removed with --force when the plain removal fails, up to three tries over about ten minutes). After an agent crash or a power loss the agent removes them itself, when it starts and every 15 minutes:

  • Guests a backup or restore of the agent works on, and guests for which Proxmox VE runs a task (a vzdump backup, a migration), are left alone.
  • A snapshot lock (lock: snapshot) left by an interrupted creation is removed with it, and Ceph RBD devices of the snapshot are unmapped first.
  • backupzit_… snapshots older than a day that the agent has no record of (for example from older versions) are removed too. Snapshots of your own are never touched.
  • A backup lock is removed only when the record shows that BackupZit set it. One it did not set is reported with the command that removes it (qm unlock, pct unlock), because vzdump uses the same lock.
  • What cannot be removed is listed on the dashboard under Attention with Remove now, and notified once.

Containers (LXC) on ZFS

On a ZFS storage, Proxmox keeps the volumes of a container (LXC) as datasets (subvol-<ID>-disk-N): file systems, not virtual disks like the zvols of a VM (QEMU). BackupZit therefore backs these containers up file by file:

  • The temporary snapshot is the same; the agent reads the files from the ZFS snapshot of each subvolume (.zfs/snapshot, also when it is hidden) while the container keeps running.
  • Owners (also the shifted IDs of unprivileged containers), permissions, times, extended attributes and ACLs, hard and symbolic links and device files are kept. Sockets are left out, as with vzdump; the services in the container create them again.
  • From the second backup on, only files whose size or modification time changed are read; the others are taken from the previous backup.
  • Such a container is restored onto a ZFS storage, as new subvolumes with the size (quota) of the original volumes.

Containers on LVM-thin or Ceph RBD have virtual disks and are backed up block by block, like VMs. The run page lists the VMs (QEMU) and the containers (LXC) in separate tables and shows how each container was stored. This needs agents 0.53 or newer.

Restoring a VM or container

Open a VM backup run (from the job page or Activity) and use Restore a VM or container:

  • Guest — one of the guests in that backup.
  • Restore on Proxmox node — any node with the BackupZit agent; also a node of another cluster.
  • As a new guest with the next free ID (default) or with ID … — the original keeps running. Because both exist, the network cards of the copy get new MAC addresses.
  • With its original ID — after the guest was deleted. If it still exists, tick stop and delete it to replace it with the backup. Since 0.59 the existing guest keeps running while the disks of the backup are written, and is stopped and deleted with its disks only when all of them are restored: if the restore fails before (storage full, data missing), the guest stays as it was and the new disks are removed. That needs room for both for a while; with Delete it before the disks are written the guest is deleted first, as before 0.59 (agents before 0.59 always do so).
  • Name and Storage for the disks — e.g. restore to a different storage than the original.
  • Start the guest after the restore.

Every restore gives VMs a new generation ID (vmgenid), so Windows domain controllers and other software detect the rollback safely. Disks are allocated with pvesm on the chosen storage; on directory storage they are restored as raw files. The storage list offers only storages that fit the chosen guest: VM disks for a VM, container volumes for a container, and ZFS for a container backed up file by file.

Instant recovery

Restoring a large VM takes as long as copying its disks. With Instantly, running from the backup in the restore form, the VM runs within seconds instead, while its disks are still in the backup:

  1. The agent serves the VM's disks read-only from the backup (a small NBD server running as the systemd unit backupzit-instant-<ID>) and creates a new VM with the next free ID whose disks are qcow2 overlays on the directory storage backupzit-instant (/var/lib/backupzit-instant, added automatically). Data is read from the backup on demand; everything the VM writes stays in the overlays. Firmware variables (EFI disk) and TPM state are small and copied.
  2. The VM starts. Check it — it gets new MAC addresses like any copy. The dashboard lists every VM that still runs from a backup.
  3. On the run page, either Finish: the disks are moved to the chosen storage while the VM keeps running (qm disk move), then the backup is no longer used. Or Discard: the VM is stopped and deleted together with its changes.

While a VM runs from a backup, retention never removes that backup. The VM is as fast as the backup storage allows: a repository on a local disk or a fast network share works best; reads over SFTP or S3 from far away make it slow until it is finished. Instant recovery is for VMs (not containers) and creates a new VM — restore in place with a normal restore. The EFI disk cannot be moved while the VM runs; it then stays on backupzit-instant (see the run message) and can be moved after shutting the VM down: qm disk move ID efidisk0 STORAGE --delete 1.

Replication

For guests that must be back within minutes, a VM job can keep replicas: under Advanced in the job form tick Keep replicas of the VMs and choose the node (any node with the BackupZit agent, also in another cluster) and the storage. After each backup, the agent on that node brings a stopped copy of every guest of the job up to date:

  • The first time, the replica is restored like a new guest (next free ID, name original-replica, new MAC addresses, never started with the node).
  • Later only the blocks that changed since the backup the replica holds are written — typically a few seconds per backup.
  • The job page lists the replicas, the backup each holds and its state. If a guest is lost, click Start replica: it runs with the data of the last backup, without a restore. Start it only when the original is really gone — both on the network at the same time can conflict. After a replica was started (also in the Proxmox VE interface, for example for a failover test), the next update compares every block instead of writing only the changes, so that the replica matches the backup again. The same happens after an update that was interrupted (an agent or node crash), and when the Proxmox VE task log cannot be read to tell whether the replica was started.
  • While a replica runs it is no longer updated (the run reports it). To replicate again, delete the replica guest in Proxmox; the next backup creates a new one. Replicas with Proxmox snapshots are not updated either.
  • Disks added to a guest later are not replicated (delete the replica to start over); disks that grew are grown on the replica too. Changes to the configuration (memory, CPUs) are taken when the replica is created.
  • Replication reads the backups like a restore: the replica node must reach the storage. Switching replication off leaves the replicas as they are.

Command line

backupzit-agent pve list
backupzit-agent pve backup  --repo ... [--vmid 100,200] [--exclude 300]
backupzit-agent pve show    --repo ... latest
backupzit-agent pve restore --repo ... --vmid 100 [--new-vmid -1|N] [--name copy] [--storage local-lvm] [--overwrite [--remove-first]] [--start] SNAPSHOT|latest
backupzit-agent pve instant --repo ... --vmid 100 [--new-vmid N] [--name X] SNAPSHOT|latest
backupzit-agent pve instant-finish --vmid 101 --storage local-lvm
backupzit-agent pve instant-discard --vmid 101

The repository options are the same as for all commands (see Command line reference). The command line works without the console, for example to restore a whole node after a disaster.

Clusters

Install the agent on every node. A job backs up the guests running on its agent's node; a guest listed in a job that has been migrated to another node is reported as a warning naming that node — back up each node with its own job, or use All VMs (and containers) on the host on every node so migrated guests are always covered.

Restoring single files

In the guest table of a VM backup run click Browse files. The console reads the disk directly from the backup — nothing is restored first — and shows its partitions and LVM logical volumes; NTFS (Windows), ext2/3/4 and XFS (Linux) can be browsed, also inside LVM. Tick files and folders and:

  • Download — one file as is, several files or folders as a ZIP archive, straight to your browser;
  • Restore on agent — copy them into a folder on any agent, e.g. back into the VM (if it runs the BackupZit agent) or onto a file server.

On the command line: backupzit-agent pve ls --vmid 100 latest /etc and backupzit-agent pve extract --vmid 100 --target /srv/restore latest /etc/nginx; --volume selects a partition or logical volume (pve ls without a path lists them). Browsing in the console needs the backup on network storage (SFTP, S3, SMB, Azure, hardened repository).

For containers (LXC) on ZFS, Browse files opens their files directly, like those of a file backup; the folders rootfs, mp0, mp1… are the container's volumes. Files restored on an agent keep their owners and permissions. They are restored into a folder, not to the original location: the paths in the backup are those inside the container, not on the host. A symbolic link is followed only inside its volume. Replicas of containers backed up file by file are not supported yet; restore them instead.

Backing up the host configuration

The guests are only half of a Proxmox node: storage definitions, network, users, firewall, certificates and the settings of every VM and container are in its configuration. Back it up with an ordinary files job on the node's agent: on Backup jobs choose the node's agent and Files and folders, then click Fill in the host configuration. It enters the paths /etc (with /etc/pve, the network and /etc/hosts), /var/lib/pve-cluster (the configuration database config.db) and /root; run the job e.g. daily. The database changes while the node runs, so the agent first makes a consistent copy of it, which the backup contains as /var/lib/backupzit/pve-config/config.db; no extra packages are needed.

To rebuild a failed node: install the same Proxmox VE version with the same host name and address, install the agent, restore /etc/network/interfaces and /etc/hosts into place, then stop the cluster service (systemctl stop pve-cluster), delete config.db-wal and config.db-shm in /var/lib/pve-cluster if they exist, restore the consistent copy from /var/lib/backupzit/pve-config into /var/lib/pve-cluster (config.db, and config.db-wal if the backup has one), start the service again and restore the guests. In a cluster, add a reinstalled node to the cluster again instead of restoring config.db.
