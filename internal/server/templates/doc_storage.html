Storage targets

A storage target is where agents write their backups. Each agent uses its own repository below the target's location.

Choosing a storage type

TypeGood forNotes
SFTPAny Linux server or NAS with SSHEncrypted transport; the server's host key is pinned.
S3 compatibleOff-site / cloud copies: AWS S3, Wasabi, Backblaze B2, MinIO, Ceph, Google Cloud StorageSupports immutability with Object Lock.

SMB shareWindows file servers, Synology/QNAP NASSMB 2/3; agents log in themselves, no drive mapping needed.
Hardened repositoryRansomware-proof on-premises storageA Linux server running backupzit-repo; backups cannot be deleted before their immutability period ends.

3-2-1 rule: keep 3 copies of your data, on 2 different media, 1 of them off-site — for example one job to a local NAS and another to S3 or a hardened repository in another building.

Testing the connection

When a storage target is added, the console tests it right away with the entered credentials: it writes a small file, reads it back and removes it. On immutable storage (S3 with Object Lock, hardened repository) it only signs in and lists, so nothing locked stays behind; for S3 it also checks that the bucket has Object Lock when immutability is requested. The target is saved either way, and the result is shown — a wrong password, host key, bucket or share shows now and not at the first backup. Test connection on the Storage page repeats the test. The console tests from its own network; agents write the backups, so a target only the agents can reach (a local or USB disk) is tested by the first backup.

SFTP

Location: sftp://user@host:22/path (use /~/path for a path relative to the user's home). Enter a password or a private key, and the server's host key fingerprint, which you get on the server with:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Create a dedicated user that can only write into the backup folder.

S3 compatible

Enter the endpoint (e.g. s3.eu-central-1.amazonaws.com, s3.wasabisys.com, 10.0.0.5:9000), bucket, optional folder and an access key with read/write access to that bucket. Tick Plain HTTP only for a local MinIO without a certificate.

Object storage answers slowly or with a temporary error now and then. The agent waits up to five minutes for an answer and retries timeouts, dropped connections, short reads, server errors and throttling (SlowDown) several times with growing pauses before a backup or restore gives up. Sending a piece again is safe, also with Object Lock. Every upload carries a checksum (Content-MD5) that the provider verifies, and after each upload the agent checks the size of the stored object: one that arrived short is uploaded again (agents 0.54.2 and newer).

On S3, Azure and hardened repositories the agent uploads up to four packs at once, and VM and disk restores read up to four blocks ahead, which helps most with distant or slow providers. A bandwidth limit still holds for the total. SFTP, SMB and local or USB disks are written and read one piece after another as before. The index of a large repository is read eight files at a time there too; while that takes, the agent log shows "loading the repository index" with its progress.

Immutable backups (Object Lock)

Create the bucket with Object Lock enabled and tick Immutable backups … for N days. Every file the agents write is locked in compliance mode for N days (+1 day margin): nobody — not an attacker with the keys, not the bucket owner — can delete or overwrite it before then. After each backup, data reused from older backups gets its lock extended, so every restore point is protected for the full period. The agent extends 16 objects at a time and remembers the known lock dates in its own folder, so a restart or an update does not check every object again. First the agent reads the backups the job keeps, several trees and block maps at a time (the run shows Reading the kept backups for the object locks: N read), then the run shows Extending object locks N / M; the agent log notes how long each step took.

Also give the bucket a default retention in compliance mode of at least N days (AWS: Object Lock → Default retention; MinIO: mc retention set --default COMPLIANCE 30d). The bucket then locks every new object itself, even one that a compromised computer writes without a lock. The connection test of the target warns when the default retention is missing or shorter than N days.

Deleting (by retention or by an attacker) only adds a "delete marker". Add a lifecycle rule that expires noncurrent versions after one day, so space is freed once locks end. See Ransomware protection.

Google Cloud Storage

Google Cloud Storage works as an S3 compatible target through its interoperability API:

  1. In the Google Cloud console open Cloud Storage → Settings → Interoperability and create an HMAC key for a service account that has the Storage Object Admin role on the bucket.
  2. Add an S3 target with endpoint storage.googleapis.com, the bucket name, the HMAC access key and secret, and region auto.

The S3 Object Lock option is not available on Google Cloud Storage; for immutability set a bucket retention policy (and lock it) in Google Cloud. Deleted backups then remain until the retention period ends.

Azure Blob Storage

  1. In the Azure portal create a storage account (StorageV2, any redundancy) and a container, e.g. backups.
  2. Add an Azure Blob Storage target with the account name, container and optional folder.
  3. Authenticate with an access key (Storage account → Access keys) or, more restricted, a SAS token for the container with read, write, delete and list permissions and a suitable expiry.

For ransomware protection enable version-level immutability with a time-based retention policy on the container; deleted or overwritten backups then remain recoverable for that time. The Advanced endpoint field is only needed for Azure Government/China, Azure Stack Hub or the Azurite emulator.

Rotating USB disks

Disks that are disconnected and taken off-site are the simplest protection against ransomware, fire and theft for small offices. BackupZit finds the disk by its volume label, whatever drive letter Windows assigns:

  1. Format two or more disks with NTFS (Linux: ext4) and name them BZBACKUP1, BZBACKUP2, … (Windows: right-click the drive → Properties → name).
  2. Add a storage target of type Rotating USB / removable disks with the label BZBACKUP*.
  3. Create a backup job to it — or, better, a backup copy job that copies a NAS or cloud job to the disk.
  4. Swap the disks regularly (e.g. weekly) and keep the disconnected one in a safe place.
  • Each disk holds a complete, independent backup with its own retention; all disks are encrypted with the target's recovery key.
  • The run shows which disk was used (Disk BZBACKUP2). A restore asks for exactly that disk and tells you which one is connected.
  • When no disk is connected, the run fails with a clear message and an alert — a reminder to plug the disk back in.
  • Connect only one of the disks at a time.

SMB share

Server, share, optional folder, user, password and (for domain accounts) the domain. Agents connect with these credentials themselves, so it works for services running as SYSTEM.

SMB accounts must be allowed to replace existing repository files by renaming a temporary file, as well as create, read and delete files. This keeps lock refreshes visible atomically. A failed replacement is reported as a write error; the previous file is kept. If a repository lock cannot be read, maintenance stops rather than assuming it is absent.

Hardened repository

Install the backupzit-repo package on a dedicated Linux server, then on that server:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

Enter the server address, the access key and the fingerprint in the console. The immutability period is configured on the repository server (/etc/backupzit-repo/repo.env) and cannot be changed from the console or agents. Details in Ransomware protection.

An access key can be bound to one repository path and limited. Give every computer its own storage target and key, so that a compromised computer reaches only its own backups:

backupzit-repo add-key pc-anna --path office/pc-anna --quota 500G --daily 100G --rate 600
backupzit-repo set-key pc-anna --quota 1T     # change a limit; none removes it
backupzit-repo keys                           # keys and their limits

With --path, nothing outside hardened://server/office/pc-anna exists for the key. --quota limits the data stored below the path (deleted files count while they are retained), --daily the new data per day (UTC), --rate the write requests per minute. A limit only refuses new uploads, and the backup then fails with a message; it never deletes or shortens anything, and reading and restoring are never limited. Without options a key has no limits, so a large first backup is not blocked by accident.

Encryption and the recovery key

With Encrypt backups (the default), everything in the repository — file contents, file names, folder structure, snapshot lists — is encrypted with AES-256-GCM before it leaves the agent. The storage provider sees only random data.

When you create an encrypted target the console shows a recovery key and offers a recovery sheet to download.

Print the recovery sheet or store it in a password manager, separately from the backups. If the console is lost, the recovery key plus the storage location and credentials are all you need to restore. Without the key, encrypted backups cannot be read by anyone — including BackupZit support.

You can show the key again later with Recovery key in the storage list; this is logged.

To read backups made earlier with a known key — for example after reinstalling the console without a console backup — enter it under Existing recovery key when adding the target with the same location and credentials, then use Find backups.

The storage list

The list shows each target's type, location, encryption (with access to the recovery key for administrators) and immutability: the Object Lock period for S3, or set on the repository server for hardened repositories. Credentials are never shown again after saving and are stored encrypted. Only administrators can add or remove targets and see recovery keys.

Finding backups on storage

Find backups in the storage list searches the target for repositories the console does not know: of agents removed earlier, or made by another console (e.g. before a reinstall). It lists each folder with the computer, the jobs (named after what they back up), the number of backups and their dates; folders it cannot read are marked, e.g. when they were encrypted with another recovery key. Add the selected backups records them as the history of a removed agent named after the computer: they appear under Removed agents with kept backups on the Agents page and in Activity (trigger imported), and can be restored to any agent, connected to the agent of that computer or deleted (see Agents). Nothing on the storage is changed. Repositories the console already has are not listed; adding twice adds nothing.

Network storage is searched by the console from its own network, so it must reach the storage. A local or USB disk is searched by the agent of the computer it is connected to: choose that agent on the search page (agent 0.44.0 or newer); for rotating USB disks the disk connected at the moment is searched. Backups of VMware connections and Microsoft 365 tenants can be restored, but not connected to an agent.

Storage usage and forecast

After every backup (and its retention) the agent reports how much space its repository takes, and — for local and USB disks, SFTP servers (OpenSSH's statvfs extension) and SMB shares — the size and free space of the storage. Under Storage → Storage usage each target shows:

  • the space used by all repositories on it (one per agent; rotating USB disks count each disk);
  • for storage with a known size, how full it is (yellow from 75 %, red from 90 %), with the capacity as a dashed red line in the chart;
  • a chart of the last 90 days and, after a week of backups, the growth per day (a linear trend of the last 30 days), drawn 30 days ahead as a dashed line, and when the storage will be full — or, without a known size, the expected use in 90 days.

The dashboard's Needs attention warns when a storage target is 90 % full or will be full within 30 days. S3 and Azure have no fixed size; there only the used space and its growth are shown. The used space is the stored (compressed, encrypted, deduplicated) data; files the storage keeps for other reasons (object versions, other programs) are not counted.

Removing a target

A storage target that jobs still use cannot be removed. Removing a target from the console does not delete any data on the storage, but the console forgets its credentials and recovery key, so its backups can no longer be restored from the console — download the recovery sheet first. With four-eyes approval on, a second user has to approve it first.
