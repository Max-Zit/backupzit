Storage targets

A storage target is where agents write their backups. Each agent uses its own repository below the target's location.

Choosing a storage type

3-2-1 rule: keep 3 copies of your data, on 2 different media, 1 of them off-site — for example one job to a local NAS and another to S3 or a hardened repository in another building.

SFTP

Location: sftp://user@host:22/path (use /~/path for a path relative to the user's home). Enter a password or a private key, and the server's host key fingerprint, which you get on the server with:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Create a dedicated user that can only write into the backup folder.

S3 compatible

Enter the endpoint (e.g. s3.eu-central-1.amazonaws.com, s3.wasabisys.com, 10.0.0.5:9000), bucket, optional folder and an access key with read/write access to that bucket. Tick Plain HTTP only for a local MinIO without a certificate.

Immutable backups (Object Lock)

Create the bucket with Object Lock enabled and tick Immutable backups … for N days. Every file the agents write is locked in compliance mode for N days (+1 day margin): nobody — not an attacker with the keys, not the bucket owner — can delete or overwrite it before then. After each backup, data reused from older backups gets its lock extended, so every restore point is protected for the full period.

Deleting (by retention or by an attacker) only adds a "delete marker". Add a lifecycle rule that expires noncurrent versions after one day, so space is freed once locks end. See Ransomware protection.

Google Cloud Storage

Google Cloud Storage works as an S3 compatible target through its interoperability API:

  1. In the Google Cloud console open Cloud Storage → Settings → Interoperability and create an HMAC key for a service account that has the Storage Object Admin role on the bucket.
  2. Add an S3 target with endpoint storage.googleapis.com, the bucket name, the HMAC access key and secret, and region auto.

The S3 Object Lock option is not available on Google Cloud Storage; for immutability set a bucket retention policy (and lock it) in Google Cloud. Deleted backups then remain until the retention period ends.

Azure Blob Storage

  1. In the Azure portal create a storage account (StorageV2, any redundancy) and a container, e.g. backups.
  2. Add an Azure Blob Storage target with the account name, container and optional folder.
  3. Authenticate with an access key (Storage account → Access keys) or, more restricted, a SAS token for the container with read, write, delete and list permissions and a suitable expiry.

For ransomware protection enable version-level immutability with a time-based retention policy on the container; deleted or overwritten backups then remain recoverable for that time. The Advanced endpoint field is only needed for Azure Government/China, Azure Stack Hub or the Azurite emulator.

Rotating USB disks

Disks that are disconnected and taken off-site are the simplest protection against ransomware, fire and theft for small offices. BackupZit finds the disk by its volume label, whatever drive letter Windows assigns:

  1. Format two or more disks with NTFS (Linux: ext4) and name them BZBACKUP1, BZBACKUP2, … (Windows: right-click the drive → Properties → name).
  2. Add a storage target of type Rotating USB / removable disks with the label BZBACKUP*.
  3. Create a backup job to it — or, better, a backup copy job that copies a NAS or cloud job to the disk.
  4. Swap the disks regularly (e.g. weekly) and keep the disconnected one in a safe place.
  • Each disk holds a complete, independent backup with its own retention; all disks are encrypted with the target's recovery key.
  • The run shows which disk was used (Disk BZBACKUP2). A restore asks for exactly that disk and tells you which one is connected.
  • When no disk is connected, the run fails with a clear message and an alert — a reminder to plug the disk back in.
  • Connect only one of the disks at a time.

SMB share

Server, share, optional folder, user, password and (for domain accounts) the domain. Agents connect with these credentials themselves, so it works for services running as SYSTEM.

Hardened repository

Install the backupzit-repo package on a dedicated Linux server, then on that server:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

Enter the server address, the access key and the fingerprint in the console. The immutability period is configured on the repository server (/etc/backupzit-repo/repo.env) and cannot be changed from the console or agents. Details in Ransomware protection.

Encryption and the recovery key

With Encrypt backups (the default), everything in the repository — file contents, file names, folder structure, snapshot lists — is encrypted with AES-256-GCM before it leaves the agent. The storage provider sees only random data.

When you create an encrypted target the console shows a recovery key and offers a recovery sheet to download.

Print the recovery sheet or store it in a password manager, separately from the backups. If the console is lost, the recovery key plus the storage location and credentials are all you need to restore. Without the key, encrypted backups cannot be read by anyone — including BackupZit support.

You can show the key again later with Recovery key in the storage list; this is logged.

The storage list

The list shows each target's type, location, encryption (with access to the recovery key for administrators) and immutability: the Object Lock period for S3, or set on the repository server for hardened repositories. Credentials are never shown again after saving and are stored encrypted. Only administrators can add or remove targets and see recovery keys.

Storage usage and forecast

After every backup (and its retention) the agent reports how much space its repository takes, and — for local and USB disks, SFTP servers (OpenSSH's statvfs extension) and SMB shares — the size and free space of the storage. Under Storage → Storage usage each target shows:

  • the space used by all repositories on it (one per agent; rotating USB disks count each disk);
  • for storage with a known size, how full it is (yellow from 75 %, red from 90 %), with the capacity as a dashed red line in the chart;
  • a chart of the last 90 days and, after a week of backups, the growth per day (a linear trend of the last 30 days), drawn 30 days ahead as a dashed line, and when the storage will be full — or, without a known size, the expected use in 90 days.

The dashboard's Needs attention warns when a storage target is 90 % full or will be full within 30 days. S3 and Azure have no fixed size; there only the used space and its growth are shown. The used space is the stored (compressed, encrypted, deduplicated) data; files the storage keeps for other reasons (object versions, other programs) are not counted.

Removing a target

Removing a storage target from the console does not delete any data on the storage. With four-eyes approval on, a second user has to approve it first.
