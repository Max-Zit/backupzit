Storage targets

A storage target is where agents write their backups. Each agent uses its own repository below the target's location.

Choosing a storage type

TypeGood forNotes
SFTPAny Linux server or NAS with SSHEncrypted transport; the server's host key is pinned.
S3 compatibleOff-site / cloud copies: AWS S3, Wasabi, Backblaze B2, MinIO, CephSupports immutability with Object Lock.
SMB shareWindows file servers, Synology/QNAP NASSMB 2/3; agents log in themselves, no drive mapping needed.
Hardened repositoryRansomware-proof on-premises storageA Linux server running backupzit-repo; backups cannot be deleted before their immutability period ends.
Local / mounted pathA USB disk, second disk, or an NFS/iSCSI volume mounted on the agentPath as seen by the agent, e.g. E:\Backups or /mnt/backup.

3-2-1 rule: keep 3 copies of your data, on 2 different media, 1 of them off-site — for example one job to a local NAS and another to S3 or a hardened repository in another building.

SFTP

Location: sftp://user@host:22/path (use /~/path for a path relative to the user's home). Enter a password or a private key, and the server's host key fingerprint, which you get on the server with:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Create a dedicated user that can only write into the backup folder.

S3 compatible

Enter the endpoint (e.g. s3.eu-central-1.amazonaws.com, s3.wasabisys.com, 10.0.0.5:9000), bucket, optional folder and an access key with read/write access to that bucket. Tick Plain HTTP only for a local MinIO without a certificate.

Immutable backups (Object Lock)

Create the bucket with Object Lock enabled and tick Immutable backups … for N days. Every file the agents write is locked in compliance mode for N days (+1 day margin): nobody — not an attacker with the keys, not the bucket owner — can delete or overwrite it before then. After each backup, data reused from older backups gets its lock extended, so every restore point is protected for the full period.

Deleting (by retention or by an attacker) only adds a "delete marker". Add a lifecycle rule that expires noncurrent versions after one day, so space is freed once locks end. See Ransomware protection.

SMB share

Server, share, optional folder, user, password and (for domain accounts) the domain. Agents connect with these credentials themselves, so it works for services running as SYSTEM.

Hardened repository

Install the backupzit-repo package on a dedicated Linux server, then on that server:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

Enter the server address, the access key and the fingerprint in the console. The immutability period is configured on the repository server (/etc/backupzit-repo/repo.env) and cannot be changed from the console or agents. Details in Ransomware protection.

Encryption and the recovery key

With Encrypt backups (the default), everything in the repository — file contents, file names, folder structure, snapshot lists — is encrypted with AES-256-GCM before it leaves the agent. The storage provider sees only random data.

When you create an encrypted target the console shows a recovery key and offers a recovery sheet to download.

Print the recovery sheet or store it in a password manager, separately from the backups. If the console is lost, the recovery key plus the storage location and credentials are all you need to restore. Without the key, encrypted backups cannot be read by anyone — including BackupZit support.

You can show the key again later with Recovery key in the storage list; this is logged.

Removing a target

Removing a storage target from the console does not delete any data on the storage.
