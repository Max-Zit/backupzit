Backup jobs & schedules

A job says what to back up on which agent, where to store it, when to run and how many backups to keep.

Creating a job

  1. Go to Backup jobs and fill in New backup job.
  2. Choose the agent and the storage target.
  3. Choose what to back up:
    • Files and folders — one path per line as seen on the agent, e.g. C:\Users, D:\Data, /home, /etc.
    • Disk image — a whole disk or selected partitions, restorable to an empty disk or new hardware. See Disk images.
    • Linux system — all file systems and the disk layout of a Linux machine, restorable onto an empty disk or as a Proxmox VM. See Linux system backup.
    • Virtual machines (Proxmox VE, Hyper-V, VMware) — VMs (and Proxmox containers) of a hypervisor host, backed up without agents in the guests: by the agent on the Proxmox or Hyper-V host, or for VMware ESXi by the host's proxy agent (choose the ESXi host in the agent list). See Proxmox VE, Hyper-V and VMware ESXi.
    • Databases — SQL Server, PostgreSQL or MySQL/MariaDB on the agent's machine, with log backups for restores to any point in time. See Databases.
    • NAS / file share — an SMB or NFS share read by the agent; see below.
  4. Optionally add excludes, one pattern per line: *.tmp, node_modules, Thumbs.db, *.iso.
  5. Set Keep backups and the Schedule, then Create job.

NAS and file shares (SMB, NFS)

A NAS / file share job backs up a network share without installing anything on the NAS (Synology, QNAP, TrueNAS, a Windows file server …). Choose any agent that reaches the share — it reads the share and writes the backup — and enter:

  • Share: smb://nas01/data (optionally with a folder: smb://nas01/data/Office) or nfs://nas01/volume1/data (the export path);
  • for SMB the account (user, optional domain, password — stored encrypted); empty means guest access. NFS uses the agent machine's access to the export (allow its address on the NAS);
  • the folders in the share to back up, one per line (empty: the whole share), and exclusions such as #recycle, @eaDir or .snapshot.

For every run the agent connects the share — Windows agents through its UNC path (\\nas01\data, SMB only), Linux agents by mounting it read-only below /mnt/backupzit-nas (needs cifs-utils for SMB, nfs-common or nfs-utils for NFS; Proxmox VE has both) — and disconnects it afterwards. The backups are ordinary file backups: deduplicated and incremental, with retention, copy jobs, restore tests, browsing and file restore. Restore to the original location connects the share again, writable, and writes the files back onto it; or restore into a folder on any agent, or download.

Open and locked files (VSS)

On Windows the agent uses the Volume Shadow Copy Service: it takes a consistent, point-in-time snapshot of the volume and backs up from that, so open files (Outlook PST, databases, documents being edited) are backed up consistently. Applications that support VSS (for example SQL Server) flush their data to disk before the snapshot is taken.

Schedules

OptionExample
At specific timesEvery working day at 22:00; or at 12:00 and 18:00 every day. Up to three times a day, on the days you tick.
RepeatedlyEvery 2 hours between 08:00 and 18:00, Monday–Friday. Intervals from 15 minutes to 12 hours.
Once a monthOn the 1st at 23:00.
Manually onlyRuns only when you click Run backup now.

Times are in the console server's time zone. If an agent is offline at the scheduled time, the backup waits in the queue and starts as soon as the agent is back. See all planned runs in the Calendar.

Retention: how many backups to keep

A snapshot is kept if any rule selects it:

  • Most recent — the newest N backups.
  • Daily — the newest backup of each of the last N days that have backups.
  • Weekly — the newest backup of each of the last N weeks.
  • Monthly — the newest backup of each of the last N months.

Example: 3 recent, 7 daily, 4 weekly, 6 monthly keeps about half a year of history with ~20 restore points. After each successful run, snapshots no longer selected are removed (shown as expired in Activity) and data that is no longer used by any snapshot is deleted from the storage. All zeros keeps everything.

Thanks to deduplication, long retention is cheap: unchanged data is stored only once no matter how many snapshots reference it.

Backup copy jobs (3-2-1)

A backup copy job copies the backups of another job to a second storage target — for example nightly backups to the office NAS, copied to S3 or a hardened repository off-site. Choose Backup copy in the job form, select the job to copy and the destination storage.

  • The agent of the source job does the copying; the protected machine is not read again.
  • Only data that is not yet at the destination is transferred, re-encrypted with the destination's key.
  • Schedule After each backup of the source job (default) keeps the copy current; any normal schedule works too, e.g. once a night for a slow internet line.
  • The copy has its own retention, e.g. 7 daily on the NAS and 12 monthly in the cloud.
  • Copied file backups and VM backups (Proxmox VE, Hyper-V, VMware) are restored from the copy run's page or the restore wizard, like the originals — whole VMs, single files from VM disks, and Proxmox instant recovery. VM backups copied by an agent older than 0.29 cannot be restored this way; the next copy run with a newer agent makes its newest copy restorable. Copies of disk images are restored with the command line agent.

Changing a job

Open the job and expand Edit job. You can change the name, the folders and exclusions (file jobs), the VMs (VM jobs), the schedule, the retention, the speed limit and the commands. The agent, the storage target and the disk of an image job stay as they are, so the job's backups remain one chain; to move a job, create a new one — with a copy job if older backups should come along. Changes apply from the next run and are recorded in the audit log. With four-eyes approval on, a shorter retention waits for a second user's approval; the other changes are saved at once.

Replicas (Proxmox VE)

Proxmox VM jobs can keep stopped, up-to-date copies of their guests on a node of your choice, started with one click if a guest is lost — see Proxmox VE → Replication.

Speed limit

Under Advanced in the job form, Limit the upload speed caps how fast the agent sends data to the storage, in MB/s — for example 10 MB/s from 08:00 to 18:00, so backups during working hours leave the office line usable; outside the window the job runs at full speed. The hours are the agent's local time, and a window may span midnight (22:00 to 06:00). The limit applies to backups and to copy jobs (the upload to the second storage), not to restores: a restore always runs at full speed.

Commands before and after the backup

Administrators can let a job run a command on the agent before and after each backup — for example a database dump, stopping a service for a consistent copy, or a notification:

pg_dump -U postgres app > /var/backups/app.sql          # Linux, before
sqlcmd -S . -Q "BACKUP DATABASE app TO DISK='D:\dump\app.bak'"   # Windows, before
  • Commands run as the agent's service account (root on Linux, SYSTEM on Windows) with sh or cmd; several lines are allowed. Only Administrators can see and change them — a backup operator could otherwise run anything on every machine.
  • If the command before fails (exit code not 0) or runs longer than the time limit (default 30 minutes), the backup does not run and the run fails with the command's output.
  • The command after runs also when the backup failed, so it can restart what the first command stopped. A failing command after the backup turns the run into a warning.
  • Both get BACKUPZIT_STAGE (pre or post), BACKUPZIT_JOB, BACKUPZIT_JOB_ID, BACKUPZIT_RUN_ID and, after the backup, BACKUPZIT_STATUS (success, warning or failed).
  • For VM jobs the commands run on the hypervisor host (or the VMware proxy), not inside the VMs. Copy jobs have no commands.

Running, disabling, deleting

  • Run backup now (Copy now for copy jobs) queues the job immediately.
  • Test restore restores a random sample of the newest backup and verifies it (see Restoring).
  • Disable pauses the schedule without losing the job.
  • Delete removes the job; existing backups stay on the storage and remain restorable from Activity.

Retention paused

If a backup of the job looked like ransomware or mass deletion, the job page shows Retention is paused: no backups are removed until someone checks the machine and clicks Reviewed — resume retention (with four-eyes approval on, a second user has to approve it). See Ransomware protection.

What a backup run reports

Open a run in Activity: number of files, new/changed files, data read, new data uploaded (after deduplication and compression), duration, and any files that could not be read. A run with unreadable files ends with status warning — the rest of the data is backed up.
