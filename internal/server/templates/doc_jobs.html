Backup jobs & schedules

A job says what to back up on which agent, where to store it, when to run and how many backups to keep.

Creating a job

  1. Go to Backup jobs and fill in New backup job.
  2. Choose the agent and the storage target.
  3. Choose what to back up:
    • Files and folders — one path per line as seen on the agent, e.g. C:\Users, D:\Data, /home, /etc.
    • Disk image — a whole disk or selected partitions, restorable to an empty disk or new hardware. See Disk images.
    • Linux system — all file systems and the disk layout of a Linux machine, restorable onto an empty disk or as a Proxmox VM. See Linux system backup.
    • Virtual machines (Proxmox VE, Hyper-V, VMware) — VMs (and Proxmox containers) of a hypervisor host, backed up without agents in the guests: by the agent on the Proxmox or Hyper-V host, or for VMware ESXi by the host's proxy agent (choose the ESXi host in the agent list). See Proxmox VE, Hyper-V and VMware ESXi.
    • Databases — SQL Server, PostgreSQL or MySQL/MariaDB on the agent's machine, with log backups for restores to any point in time. See Databases.
    • NAS / file share — an SMB or NFS share read by the agent; see below.
    • Microsoft 365 — Exchange Online mailboxes, calendars, contacts, OneDrive and SharePoint sites, read through Microsoft Graph by any agent; see Microsoft 365.
  4. Optionally add excludes, one per line: a name pattern, which applies in every folder (*.tmp, node_modules, Thumbs.db, *.iso), or a full path, which applies to that one file or folder (C:\Data\Temp, /srv/www/cache, also with wildcards: D:\VMs\*.iso). Full paths ignore upper and lower case on Windows.
  5. Set Keep backups and the Schedule, then Create job.

Folders of every user

Below the paths, For every user of the computer adds Desktop, Documents, Downloads, Pictures or the Whole user profile. They are written as {users}/Documents, and the agent finds the folders anew at each backup: C:\Users\<name>\Documents on Windows (also a folder that OneDrive moved, …\OneDrive\Documents), /home/<name>/Documents and /root/Documents on Linux, /Users/<name>/Documents on macOS. Users added later are backed up without changing the job; system profiles (Default, Public) are left out. Any folder can follow {users}, e.g. {users}/AppData/Roaming/Thunderbird.

Paths can also hold the wildcards * (any characters within one folder name) and ? (one character): D:\Projects\*\Documentation, /srv/sites/*/uploads. Upper and lower case count as written. A {users} or wildcard path that finds nothing on a computer is no error: the run reports Nothing matched …, and fails only when nothing at all is left to back up. This needs agent 0.45.0 or newer. The whole profile includes caches; exclude them with full paths such as C:\Users\*\AppData\Local\Temp.

One job for several agents

To back up the same folders on many computers, choose under Agent one of Several agents: All agents, All Windows agents, All Linux agents, All macOS agents or Choose agents… (then tick them). Such a job backs up files and folders; together with {users} paths, e.g. {users}/Documents, it covers the documents of everyone in the company with one job. Agents that enroll later join the job automatically within a minute (for Choose agents… only the ticked ones).

Each agent backs up to its own repository on the storage target, with its own history, restores and retention, as with a job for one agent. The jobs page lists the job under Jobs for several agents; its page shows every agent with its last result, and Run backup now on all agents starts them all. The job of one agent is marked several agents: open it for its history and restores, or disable it to pause that one computer. Folders, schedule and retention are changed on the job for several agents and apply to all its agents; there, agents can also be left out. Leaving agents out or deleting the job keeps their backups on the storage. With four-eyes approval, leaving agents out, a shorter retention, disabling and deleting wait for a second user.

An agent that cannot run the job yet is listed with the reason, e.g. an agent older than 0.45.0 for {users} and wildcards; it joins once it is updated. Many agents with the same schedule start at the same time; a backup window or a different time per job spreads the load on the storage.

NAS and file shares (SMB, NFS)

A NAS / file share job backs up a network share without installing anything on the NAS (Synology, QNAP, TrueNAS, a Windows file server …). Choose any agent that reaches the share — it reads the share and writes the backup — and enter:

  • Share: smb://nas01/data (optionally with a folder: smb://nas01/data/Office) or nfs://nas01/volume1/data (the export path);
  • for SMB the account (user, optional domain, password — stored encrypted); empty means guest access. NFS uses the agent machine's access to the export (allow its address on the NAS);
  • the folders in the share to back up, one per line (empty: the whole share), and exclusions such as #recycle, @eaDir or .snapshot.

For every run the agent connects the share — Windows agents through its UNC path (\\nas01\data, SMB only), Linux agents by mounting it read-only below /mnt/backupzit-nas (needs cifs-utils for SMB, nfs-common or nfs-utils for NFS; Proxmox VE has both) — and disconnects it afterwards. The backups are ordinary file backups: deduplicated and incremental, with retention, copy jobs, restore tests, browsing and file restore. Restore to the original location connects the share again, writable, and writes the files back onto it; or restore into a folder on any agent, or download.

Open and locked files (VSS)

On Windows the agent uses the Volume Shadow Copy Service: it takes a consistent, point-in-time snapshot of the volume and backs up from that, so open files (Outlook PST, databases, documents being edited) are backed up consistently. Applications that support VSS (for example SQL Server) flush their data to disk before the snapshot is taken.

Schedules

OptionExample
At specific timesEvery working day at 22:00; or at 12:00 and 18:00 every day. Up to three times a day, on the days you tick.
RepeatedlyEvery 2 hours between 08:00 and 18:00, Monday–Friday. Intervals from 15 minutes to 12 hours.
Once a monthOn the 1st at 23:00.
Manually onlyRuns only when you click Run backup now.
After another jobFirst the database, then the file server: the job starts as soon as the chosen job has finished successfully — or after any result, with also when that job failed. Chains can be longer (A → B → C); a job cannot run after itself or in a circle.

Times are in the console server's time zone (on the appliance: Settings → Network → Time zone or item 9 of the setup menu; it starts in UTC). If an agent is offline at the scheduled time, the backup waits in the queue and starts as soon as the agent is back. See all planned runs in the Calendar. The current date and time of the console are shown at the bottom left, below the time zone.

Backup window

With Backup window: start only between in the job form (e.g. 22 to 6), scheduled and chained runs of the job start only inside the window. A run still waiting when the window closes — for example because the night's jobs took longer — is cancelled, so it does not load the network and the machines during working hours. A run that has already started continues; to stop long runs use the time limit of a run (below). Starting the job by hand ignores the window. Daily and monthly schedule times must lie inside the window.

Recovery point objective (RPO)

The RPO says how old the newest good backup of a job may get, in hours — for example 26 for a daily backup (a day plus some slack). Set it in the job form under Recovery point objective (RPO), hours. The dashboard shows how many jobs are within RPO and lists every job that missed it, and the job page shows its state. A notification (email and chat, like a failure) goes out once when a job misses its RPO, and again only after it met it in between. Unlike the status of the last run, the RPO also catches a schedule removed by mistake, an agent offline for days and a backup that keeps failing.

Retention: how many backups to keep

A snapshot is kept if any rule selects it:

  • Most recent — the newest N backups.
  • Daily — the newest backup of each of the last N days that have backups.
  • Weekly — the newest backup of each of the last N weeks.
  • Monthly — the newest backup of each of the last N months.

Example: 3 recent, 7 daily, 4 weekly, 6 monthly keeps about half a year of history with ~20 restore points. After each successful run, snapshots no longer selected are removed (shown as expired in Activity) and data that is no longer used by any snapshot is deleted from the storage. All zeros keeps everything.

Thanks to deduplication, long retention is cheap: unchanged data is stored only once no matter how many snapshots reference it.

Backup copy jobs (3-2-1)

A backup copy job copies the backups of another job to a second storage target — for example nightly backups to the office NAS, copied to S3 or a hardened repository off-site. Choose Backup copy in the job form, select the job to copy and the destination storage.

  • The agent of the source job does the copying; the protected machine is not read again.
  • Only data that is not yet at the destination is transferred, re-encrypted with the destination's key.
  • Schedule After each backup of the source job (default) keeps the copy current; any normal schedule works too, e.g. once a night for a slow internet line.
  • The copy has its own retention, e.g. 7 daily on the NAS and 12 monthly in the cloud.
  • Copied file backups and VM backups (Proxmox VE, Hyper-V, VMware) are restored from the copy run's page or the restore wizard, like the originals — whole VMs, single files from VM disks, and Proxmox instant recovery. VM backups copied by an agent older than 0.29 cannot be restored this way; the next copy run with a newer agent makes its newest copy restorable. Copies of disk images are restored with the command line agent.

Changing a job

Open the job and click Edit; the form opens on a page of its own that does not reload while a backup runs. You can change the name, the folders and exclusions (file jobs), the VMs (VM jobs), the schedule, the retention, the speed limit, the compression level and the commands. The agent, the storage target and the disk of an image job stay as they are, so the job's backups remain one chain; to move a job, create a new one — with a copy job if older backups should come along. Changes apply from the next run and are recorded in the audit log. With four-eyes approval on, a shorter retention waits for a second user's approval; the other changes are saved at once.

Replicas (Proxmox VE)

Proxmox VM jobs can keep stopped, up-to-date copies of their guests on a node of your choice, started with one click if a guest is lost — see Proxmox VE → Replication.

Speed limit

Under Advanced in the job form, Limit the upload speed caps how fast the agent sends data to the storage, in MB/s — for example 10 MB/s from 08:00 to 18:00, so backups during working hours leave the office line usable; outside the window the job runs at full speed. The hours are the agent's local time, and a window may span midnight (22:00 to 06:00). The limit applies to backups and to copy jobs (the upload to the second storage), not to restores: a restore always runs at full speed.

Compression and deduplication

Every backup is deduplicated: data that is already in the repository — from earlier backups of the same job, or from other jobs on the same storage target — is not stored again. New data is then compressed with zstd; pieces that do not get smaller (video, archives, encrypted files) are stored as they are. Encryption comes after compression.

The compression level is a job setting (Edit → Advanced):

LevelWhen to use it
Standard (recommended)Good compression at high speed; fits almost every job.
FastUses less CPU on busy or weak machines; backups are slightly larger.
MaximumUsually 5–15 % smaller than standard, but several times slower to compress. For slow uplinks and paid cloud storage, when the machine has CPU to spare.
OffFor data that is already compressed: saves CPU without making backups larger.

The level applies to new data from the next run; existing backups stay as they are, and restoring never depends on it. The run page shows the result: the compression ratio of the new data (e.g. 2.4×) and how much of the data read was already stored (deduplication).

Commands before and after the backup

Administrators can let a job run a command on the agent before and after each backup — for example a database dump, stopping a service for a consistent copy, or a notification:

pg_dump -U postgres app > /var/backups/app.sql          # Linux, before
sqlcmd -S . -Q "BACKUP DATABASE app TO DISK='D:\dump\app.bak'"   # Windows, before
  • Commands run as the agent's service account (root on Linux, SYSTEM on Windows) with sh or cmd; several lines are allowed. Only Administrators can see and change them — a backup operator could otherwise run anything on every machine.
  • If the command before fails (exit code not 0) or runs longer than the time limit (default 30 minutes), the backup does not run and the run fails with the command's output.
  • The command after runs also when the backup failed, so it can restart what the first command stopped. A failing command after the backup turns the run into a warning.
  • Both get BACKUPZIT_STAGE (pre or post), BACKUPZIT_JOB, BACKUPZIT_JOB_ID, BACKUPZIT_RUN_ID and, after the backup, BACKUPZIT_STATUS (success, warning or failed).
  • The run page shows the result and the output of each command, also when it succeeded.
  • For VM jobs the commands run on the hypervisor host (or the VMware proxy), not inside the VMs. Copy jobs have no commands.

Running, disabling, deleting

  • Run backup now (Copy now for copy jobs) queues the job immediately.
  • Test restore restores a random sample of the newest backup and verifies it (see Restoring).
  • Disable pauses the schedule without losing the job (with four-eyes approval on, a second user has to approve it).
  • Delete removes the job; existing backups stay on the storage and remain restorable from Activity.

Stopping a run

A queued or running backup, copy or restore can be stopped with Cancel or Stop run on the run page, or Stop run #… on the job page. A waiting run is cancelled at once; a running one is stopped by the agent within seconds — the command before the backup is ended too, the command after the backup still runs. The run gets the status cancelled (message "Cancelled by" and the user's name): it does not count as a failure in reports, sends no failure email and is recorded in the audit log. A backup stopped halfway is not used for restores. Agent updates cannot be stopped.

To stop everything at once, use Cancel all queued and running at the top of Activity and confirm. Only the runs listed as queued or running at that moment are cancelled (running ones stop within seconds); runs scheduled later today or on other days, and chained jobs, start as planned.

Time limit of a run (hours) under Advanced in the job form stops a backup or copy of the job that runs longer and marks it as failed; this one does send the failure notification. Empty or 0 means no limit. If the agent does not confirm a stop within 10 minutes, the console marks the run as failed itself.

Retention paused

If a backup of the job looked like ransomware or mass deletion, the job page shows Retention is paused: no backups are removed until someone checks the machine and clicks Reviewed — resume retention (with four-eyes approval on, a second user has to approve it). See Ransomware protection.

What a backup run reports

Open a run in Activity: number of files, new/changed files, data read, new data uploaded (after deduplication and compression, with the compression ratio and the share already stored — see Compression), duration, and any files that could not be read. A run with unreadable files ends with status warning — the rest of the data is backed up.
