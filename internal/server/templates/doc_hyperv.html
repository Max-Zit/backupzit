Hyper-V virtual machines

BackupZit backs up Hyper-V virtual machines from the agent on the Hyper-V host; nothing is installed inside the VMs. Windows and Linux guests are captured while they keep running. You can restore them as a new VM or in place of the original.

Setup

  1. Install the Windows agent MSI from Agents on the Hyper-V host and enroll it. Supported hosts: Windows Server 2016 or newer with the Hyper-V role, or Windows 10/11 with Hyper-V. In a cluster, install the agent on every host.
  2. Within a minute the host appears on the Agents page with the badge Hyper-V · N VMs.
  3. In Backup jobs select that agent and choose Virtual machines (Proxmox VE, Hyper-V, VMware). Then pick one:
    • all VMs of the host, which also covers VMs created later;
    • individual VMs, by ticking them.

The agent works through Hyper-V's own interfaces: the Hyper-V PowerShell module and the Windows Virtual Disk API. The console stores no Hyper-V credentials.

How a VM is backed up

  1. A temporary recovery checkpoint (backupzit_…) is taken. This is the checkpoint type Hyper-V provides for backup applications. Hyper-V asks the guest to prepare for it:
    • Windows guests flush their applications through VSS.
    • Linux guests freeze their file systems, if the Hyper-V daemons are installed (hyperv-daemons / hv-vss-daemon).
    If the guest can't do either, the checkpoint is taken crash-consistent. The run page shows which kind was used.
  2. The recovery checkpoint switches on Resilient Change Tracking (RCT) for the VM's disks; you will see .rct and .mrt files next to them. The first backup reads the whole disks. After that, RCT reports which blocks changed since the previous backup, and only those are read.
  3. The disks are read as of the checkpoint, through the Virtual Disk API, in 1 MiB blocks. This covers VHDX and VHD files, including chains of earlier checkpoints. Empty blocks are not stored, and blocks already in the repository are not uploaded again.
  4. The checkpoint is removed, and Hyper-V merges it in the background.
  5. The VM's configuration is stored with the backup: generation, CPU, memory, network adapters (switch, VLAN, MAC address), disk controllers, secure boot and TPM.

VMs that are turned off are read directly, without a checkpoint. On hosts older than Windows Server 2016 (no recovery checkpoints) a production checkpoint is used and every backup reads the whole disks.

Example from the test lab: a Linux VM with a 3 GB disk. The first backup read 3 GB. The next one, after 64 MB of new data, read 96 MB.

On Windows 10/11, Hyper-V takes an automatic checkpoint when a VM starts, unless that option is turned off in the VM's settings. BackupZit handles such checkpoints, but for servers you will want to turn automatic checkpoints off (VM settings → Checkpoints).

Restoring a VM

Open the VM backup run (from the job page or Activity) and use Restore a Hyper-V VM.

As a new VM next to the original

Creates a second VM with new MAC addresses, so it can run on the same network as the original. By default it is named after the original plus "restored" and the date. Automatic checkpoints are turned off on it (Windows turns them on for new VMs), so starting it does not leave checkpoint files behind. If the copy runs next to the original and has the BackupZit agent inside, see Two machines using one agent.

Guest network settings that are tied to a MAC address don't apply to the new adapters. One example is netplan's match: macaddress, which Linux cloud images use.

In place of the original VM

Tick turn it off and replace its disks. BackupZit then:

  • turns off the existing VM;
  • merges its checkpoints;
  • swaps its disks for the restored ones.

The VM keeps its ID, network adapters and MAC addresses, so jobs, monitoring and the guest's network keep working.

The old disk files are not deleted; they are renamed to ….replaced-DATE. Delete them once the restored VM works.

If the original VM no longer exists, it is created again, with a new Hyper-V ID.

Options

  • Folder for the virtual disks: the host's default folder or any folder that holds VM disks. An in-place restore puts the new disks next to the original ones.
  • Start the VM after the restore.

What a restored VM gets

  • Virtual switches are connected by name. If a switch doesn't exist on the host, the adapter stays disconnected.
  • Every restored VM gets a new generation ID, so Active Directory domain controllers detect the restore safely.

Restoring single files

In the VM table of the run, click Browse files to see the partitions and volumes on the VM's disks. You can browse NTFS, ext2/3/4 and XFS, also inside LVM. From there you can download files or restore them to any agent. It works exactly as for Proxmox VE.

Command line

Run these on the Hyper-V host, as administrator:

backupzit-agent hyperv list
backupzit-agent hyperv backup  --repo ... [--vmid N,N]
backupzit-agent hyperv restore --repo ... --vmid N [--new] [--name NAME] [--folder D:\VMs] [--overwrite] [--start] SNAPSHOT|latest
  • --vmid is the number shown by hyperv list. BackupZit derives it from the VM's GUID.
  • Without --new, the VM is restored in place.
  • --overwrite confirms that the disks of an existing VM should be replaced.

The repository options are the same as for all commands; see Command line reference.

Not yet included

  • Some disk types. Shared VHDX, VHD Set and pass-through disks are not backed up.
