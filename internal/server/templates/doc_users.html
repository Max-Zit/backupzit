Users, roles & LDAP

Give every person their own account with only the rights they need — as local accounts, or with their Active Directory / LDAP sign-in.

Typical use: IT administrators are Administrators; the people who run day-to-day backups are Backup operators; help desk staff who recover deleted files are Restore operators; management and auditors are Viewers. Pages and buttons a role may not use are hidden, and the server refuses them in any case. Note that restoring can overwrite data — a disk image or Linux system restore erases the target disk, and a VM restore with replace deletes the existing VM — so give the restore roles only to people you would trust with that; every restore is in the audit log.

Local users

Under Users → New local user enter a username, role and a password of at least 10 characters. On the user's page you can change the role, disable the account (open sessions end immediately), set a new password or delete the user.

Every user can change their own password under My account (click your name at the top right).

At least one enabled local administrator always remains, so you can sign in even when the directory is unreachable. You cannot demote, disable or delete yourself.

Sign-in with Active Directory / LDAP

Under Settings → LDAP / Active Directory:

  1. Server: ldaps://dc1.example.local:636. Plain ldap:// is only accepted with StartTLS, so passwords never travel unencrypted.
  2. Service account: a normal domain account used to look up users and groups (read access is enough), e.g. CN=svc-backupzit,OU=Service Accounts,DC=example,DC=local.
  3. Search base: e.g. DC=example,DC=local.
  4. User filter: Active Directory (&(objectClass=user)(sAMAccountName={username})), OpenLDAP (&(objectClass=inetOrgPerson)(uid={username})).
  5. Groups → roles: the full DN of a group for each role you want to use, e.g. CN=BackupZit Admins,OU=Groups,DC=example,DC=local. The highest matching role wins; users in none of the groups cannot sign in. Tick nested groups in Active Directory to include members of sub-groups.
  6. Certificate trust: if the domain controllers use an internal CA, paste the CA certificate; for a self-signed certificate enter its fingerprint.
  7. Use Test with a real user to check the connection, the password and the resulting role, then Save.

Directory users appear in the user list after their first sign-in. Their name, email and role are updated from the directory at every sign-in. To block a directory user immediately, disable the account in BackupZit (or in the directory).

Single sign-on (SAML, OpenID Connect)

With single sign-on, users click Sign in with … on the sign-in page and sign in at your identity provider — Microsoft Entra ID (Azure AD), Okta, Google Workspace, Keycloak, ADFS or any other SAML 2.0 or OpenID Connect provider. Set it up under Settings → Single sign-on:

  1. Choose OpenID Connect (recommended where available) or SAML 2.0.
  2. OpenID Connect: register a web application at the identity provider with the redirect URI shown on the settings page (https://<console>/login/sso/callback), and enter its issuer, client ID and client secret. Let the provider put the user's groups into a groups claim (Entra ID: Token configuration → Add groups claim, which sends group IDs; Keycloak: a Group Membership mapper; Okta: a groups claim).
  3. SAML 2.0: add the console at the identity provider with its metadata URL (https://<console>/login/sso/metadata, assertion consumer service /login/sso/acs), let it send the groups as an attribute, and enter the identity provider's metadata URL or paste its metadata XML. SAML needs the console on HTTPS. Assertions must be signed; the console's requests are not signed.
  4. Map groups (names, or IDs for Entra ID) to the four roles; the highest matching role wins. Users in none of them cannot sign in, unless you choose a role for them.

Saving checks that the identity provider answers. Users are created at their first sign-in (marked SSO under Users) and get their role from their groups at every sign-in, like directory users; their name and email come from the identity provider. The identity provider handles the second factor, so the console does not ask SSO users for its own two-factor code. Local accounts keep working, so an administrator can always sign in even when the identity provider is unreachable. A sign-in answer can be used once only and must be signed by the identity provider; every SSO sign-in and refusal is in the audit log.

Sessions

Under Settings → Sign-in & security set how long a sign-in lasts (default 12 hours) and after how many minutes of inactivity users are signed out (default 60, 0 = never). Repeated wrong passwords block the address for a while: by default after 5 failures within 15 minutes, for 30 minutes. The limits are on the same page; see Security.

Two-factor authentication

Every user can protect their sign-in with a second factor under My account → Two-factor: scan the QR code with an authenticator app (Microsoft or Google Authenticator, Authy, 1Password, Bitwarden …) and enter the 6-digit code. Ten one-time recovery codes are shown once — store them safely; each works once if the phone is lost. Users who sign in with single sign-on are not asked for the console's code: their identity provider handles the second factor.

Under Settings → Sign-in & security you can require two-factor authentication for administrators or for all users; they are asked to set it up after their next sign-in. If a user loses both phone and recovery codes, an administrator resets two-factor on the user's page. Two-factor also works for directory (LDAP) accounts.

API tokens

Scripts and monitoring tools use API tokens instead of passwords. Every user creates and revokes their own tokens under My account → API tokens; a token's role can be lower than the user's own. Administrators see and can revoke all tokens on the Users page. See REST API.

Four-eyes approval

Optional and off by default. Turn it on under Settings → Sign-in & security → Four-eyes approval; it needs at least two enabled administrators. Then these changes only take effect when a second user approves them:

ChangeWho can approve
Deleting a backup job, shortening a job's retention (any rule lower than before, or rules where everything was kept), resuming retention after a suspicious backupUsers who may manage jobs
Removing an agent or an ESXi hostUsers who may manage agents
Removing a storage targetUsers who may manage storage
Deleting a userAdministrators
Turning four-eyes approval offAdministrators

The request appears under Approvals (with a counter in the menu and on the dashboard) and the notification recipients get an email. Any other user with the right permission approves or rejects it; the requester can only cancel it. An approved change is carried out at once. Requests expire after 7 days. When a job is edited with a shorter retention, its other changes are saved immediately and only the retention waits. Requests, approvals, rejections and their users are in the audit log.

This protects against a single stolen or misused account removing the configuration or letting retention delete the backups. It does not replace immutable storage: for that, see Ransomware protection.

Audit log

Users → Audit log shows sign-ins, failed sign-ins and changes: users, jobs, storage targets, restores, displayed recovery keys and settings — with time, user and address.
