Protección contra ransomware

Los atacantes intentan borrar o cifrar las copias antes de cifrar los datos de producción. BackupZit ofrece almacenamiento donde las copias no se pueden destruir, ni siquiera con credenciales robadas.

Las capas

CapaProtege contra
Cifrado (AES-256)La lectura o manipulación de las copias en el almacenamiento. Cualquier cambio se detecta.
S3 inmutable (Object Lock, modo de cumplimiento)El borrado o sobrescritura de copias: por un atacante con las claves, un administrador malintencionado o un error.
Repositorio reforzadoLo mismo, en su propio servidor Linux: los archivos se escriben una sola vez y reciben el atributo de inmutabilidad del sistema de archivos.
Copia externaIncendio, robo, pérdida total de la sede.
Aprobación de cuatro ojos (opcional)Una cuenta de consola robada o mal usada que borra trabajos y destinos de almacenamiento o acorta la retención: un segundo usuario debe aprobarlo. Consulte Usuarios, roles y LDAP.

Detección automática de copias sospechosas

Cada copia se compara con el historial reciente de su trabajo. Se marca como sospechosa cuando muestra rastros de ransomware o de borrado masivo:

  • cambiaron muchos más archivos de lo habitual (p. ej., 95 % en lugar del 1 % habitual),
  • los datos nuevos ya no se comprimen: los archivos cifrados parecen datos aleatorios,
  • el número de archivos cayó de repente en un tercio o más,
  • un salto repentino en la cantidad de datos nuevos (también para imágenes de disco, sistemas Linux y VM).

Entonces BackupZit envía un correo de alerta (con las notificaciones de fallos activadas), muestra la copia en el panel como copias sospechosas por revisar y pausa la retención del trabajo: no se borra ninguna copia anterior, de modo que las últimas copias limpias siguen siendo restaurables aunque sigan llegando copias dañadas. Tras revisar la máquina, haga clic en Revisado: reanudar la retención en la página del trabajo.

S3 inmutable con Object Lock

  1. Cree un bucket con Object Lock habilitado (AWS, Wasabi, Backblaze B2, MinIO: mc mb --with-lock).
  2. Añada una regla de ciclo de vida que borre las versiones no actuales (noncurrent versions) tras 1 día (MinIO: mc ilm rule add --noncurrent-expire-days 1 --expire-delete-marker).
  3. Añada el destino S3 y marque Copias inmutables durante N días. Elija N al menos tan largo como la retención más larga que necesite proteger, p. ej., 30.

Cada punto de restauración permanece bloqueado al menos N días tras su creación; los datos compartidos con copias más recientes se prolongan automáticamente.

Repositorio reforzado

Un servidor Linux dedicado que ejecuta backupzit-repo:

  • Los agentes y la consola solo pueden añadir archivos; los archivos existentes nunca se sobrescriben.
  • Cada archivo recibe el atributo chattr +i durante el periodo configurado en ese servidor. Ni siquiera root puede borrarlo sin quitar antes el atributo.
  • Los borrados de los clientes solo ocultan archivos hasta que termina su periodo.
  • El servicio se ejecuta como usuario sin privilegios; su único privilegio es poner el atributo de inmutabilidad.
apt install ./backupzit-repo_*.deb
vi /etc/backupzit-repo/repo.env        # BACKUPZIT_REPO_LOCK_DAYS=30
systemctl start backupzit-repo
backupzit-repo add-key office-console
backupzit-repo fingerprint

Tras la configuración, desactive SSH y cualquier otro acceso remoto en el servidor del repositorio y proteja el acceso a su consola local / iDRAC / iLO / hipervisor. La protección es tan fuerte como la cuenta root de esa máquina.

Recuperarse tras un ataque

Si un atacante borró o sobrescribió copias, lea el almacenamiento tal como estaba antes del ataque: es solo lectura y no cambia nada:

backupzit-agent snapshots --repo <repositorio> --as-of 2026-10-01T14:30
backupzit-agent restore   --repo <repositorio> --as-of 2026-10-01T14:30 --target D:\Restore latest

En un repositorio reforzado, el administrador también puede recuperar los archivos ocultos para que las copias continúen con normalidad:

backupzit-repo status
backupzit-repo undelete --since 2026-10-01T14:00

Recomendaciones

  • Use para el almacenamiento una cuenta independiente que no forme parte de su dominio de Windows.
  • Mantenga al menos una copia inmutable (S3 Object Lock o repositorio reforzado).
  • Guarde las hojas de recuperación sin conexión (impresas, en una caja fuerte).
  • Active las alertas por correo: un cambio repentino en los fallos o en el volumen de datos enviados suele ser la primera señal de un ataque.
