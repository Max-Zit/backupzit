Instalar el servidor

La consola se ejecuta en Linux (Debian, Ubuntu, AlmaLinux, Rocky Linux) con PostgreSQL. Cada organización ejecuta su propia consola en su propia red.

Requisitos

  • Una VM o un servidor Linux: 2 vCPU, 2–4 GB de RAM y 20 GB de disco bastan para cientos de agentes (los datos de copia no se guardan en él).
  • PostgreSQL 13 o posterior (local o en otro servidor).
  • Red: los agentes deben llegar a la consola por TCP 8443 (HTTPS). Los agentes también deben llegar directamente al almacenamiento.

1. Imagen de VM lista para usar

Un appliance terminado (Debian, PostgreSQL, la consola, actualizaciones de seguridad automáticas) que arranca en menos de un minuto y no necesita acceso a internet:

HipervisorCómo
VMware ESXiHost Client: Create / Register VM → Deploy a virtual machine from an OVF or OVA file, elija backupzit-appliance.ova. vSphere: Deploy OVF Template. Workstation y VirtualBox: File → Open / Import.
Proxmox VECopie backupzit-appliance.qcow2 al nodo, cree una VM sin disco (2 vCPU, 2–4 GB de RAM, red VirtIO) y luego
qm importdisk <vmid> backupzit-appliance.qcow2 local-lvm
conecte el disco importado como SCSI, conviértalo en el disco de arranque y active el agente invitado de QEMU.
Hyper-VDescomprima backupzit-appliance-vhdx.zip y luego Nuevo → Máquina virtual, generación 1, 2–4 GB de RAM, Usar un disco duro virtual existente: el VHDX.

Arranque la VM. Su pantalla muestra la dirección de la consola web y la contraseña inicial de admin (consulte Primer inicio de sesión). Asigne a la VM 2 vCPU y 2–4 GB de RAM; puede ampliar el disco de 16 GB en cualquier momento: el appliance usa el espacio nuevo en su siguiente arranque (el sistema de archivos raíz crece en caliente). En el primer arranque cada copia crea sus propias claves SSH, contraseña de base de datos y clave de secretos, así que una misma imagen puede desplegarse muchas veces. El adaptador de red obtiene su dirección por DHCP.

2. ISO del appliance

La ISO del appliance lo instala todo sin hacer preguntas: Debian, PostgreSQL, la consola y las actualizaciones de seguridad automáticas.

  1. Cree una VM (o use un servidor) con 2 vCPU, 2–4 GB de RAM y un disco de 16 GB o más. Use VirtIO o los dispositivos predeterminados del hipervisor, BIOS o UEFI.
  2. Arránquela desde backupzit-appliance.iso. A los 5 segundos la instalación empieza sola, borra el primer disco e instala. Descarga los paquetes del sistema operativo, por lo que el servidor necesita acceso a internet durante la instalación. Tarda unos 10–20 minutos y después el servidor se reinicia.
  3. La pantalla del servidor muestra la dirección de la consola web y la contraseña inicial de admin. Abra la dirección, inicie sesión y cambie la contraseña.

El appliance (imagen o ISO)

El appliance tiene dos cuentas separadas:

  • admin en la consola web (https://<address>:8443) para el trabajo diario. Su contraseña inicial se muestra en la pantalla del servidor tras el primer arranque; cámbiela en Mi cuenta.
  • bzadmin en el propio servidor (su pantalla en la consola del hipervisor, o SSH), contraseña inicial backupzit. Debe cambiarla en el primer inicio de sesión; el usuario puede usar sudo. Root no puede iniciar sesión.

Las actualizaciones de BackupZit y del sistema operativo se gestionan desde la consola (ver más abajo). Incluye VMware Tools y el agente invitado de QEMU, para que los hipervisores muestren la dirección del appliance.

Menú de configuración en la pantalla del servidor

Cuando bzadmin inicia sesión en la propia pantalla del servidor (no por SSH), se abre un menú:

OpciónQué hace
1 NetworkDHCP o una dirección estática con longitud de prefijo (p. ej. 192.168.1.20/24), puerta de enlace y hasta tres servidores DNS.
2 Server nameEl nombre de host (letras, dígitos y -).

4 Reset the password of "admin"Para una contraseña olvidada de la consola web; también levanta los bloqueos de inicio de sesión. Después la pantalla deja de mostrar la contraseña inicial generada (también a partir del siguiente arranque, una vez cambiada la contraseña de admin en la consola web).

0 Command lineSale del menú. Ábralo de nuevo con sudo backupzit-server --setup (también por SSH).

Los mismos ajustes de red, nombre del servidor, SSH y zona horaria están en Configuración → Red en la consola web (solo administradores). Allí, una dirección estática cuya puerta de enlace no responde en medio minuto se deshace automáticamente, para que un error tipográfico no deje el appliance sin red; si aun así no se puede llegar a la consola, use el menú de la pantalla del servidor, que funciona incluso con SSH desactivado.

Los agentes recuerdan el certificado de la consola, no su dirección. Si llegan a la consola por su dirección IP y esta cambia, apúntelos a la nueva con backupzit-agent set-server (consulte Agentes), o use un nombre DNS desde el principio. Con DHCP, reserve la dirección del appliance en el servidor DHCP para que no cambie.

El servidor SSH del appliance solo ofrece cifrados AES-GCM/CTR y MAC SHA-2 (ni chacha20-poly1305 ni MAC de 64 bits, que los escáneres de vulnerabilidades señalan como débiles).

3. Script de instalación

En un servidor existente con Debian 12+, Ubuntu 22.04+, AlmaLinux o Rocky Linux 9+ (x86-64), como root:

curl -fsSL https://github.com/Max-Zit/backupzit/releases/latest/download/install.sh | sudo sh

El script instala PostgreSQL, descarga la versión más reciente, comprueba su firma con la clave de publicación de BackupZit y la suma de comprobación del paquete, instala la consola, crea la base de datos con una contraseña aleatoria, escribe /etc/backupzit/server.env, activa las actualizaciones de seguridad automáticas, abre el puerto 8443 en firewalld o ufw si están activos, inicia la consola y muestra su dirección y la contraseña inicial de admin. Opciones (después de sh -s --):

OpciónEfecto
--version 0.32.0instalar esta versión en lugar de la más reciente
--db postgres://user:pw@host:5432/dbusar una base de datos PostgreSQL existente en lugar de una local
--hosts backup.example.local,10.0.0.10nombres y direcciones para el certificado de la consola (por defecto: la dirección y el nombre del servidor)
--no-auto-updatesdejar las actualizaciones de seguridad automáticas como están

Ejemplo: curl -fsSL …/install.sh | sudo sh -s -- --hosts backup.example.local. Ejecutar de nuevo el script en una consola instalada actualiza BackupZit y conserva la configuración y los datos. Para leer el script antes de ejecutarlo, descárguelo primero: curl -fsSLO …/install.sh; less install.sh; sudo sh install.sh.

4. Paquetes a mano

Debian / Ubuntu

apt install postgresql
apt install ./backupzit-server_*.deb

AlmaLinux / Rocky Linux

dnf install postgresql-server && postgresql-setup --initdb && systemctl enable --now postgresql
dnf install ./backupzit-server-*.rpm

En AlmaLinux y Rocky Linux, cambie ident por scram-sha-256 en las líneas 127.0.0.1 y ::1 de /var/lib/pgsql/data/pg_hba.conf y reinicie PostgreSQL, para que la consola pueda iniciar sesión con contraseña.

Crear la base de datos

sudo -u postgres psql -c "SET password_encryption = 'scram-sha-256'; CREATE USER backupzit WITH PASSWORD 'choose-a-strong-password'"
sudo -u postgres psql -c "CREATE DATABASE backupzit OWNER backupzit"

Ponga la cadena de conexión en /etc/backupzit/server.env:

BACKUPZIT_DB=postgres://backupzit:choose-a-strong-password@localhost:5432/backupzit?sslmode=disable
BACKUPZIT_PUBLIC_URL=https://backup.example.local:8443
BACKUPZIT_TLS_HOSTS=backup.example.local,10.0.0.10
systemctl start backupzit-server

Primer inicio de sesión

Abra https://<server>:8443. El administrador inicial es admin; la contraseña está en /var/lib/backupzit/initial-admin-password.txt (o defina BACKUPZIT_ADMIN_PASSWORD antes del primer arranque). Cámbiela después de iniciar sesión. Para restablecer una contraseña olvidada en el servidor:

set -a; . /etc/backupzit/server.env; set +a
backupzit-server --set-admin-password 'NEW-PASSWORD'

El certificado

En el primer arranque la consola crea un certificado autofirmado. Su navegador avisará una vez; los agentes no dependen en absoluto de autoridades de certificación: fijan la huella del certificado que se muestra en la página Agentes al registrarse. Eso protege a los agentes frente a un servidor falso incluso en una red no fiable.

No sustituya ese certificado (cert.pem/key.pem en el directorio de datos): los agentes registrados antes se negarían a conectarse hasta volver a registrarse. Para los navegadores, añada en su lugar un certificado de confianza como se describe a continuación.

Un certificado de confianza para los navegadores

Para evitar el aviso del navegador, abra Configuración → Certificado. La consola responde entonces también en un nombre DNS, por ejemplo https://backup.example.com en el puerto 443, con un certificado de confianza. Los agentes siguen usando el puerto 8443 y el certificado fijado, así que no les afecta.

  • Subir un certificado de la CA de su empresa o de una CA pública, también un certificado comodín como *.example.com. Pegue el certificado (con sus certificados intermedios) y la clave privada en PEM, o elija los archivos. La consola comprueba que la clave corresponde al certificado, que es válido ahora y que cubre el nombre DNS. Sin DNS interno, introduzca en su lugar la dirección IP de la consola y use un certificado emitido para esa IP (nombre alternativo IP:192.168.1.20); en ese caso dé a la consola una dirección fija. Recibirá un correo 21 días antes de que caduque.
  • Let's Encrypt: certificados gratuitos, renovados automáticamente 30 días antes de caducar. Let's Encrypt tiene que verificar que usted controla el nombre, de una de dos formas:
    • Comprobación DNS mediante Cloudflare, recomendada para consolas que no son accesibles desde internet. BackupZit crea un registro TXT temporal con un token de API de Cloudflare. En Cloudflare, vaya a My Profile → API Tokens → Create Token, use la plantilla Edit zone DNS y limítelo a su zona.
    • Comprobación HTTP: el puerto 80 de la consola debe ser accesible desde internet con el nombre DNS. Rara vez se quiere esto para un servidor de copias.
    Pruebe primero la configuración con Usar el sistema de pruebas de Let's Encrypt. Los navegadores no confían en sus certificados, pero no tiene límites de frecuencia.
  • Servir el puerto 80 redirige http:// a https://.

El nombre DNS debe apuntar a la dirección IP de la consola, normalmente mediante un registro A en su DNS interno. Los archivos del certificado se guardan en /var/lib/backupzit/web y la clave solo la puede leer el servicio. En Linux el servicio puede usar los puertos 80 y 443 (CAP_NET_BIND_SERVICE); ábralos en el cortafuegos si se conectan navegadores desde otras redes.

Actualizar BackupZit

Por defecto, la consola obtiene las actualizaciones de las versiones oficiales de BackupZit en GitHub (https://github.com/Max-Zit/backupzit/releases). En Configuración → Actualizaciones puede indicar otro origen de actualizaciones: su propio espejo HTTPS o una carpeta del servidor. Sea cual sea el origen, cada versión debe llevar una firma válida de BackupZit. La consola comprueba cada día si hay versiones nuevas y envía un correo a los administradores cuando hay una disponible. Para instalarla, haga clic en Instalar:

  1. La consola comprueba la firma de la versión y la suma de comprobación del paquete, y espera hasta que no haya ninguna copia ni restauración en curso.
  2. Un servicio del sistema (backupzit-update, ejecutado como root) vuelve a comprobar la firma con las claves de publicación integradas en BackupZit. Ni siquiera una consola comprometida puede hacer que se instale otro paquete.
  3. Hace una copia de la base de datos (pg_dump), conserva el programa actual, instala el paquete y reinicia la consola.
  4. Si la nueva versión no responde en dos minutos, el programa anterior y la base de datos tal como estaba se restauran automáticamente. El resultado, con el registro del arranque fallido, se muestra en la página Actualizaciones, queda en el registro de auditoría y se envía por correo.
  5. Tras una actualización correcta también se actualizan los agentes: cada uno instala la nueva versión cuando está inactivo. Desactívelo en la misma página si prefiere actualizarlos usted.

La consola no está disponible durante aproximadamente un minuto. Las copias de la base de datos y los programas anteriores de las tres últimas actualizaciones se guardan en /var/lib/backupzit-update.

Sin acceso a internet: descargue los archivos de la versión (manifest.json, manifest.json.sig y el paquete del servidor) en otro equipo. Luego súbalos en Instalar una actualización desde archivos, o cópielos en una carpeta del servidor y use esa carpeta como origen de actualizaciones.

También puede seguir actualizando con el gestor de paquetes (apt install ./backupzit-server_….deb); la base de datos se migra cuando arranca la nueva versión.

Actualizaciones del sistema operativo

La misma página (Configuración → Actualizaciones) muestra el sistema operativo del servidor de la consola: cuántas actualizaciones hay disponibles, cuántas son de seguridad, si hace falta reiniciar y si las actualizaciones de seguridad automáticas están activadas. El estado se actualiza a diario, o con Comprobar ahora. Puede:

  • Activar las actualizaciones de seguridad automáticas (recomendado). La herramienta propia del sistema instala solo las correcciones de seguridad, a diario: unattended-upgrades en Debian y Ubuntu, dnf-automatic en AlmaLinux y Rocky Linux.
  • Instalar ahora todas las actualizaciones. Servicios como PostgreSQL pueden reiniciarse brevemente y la consola se reconecta sola.
  • Reiniciar servidor, por ejemplo tras una actualización del kernel. La consola lo rechaza mientras haya copias o restauraciones en curso. Los agentes conservan sus trabajos e informan de los resultados cuando la consola vuelve.

Estas tareas se ejecutan mediante el mismo servicio root que las actualizaciones de la consola. Quedan en el registro de auditoría y la salida de la última tarea se muestra en la página.

Copiar la propia consola

Las copias de su almacenamiento siguen siendo legibles sin la consola, gracias a las hojas de recuperación. Para recuperar también la propia consola tras perder su servidor, active Configuración → Copia de la consola. Esto incluye trabajos, programaciones, agentes, usuarios, configuración, historial de ejecuciones y credenciales guardadas. La consola se copia entonces a sí misma cada día en un destino de almacenamiento de red, en la carpeta backupzit-console.

Una copia de la consola contiene:

  • toda la base de datos, exportada tabla por tabla, para que no haga falta ninguna versión concreta de pg_dump;
  • la clave de secretos que descifra las credenciales guardadas;
  • el certificado de la consola, que fijan los agentes.

Está cifrada con la clave de recuperación del destino y deduplicada. Se conservan las copias más recientes: 14 por defecto.

Restaurar la consola

  1. Instale una consola nueva con la misma versión o una posterior, por ejemplo desde la ISO del appliance.
  2. En el servidor nuevo, como root, ejecute lo siguiente. Las credenciales son las de la hoja de recuperación del destino de almacenamiento, y la dirección del repositorio se muestra en la página Copia de la consola. 
    systemctl stop backupzit-server
set -a; . /etc/backupzit/server.env; set +a
export BACKUPZIT_PASSWORD='<recovery key>'
export BACKUPZIT_SFTP_PASSWORD='…' BACKUPZIT_SFTP_HOSTKEY='SHA256:…'   # or BACKUPZIT_S3_ACCESS_KEY/_SECRET_KEY, _SMB_PASSWORD, _AZURE_KEY, _HARDENED_KEY/_FINGERPRINT
backupzit-server --restore-console --repo 'sftp://backup@nas:22/backups/backupzit-console'
systemctl start backupzit-server
  3. Asigne al servidor nuevo la dirección IP o el nombre DNS del antiguo. Los agentes confían en el certificado restaurado y se reconectan solos.

La restauración sustituye la base de datos de la consola nueva por la de la copia y la actualiza a la versión instalada. --snapshot ID restaura una copia más antigua en lugar de la más reciente.

Guarde también una copia de las hojas de recuperación y de secrets.key fuera del servidor, por ejemplo en su gestor de contraseñas.
