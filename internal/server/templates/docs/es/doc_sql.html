Bases de datos: SQL Server, PostgreSQL, MySQL

BackupZit copia bases de datos con las herramientas propias del servidor de base de datos, desde el agente de la máquina de la base: Microsoft SQL Server en Windows, PostgreSQL y MySQL/MariaDB en Linux. Las copias completas siguen la programación del trabajo; las copias de registros cada pocos minutos permiten restaurar una sola base de datos a cualquier momento, por ejemplo a un minuto antes de un DELETE erróneo.

Crear un trabajo

En Trabajos de copia cree un trabajo del tipo Bases de datos en el agente de la máquina de la base y elija:

  • Servidor de base de datos: Microsoft SQL Server, PostgreSQL o MySQL/MariaDB. No se puede cambiar después.
  • Instancia o puerto: la instancia de SQL Server (vacío para la instancia predeterminada, p. ej. SQLEXPRESS) o el puerto de PostgreSQL (vacío para 5432). A MySQL/MariaDB se accede por el socket local.
  • Bases de datos: un nombre por línea, o vacío para todas las bases de usuario; las bases creadas más tarde se incluyen automáticamente.
  • Copiar los registros cada … minutos: p. ej. 15: registros de transacciones (SQL Server), WAL archivado (PostgreSQL) o registros binarios (MySQL). Déjelo vacío si basta con restaurar a la hora de una copia completa.
  • La programación es la de las copias completas, p. ej. a diario a las 22:00.

Las copias se deduplican (los datos sin cambios no se vuelven a enviar) y se cifran como cualquier copia. La retención cuenta las copias completas; las copias de registros se conservan mientras exista la copia completa en la que se basan. La página de la ejecución muestra qué contiene cada copia.

Microsoft SQL Server

  1. Instale el agente en la máquina Windows que ejecuta SQL Server (cualquier edición desde 2012, incluida Express).
  2. El agente se ejecuta como NT AUTHORITY\SYSTEM y se conecta con autenticación de Windows. Dé a esa cuenta el rol sysadmin, una vez por instancia: 
    sqlcmd -S .\SQLEXPRESS -E -Q "ALTER SERVER ROLE sysadmin ADD MEMBER [NT AUTHORITY\SYSTEM]"
  • Cada ejecución escribe un archivo de copia por base de datos (BACKUP DATABASE / BACKUP LOG … WITH CHECKSUM) en la carpeta de copias predeterminada de la instancia, guarda los archivos y los borra. Mientras dura la ejecución, la carpeta necesita espacio libre para la base más grande.
  • Con las copias de registros activadas, las copias completas inician la cadena de registros. Sin ellas, las copias completas se hacen como COPY_ONLY, para no alterar otros planes de copia o mantenimiento.
  • Las copias de registros se hacen para bases con modelo de recuperación full o bulk-logged; las bases con modelo simple solo tienen copias completas. Marque bases del sistema para añadir master, model y msdb.

PostgreSQL

El agente trabaja como la cuenta postgres por el socket local: no hay nada que configurar para las copias. Una copia completa guarda todo el clúster (pg_basebackup), los roles (pg_dumpall --globals-only) y un pg_dump de cada base de datos.

La recuperación a un momento concreto requiere el archivado de WAL. Con las copias de registros activadas, la primera copia completa lo configura con ALTER SYSTEM: archive_mode = on y un archive_command que copia los segmentos WAL terminados en /var/lib/backupzit-pg/wal; las copias de registros los guardan y los eliminan de ahí. archive_mode entra en vigor tras un reinicio de PostgreSQL (systemctl restart postgresql); la ejecución se lo indica. Si otra herramienta ya usa archive_command, BackupZit no lo toca y copia sin recuperación a un momento concreto. Si las copias de registros se detienen (trabajo deshabilitado o eliminado), vuelva a desactivar el archivado (ALTER SYSTEM RESET archive_mode, reinicio) para que la carpeta no se llene.

  • Restaurar una base de datos al estado de la copia completa: desde su pg_dump al servidor en marcha, con un nombre nuevo o sustituyendo la base.
  • En un momento concreto (o el más reciente): el agente descomprime la copia del clúster en una instancia temporal en un puerto libre (solo socket, sin red, sin archivado), reproduce el WAL hasta ese momento, vuelca la base desde ella al servidor en marcha y elimina la instancia temporal. La máquina necesita durante un rato espacio libre para el clúster.
  • Clúster completo: se restaura de la misma forma como una instancia aparte que sigue funcionando en un puerto libre; la ejecución le indica su puerto y su directorio de datos (bajo /var/lib/backupzit-pg) y cómo conectarse y detenerla.

MySQL y MariaDB

El agente se conecta como root por el socket local (autenticación por socket, la predeterminada en Debian y Ubuntu), o con las credenciales de /root/.my.cnf. Una copia completa guarda un mysqldump de cada base de datos (coherente, con rutinas, eventos y disparadores) junto con la posición del registro binario correspondiente.

La recuperación a un momento concreto requiere el registro binario. Actívelo una vez en la configuración del servidor y reinicie el servidor, p. ej. /etc/mysql/mariadb.conf.d/60-binlog.cnf:

[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin
binlog_format = ROW
expire_logs_days = 7

(cree la carpeta del registro, con la cuenta mysql como propietaria). Las copias de registros guardan entonces cada registro binario cerrado. Mantenga la caducidad propia del servidor más larga que el intervalo de las copias de registros; un hueco se notifica, y las restauraciones no pueden cruzarlo.

  • Restaurar una base de datos: su volcado se carga en una base nueva (o sustituye a una existente). En un momento concreto o la más reciente, los cambios de esa base registrados en los registros binarios tras el volcado se reproducen hasta ese momento, también cuando la base recibe un nombre nuevo. La reproducción no se escribe en el registro binario del servidor.
  • Los usuarios y privilegios (la base del sistema mysql) no forman parte de los volcados.

Restaurar

Abra una ejecución de copia completa (o use el asistente de restauración → Base de datos) y elija la base, la máquina donde restaurar (el mismo servidor u otro con el mismo servidor de base de datos) y:

  • Como base de datos nueva llamada p. ej. sales_restored (el original queda intacto y puede copiar filas de vuelta) o con su nombre original; marque sustituirla para sobrescribir una base existente (antes se desconectan sus usuarios).
  • Estado: el de la copia completa; el estado más reciente (la copia completa y cada copia de registros posterior); o un momento concreto entre la copia completa y la copia de registros utilizable más reciente, como muestra la tabla. Escriba la hora tal como la muestra la consola, en la zona horaria del servidor de la consola (consulte Zona horaria); el agente la convierte a la zona horaria del servidor de base de datos.

Línea de comandos

backupzit-agent sql list    [--instance SQLEXPRESS]
backupzit-agent sql backup  --repo ... [--instance I] [--db a,b] [--system] [--log] [--copy-only]
backupzit-agent sql restore --repo ... [--instance I] --db NAME [--as NEW] [--replace] [--at "2026-10-04 14:59:00"] SNAPSHOT|latest
backupzit-agent pg list     [--port 5432]
backupzit-agent pg backup   --repo ... [--port P] [--db a,b] [--pitr | --wal]
backupzit-agent pg restore  --repo ... --db NAME|"(cluster)" [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest
backupzit-agent mysql list
backupzit-agent mysql backup  --repo ... [--db a,b] [--binlog]
backupzit-agent mysql restore --repo ... --db NAME [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest

No incluido

  • Copias diferenciales de SQL Server y grupos de disponibilidad Always On; servidores de bases de datos remotos: el agente copia los servidores de su propia máquina.
  • Restaurar tablas sueltas: restaure la base con un nombre nuevo y copie las filas.
