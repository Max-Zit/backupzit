Máquinas virtuales de VMware ESXi

BackupZit copia las máquinas virtuales de los hosts VMware ESXi sin instalar nada en ESXi ni dentro de las VM. Un agente BackupZit en cualquier máquina de la red actúa como proxy del host. Toma instantáneas, lee solo los bloques cambiados de los discos virtuales y los escribe en su almacenamiento.

Requisitos

  • ESXi 6.7, 7 u 8 conectado directamente, o vCenter Server 7 u 8 con sus hosts ESXi (vea vCenter Server).
  • Un usuario con derechos de administrador en el host, normalmente root.
  • SSH habilitado en los hosts con licencia gratuita: Host → Actions → Services → Enable Secure Shell. La licencia gratuita de ESXi deja la API en solo lectura, así que las instantáneas y restauraciones van por SSH. Los hosts con licencia se modifican mediante la API de vSphere y no necesitan SSH.
  • Un agente proxy: cualquier agente Windows o Linux que llegue al host por el puerto 443 (y el 22 cuando se usa SSH). Los datos de copia pasan por él, así que colóquelo en una red rápida cerca del host y del almacenamiento.
  • Espacio libre en el datastore de la VM mientras se copia una VM en marcha. BackupZit copia allí el disco por un momento (ver abajo). La copia es thin, así que necesita tanto espacio como el disco usa realmente. Con hot-add no se hace ninguna copia.

Añadir un host

  1. Abra Agentes → Hosts VMware ESXi → Añadir un host ESXi o vCenter Server.
  2. Introduzca la dirección, el usuario, la contraseña y el agente proxy.
  3. La consola se conecta una vez para comprobarlos. Lee la lista de VM y la licencia, y fija el certificado HTTPS y la clave de host SSH del host. Si más adelante el host se sustituye por otra máquina con la misma dirección, BackupZit se niega a conectarse en lugar de enviarle la contraseña. Si el certificado cambia por un motivo conocido — el host se reinstaló, recibió un nuevo certificado o se añadió a vCenter (que sustituye los certificados de sus hosts) —, el host muestra la nueva huella con un botón Aceptar el nuevo certificado en la página Agentes. Compare la huella con la del host antes de aceptarla.

La contraseña se guarda cifrada, como todos los demás secretos. La propia consola se conecta al host (HTTPS 443, y SSH 22 con la licencia gratuita) al añadirlo, con Actualizar y cada 10 minutos para actualizar la lista de VM, salvo que se llegue al host a través del agente proxy. Quitar elimina el host junto con sus trabajos de copia; las copias permanecen en el almacenamiento. La tabla muestra el modo de cada host:

  • API de vSphere (host con licencia, SSH no necesario): las instantáneas, copias de discos, restauraciones y la recuperación instantánea van por la API.
  • vCenter Server (API de vSphere): un vCenter con sus hosts ESXi; todo va por la API de vCenter.
  • licencia gratuita: instantáneas y restauraciones por SSH: la API del host es de solo lectura, así que estos pasos van por SSH.
  • SSH (elegido para este host): el host se modifica por SSH aunque su API podría hacerlo (Siempre SSH al añadir el host).

A través del agente proxy (agente 0.56 o posterior): marque Conectar a través del agente proxy al añadir el host, o Conectar a través del proxy en su fila, y la consola nunca se conectará al host por sí misma. El agente proxy comprueba la dirección y la contraseña, lee la lista de VM, la versión y la licencia, e informa del certificado HTTPS y la clave de host SSH que ha visto; la consola los fija la primera vez, igual que con una conexión directa, y a partir de entonces el agente proxy rechaza un host que presente otro certificado (la fila del host ofrece entonces Aceptar el nuevo certificado). Actualizar y la lista de VM cada 10 minutos también vienen del agente proxy; estas comprobaciones no aparecen en Actividad. Solo el agente proxy necesita llegar al host, exactamente como para las copias de seguridad y las restauraciones, así que la consola puede estar en otra red, detrás de NAT o en un rango de direcciones solapado. Una dirección o contraseña incorrecta aparece como error del host tras la primera comprobación del agente proxy: quite el host y vuelva a añadirlo. Mientras el agente proxy esté sin conexión u ocupado, se mantiene la última lista de VM.

Con Automático la consola elige sola, así que un host que reciba una licencia más tarde pasa a la API sin más configuración. Cómo se modifica el host, en la fila del host (y al añadirlo), puede forzar Siempre SSH o Siempre la API de vSphere; el cambio se comprueba al instante. Las copias anteriores y sus puntos de restauración no dependen del método.

vCenter Server

Añada un vCenter Server como un host: su dirección, administrator@vsphere.local (o un usuario con el rol Administrator) y un agente proxy. BackupZit ve entonces las VM de todos los hosts ESXi y clústeres del datacenter a través de esta única conexión; no se cambia nada por SSH y no hace falta la contraseña de ningún host.

  • Una VM movida a otro host con vMotion se sigue copiando: las VM se reconocen por su UUID de instancia, no por su host.
  • Una restauración puede elegir el host ESXi que ejecuta la VM (por defecto: el host de la VM original) y el datastore.
  • La recuperación instantánea arranca la VM en el host elegido; Finalizar la mueve a un datastore con Storage vMotion mientras sigue funcionando, sin interrupción.
  • Todavía no se puede añadir un vCenter con varios datacenters; añada directamente los hosts de los demás datacenters.

No añada el mismo host ESXi directamente y además a través de vCenter: cada conexión tiene su propio repositorio, así que sus VM se copiarían dos veces. Si un host que BackupZit respalda directamente se añade después a vCenter, acepte su nuevo certificado en la página Agentes; sus trabajos siguen funcionando: vCenter asigna un nuevo ID a las VM creadas en el host independiente y BackupZit pasa los trabajos a él en la siguiente actualización.

Trabajos de copia

En Trabajos de copia, elija el host ESXi (aparece en Hosts VMware ESXi en la lista de agentes) y Máquinas virtuales. Copie todas las VM del host (las VM creadas más tarde se incluyen automáticamente) o marque algunas. El trabajo se ejecuta en el agente proxy del host. Si cambia el proxy, los trabajos existentes lo siguen.

Para dejar fuera VM concretas, p. ej., la VM de la consola de BackupZit, elija Todas las VM (y contenedores) del host excepto las marcadas y márquelas.

Cómo se copia una VM

  1. Se activa el seguimiento de bloques cambiados (CBT) para la VM si está desactivado.
    • En hosts con licencia esto ocurre automáticamente.
    • En hosts gratuitos, el CBT solo puede activarse con la VM apagada. BackupZit lo hace en la primera copia que encuentra la VM apagada. Hasta entonces, cada copia lee los discos completos y la ejecución muestra una advertencia.
  2. Se toma una instantánea backupzit_…. Cuando las VMware Tools se ejecutan en el invitado, la instantánea se pone en reposo (quiesced): primero se vacían las aplicaciones y los sistemas de archivos, lo que hace la copia coherente con las aplicaciones. Sin VMware Tools es coherente ante bloqueos. Instale open-vm-tools en las VM Linux y VMware Tools en las VM Windows.
  3. El CBT indica qué bloques leer:
    • en la primera copia, solo los bloques en uso;
    • después, solo los bloques cambiados desde la copia anterior.
  4. Una VM en marcha mantiene sus discos bloqueados. Por eso sus discos se copian en el datastore (thin) y la instantánea se elimina enseguida, normalmente tras unos segundos. Luego la copia se lee por HTTPS y se borra. Las VM apagadas se leen directamente. Con hot-add, los discos de las VM en marcha se leen en cambio a través de la propia VM del proxy, sin copia.
  5. La configuración de la VM (.vmx) y la NVRAM se guardan con la copia.

Ejemplo del laboratorio de pruebas: una VM Debian con un disco de 8 GB, 1,6 GB en uso. La primera copia leyó 1,6 GB. La siguiente, tras 50 MB de datos nuevos, leyó 70 MB y tardó 23 segundos.

Hot-add: sin copia en el datastore

Copiar los discos de una VM en marcha cuesta tiempo y E/S en el datastore de producción en cada copia de seguridad, también en las incrementales, y necesita espacio libre para los bloques usados de los discos. Con VM grandes en discos lentos, eso importa. Con Hot-add (Agentes → Hosts VMware ESXi, la casilla bajo el agente proxy), el proxy los lee en cambio en su sitio:

  • Requisitos: el proxy es un agente Linux en una VM que ve los datastores de la VM (en el mismo host, o en un host del mismo vCenter con acceso a ellos), y el host se modifica mediante la API de vSphere (vCenter o un host con licencia). El proxy encuentra su propia VM por su BIOS UUID.
  • Cómo: mientras existe la instantánea, cada disco se conecta a la VM del proxy como independent-nonpersistent. El proxy lo abre en solo lectura; todo lo que se escribiera en él iría a un redo log que vSphere descarta al desconectar el disco, así que el disco de la VM nunca se modifica. El proxy lee solo los bloques que indica el CBT, desconecta el disco y después se elimina la instantánea.
  • Qué ahorra: ni copia temporal ni espacio adicional en el datastore. Una copia incremental de una VM de 2 TB con 20 GB de cambios lee 20 GB. La instantánea se mantiene mientras se leen los discos (en lugar de solo durante la copia), así que la VM escribe en la instantánea un poco más de tiempo.
  • Alternativa: si el proxy no es una VM del host, o falla la conexión o la lectura de un disco, ese disco se copia en el datastore como antes y la ejecución muestra una advertencia con el motivo. Hot-add está desactivado de forma predeterminada; los agentes anteriores a 0.54 lo ignoran. La página de la ejecución muestra cuántos discos se leyeron mediante hot-add.
  • En la VM del proxy: impida que LVM active volúmenes de los discos conectados, con el archivo de dispositivos de LVM (use_devicesfile = 1 en /etc/lvm/lvm.conf, con los discos propios del proxy registrados mediante lvmdevices). Los volúmenes que LVM active de todos modos se retiran antes de desconectar el disco. No conecte a mano discos de otras VM al proxy: un disco independent-nonpersistent de la carpeta de otra VM se toma por uno que dejó una copia interrumpida, y se desconecta.

Varios agentes proxy (vCenter)

Un agente proxy lee un disco tras otro y, mediante hot-add, solo en los hosts cuyos datastores ve. Con una conexión vCenter, añada un agente Linux en una VM de cada host ESXi como agente proxy adicional (Agentes → Hosts VMware ESXi, Agentes proxy adicionales bajo el agente proxy; agentes 0.55 o posteriores):

  • División por host: cada copia de seguridad del trabajo se divide. Cada VM va al agente proxy del host ESXi en el que se ejecuta (según la última lista de VM), y cualquier otra VM al agente proxy de la conexión. Cada agente proxy respalda su parte como una ejecución propia, a la vez que los demás, mediante hot-add en su propio host. Solo participan los agentes proxy en línea: las VM de un agente proxy apagado van al agente proxy de la conexión. La primera copia de seguridad en un repositorio nuevo y las copias a un destino local o USB no se dividen.
  • Un inicio: el trabajo muestra las partes de un inicio como una sola: en ejecución mientras una parte se ejecuta, fallida si una parte falló. Las alertas de RPO y el panel cuentan una copia de seguridad cuando todas las partes tuvieron éxito; un trabajo encadenado o una copia «después de cada copia de seguridad» se inicia una vez, tras la última parte.
  • Sin solapamiento: las copias de seguridad y restauraciones de la conexión en distintos agentes proxy no se ejecutan a la vez (solo las partes de un mismo inicio), así que una VM movida entre hosts nunca la tratan dos agentes proxy al mismo tiempo.
  • Retención por agente proxy: cada parte conserva el número de copias de seguridad del trabajo para sus VM, y los trabajos de copia también las copian y conservan por parte. Las copias de seguridad de antes de dividir el trabajo y las de un agente proxy quitado se quedan como están: siguen siendo puntos de restauración de sus VM. Una VM movida a otro host (vMotion) pasa al agente proxy de ese host a partir de la siguiente actualización de la lista de VM.
  • BackupZit encuentra el host de un agente proxy por el BIOS UUID que informa su agente; la página Agentes lo muestra junto a cada agente. Host ESXi no encontrado: el agente no es una VM de este vCenter, o la lista de VM es anterior al agente (haga clic en Actualizar).

Cancelar una copia de seguridad de VMware (Actividad → Cancelar) también detiene una copia de disco en curso en el datastore y elimina la copia parcial; la instantánea se elimina como tras cada copia de seguridad. Si al cancelar todavía se está creando una instantánea, se espera a que termine (hasta cinco minutos) y también se elimina.

Instantáneas que quedan atrás. El agente proxy registra cada instantánea y cada copia temporal de disco antes de crearlas, y borra el registro solo cuando comprueba que el objeto ha desaparecido: tras la eliminación vuelve a listar las instantáneas de la VM, lo intenta hasta tres veces durante unos diez minutos, vuelve a iniciar sesión cuando la sesión de vSphere ha terminado (también antes de cada VM, para que una sesión perdida no haga fallar las VM siguientes) y consolida los discos cuando vSphere indica que lo necesitan; una VM sin instantáneas cuyos discos aún necesitan consolidación por una eliminación anterior se consolida antes de su siguiente copia. Si el agente se detiene a medias (fallo, corte de corriente) o la eliminación sigue fallando, el registro se mantiene:

  • La consola pone en cola una ejecución de limpieza en el agente proxy (solo él tiene las credenciales del host), y el agente proxy también elimina esos restos tras cada copia de seguridad de la conexión. Las VM con las que está trabajando una copia o restauración del agente proxy no se tocan.
  • El panel muestra cada resto en Requiere atención (VM, desde cuándo, por qué) con Quitar ahora, y se envía una notificación (correo, chat) una sola vez por cada resto que permanece.
  • La consola también busca instantáneas backupzit_… de más de seis horas en la lista de VM que actualiza cada 10 minutos, mientras no se ejecuta ninguna copia de seguridad de la conexión, así que también aparecen los restos de agentes más antiguos. Solo se eliminan instantáneas llamadas backupzit_…; las instantáneas propias de la VM nunca se tocan.

Restaurar una VM

Use el asistente de restauración (Máquina virtual completa) o la página de la copia en Actividad. Elija:

  • Como VM nueva junto a la original: una copia con nombre, UUID y direcciones MAC nuevos. El nombre predeterminado es el del original más -restored- y la fecha. La configuración de red del invitado vinculada a las direcciones MAC antiguas, como netplan match: macaddress en imágenes de nube, no se aplica a la copia.
  • En lugar de la VM original: con apagarla y sustituir sus discos, BackupZit:
    • apaga la VM y elimina sus instantáneas;
    • renombra los discos actuales a ….replaced-DATE.vmdk (bórrelos cuando la VM restaurada funcione);
    • escribe la copia en discos nuevos con los nombres originales y ajusta la CPU y la memoria como en la copia.
    La VM conserva su UUID, sus adaptadores de red y sus direcciones MAC. Si la VM se eliminó, se vuelve a crear con su identidad original.
  • Host ESXi y datastore: otro host u otro datastore del mismo host.
  • Iniciar la VM tras la restauración.

Los discos se restauran thin y solo se escriben los bloques con datos. Las imágenes ISO conectadas a unidades de CD/DVD no forman parte de la copia, así que esas unidades quedan vacías.

Recuperación instantánea

Elija Al instante, ejecutándose desde la copia para iniciar una VM en segundos, sin copiar antes sus discos. El agente proxy del host —debe ser un agente Linux— sirve los discos de la VM directamente desde la copia por NFS; el host lo monta como datastore backupzit-<agent> y ejecuta la VM desde ahí. Los cambios que hace la VM se guardan en el agente (/var/lib/backupzit/instant-esxi, que necesita espacio libre para ellos); la copia en sí nunca se modifica y la retención la conserva mientras la VM se ejecute desde ella. Si la VM original aún existe, la VM instantánea recibe un UUID y direcciones MAC nuevos.

En la página de la ejecución, cuando la VM funcione como debe:

  • Finalizar la copia a un datastore del host: la VM se apaga (mediante VMware Tools si se ejecutan), sus discos se copian thin (mediante la API en hosts con licencia, con vmkfstools por SSH con la licencia gratuita), se registra desde el datastore y se vuelve a iniciar. Un host independiente no tiene Storage vMotion, así que esto requiere una breve interrupción que crece con el tamaño de los discos. Si la copia falla, la VM sigue ejecutándose desde la copia de seguridad.
  • Descartar detiene y elimina la VM con todos sus cambios.

El agente responde a NFS en el puerto 2049 (y lo registra en el rpcbind de la máquina en el puerto 111, o responde él mismo en el puerto 111) solo para la dirección del host ESXi; abra estos puertos del host al agente si hay un cortafuegos en medio. Cuando la última VM instantánea se finaliza o se descarta, el datastore se elimina y el servidor NFS se detiene.

Archivos sueltos

Examinar archivos en la página de la copia (o Archivos de una máquina virtual en el asistente de restauración) abre los discos de la VM. Puede examinar NTFS, ext2/3/4 y XFS, también sobre LVM, y descargar archivos o restaurarlos en cualquier agente.

Línea de comandos

Estos comandos se ejecutan en cualquier agente. Defina la contraseña de ESXi en BACKUPZIT_VMWARE_PASSWORD:

backupzit-agent vmware list    --host 192.168.1.20 [--user root]
backupzit-agent vmware backup  --host … --repo … [--vmid N,N]
backupzit-agent vmware restore --host … --repo … --vmid N [--new] [--name NAME] [--datastore DS] [--overwrite] [--start] SNAPSHOT|latest

vmware list muestra las huellas del certificado y de la clave SSH del host. Páselas con --thumbprint y --ssh-host-key para fijarlas también en la línea de comandos.

Aún no incluido

  • vCenter con varios datacenters. Solo se puede añadir un vCenter con un datacenter; añada directamente los hosts de los demás.
  • VM con instantáneas propias. Sus discos son deltas; elimine o consolide primero las instantáneas.
  • Algunos tipos de disco. Asignaciones de dispositivos sin formato (RDM) y discos independientes.
  • Recuperación instantánea mediante un agente proxy Windows. La recuperación instantánea necesita un agente proxy Linux.
