Installare il server

La console gira su Linux (Debian, Ubuntu, AlmaLinux, Rocky Linux) con PostgreSQL. Ogni organizzazione gestisce la propria console nella propria rete.

Requisiti

  • Una VM o un server Linux: 2 vCPU, 2–4 GB di RAM e 20 GB di disco bastano per centinaia di agenti (i dati di backup non vengono archiviati lì).
  • PostgreSQL 13 o successivo (locale o su un altro server).
  • Rete: gli agenti devono raggiungere la console su TCP 8443 (HTTPS). Gli agenti devono anche raggiungere direttamente lo storage.

1. Immagine VM pronta

Un'appliance finita (Debian, PostgreSQL, la console, aggiornamenti di sicurezza automatici) che si avvia in meno di un minuto e non richiede accesso a internet:

HypervisorCome
VMware ESXiHost Client: Create / Register VM → Deploy a virtual machine from an OVF or OVA file, scegliete backupzit-appliance.ova. vSphere: Deploy OVF Template. Workstation e VirtualBox: File → Open / Import.
Proxmox VECopiate backupzit-appliance.qcow2 sul nodo, create una VM senza disco (2 vCPU, 2–4 GB di RAM, rete VirtIO), poi
qm importdisk <vmid> backupzit-appliance.qcow2 local-lvm
collegate il disco importato come SCSI, rendetelo il disco di avvio e abilitate l'agente guest QEMU.
Hyper-VDecomprimete backupzit-appliance-vhdx.zip, poi Nuovo → Macchina virtuale, generazione 1, 2–4 GB di RAM, Usa un disco rigido virtuale esistente: il VHDX.

Avviate la VM. Il suo schermo mostra l'indirizzo della console web e la password iniziale di admin (vedete Primo accesso). Assegnate alla VM 2 vCPU e 2–4 GB di RAM; potete ingrandire il disco da 16 GB in qualsiasi momento — l'appliance usa il nuovo spazio al successivo avvio (il file system root si espande a caldo). Al primo avvio ogni copia crea le proprie chiavi SSH, la password del database e la chiave dei segreti, così la stessa immagine può essere distribuita molte volte. La scheda di rete ottiene l'indirizzo via DHCP.

2. ISO dell'appliance

La ISO dell'appliance installa tutto senza domande: Debian, PostgreSQL, la console e gli aggiornamenti di sicurezza automatici.

  1. Create una VM (o usate un server) con 2 vCPU, 2–4 GB di RAM e un disco da 16 GB o più. Usate VirtIO o i dispositivi predefiniti dell'hypervisor, BIOS o UEFI.
  2. Avviatela da backupzit-appliance.iso. Dopo 5 secondi l'installazione parte da sola, cancella il primo disco e installa. Scarica i pacchetti del sistema operativo, quindi il server ha bisogno di accesso a internet durante l'installazione. Ci vogliono circa 10–20 minuti, poi il server si riavvia.
  3. Lo schermo del server mostra l'indirizzo della console web e la password iniziale di admin. Aprite l'indirizzo, accedete e cambiate la password.

L'appliance (immagine o ISO)

L'appliance ha due account separati:

  • admin nella console web (https://<address>:8443) per il lavoro quotidiano. La sua password iniziale viene mostrata sullo schermo del server dopo il primo avvio; cambiatela in Il mio account.
  • bzadmin sul server stesso (il suo schermo nella console dell'hypervisor, o SSH), password iniziale backupzit. Dovete cambiarla al primo accesso; l'utente può usare sudo. Root non può accedere.

Gli aggiornamenti di BackupZit e del sistema operativo si gestiscono dalla console (vedete sotto). VMware Tools e l'agente guest QEMU sono inclusi, così gli hypervisor mostrano l'indirizzo dell'appliance.

Menu di configurazione sullo schermo del server

Quando bzadmin accede dallo schermo stesso del server (non via SSH), si apre un menu:

VoceCosa fa

4 Reset the password of "admin"Per una password della console web dimenticata; rimuove anche i blocchi di accesso. Poi lo schermo smette di mostrare la password iniziale generata (lo stesso avviene dal successivo avvio, una volta cambiata la password di admin nella console web).

Le stesse impostazioni di rete, nome del server, SSH e fuso orario si trovano in Impostazioni → Rete nella console web (solo amministratori). Lì un indirizzo statico il cui gateway non risponde entro mezzo minuto viene annullato automaticamente, così un errore di battitura non può isolare l'appliance dalla rete; se la console resta irraggiungibile, usate il menu sullo schermo del server, che funziona anche con SSH disattivato.

Gli agenti ricordano il certificato della console, non il suo indirizzo. Se raggiungono la console tramite l'indirizzo IP e questo cambia, indirizzateli al nuovo con backupzit-agent set-server (vedete Agenti), oppure usate un nome DNS fin dall'inizio. Con DHCP, riservate l'indirizzo dell'appliance nel server DHCP così che non cambi.

Il server SSH dell'appliance offre solo cifrari AES-GCM/CTR e MAC SHA-2 (niente chacha20-poly1305 né MAC a 64 bit, che gli scanner di vulnerabilità segnalano come deboli).

3. Script di installazione

Su un server esistente con Debian 12+, Ubuntu 22.04+, AlmaLinux o Rocky Linux 9+ (x86-64), come root:

curl -fsSL https://github.com/Max-Zit/backupzit/releases/latest/download/install.sh | sudo sh

Lo script installa PostgreSQL, scarica la versione più recente, ne verifica la firma con la chiave di rilascio BackupZit e il checksum del pacchetto, installa la console, crea il database con una password casuale, scrive /etc/backupzit/server.env, attiva gli aggiornamenti di sicurezza automatici, apre la porta 8443 in firewalld o ufw se attivi, avvia la console e mostra il suo indirizzo e la password iniziale di admin. Opzioni (dopo sh -s --):

OpzioneEffetto
--version 0.32.0installa questa versione invece della più recente
--db postgres://user:pw@host:5432/dbusa un database PostgreSQL esistente invece di uno locale
--hosts backup.example.local,10.0.0.10nomi e indirizzi per il certificato della console (predefinito: indirizzo e nome del server)
--no-auto-updateslascia invariati gli aggiornamenti di sicurezza automatici

Esempio: curl -fsSL …/install.sh | sudo sh -s -- --hosts backup.example.local. Eseguire di nuovo lo script su una console installata aggiorna BackupZit mantenendo configurazione e dati. Per leggere lo script prima di eseguirlo, scaricatelo prima: curl -fsSLO …/install.sh; less install.sh; sudo sh install.sh.

4. Pacchetti a mano

Debian / Ubuntu

apt install postgresql
apt install ./backupzit-server_*.deb

AlmaLinux / Rocky Linux

dnf install postgresql-server && postgresql-setup --initdb && systemctl enable --now postgresql
dnf install ./backupzit-server-*.rpm

Su AlmaLinux e Rocky Linux, sostituite ident con scram-sha-256 nelle righe 127.0.0.1 e ::1 di /var/lib/pgsql/data/pg_hba.conf e riavviate PostgreSQL, così la console può accedere con una password.

Creare il database

sudo -u postgres psql -c "SET password_encryption = 'scram-sha-256'; CREATE USER backupzit WITH PASSWORD 'choose-a-strong-password'"
sudo -u postgres psql -c "CREATE DATABASE backupzit OWNER backupzit"

Inserite la stringa di connessione in /etc/backupzit/server.env:

BACKUPZIT_DB=postgres://backupzit:choose-a-strong-password@localhost:5432/backupzit?sslmode=disable
BACKUPZIT_PUBLIC_URL=https://backup.example.local:8443
BACKUPZIT_TLS_HOSTS=backup.example.local,10.0.0.10
systemctl start backupzit-server

Primo accesso

Aprite https://<server>:8443. L'amministratore iniziale è admin; la password si trova in /var/lib/backupzit/initial-admin-password.txt (oppure impostate BACKUPZIT_ADMIN_PASSWORD prima del primo avvio). Cambiatela dopo l'accesso. Per reimpostare una password dimenticata sul server:

set -a; . /etc/backupzit/server.env; set +a
backupzit-server --set-admin-password 'NEW-PASSWORD'

Il certificato

Al primo avvio la console crea un certificato autofirmato. Il browser vi avviserà una volta; gli agenti non si affidano affatto alle autorità di certificazione — fissano l'impronta del certificato mostrata nella pagina Agenti durante la registrazione. Questo protegge gli agenti da un server falso anche su una rete non affidabile.

Non sostituite quel certificato (cert.pem/key.pem nella directory dei dati): gli agenti registrati in precedenza rifiuterebbero di connettersi finché non vengono registrati di nuovo. Per i browser aggiungete invece un certificato attendibile come descritto sotto.

Un certificato attendibile per i browser

Per evitare l'avviso del browser, aprite Impostazioni → Certificato. La console risponde allora anche a un nome DNS, ad esempio https://backup.example.com sulla porta 443, con un certificato attendibile. Gli agenti continuano a usare la porta 8443 e il certificato fissato, quindi non ne sono toccati.

  • Carica un certificato dalla CA aziendale o da una CA pubblica, anche un certificato wildcard come *.example.com. Incollate il certificato (con i certificati intermedi) e la chiave privata in PEM, o scegliete i file. La console verifica che la chiave appartenga al certificato, che sia valido ora e che copra il nome DNS. Senza DNS interno, inserite invece l'indirizzo IP della console e usate un certificato emesso per quell'IP (nome alternativo IP:192.168.1.20); in tal caso date alla console un indirizzo fisso. Riceverete un'email 21 giorni prima della scadenza.
  • Let's Encrypt: certificati gratuiti, rinnovati automaticamente 30 giorni prima della scadenza. Let's Encrypt deve verificare che controllate il nome, in uno di due modi:
    • Verifica DNS tramite Cloudflare, consigliata per console non raggiungibili da internet. BackupZit crea un record TXT temporaneo con un token API di Cloudflare. In Cloudflare andate in My Profile → API Tokens → Create Token, usate il modello Edit zone DNS e limitatelo alla vostra zona.
    • Verifica HTTP: la porta 80 della console deve essere raggiungibile da internet con il nome DNS. Raramente lo si vuole per un server di backup.
    Provate prima la configurazione con Usa il sistema di test di Let's Encrypt. I suoi certificati non sono attendibili per i browser, ma non ha limiti di frequenza.
  • Usa la porta 80 reindirizza http:// a https://.

Il nome DNS deve puntare all'indirizzo IP della console, di solito tramite un record A nel DNS interno. I file del certificato sono conservati in /var/lib/backupzit/web e la chiave è leggibile solo dal servizio. Su Linux il servizio può usare le porte 80 e 443 (CAP_NET_BIND_SERVICE); apritele nel firewall se i browser si collegano da altre reti.

Aggiornare BackupZit

Per impostazione predefinita la console prende gli aggiornamenti dalle versioni ufficiali di BackupZit su GitHub (https://github.com/Max-Zit/backupzit/releases). In Impostazioni → Aggiornamenti potete indicare invece un'altra fonte degli aggiornamenti — il vostro mirror HTTPS o una cartella sul server. Qualunque sia la fonte, ogni versione deve avere una firma BackupZit valida. La console controlla ogni giorno se ci sono nuove versioni e invia un'email agli amministratori quando ne è disponibile una. Per installarla, fate clic su Installa:

  1. La console verifica la firma della versione e il checksum del pacchetto, e attende che non ci siano backup o ripristini in corso.
  2. Un servizio di sistema (backupzit-update, eseguito come root) verifica di nuovo la firma con le chiavi di rilascio integrate in BackupZit. Nemmeno una console compromessa può far installare un altro pacchetto.
  3. Esegue il backup del database (pg_dump), conserva il programma attuale, installa il pacchetto e riavvia la console.
  4. Se la nuova versione non risponde entro due minuti, il programma precedente e il database com'era vengono ripristinati automaticamente. Il risultato, con il log dell'avvio fallito, viene mostrato nella pagina Aggiornamenti, registrato nel log di audit e inviato via email.
  5. Dopo un aggiornamento riuscito vengono aggiornati anche gli agenti: ciascuno installa la nuova versione quando è inattivo. Disattivatelo nella stessa pagina se preferite aggiornarli voi.

La console non è disponibile per circa un minuto. I backup del database e i programmi precedenti degli ultimi tre aggiornamenti vengono conservati in /var/lib/backupzit-update.

Senza accesso a internet: scaricate i file della versione (manifest.json, manifest.json.sig e il pacchetto server) su un altro computer. Poi caricateli in Installa un aggiornamento da file, oppure copiateli in una cartella del server e usate quella cartella come fonte degli aggiornamenti.

Potete sempre aggiornare con il gestore di pacchetti (apt install ./backupzit-server_….deb); il database viene migrato all'avvio della nuova versione.

Aggiornamenti del sistema operativo

La stessa pagina (Impostazioni → Aggiornamenti) mostra il sistema operativo del server della console: quanti aggiornamenti sono disponibili, quanti sono correzioni di sicurezza, se serve un riavvio e se gli aggiornamenti di sicurezza automatici sono attivi. Lo stato viene aggiornato ogni giorno, o con Verifica ora. Potete:

  • Attiva gli aggiornamenti di sicurezza automatici (consigliato). Lo strumento del sistema installa ogni giorno solo le correzioni di sicurezza: unattended-upgrades su Debian e Ubuntu, dnf-automatic su AlmaLinux e Rocky Linux.
  • Installa ora tutti gli aggiornamenti. Servizi come PostgreSQL possono riavviarsi brevemente e la console si ricollega da sola.
  • Riavvia server, ad esempio dopo un aggiornamento del kernel. La console lo rifiuta mentre sono in corso backup o ripristini. Gli agenti mantengono i loro job e riportano i risultati quando la console torna disponibile.

Queste operazioni passano per lo stesso servizio root degli aggiornamenti della console. Vengono registrate nel log di audit e l'output dell'ultima operazione viene mostrato nella pagina.

Eseguire il backup della console stessa

I backup sul vostro storage restano leggibili senza la console, grazie ai fogli di ripristino. Per recuperare anche la console stessa dopo aver perso il suo server, attivate Impostazioni → Backup della console. Questo comprende job, pianificazioni, agenti, utenti, impostazioni, storico delle esecuzioni e credenziali memorizzate. La console esegue allora ogni giorno il proprio backup su una destinazione di archiviazione di rete, nella cartella backupzit-console.

Un backup della console contiene:

  • l'intero database, esportato tabella per tabella, così non serve una specifica versione di pg_dump;
  • la chiave dei segreti che decifra le credenziali memorizzate;
  • il certificato della console, che gli agenti fissano.

È cifrato con la chiave di ripristino della destinazione e deduplicato. Vengono conservati i backup più recenti: 14 per impostazione predefinita.

Ripristinare la console

  1. Installate una nuova console con la stessa versione o una più recente, ad esempio dalla ISO dell'appliance.
  2. Sul nuovo server, come root, eseguite quanto segue. Le credenziali sono quelle del foglio di ripristino della destinazione di archiviazione, e l'indirizzo del repository è mostrato nella pagina Backup della console. 
    systemctl stop backupzit-server
set -a; . /etc/backupzit/server.env; set +a
export BACKUPZIT_PASSWORD='<recovery key>'
export BACKUPZIT_SFTP_PASSWORD='…' BACKUPZIT_SFTP_HOSTKEY='SHA256:…'   # or BACKUPZIT_S3_ACCESS_KEY/_SECRET_KEY, _SMB_PASSWORD, _AZURE_KEY, _HARDENED_KEY/_FINGERPRINT
backupzit-server --restore-console --repo 'sftp://backup@nas:22/backups/backupzit-console'
systemctl start backupzit-server
  3. Assegnate al nuovo server l'indirizzo IP o il nome DNS del vecchio. Gli agenti si fidano del certificato ripristinato e si ricollegano da soli.

Il ripristino sostituisce il database della nuova console con quello del backup e lo porta alla versione installata. --snapshot ID ripristina un backup più vecchio invece del più recente.

Conservate anche una copia dei fogli di ripristino e di secrets.key fuori dal server, ad esempio nel vostro gestore di password.
