Database: SQL Server, PostgreSQL, MySQL

BackupZit esegue il backup dei database con gli strumenti propri del server di database, tramite l'agente sulla macchina del database: Microsoft SQL Server su Windows, PostgreSQL e MySQL/MariaDB su Linux. I backup completi seguono la pianificazione del job; i backup dei log ogni pochi minuti permettono di ripristinare un singolo database a qualsiasi momento — ad esempio a un minuto prima di un DELETE sbagliato.

Creare un job

In Job di backup crea un job di tipo Database sull'agente della macchina del database e scegli:

  • Server di database: Microsoft SQL Server, PostgreSQL o MySQL/MariaDB. Non può essere cambiato in seguito.
  • Istanza o porta: l'istanza SQL Server (vuoto per l'istanza predefinita, ad es. SQLEXPRESS) o la porta PostgreSQL (vuoto per 5432). MySQL/MariaDB si raggiunge tramite il socket locale.
  • Database: un nome per riga, o vuoto per tutti i database utente — i database creati in seguito sono inclusi automaticamente.
  • Esegui il backup dei log ogni … minuti: ad es. 15 — log delle transazioni (SQL Server), WAL archiviati (PostgreSQL) o log binari (MySQL). Lascia vuoto se basta ripristinare all'ora di un backup completo.
  • La pianificazione è quella dei backup completi, ad es. ogni giorno alle 22:00.

I backup sono deduplicati — i dati invariati non vengono ricaricati — e cifrati come ogni backup. La conservazione conta i backup completi; i backup dei log vengono mantenuti finché esiste il backup completo su cui si basano. La pagina dell'esecuzione elenca cosa contiene ogni backup.

Microsoft SQL Server

  1. Installa l'agente sulla macchina Windows su cui gira SQL Server (qualsiasi edizione dal 2012, inclusa Express).
  2. L'agente gira come NT AUTHORITY\SYSTEM e si collega con l'autenticazione Windows. Assegna a quell'account il ruolo sysadmin, una volta per istanza: 
    sqlcmd -S .\SQLEXPRESS -E -Q "ALTER SERVER ROLE sysadmin ADD MEMBER [NT AUTHORITY\SYSTEM]"
  • Ogni esecuzione scrive un file di backup per database (BACKUP DATABASE / BACKUP LOG … WITH CHECKSUM) nella cartella di backup predefinita dell'istanza, archivia i file e li elimina. Durante l'esecuzione la cartella deve avere spazio libero per il database più grande.
  • Con i backup dei log attivi, i backup completi avviano la catena dei log. Senza, i backup completi vengono eseguiti come COPY_ONLY, così non disturbano altri piani di backup o di manutenzione.
  • I backup dei log vengono eseguiti per i database con modello di recupero full o bulk-logged; i database con modello simple ricevono solo backup completi. Seleziona database di sistema per aggiungere master, model e msdb.

PostgreSQL

L'agente lavora come account postgres tramite il socket locale — nulla da configurare per i backup. Un backup completo salva l'intero cluster (pg_basebackup), i ruoli (pg_dumpall --globals-only) e un pg_dump di ogni database.

Il ripristino a un momento preciso richiede l'archiviazione dei WAL. Con i backup dei log attivi, il primo backup completo la configura con ALTER SYSTEM: archive_mode = on e un archive_command che copia i segmenti WAL completati in /var/lib/backupzit-pg/wal; i backup dei log li archiviano e li rimuovono da lì. archive_mode diventa effettivo dopo un riavvio di PostgreSQL (systemctl restart postgresql) — l'esecuzione te lo segnala. Se un altro strumento usa già archive_command, BackupZit non lo tocca ed esegue il backup senza ripristino a un momento preciso. Se i backup dei log si fermano (job disattivato o eliminato), disattiva di nuovo l'archiviazione (ALTER SYSTEM RESET archive_mode, riavvio) perché la cartella non si riempia.

  • Ripristina un database allo stato del backup completo: dal suo pg_dump nel server in esecuzione, con un nuovo nome o al posto del database.
  • A un momento preciso (o il più recente): l'agente estrae il backup del cluster in un'istanza temporanea su una porta libera (solo socket, nessuna rete, nessuna archiviazione), riapplica i WAL fino a quel momento, ne esporta il database nel server in esecuzione e rimuove l'istanza temporanea. Per un po' la macchina ha bisogno di spazio libero per il cluster.
  • Intero cluster: ripristinato allo stesso modo come istanza separata che continua a girare su una porta libera; l'esecuzione ti indica la sua porta e la cartella dei dati (sotto /var/lib/backupzit-pg) e come collegarti e arrestarla.

MySQL e MariaDB

L'agente si collega come root tramite il socket locale (autenticazione via socket, predefinita su Debian e Ubuntu), oppure con le credenziali in /root/.my.cnf. Un backup completo salva un mysqldump di ogni database (coerente, con routine, eventi e trigger) insieme alla posizione del log binario a cui corrisponde.

Il ripristino a un momento preciso richiede il log binario. Attivalo una volta nella configurazione del server e riavvia il server, ad es. /etc/mysql/mariadb.conf.d/60-binlog.cnf:

[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin
binlog_format = ROW
expire_logs_days = 7

(crea la cartella per il log, con l'account mysql come proprietario). I backup dei log salvano poi ogni log binario chiuso. Mantieni la scadenza propria del server più lunga dell'intervallo dei backup dei log; un buco viene segnalato e i ripristini non possono superarlo.

  • Ripristina un database: il suo dump viene caricato in un nuovo database (o ne sostituisce uno esistente). A un momento preciso o il più recente, le modifiche di quel database registrate nei log binari dopo il dump vengono riapplicate fino a quel momento — anche quando il database riceve un nuovo nome. La riapplicazione non viene scritta nel log binario del server.
  • Utenti e privilegi (il database di sistema mysql) non fanno parte dei dump.

Ripristino

Apri un'esecuzione di backup completo (o usa la procedura guidata di ripristino → Database) e scegli il database, la macchina su cui ripristinare (lo stesso server o un altro con lo stesso server di database) e:

  • Come nuovo database chiamato ad es. sales_restored — l'originale resta intatto e puoi ricopiare le righe — oppure con il nome originale; seleziona sostituirlo per sovrascrivere un database esistente (i suoi utenti vengono prima disconnessi).
  • Stato: quello del backup completo; lo stato più recente (il backup completo e ogni backup dei log successivo); oppure un momento preciso tra il backup completo e il backup dei log utilizzabile più recente, come mostra la tabella. Inserisci l'ora come la mostra la console, nel fuso orario del server della console (vedi Fuso orario); l'agente la converte nel fuso orario del server di database.

Riga di comando

backupzit-agent sql list    [--instance SQLEXPRESS]
backupzit-agent sql backup  --repo ... [--instance I] [--db a,b] [--system] [--log] [--copy-only]
backupzit-agent sql restore --repo ... [--instance I] --db NAME [--as NEW] [--replace] [--at "2026-10-04 14:59:00"] SNAPSHOT|latest
backupzit-agent pg list     [--port 5432]
backupzit-agent pg backup   --repo ... [--port P] [--db a,b] [--pitr | --wal]
backupzit-agent pg restore  --repo ... --db NAME|"(cluster)" [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest
backupzit-agent mysql list
backupzit-agent mysql backup  --repo ... [--db a,b] [--binlog]
backupzit-agent mysql restore --repo ... --db NAME [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest

Non incluso

  • Backup differenziali di SQL Server e gruppi di disponibilità Always On; server di database remoti — l'agente salva i server della propria macchina.
  • Ripristino di singole tabelle: ripristina il database con un nuovo nome e copia le righe.
