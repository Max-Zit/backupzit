Macchine virtuali Hyper-V

BackupZit esegue il backup delle macchine virtuali Hyper-V tramite l'agente sull'host Hyper-V; nelle VM non viene installato nulla. I guest Windows e Linux vengono acquisiti mentre continuano a funzionare. Puoi ripristinarli come nuova VM o al posto dell'originale.

Configurazione

  1. Installa l'MSI dell'Agente Windows da Agenti sull'host Hyper-V e registralo. Host supportati: Windows Server 2016 o successivo con il ruolo Hyper-V, oppure Windows 10/11 con Hyper-V. In un cluster installa l'agente su ogni host.
  2. Entro un minuto l'host compare nella pagina Agenti con il badge Hyper-V · N VMs.
  3. In Job di backup seleziona quell'agente e scegli Macchine virtuali (Proxmox VE, Hyper-V, VMware). Poi scegli:
    • Tutte le VM (e i container) dell’host, che include anche le VM create in seguito;
    • Tutte le VM dell’host tranne quelle selezionate, ad es. senza la VM della console BackupZit; anche le VM create in seguito sono incluse;
    • singole VM, selezionandole.

L'agente lavora tramite le interfacce proprie di Hyper-V: il modulo PowerShell di Hyper-V e la Virtual Disk API di Windows. La console non memorizza credenziali Hyper-V.

Come viene salvata una VM

  1. Viene creato un checkpoint di ripristino temporaneo (backupzit_…). È il tipo di checkpoint che Hyper-V fornisce alle applicazioni di backup. Hyper-V chiede al guest di prepararsi:
    • I guest Windows svuotano i buffer delle applicazioni tramite VSS.
    • I guest Linux congelano i file system, se sono installati i daemon Hyper-V (hyperv-daemons / hv-vss-daemon).
    Se il guest non può fare né l'una né l'altra cosa, il checkpoint viene preso in modalità crash-consistent. La pagina dell'esecuzione mostra quale tipo è stato usato.
  2. Il checkpoint di ripristino attiva il Resilient Change Tracking (RCT) per i dischi della VM; accanto a essi vedrai file .rct e .mrt. Il primo backup legge i dischi interi. In seguito RCT indica quali blocchi sono cambiati dal backup precedente, e vengono letti solo quelli. Un disco ingrandito (per esempio con Resize-VHD) viene letto allo stesso modo: i blocchi modificati e lo spazio nuovo. Un disco ridotto viene letto per intero una volta.
  3. I dischi vengono letti allo stato del checkpoint, tramite la Virtual Disk API, in blocchi da 1 MiB. Ciò comprende file VHDX e VHD, incluse le catene di checkpoint precedenti. I blocchi vuoti non vengono memorizzati e i blocchi già presenti nel repository non vengono ricaricati. È la dimensione di blocco predefinita; un job può usare invece 256 o 512 KiB (vedete Job).
  4. Il checkpoint viene rimosso e Hyper-V lo unisce in background.
  5. La configurazione della VM viene salvata con il backup: generazione, CPU, memoria, schede di rete (switch, VLAN, indirizzo MAC), controller disco, avvio protetto e TPM.

Anche le VM spente ricevono un checkpoint di ripristino (agente 0.58), così il tracciamento delle modifiche legge solo ciò che è cambiato dal loro backup precedente, anche finché restano spente; dove Hyper-V non può crearne uno (per esempio nelle VM Replica), i loro dischi vengono letti direttamente. Sugli host senza checkpoint di ripristino si crea un checkpoint normale (di produzione quando possibile, altrimenti crash-consistent) e ogni backup legge i dischi interi.

I backup sovrapposti della stessa VM attendono il proprio turno su ogni host, sia dal servizio sia dalla riga di comando. Un backup elimina solo il proprio checkpoint temporaneo. L’agente rimuove un checkpoint rimasto quando il suo backup è terminato su un altro nodo (dopo una migrazione in tempo reale) o quando ha più di 48 ore (un backup interrotto da un arresto anomalo o da un’interruzione di corrente). Tutti i processi di backup sovrapposti devono usare programmi aggiornati.

Checkpoint rimasti. L'agente registra ogni checkpoint di backup prima di crearlo e cancella la registrazione solo quando il checkpoint non c'è più (dopo la rimozione elenca di nuovo i checkpoint della VM, fino a tre tentativi nell'arco di una decina di minuti). I checkpoint registrati vengono rimossi subito dopo un arresto anomalo o una rimozione non riuscita, all'avvio dell'agente e ogni 15 minuti, non solo dopo 48 ore; una VM usata da un backup non viene toccata. Se la VM è stata spostata su un altro nodo, il checkpoint lo rimuove l'agente di quel nodo. Se un backup viene annullato mentre Hyper-V sta ancora creando il suo checkpoint e ciò richiede più di cinque minuti, Hyper-V può aggiungerlo con il nome predefinito (il nome della VM e la data): l'agente rimuove quell'unico checkpoint di ripristino quando compare. Ciò che non si può rimuovere compare nella dashboard in Richiede attenzione con Rimuovi ora e viene notificato una volta.

Solo coerente con le applicazioni. Per Active Directory, SQL Server, Exchange e altri database, spunta Richiedi checkpoint coerenti con le applicazioni nel job (anche in un job per un cluster). Una VM in esecuzione viene allora salvata solo da un checkpoint preparato dal guest con VSS; se fallisce, la VM non viene salvata e l'esecuzione fallisce (con una notifica) invece di creare un checkpoint coerente con l'arresto anomalo. Le altre VM del job vengono comunque salvate e si possono ripristinare da quell'esecuzione. Controlla il servizio di integrazione Backup (volume shadow copy) nelle impostazioni della VM e VSS nel guest (vssadmin list writers). Richiede agenti 0.48.0 o successivi; con agenti più vecchi l'esecuzione fallisce chiedendo di aggiornarli.

Coerente con l’arresto, previsto. I guest che non possono preparare da soli un checkpoint (per esempio un vecchio Linux senza i demoni Hyper-V) si possono elencare nel job in VM per cui basta un checkpoint coerente con l’arresto, per nome o modello (legacy-*): il loro checkpoint coerente con l’arresto non è più un avviso, e la pagina dell’esecuzione indica comunque che lo era. Richiedi checkpoint coerenti con le applicazioni ha la precedenza. Richiede agenti 0.53.0 o successivi; quelli più vecchi continuano ad avvisare.

vTPM e BitLocker. Per le VM di generazione 2 con TPM virtuale il backup conserva anche il vTPM (il file di stato guest e la protezione della chiave). Ripristinata come nuova VM sullo stesso host, o su un host con il certificato guardian dell'host originale, la VM riottiene il suo vTPM e BitLocker non chiede la chiave di ripristino. Su altri host la VM riceve un vTPM nuovo e vuoto e il ripristino lo segnala; per evitarlo importa prima lì il certificato UntrustedGuardian dell'host originale. Il ripristino sopra la VM esistente ne conserva il vTPM. Le VM schermate (Host Guardian Service) non sono supportate. Conserva comunque le chiavi di ripristino di BitLocker.

Il controllo di integrità del repository verifica anche lo stato salvato del sistema guest. Dopo l’aggiornamento, controllare i repository e le copie esistenti: un aggiornamento non può recuperare uno stato guest già eliminato. Se manca, utilizzare una copia integra o creare un nuovo backup.

Esempio dal laboratorio di test: una VM Linux con un disco da 3 GB. Il primo backup ha letto 3 GB. Il successivo, dopo 64 MB di nuovi dati, ha letto 96 MB.

Su Windows 10/11 Hyper-V crea un checkpoint automatico all'avvio di una VM, a meno che l'opzione non sia disattivata nelle impostazioni della VM. BackupZit gestisce questi checkpoint, ma per i server conviene disattivare i checkpoint automatici (impostazioni della VM → Checkpoint).

Escludere dischi

I dischi dati salvati in altro modo possono essere esclusi: indicarli nel job in Escludi dischi, uno per riga, come modello di nome file (*-data.vhdx) o percorso completo (D:\VMs\SQL01\data.vhdx); maiuscole e minuscole non contano. La pagina dell’esecuzione mostra i dischi esclusi di ogni VM. Una VM ripristinata come nuova VM riceve solo i dischi salvati; un ripristino sul posto lascia i dischi esclusi collegati senza modifiche. Una VM con tutti i dischi esclusi non viene salvata. Gli agenti precedenti alla 0.49 non possono escludere dischi, quindi la console non avvia un job di questo tipo su di essi.

Ripristinare una VM

Apri l'esecuzione del backup della VM (dalla pagina del job o da Attività) e usa Ripristina una VM Hyper-V.

Come nuova VM accanto all'originale

Crea una seconda VM con nuovi indirizzi MAC, così può girare sulla stessa rete dell'originale. Per impostazione predefinita prende il nome dell'originale più "restored" e la data. I checkpoint automatici vengono disattivati su di essa (Windows li attiva per le nuove VM), così avviarla non lascia file di checkpoint. Se la copia gira accanto all'originale e contiene l'agente BackupZit, vedi Due macchine che usano lo stesso agente.

Le impostazioni di rete del guest legate a un indirizzo MAC non si applicano alle nuove schede. Un esempio è match: macaddress di netplan, usato dalle immagini cloud Linux.

Al posto della VM originale

Seleziona spegnila e sostituisci i suoi dischi. BackupZit quindi:

  • spegne la VM esistente;
  • unisce i suoi checkpoint;
  • sostituisce i suoi dischi con quelli ripristinati.

La VM mantiene ID, schede di rete e indirizzi MAC, quindi job, monitoraggio e rete del guest continuano a funzionare.

Prima di arrestare la VM originale o unire i suoi checkpoint, BackupZit ricostruisce tutti i dischi in una sottocartella univoca backupzit-restore-* della cartella scelta (quella originale dei dischi per impostazione predefinita). Gli errori di preparazione lasciano la VM invariata. I vecchi dischi mantengono i percorsi; eliminarli solo dopo aver verificato la VM ripristinata. Un errore dopo l’inizio della sostituzione può richiedere il recupero manuale: i dischi ricostruiti vengono conservati, l’errore indica la cartella e impostazioni e checkpoint non vengono ripristinati automaticamente.

Se la VM originale non esiste più, viene ricreata, con un nuovo ID Hyper-V.

Opzioni

  • Cartella per i dischi virtuali: la cartella predefinita dell'host o qualsiasi cartella che contenga dischi di VM. Un ripristino sul posto mette i nuovi dischi in una nuova sottocartella backupzit-restore-… e lascia quelli vecchi dove si trovavano.
  • Avvia la VM dopo il ripristino.

Cosa riceve una VM ripristinata

  • Gli switch virtuali vengono collegati per nome. Se uno switch non esiste sull'host, la scheda resta scollegata.
  • Ogni VM ripristinata riceve un nuovo ID di generazione, così i controller di dominio Active Directory rilevano il ripristino in sicurezza.

Cluster di failover

Le VM di un cluster di failover Hyper-V si salvano con un unico job per tutto il cluster. Tre passaggi:

1. Installare l'agente su ogni nodo

Installa l'agente Windows su ogni nodo del cluster (non dentro le VM). Una VM viene sempre salvata dall'agente del nodo su cui è in esecuzione in quel momento: i checkpoint e il tracciamento delle modifiche di Hyper-V funzionano solo lì. Finché una VM gira su un nodo senza agente non viene salvata; torna a esserlo appena passa a un nodo con l'agente.

2. La console riconosce il cluster da sola

Per il cluster non va configurato nulla, né in BackupZit né in Windows. Ogni agente (versione 0.47.0 o successiva) segnala il cluster di failover del suo nodo e quali VM sono in cluster. Circa un minuto dopo l'installazione o l'aggiornamento degli agenti:

  • la pagina Agents contrassegna ogni nodo con cluster NOME;
  • il cluster compare nel modulo del job (passo successivo), con il numero dei suoi nodi.

I nodi aggiunti in seguito al cluster vengono riconosciuti allo stesso modo ed entrano nel job automaticamente appena il loro agente è installato.

3. Creare il job per il cluster

  1. Apri Backup jobs e il modulo New backup job.
  2. Apri l'elenco Agent e vai in fondo: sotto Hyper-V failover clusters (virtual machines) scegli il cluster, ad es. HVC01 — 2 nodes. Scegli il cluster, non un singolo nodo.
  3. Il tipo è impostato su Virtual machines. Scegli All clustered VMs (anche le VM aggiunte in seguito al cluster), All clustered VMs except the ticked ones oppure Only these; accanto a ogni VM c'è il nodo su cui è in esecuzione ora.
  4. Scegli lo storage, la pianificazione e quanti backup conservare, poi fai clic su Create job.

La pagina del job mostra ogni nodo con il suo ultimo risultato; Run backup now on all agents li avvia tutti. Un nodo che in quel momento non esegue nessuna VM del job segnala None of the job's VMs runs on this node now: è un successo.

Job di VM creati prima per singoli nodi: disattivali o eliminali dopo il primo backup del job del cluster, altrimenti le VM del cluster vengono salvate due volte; i loro backup restano sullo storage. Le VM fuori dal cluster (appartengono a un nodo) non fanno parte del job del cluster; salvale con un job di quel nodo.

Come funziona

  • Ogni nodo salva le VM del cluster che sta eseguendo in quel momento, tutte in un unico repository del cluster sullo storage.
  • Quando una VM passa a un altro nodo (migrazione live o failover), la sua cronologia continua lì e Resilient Change Tracking legge ancora solo i blocchi modificati: nessun nuovo backup completo.
  • Una VM spostata durante il backup viene comunque salvata per intero. Il nodo su cui è stata spostata rimuove il checkpoint del backup entro pochi minuti, quando il backup ha finito di leggere; l'esecuzione segnala che la VM è stata spostata.

Ripristino

  • Al posto dell'originale viene eseguito sul nodo che possiede la VM in quel momento (la console lo sceglie). La VM viene arrestata e avviata tramite il cluster, così il cluster non scambia l'arresto per un guasto.
  • Come nuova VM: scegli una cartella su un Cluster Shared Volume (C:\ClusterStorage\…). Anche la configurazione della VM va lì e la VM viene aggiunta al cluster come ruolo.

Ripristinare singoli file

Nella tabella delle VM dell'esecuzione, fai clic su Sfoglia file per vedere partizioni e volumi sui dischi della VM. Puoi sfogliare NTFS, ext2/3/4 e XFS, anche dentro LVM. Da lì puoi scaricare file o ripristinarli su qualsiasi agente. Funziona esattamente come per Proxmox VE.

Riga di comando

Esegui questi comandi sull'host Hyper-V, come amministratore:

Il ripristino Hyper-V dalla riga di comando acquisisce un blocco condiviso del repository prima di selezionare lo snapshot e lo mantiene fino alla fine del ripristino. Attende il completamento della manutenzione con blocco esclusivo; se non riesce ad acquisire il blocco, termina con un errore senza modificare la VM.

backupzit-agent hyperv list
backupzit-agent hyperv backup  --repo ... [--vmid N,N]
backupzit-agent hyperv restore --repo ... --vmid N [--new] [--name NAME] [--folder D:\VMs] [--overwrite] [--start] SNAPSHOT|latest
  • --vmid è il numero mostrato da hyperv list. BackupZit lo ricava dal GUID della VM.
  • Senza --new, la VM viene ripristinata sul posto.
  • --overwrite conferma che i dischi di una VM esistente vanno sostituiti.

Le opzioni del repository sono le stesse di tutti i comandi; vedi Riferimento della riga di comando.

Non ancora incluso

  • Alcuni tipi di disco. VHDX condivisi, VHD Set e dischi pass-through non vengono salvati. L'esecuzione avvisa per ciascuno, e un ripristino sul posto li lascia collegati senza modifiche.

Diagnosi delle letture complete

Il registro dell’agente (Agenti → Ottieni registro) e l’output CLI riportano hyperv disk read per ogni disco con vm_id, disk, mode (full o incremental), reason e disk_bytes. Dopo una lettura riuscita, hyperv disk read complete aggiunge bytes_read: byte letti dalla sorgente in blocchi interi, non trasferiti dopo la deduplicazione. Il primo backup o il tracciamento non disponibile possono richiedere una lettura completa; una VM spenta viene letta in modo incrementale dall’agente 0.58 in poi (prima, ogni backup rileggeva tutto ciò che era cambiato dall’ultima volta in cui la VM era in esecuzione). Gli errori dell’API RCT compaiono in error e causano una lettura completa sicura; questo da solo non fa fallire il backup né aggiunge un avviso. Un disco sostituito può causare un errore di query RCT, ma l’errore non prova la sostituzione. Codici motivo:

rct_not_requested · rct_state_failed · rct_disabled · no_previous_backup · disk_size_changed · previous_id_missing · rct_query_failed · rct_changes
