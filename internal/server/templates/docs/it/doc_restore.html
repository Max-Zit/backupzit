Ripristino

Ogni backup riuscito può essere ripristinato: per intero o solo alcune cartelle, sulla stessa macchina, su un altro agente o come nuova macchina virtuale.

La procedura guidata di ripristino

Fate clic su Ripristina nel menu. La procedura pone quattro domande:

  1. Cosa volete ripristinare?
    • un'intera macchina virtuale
    • file da una macchina virtuale
    • file e cartelle
    • un'immagine disco / bare metal
    • file da un'immagine disco
    • un database (a un momento preciso)
    • un intero sistema Linux
    • posta di Microsoft 365, OneDrive, calendari e contatti e file di SharePoint (vedete Microsoft 365)
    Ogni scelta mostra quanti punti di ripristino esistono.
  2. Origine: la macchina virtuale (su tutti gli hypervisor e i job), oppure il job di backup e la sua macchina.
  3. Punto di ripristino: il backup da cui ripristinare, prima il più recente, con stato, storage e dimensione.
    • I backup segnalati come sospetti (possibile ransomware) sono contrassegnati.
    • Le copie su uno storage secondario create da un job di copia di backup sono elencate come copia (backup di file e di VM).
  4. Opzioni: dove e come ripristinare. Sopra le opzioni viene mostrato un riepilogo delle scelte.

I passaggi in alto sono link, quindi potete tornare a qualsiasi passaggio precedente. Ogni passaggio ha un proprio indirizzo, così potete aggiungerlo ai preferiti o condividerlo.

Le opzioni sono le stesse della pagina di un backup in Attività, dove potete anche avviare direttamente un ripristino. Vedono la procedura guidata solo gli utenti il cui ruolo consente il ripristino.

Ripristinare da un backup di file

  1. Scegliete File e cartelle nella procedura guidata di ripristino, poi il job e il punto di ripristino. In alternativa aprite il backup in Attività o nella pagina del job.
  2. In Ripristina file da questo backup scegliete l'agente che riceverà i file. Può essere una macchina diversa da quella salvata — ad esempio un PC sostitutivo.
  3. Scegliete dove:
    • Ripristina in una cartella (consigliato) — ad es. D:\Restore. Al suo interno viene ricreata la struttura originale: D:\Restore\C\Users\ana\Documents\…. Nulla di esistente viene toccato.
    • Ripristina nella posizione originale — riscrive i file dove si trovavano, sovrascrivendo le versioni attuali. Per una condivisione NAS l'agente ricollega la condivisione in scrittura. I file sparse (immagini di VM, database) tornano sparse. Su Windows viene contrassegnato di nuovo come sparse solo un file che lo era; gli altri, come i dischi VHD/VHDX (Hyper-V rifiuta quelli sparse), tornano come file normali, così come tutti i file dei backup creati con agenti precedenti alla 0.57, che non registravano l'attributo. Non si scrive mai attraverso un collegamento simbolico o una giunzione (junction) che si trova sul percorso: il ripristino in una cartella lo sostituisce con una cartella, e ogni ripristino scrive solo nelle cartelle che ha aperto, anche se un collegamento compare mentre è in corso (0.58: anche per i backup di file e nella posizione originale; la radice di un volume come / o C: non si può scegliere come cartella per i file da backup di VM e di immagine). Nella posizione originale si seguono solo i collegamenti del sistema (di proprietà di root o dell'utente dell'agente su Linux, di SYSTEM, TrustedInstaller o di un amministratore su Windows, e che nessun altro può modificare o sostituire: i vecchi collegamenti di compatibilità nei profili utente come Application Data non vengono seguiti); un collegamento a una cartella che non esiste è un errore e nel punto a cui rimanda non viene creato nulla. Proprietario, permessi e attributi vengono impostati sul file ripristinato stesso, mai attraverso un collegamento messo al suo posto. Dalla 0.59 un tale collegamento deve anche avere un solo nome: un collegamento fisico a esso, che un altro utente potrebbe creare, non viene seguito.
  4. Facoltativamente limitate a Solo questi percorsi, uno per riga, ad es. C:\Users\ana\Documents\Contracts — oppure selezionateli nel browser dei file (sotto).
  5. Lasciate attivo Verifica i file ripristinati: ogni file viene riletto e confrontato con il checksum del backup.
  6. Fate clic su Avvia ripristino. Avanzamento e risultati compaiono nella pagina dell'esecuzione di ripristino.

Vengono ripristinati anche gli orari dei file, gli attributi di Windows (nascosto, sola lettura, …) e, su Linux, proprietari, permessi (inclusi i bit setuid), ACL, attributi estesi (etichette SELinux, capability dei file), link simbolici e fisici. Su macOS anche i flag di file BSD (nascosto, bloccato…), la data di creazione e gli attributi estesi (vedete Agenti macOS). I proprietari vengono impostati solo se l'agente è eseguito come root/amministratore.

Sfogliare, scaricare e scegliere file

Nell'esecuzione di backup, Sfoglia file mostra le cartelle salvate com'erano (anche per condivisioni NAS e backup del sistema Linux). Aprite le cartelle, selezionate file e cartelle, poi:

  • Scarica — un file arriva così com'è, più file o cartelle come archivio ZIP, direttamente nel browser. I download vengono registrati nel log di audit.
  • Ripristinali su un agente — in una cartella o nella posizione originale, come un ripristino con Solo questi percorsi.

Inizio del backup, all'inizio del percorso, riporta al primo livello, e la riga .. in cima all'elenco sale di una cartella; la navigazione dei file in un disco di VM funziona allo stesso modo.

Un link simbolico a un file (ad es. /etc/os-release) viene scaricato come il file a cui punta, se quel file è nel backup; i link a cartelle vengono esclusi dagli archivi ZIP. Lo stesso vale per i file scaricati dai backup di macchine virtuali (ext4, XFS, btrfs). Un ripristino su un agente ricrea i link come link.

La console legge il backup dallo storage da sola, quindi la navigazione funziona per i backup su storage di rete (SFTP, S3, SMB, Azure, repository rafforzato); lo storage raggiungibile solo dagli agenti viene letto tramite un agente che lo usa (agenti 0.61 e successivi). Per un disco locale o un disco USB di un agente, ripristinate con i percorsi. Gli utenti con un ruolo di ripristino possono sfogliare e scaricare.

Trovare il backup giusto: usate il Calendario per vedere quali backup sono stati eseguiti in quale giorno, o lo storico nella pagina del job.

Ripristinare singoli file da un'immagine disco

Per i backup di immagine, fate clic su Sfoglia file nell'esecuzione di backup. Potete navigare il file system NTFS dell'immagine direttamente nella console, selezionare file e cartelle e ripristinarli su qualsiasi agente — senza ripristinare l'intero disco. Ripristinati in una cartella, i file hanno la stessa struttura di un backup di file: la lettera di unità diventa la prima cartella (D:\Restore\C\Users\…).

Potete anche scaricare i file selezionati direttamente nel browser: un file arriva così com’è, più file o cartelle in un archivio ZIP — comodo per un singolo documento da un grande backup di immagine. Come la navigazione, funziona per i backup di immagine su storage di rete, richiede l’autorizzazione Ripristino, e il registro di audit annota quali percorsi sono stati scaricati.

Ripristinare singoli file da una VM (Proxmox VE, Hyper-V, VMware)

In un'esecuzione di backup di VM fate clic su Sfoglia file accanto al guest. La console mostra le partizioni e i volumi LVM dei suoi dischi e permette di sfogliare i file system NTFS, ext4, XFS e btrfs. Scaricate i file selezionati (più file come archivio ZIP) o ripristinateli su qualsiasi agente. Vedete Proxmox VE, Hyper-V e VMware ESXi. I file ripristinati su un agente mantengono i permessi Unix che avevano nella VM (ext4, XFS, btrfs), quindi i segreti ripristinati come /etc/shadow restano privati; su Linux i file dei volumi NTFS sono leggibili solo dal proprietario. Ripristinati su un agente Windows, i nomi con : provenienti da guest Linux (ext4, XFS, btrfs) vengono saltati ed elencati: Windows leggerebbe la parte dopo i due punti come un flusso di un altro file. I flussi di dati alternativi NTFS vengono ripristinati come flussi.

btrfs viene mostrato come appare con il sottovolume di primo livello montato: sottovolumi e snapshot sono cartelle nel punto in cui sono collegati (in uno snapshot, un sottovolume che si trovava nell'originale è una cartella vuota, come su Linux). I file compressi con zstd, LZO o zlib si leggono come tutti gli altri. Si può sfogliare solo btrfs su un disco: per un file system distribuito su più dischi (RAID btrfs o dispositivi aggiunti) la console mostra un errore; avvia la VM con il ripristino istantaneo e copia i file da lì.

Ripristinare intere macchine

  • Immagini disco Windows: su un disco o bare metal, anche su hardware diverso — Immagini disco.
  • Sistemi Linux: su un disco o bare metal, o come nuova VM Proxmox — Backup del sistema Linux.
  • VM e container Proxmox: come nuovo guest o sul posto — Proxmox VE. Le VM Proxmox possono anche essere eseguite istantaneamente dal backup e spostate su uno storage mentre sono in funzione (ripristino istantaneo).
  • Database (SQL Server, PostgreSQL, MySQL/MariaDB): con un nuovo nome o sul posto, a un momento preciso — Database.
  • VM Hyper-V: come nuova VM o sul posto (mantiene ID e indirizzi MAC) — Hyper-V.
  • VM VMware ESXi: come nuova VM o sul posto (mantiene UUID e indirizzi MAC), su qualsiasi host ESXi e datastore — VMware ESXi; anche istantaneamente dal backup tramite un agente proxy Linux, poi copiata su un datastore (ripristino istantaneo).

ISO di ripristino

I ripristini bare metal avviano la macchina da una ISO di ripristino (su una chiavetta USB o collegata a una VM), vedete Supporti di ripristino:

  • ISO di ripristino Linux — pubblicata con ogni versione (backupzit-recovery-linux.iso); la pagina Supporti di ripristino la collega dalla fonte degli aggiornamenti.
  • ISO di ripristino Windows — Windows PE non può essere ridistribuito, quindi si crea una volta su qualsiasi PC Windows 10/11 o Server:
    1. Installate il Windows ADK gratuito (funzionalità Deployment Tools) e il componente aggiuntivo Windows PE di Microsoft.
    2. Scaricate build-winpe.ps1 dalla versione (accanto ai pacchetti dell'agente) e prendete backupzit-agent.exe da C:\Program Files\backupzit Agent di una macchina con l'agente.
    3. In un PowerShell da amministratore: .\build-winpe.ps1 -AgentExe .\backupzit-agent.exe -Out .\backupzit-recovery.iso. Aggiungete -DriverDir C:\Drivers per driver di storage o di rete (ad es. VirtIO per le VM Proxmox) e -RecoveryJson .\recovery.json perché si colleghi senza digitare nulla.
    4. All'avvio la ISO cerca \backupzit\recovery.json su ogni unità. Se il file c'è, l'agente di ripristino si collega a questa console e il ripristino viene avviato da qui, così sul posto basta avviare la chiavetta. Altrimenti si apre il programma grafico di ripristino (backupzit-recovery.exe, installato accanto all'agente): ripristinare un'immagine disco o singole partizioni, anche su un disco più piccolo o più grande, riparare l'avvio, caricare driver. Il prompt dei comandi del supporto avvia l'altro (backupzit-recovery o backupzit-agent recovery). Con -AccessPackage .\backupzit.bzaccess (creato in Supporti di ripristino) il programma apre i backup senza questa console; serve solo la passphrase. Questa richiede 12 caratteri di tre tipi (16 di due, 20 di uno), e le password comuni vengono rifiutate; la pagina ne propone una generata che si digita allo stesso modo su tastiere QWERTY, QWERTZ e AZERTY.
    5. Lingua e tastiera di Windows PE sono quelle del PC che crea la ISO, come il fuso orario (-Language de-de, -KeyboardLayout e -TimeZone ne scelgono altri), così un indirizzo del server o una passphrase si digita come su quel PC. Il programma di ripristino parla le 14 lingue della console. -NoUi include solo l'agente da console. Il supporto contiene i testi delle licenze e SOURCE-CODE.txt in \backupzit\.
    6. Prima di scrivere, il programma controlla di nuovo il disco di destinazione per dimensione, modello, numero di serie e ID della tabella delle partizioni: un disco che nel frattempo ha ricevuto il numero scelto (un disco USB ricollegato) viene rifiutato, come i dischi con i backup, il supporto di ripristino e un pacchetto di accesso. Un ripristino sul disco originale mantiene il layout del backup quando ci sta (nessuna partizione si estende in uno spazio vuoto); Adatta al disco di destinazione viene proposto per un disco più piccolo o quando lo si sceglie. Un disco convertito in GPT o MBR non può restare offline. Se il disco salvato è ancora nel computer (un altro disco con lo stesso ID disco), il programma e image-restore avvisano prima di scrivere: Windows lascia offline la copia finché entrambi i dischi sono presenti, quindi una partizione che cresce viene estesa solo dopo aver rimosso il vecchio disco (in Gestione disco); seleziona Lascia offline il disco di destinazione. Quando una partizione non può essere ridotta (per esempio una copia non spenta correttamente), la pagina delle dimensioni e i messaggi su un disco troppo piccolo ne indicano il motivo. La riparazione dell'avvio salva prima i dati di avvio in \backupzit su un'altra unità.
    7. Il programma si usa anche solo con la tastiera (Tab, Invio, Spazio, Esc) e funziona su schermi fino a 800×600, dove le sue pagine scorrono. Il riepilogo indica in rosso il disco che verrà cancellato (numero, modello, dimensione); il ripristino parte solo dopo aver digitato quel numero. Una posizione SFTP senza pacchetto di accesso mostra la chiave host del server e chiede prima di fidarsene: confrontala con ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub sul server.
    8. Facoltativamente copiate la ISO nella directory /var/lib/backupzit/dist della console; viene allora offerta nella pagina Supporti di ripristino.

Sfogliare i file nella console funziona per i backup su storage di rete (SFTP, S3, SMB, Azure, repository rafforzato): la console li legge direttamente o, per lo storage raggiungibile solo dagli agenti, tramite un agente che lo usa (anche con una chiave SSH; agenti 0.61 e successivi). Per i backup su un disco locale di un agente o su SFTP con una chiave SSH, un ripristino con Solo questi percorsi funziona ancora dalla console; per guardarci dentro, usate la riga di comando.

Ripristinare senza la console

Se la console stessa va persa, qualsiasi macchina con l'agente installato può ripristinare direttamente dallo storage usando il foglio di ripristino della destinazione di archiviazione:

set BACKUPZIT_PASSWORD=<recovery key>
set BACKUPZIT_SFTP_PASSWORD=...           (or the S3/SMB/hardened credentials)
set BACKUPZIT_SFTP_HOSTKEY=SHA256:...      (the SFTP host key, on the recovery sheet)
backupzit-agent snapshots --repo sftp://backup@nas:22/backups/pc1_1a2b3c4d
backupzit-agent restore   --repo sftp://backup@nas:22/backups/pc1_1a2b3c4d --target D:\Restore latest

latest è il backup più recente di qualsiasi job di quel computer; per ripristinare un job specifico usate un ID di snapshot ottenuto con snapshots. Vedete Riferimento della riga di comando.

Test di ripristino automatici

BackupZit mette alla prova i vostri backup regolarmente senza che dobbiate fare nulla: ogni settimana (configurabile in Impostazioni → Test di ripristino) l'agente di ogni job ripristina un campione casuale di file dal backup più recente in una cartella temporanea, verifica ogni byte rispetto ai checksum memorizzati e lo elimina. Per le immagini disco vengono letti e verificati blocchi casuali. Così si mette alla prova l'intera catena — accesso allo storage, credenziali, chiave di cifratura e integrità dei dati.

  • I risultati compaiono in Attività e nello storico del job come esecuzioni di tipo Test di ripristino, e per job in Report (colonna Test di ripristino).
  • Un test fallito è un errore come gli altri e genera un avviso via email.
  • Testa ripristino nella pagina di un job avvia subito un test.
  • La dimensione del campione limita quanto viene letto dallo storage — tenetela piccola per uno storage cloud con costi di download.

Test di avvio per le VM Proxmox

Blocchi leggibili non dimostrano che una VM si avvii ancora. Con Test di avvio per i backup delle VM Proxmox attivo (Impostazioni → Test di ripristino), il test di ripristino di un job di VM Proxmox avvia anche ogni VM del backup più recente sul nodo del job, una dopo l'altra, con il ripristino istantaneo: viene eseguita dal backup con un nuovo ID e le schede di rete scollegate (così non entra in conflitto con l'originale) e viene eliminata subito dopo. Il test è superato quando l'agente guest QEMU della VM risponde entro il tempo configurato, il che significa che il sistema operativo si è avviato. Le VM senza agente guest superano il test se restano in esecuzione per un minuto; la pagina dell'esecuzione le mostra come in esecuzione invece di avviata. La copia tralascia anche le impostazioni che arrivano fuori dalla VM: uno script hook, gli argomenti QEMU grezzi (args), i dispositivi PCI e USB passati alla VM, le condivisioni dell'host (virtiofs) e le porte seriali o parallele su dispositivi dell'host; la pagina dell'esecuzione indica cosa è stato tralasciato. Una VM che non può avviarsi senza di essi non supera il test di avvio.

  • Durante il test il nodo ha bisogno di memoria libera per una VM in più.
  • Installate l'agente guest QEMU nelle VM (qemu-guest-agent su Linux, gli strumenti guest VirtIO su Windows) e abilitatelo nelle opzioni della VM, così il test può confermare l'avvio.
  • La pagina dell'esecuzione elenca ogni VM con il risultato e il tempo impiegato dall'avvio.

Controlli dentro la VM (agenti 0.61 e successivi): una VM che si avvia può comunque essere guasta, o già compromessa quando è stato fatto il backup. In un job di VM Proxmox, Controlli del test di avvio elenca ciò che deve funzionare nella copia avviata, uno per riga: service sshd (il servizio è in esecuzione), file /var/www/index.html (il file esiste), port 443 (un programma è in ascolto sulla porta TCP) o command … (un vostro comando termina con codice di uscita 0; sh su Linux, cmd su Windows). Una riga che inizia con un ID VM e i due punti, ad es. 101: service nginx, vale solo per quella VM. I controlli vengono eseguiti tramite l’agente guest QEMU come root o SYSTEM nella copia isolata e ripetuti finché non riescono o finisce l’attesa del test di avvio; la pagina dell’esecuzione li mostra uno per uno. Li impostano solo gli utenti che possono modificare i comandi.

Testare l’avvio anche del backup più vecchio conservato dal job avvia anche le VM del punto di ripristino conservato più vecchio, così sapete che il punto a cui tornereste dopo una compromissione non notata si avvia ancora. Un backup di VM le cui VM si sono avviate e hanno superato i controlli è contrassegnato come verificato nella sua pagina di esecuzione, da cui si ripristina.

Verifica di tutti i dati archiviati

I test di ripristino leggono un campione. Inoltre un agent legge tutti i dati di ogni repository, li verifica con il loro checksum e controlla che cartelle e dati di ogni backup siano presenti — una volta al mese per impostazione predefinita (Impostazioni → Test di ripristino: Verifica i dati archiviati: mensile, ogni tre mesi o mai). Così si trovano danni sull'archiviazione stessa, come un disco che si guasta in un NAS o il degrado dei dati, prima che serva il backup. Ogni repository viene verificato una volta (i job di un agent su un'archiviazione lo condividono), dall'agent che vi scrive. La verifica legge tutto ciò che il repository contiene; sull'archiviazione cloud (S3, Azure) parte quindi solo con Anche sull'archiviazione cloud. I problemi fanno fallire l'esecuzione Verifica dei dati e inviano una notifica di errore; Verifica i dati nella pagina di un job avvia subito una verifica. Richiede agent 0.39.0 o successivi. Su S3, Azure e storage protetto la verifica legge più pacchetti di dati alla volta (agent 0.54.2 e successivi). Mentre una verifica è in corso, Attività e la sua pagina di esecuzione mostrano quanti pacchetti di dati del repository ha già verificato. Una verifica che trova pacchetti di dati danneggiati offre Riparazione nella pagina della sua esecuzione (Risoluzione dei problemi).

In aggiunta, ripristinate a mano di tanto in tanto (ad es. ogni trimestre) una cartella reale e aprite qualche file — così si addestrano anche le persone che dovranno farlo in caso di emergenza.
