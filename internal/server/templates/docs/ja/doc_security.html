セキュリティとベスト プラクティス

BackupZit がデータとコンソールをどのように保護しているか、そしてお客様の側で行うべきこと。

組み込みの保護

  • 送信元での暗号化 — エージェント内で AES-256-GCM。ストレージには暗号化されたデータしか見えません。キーは Argon2id で導出されます。
  • ピン留めされた接続 — エージェントはコンソールの証明書をピン留めします。SFTP のホスト キーと強化リポジトリの証明書もピン留めされます。どの認証局を悪用してもなりすましはできません。
  • ブラウザー向けの信頼された証明書 — 任意で、アップロードした証明書または Let's Encrypt 証明書（TLS 1.2+）を別のアドレスで使用し、自動更新します。サーバーのインストール を参照してください。
  • 保存時のシークレット — ストレージのパスワードとキー、リカバリー キー、SMTP/LDAP のパスワード、2 要素のシークレットは、データベースの外に置かれたキー（secrets.key）でデータベース内に暗号化されます。
  • エージェントのシークレット — 各エージェントは独自のシークレットを持ち、コンソールにはハッシュとしてのみ、エージェントには管理者だけが読めるファイルに保存されます。
  • Web コンソール — HttpOnly、SameSite=Strict のセッション Cookie、クロスサイト リクエストとクリックジャッキングへの保護、厳格な Content-Security-Policy、bcrypt でハッシュ化されたパスワード。機密性の高いページはキャッシュされません。
  • ブルートフォース対策 — サインインの失敗が多すぎるアドレスはブロックされます: パスワード、2 要素コード、API トークンが対象です。ブロックは再起動後も維持され、繰り返す違反者はより長くブロックされ、管理者にメールが届きます。後述を参照してください。
  • アカウント — 最小権限のロール、任意の 2 要素認証（TOTP）、LDAPS サインイン。API トークンは独自の、より低いロールと有効期限を持ちます。
  • 4 つの目による承認（任意）— ジョブの削除や無効化、エージェント、ESXi ホスト、ストレージ先、ユーザーの削除、保持期間の短縮、承認のオフ、そして 1 人の管理者に 2 人目の承認者を与えかねないあらゆる操作（新しい承認者、より多くの権限、パスワードと 2 要素のリセット、LDAP と SSO の変更）には、2 人目のユーザーの承認が必要です。ユーザー、ロール、LDAP を参照してください。
  • 監査証跡 — サインイン、失敗したサインイン、ユーザーとロールの変更、ジョブ、ストレージ先、復元、表示されたリカバリー キー、設定の変更、API 操作は 監査ログ に記録されます。エントリは連鎖しているため、データベース内での変更や削除が検出され、syslog サーバーや SIEM にコピーできます（改ざんからの保護）。強化リポジトリでの削除はそのサーバーに記録されます。
  • コンソールの更新 — リリースは BackupZit のリリース キー（Ed25519）で署名されています。コンソールと、それをインストールする root サービスの両方が署名を検証し、先にデータベースをバックアップし、失敗した更新はロールバックされます。
  • エージェントの更新 — エージェントは、ピン留めされた接続を通じて自分のコンソールからのみ新しいバージョンをダウンロードし、SHA-256 チェックサムが一致した場合にのみインストールします。
  • ローカルの状態チャネル — トレイ アプリは、ローカルの名前付きパイプ（Windows）または root 専用のソケット（Linux）を介してエージェント サービスと通信します。マシンにサインインしているユーザーは、状態を読み取り、そのマシン自身のバックアップ ジョブを開始できますが、それ以外はできません（ジョブ、スケジュール、ストレージ、復元はコンソールでのみ管理されます）。
  • ハイパーバイザーのバックアップ — Proxmox や Hyper-V ホスト上のエージェントはホスト自身のツールを使うため、ハイパーバイザーのパスワードは保存されません。VMware ESXi では、コンソールがホストのパスワードを暗号化して保存し、HTTPS 証明書と SSH ホスト キーをピン留めし、接続はそのホストのプロキシ エージェントの実行時にのみ渡します。
  • バックアップの整合性 — 各チャンクは復元時に SHA-256 ハッシュで検証されます。自動復元テストとランサムウェア検出がバックアップを継続的に監視します。

ブルートフォース対策

設定 → サインインとセキュリティ で設定します。既定値はほとんどの環境で安全です:

設定既定値意味
アドレスごとの失敗回数5集計期間内に 1 つの IP アドレスからのサインインが失敗すると、そのアドレスをブロックします。誤ったパスワード、誤った 2 要素コード、無効な API トークンが数えられます。
集計期間15 分これより古い失敗は忘れられます。
ブロック時間30 分ブロックされたアドレスは正しいパスワードでもサインインできません。サインイン ページは「サインインの失敗が多すぎます」と応答し、API は HTTP 429 を返します。
繰り返す違反者は長くブロックオン同じ日のうちにアドレスがさらにブロックされるたびに、期間が 2 倍になります: 30 分、1 時間、2 時間、… 最大 7 日。
ユーザー名ごとの失敗回数20任意のアドレスから 1 つのユーザー名に対する失敗が続くと、集計期間が過ぎるまでそのユーザー名でのサインインを一時停止します。多数のアドレスに分散した推測を止めます。アカウントが恒久的にロックされることはないため、攻撃者が管理者を締め出すことはできません。
これらのネットワークはブロックしないなしブロックしない任意のネットワーク（例: 管理者のサブネット）。ユーザー名ごとの上限は引き続き適用されます。
リバースプロキシなしコンソールが nginx、Traefik などのプロキシの背後で動作している場合は、そのアドレスを入力します: クライアントのアドレスは X-Forwarded-For から取得されます（そうしないとすべてのクライアントがプロキシに見えます）。プロキシが X-Forwarded-Proto: https を送ると、サインイン Cookie は Secure になります。両ヘッダーはほかのアドレスからは無視されるため、偽装できません。
アドレスがブロックされたときにメールオンメール設定 の受信者に送信されます。

同じページに、ブロックされたアドレスが理由と期間とともに表示され、ブロックを解除できます。ブロックと解除は 監査ログ に記録されます。

自分自身を締め出してしまった場合は、別のアドレスからサインインするか、サーバー上でサービスと同じデータベース オプションを付けて次を実行します:

backupzit-server --unblock-ip all

1 つのブロックだけを解除するには、all の代わりにアドレスを指定します。

Web コンソールへのアクセス（パブリック アドレス）

エージェントはポート 8443 でコンソールに接続します。他拠点や顧客先のエージェントのためにコンソールをパブリック アドレスで公開しつつ、Web コンソールを開けるのは管理者だけにするには、設定 → サインインとセキュリティ → Web コンソールへのアクセス を使います:

設定効果
許可するアドレスIP アドレスまたはネットワーク（例: 203.0.113.10、10.0.0.0/24）。Web コンソール、REST API、すべてのページはこれらのアドレスにのみ応答し、ほかのアドレスにはコンソールが存在しないかのように「not found」を返します。エージェントは常に自分の API（登録、ポーリング、結果、ダウンロード、プッシュ インストール）に到達できます。空欄: 全員。自分のアドレスを含まない一覧はコンソールが拒否します。
ポート 8443 はエージェント専用Web コンソールは信頼された証明書を持つ Web ポート（設定 → 証明書、通常 443）でのみ利用可能になるため、ファイアウォールで 8443 を全員に、443 を自社のアドレスだけに開放できます。Web ポートが動作してから利用できます。8443 ではなく Web ポートから変更してください。

パブリックなコンソールの典型的なファイアウォール: 8443 は全員に開放（エージェント）、443 と 80（Let's Encrypt の HTTP 確認）は自社のアドレスからのみ、SSH は自社のアドレスからのみまたは無効、それ以外はすべて閉じる。

締め出されましたか？ サーバー自体（localhost）では、コンソールは常に応答します。アプライアンスでは、画面上のセットアップ メニューの項目 5 でサインインのブロックとこれらの制限を解除できます。

推奨事項

コンソール

  • コンソールは社内ネットワークに置き、ポート 8443 をインターネットに公開しないでください。リモート管理には VPN を使います。
  • 長く一意な管理者パスワードを使い、初期パスワードは変更してください。
  • 管理者に 2 要素認証 を必須にします（設定 → サインインとセキュリティ）。
  • 各人に、機能する最も低いロールの専用アカウントを与えます。監視には閲覧者ロールの API トークンを使います。
  • secrets.key はデータベースとは別にバックアップします（サーバーのインストール）。
  • 設定 → サインインとセキュリティ で、適切なセッションの長さを選びます（短いほど安全です）。
  • サーバーは PostgreSQL を含めて最新に保ちます（apt upgrade / dnf upgrade）。

ストレージ

  • 各ストレージ先に、バックアップ用のフォルダーやバケットだけにアクセスできる専用アカウントを与えます。
  • バックアップ用ストレージを Windows ドメインに参加させず、ほかで使っていない資格情報を使います。
  • 少なくとも 1 つの変更不可のコピー（S3 Object Lock または強化リポジトリ）と 1 つのオフサイト コピーを保持します。

キー

  • リカバリーシートはオフラインで保管します。これがないと、コンソールを失ったときに暗号化されたバックアップを復元できません。
  • リカバリーシートだけを使ってコマンドラインからの復元を一度テストし、手順が機能することを確認します。
  • recovery.json を入れた USB メモリーは鍵と同様に扱います: リカバリー コードの有効期限（30 日）までは、マシンをリカバリー エージェントとしてコンソールに参加させられます。古い USB メモリーを保管するのではなく、必要なときに新しいコードを作成してください。
  • リカバリー ISO は、そこから起動した人に root / 管理者のコマンドラインを与えます — ほかの起動メディアと同じです。サーバーはファームウェア（BIOS/UEFI）のパスワードとセキュア ブートの設定で保護してください。

エージェントとハイパーバイザー

  • コンソールはエージェントにソフトウェアをインストール（エージェントの更新）し、データを復元できます。それに応じて管理者アカウントを保護してください: 2 要素認証、少数の管理者。
  • VM ディスクのファイルは参照時にコンソールとエージェントが解析します。破損した、または悪意のあるファイル システム データはクラッシュではなくエラーになります。

セキュリティ上の問題の報告

脆弱性は公開の issue を作成するのではなく、BackupZit のメンテナーに非公開で報告してください。
