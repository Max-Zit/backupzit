サーバーのインストール

コンソールは PostgreSQL とともに Linux（Debian、Ubuntu、AlmaLinux、Rocky Linux）上で動作します。各組織は自社のネットワークで自社のコンソールを運用します。

要件

  • Linux の VM またはサーバー: 2 vCPU、2～4 GB RAM、20 GB のディスクで数百のエージェントに十分です（バックアップ データはそこに保存されません）。
  • PostgreSQL 13 以降（ローカルまたは別のサーバー）。
  • ネットワーク: エージェントは TCP 8443（HTTPS）でコンソールに到達できる必要があります。エージェントはストレージにも直接到達できる必要があります。

インストール方法の選択

方法適した用途必要なもの
1. 既製の VM イメージ（OVA、qcow2、VHDX）最速: インポート、起動、サインインVMware、Proxmox/KVM、Hyper-V。インターネット アクセス不要
2. アプライアンス ISO新しい VM または物理サーバー、無人インストールインストール中のインターネット アクセス（Debian パッケージ）
3. インストール スクリプト既存の Debian、Ubuntu、AlmaLinux、Rocky Linux サーバーroot とインターネット アクセス
4. パッケージを手動で独自の PostgreSQL、構成管理、インターネット アクセスなしリリースのサーバー パッケージ

1. 既製の VM イメージ

1 分以内に起動し、インターネット アクセスを必要としない完成済みのアプライアンス（Debian、PostgreSQL、コンソール、自動セキュリティ更新）:

ハイパーバイザー方法
VMware ESXiHost Client: Create / Register VM → Deploy a virtual machine from an OVF or OVA file で backupzit-appliance.ova を選択。vSphere: Deploy OVF Template。Workstation と VirtualBox: File → Open / Import。
Proxmox VEbackupzit-appliance.qcow2 をノードにコピーし、ディスクなしの VM（2 vCPU、2～4 GB RAM、VirtIO ネットワーク）を作成してから
qm importdisk <vmid> backupzit-appliance.qcow2 local-lvm
インポートしたディスクを SCSI として接続し、ブート ディスクにして、QEMU ゲスト エージェントを有効にします。
Hyper-Vbackupzit-appliance-vhdx.zip を展開し、新規 → 仮想マシン、第 1 世代、2～4 GB RAM、既存の仮想ハード ディスクを使用する: その VHDX。

VM を起動します。画面に Web コンソールのアドレスと admin の初期パスワードが表示されます（初回サインインを参照）。VM には 2 vCPU と 2～4 GB RAM を割り当ててください。16 GB のディスクはいつでも拡張でき、アプライアンスは次回の起動時に新しい領域を使い始めます（ルート ファイル システムは稼働中に拡張されます）。初回起動時に各コピーが独自の SSH キー、データベース パスワード、シークレット キーを作成するため、1 つのイメージを何度でも展開できます。ネットワーク アダプターは DHCP でアドレスを取得します。

2. アプライアンス ISO

アプライアンス ISO は、Debian、PostgreSQL、コンソール、自動セキュリティ更新を質問なしですべてインストールします。

  1. 2 vCPU、2～4 GB RAM、16 GB 以上のディスクを持つ VM を作成します（またはサーバーを使用）。VirtIO またはハイパーバイザーの既定のデバイスを使い、BIOS でも UEFI でも構いません。
  2. backupzit-appliance.iso から起動します。5 秒後にインストールが自動で始まり、最初のディスクを消去してインストールします。オペレーティング システムのパッケージをダウンロードするため、インストール中はサーバーにインターネット アクセスが必要です。所要時間は約 10～20 分で、その後サーバーが再起動します。
  3. サーバーの画面に Web コンソールのアドレスと admin の初期パスワードが表示されます。アドレスを開いてサインインし、パスワードを変更してください。

アプライアンス（イメージまたは ISO）

アプライアンスには 2 つの独立したアカウントがあります:

  • 日常業務用の Web コンソール（https://<address>:8443）の admin。初期パスワードは初回起動後にサーバーの画面に表示されます。マイ アカウントで変更してください。
  • サーバー自体（ハイパーバイザー コンソール上の画面、または SSH）の bzadmin。初期パスワードは backupzit です。初回サインイン時に変更が必要です。このユーザーは sudo を使えます。root はサインインできません。

BackupZit とオペレーティング システムの更新はコンソールから管理します（下記参照）。VMware Tools と QEMU ゲスト エージェントが含まれているため、ハイパーバイザーにアプライアンスのアドレスが表示されます。

サーバー画面のセットアップ メニュー

bzadmin がサーバー自体の画面で（SSH 経由ではなく）サインインすると、メニューが開きます:

項目機能
1 NetworkDHCP、またはプレフィックス長付きの静的アドレス（例: 192.168.1.20/24）、ゲートウェイ、最大 3 つの DNS サーバー。
2 Server nameホスト名（英字、数字、-）。
3 SSHSSH サーバーのオン/オフとポートの変更。コンソール（80、443、8443）、PostgreSQL（5432）、インスタント リカバリ（111、2049）のポートは使用できません。
4 Reset the password of "admin"Web コンソールのパスワードを忘れた場合に。サインイン ブロックも解除します。その後、画面には生成された初期パスワードが表示されなくなります（Web コンソールで admin のパスワードを変更した場合も、次回起動以降は同様です）。
5 Lift sign-in blocks and web console limitsサインインの失敗が多すぎてアドレスがブロックされた場合や、Web コンソールが使えなくなったアドレスに制限されている場合に（セキュリティを参照）。

同じネットワーク、サーバー名、SSH、タイムゾーンの設定は、Web コンソールの設定 → ネットワークにもあります（管理者のみ）。そこでは、ゲートウェイが 30 秒以内に応答しない静的アドレスは自動的に元に戻されるため、入力ミスでアプライアンスがネットワークから切り離されることはありません。それでもコンソールに到達できない場合は、SSH がオフでも使えるサーバー画面のメニューを使ってください。

エージェントが記憶するのはコンソールのアドレスではなく証明書です。エージェントが IP アドレスでコンソールに接続していてアドレスが変わった場合は、backupzit-agent set-server で新しいアドレスに向けてください（エージェントを参照）。または最初から DNS 名を使ってください。DHCP を使う場合は、アドレスが変わらないよう DHCP サーバーでアプライアンスのアドレスを予約してください。

アプライアンスの SSH サーバーは AES-GCM/CTR 暗号と SHA-2 MAC のみを提供します（脆弱性スキャナーが弱いと報告する chacha20-poly1305 や 64 ビット MAC は提供しません）。

3. インストール スクリプト

Debian 12 以降、Ubuntu 22.04 以降、AlmaLinux または Rocky Linux 9 以降（x86-64）の既存サーバーで、root として:

curl -fsSL https://github.com/Max-Zit/backupzit/releases/latest/download/install.sh | sudo sh

スクリプトは PostgreSQL をインストールし、最新リリースをダウンロードして、BackupZit のリリース キーで署名を確認し、パッケージのチェックサムも確認します。さらにコンソールをインストールし、ランダムなパスワードでデータベースを作成し、/etc/backupzit/server.env を書き込み、自動セキュリティ更新をオンにし、firewalld または ufw が有効ならポート 8443 を開き、コンソールを起動して、アドレスと初期 admin パスワードを表示します。オプション（sh -s -- の後）:

オプション効果
--version 0.32.0最新ではなくこのリリースをインストール
--db postgres://user:pw@host:5432/dbローカルではなく既存の PostgreSQL データベースを使用
--hosts backup.example.local,10.0.0.10コンソールの証明書に使う名前とアドレス（既定: サーバーのアドレスと名前）
--no-auto-updates自動セキュリティ更新の設定を変更しない

例: curl -fsSL …/install.sh | sudo sh -s -- --hosts backup.example.local。インストール済みのコンソールでスクリプトを再度実行すると、構成とデータを保持したまま BackupZit が更新されます。実行前にスクリプトを読むには、先にダウンロードしてください: curl -fsSLO …/install.sh; less install.sh; sudo sh install.sh。

4. パッケージを手動で

Debian / Ubuntu

apt install postgresql
apt install ./backupzit-server_*.deb

AlmaLinux / Rocky Linux

dnf install postgresql-server && postgresql-setup --initdb && systemctl enable --now postgresql
dnf install ./backupzit-server-*.rpm

AlmaLinux と Rocky Linux では、コンソールがパスワードでサインインできるよう、/var/lib/pgsql/data/pg_hba.conf の 127.0.0.1 と ::1 の行の ident を scram-sha-256 に変更し、PostgreSQL を再起動してください。

データベースの作成

sudo -u postgres psql -c "SET password_encryption = 'scram-sha-256'; CREATE USER backupzit WITH PASSWORD 'choose-a-strong-password'"
sudo -u postgres psql -c "CREATE DATABASE backupzit OWNER backupzit"

接続文字列を /etc/backupzit/server.env に書き込みます:

BACKUPZIT_DB=postgres://backupzit:choose-a-strong-password@localhost:5432/backupzit?sslmode=disable
BACKUPZIT_PUBLIC_URL=https://backup.example.local:8443
BACKUPZIT_TLS_HOSTS=backup.example.local,10.0.0.10
systemctl start backupzit-server

初回サインイン

https://<server>:8443 を開きます。初期管理者は admin で、パスワードは /var/lib/backupzit/initial-admin-password.txt にあります（または初回起動前に BACKUPZIT_ADMIN_PASSWORD を設定）。サインイン後に変更してください。忘れたパスワードをサーバーでリセットするには:

set -a; . /etc/backupzit/server.env; set +a
backupzit-server --set-admin-password 'NEW-PASSWORD'

証明書

初回起動時、コンソールは自己署名証明書を作成します。ブラウザーは一度警告を表示しますが、エージェントは証明機関にまったく依存しません。エージェントは登録時にエージェントページに表示される証明書のフィンガープリントを固定します。これにより、信頼できないネットワークでも偽のサーバーからエージェントが保護されます。

この証明書（データ ディレクトリ内の cert.pem/key.pem）は置き換えないでください。以前に登録したエージェントは、再登録するまで接続を拒否します。ブラウザー向けには、代わりに次のように信頼された証明書を追加してください。

ブラウザー用の信頼された証明書

ブラウザーの警告を避けるには、設定 → 証明書を開きます。するとコンソールは、信頼された証明書を使って DNS 名（例: ポート 443 の https://backup.example.com）でも応答します。エージェントは引き続きポート 8443 と固定された証明書を使うため、影響を受けません。

  • 社内 CA または公的 CA の証明書をアップロードします。*.example.com のようなワイルドカード証明書も使えます。証明書（中間証明書を含む）と秘密キーを PEM で貼り付けるか、ファイルを選択します。コンソールは、キーが証明書と一致すること、証明書が現在有効であること、DNS 名をカバーしていることを確認します。社内 DNS がない場合は、代わりにコンソールの IP アドレスを入力し、その IP アドレス向けに発行された証明書（サブジェクト代替名 IP:192.168.1.20）を使ってください。その場合はコンソールに固定アドレスを割り当ててください。有効期限の 21 日前にメールが届きます。
  • Let's Encrypt: 無料の証明書で、有効期限の 30 日前に自動更新されます。Let's Encrypt は、次の 2 つの方法のいずれかで名前の管理権を確認する必要があります:
    • Cloudflare による DNS 確認。インターネットから到達できないコンソールにはこちらをお勧めします。BackupZit は Cloudflare API トークンを使って一時的な TXT レコードを作成します。Cloudflare で My Profile → API Tokens → Create Token に進み、テンプレート Edit zone DNS を使い、対象をお使いのゾーンに限定してください。
    • HTTP 確認: コンソールのポート 80 が DNS 名でインターネットから到達できる必要があります。バックアップ サーバーではあまり望ましくありません。
    まずは Let's Encrypt のテストシステムを使用で設定を試してください。その証明書はブラウザーに信頼されませんが、レート制限がありません。
  • ポート 80 で応答すると、http:// が https:// にリダイレクトされます。

DNS 名は、通常は社内 DNS の A レコードによってコンソールの IP アドレスを指す必要があります。証明書ファイルは /var/lib/backupzit/web に保存され、キーはサービスだけが読み取れます。Linux ではサービスがポート 80 と 443 を使用できます（CAP_NET_BIND_SERVICE）。ブラウザーが別のネットワークから接続する場合は、ファイアウォールでこれらのポートを開いてください。

BackupZit の更新

既定では、コンソールは GitHub 上の BackupZit 公式リリース（https://github.com/Max-Zit/backupzit/releases）から更新を取得します。設定 → 更新で、代わりに別の更新ソース（独自の HTTPS ミラーまたはサーバー上のフォルダー）を指定できます。ソースが何であれ、すべてのリリースには有効な BackupZit 署名が必要です。コンソールは毎日新しいリリースを確認し、利用可能になると管理者にメールを送ります。インストールするにはインストールをクリックします:

  1. コンソールはリリースの署名とパッケージのチェックサムを確認し、バックアップや復元が実行されていない状態になるまで待ちます。
  2. システム サービス（backupzit-update、root として実行）が、BackupZit に組み込まれたリリース キーで署名を再確認します。コンソールが侵害されても、他のパッケージをインストールさせることはできません。
  3. データベースをバックアップし（pg_dump）、現在のプログラムを保持し、パッケージをインストールしてコンソールを再起動します。
  4. 新しいバージョンが 2 分以内に応答しない場合は、以前のプログラムと元の状態のデータベースが自動的に復元されます。起動失敗のログを含む結果は、更新ページに表示され、監査ログに記録され、メールで送信されます。
  5. 更新が成功すると、エージェントも更新されます。各エージェントはアイドル時に新しいバージョンをインストールします。自分で更新したい場合は、同じページでこれを無効にしてください。

コンソールは約 1 分間利用できなくなります。直近 3 回の更新のデータベース バックアップと以前のプログラムは /var/lib/backupzit-update に保存されます。

インターネット アクセスがない場合: 別のコンピューターでリリース ファイル（manifest.json、manifest.json.sig、サーバー パッケージ）をダウンロードします。その後、ファイルから更新をインストールでアップロードするか、サーバー上のフォルダーにコピーしてそのフォルダーを更新ソースとして使います。

パッケージ マネージャーで更新することもできます（apt install ./backupzit-server_….deb）。データベースは新しいバージョンの起動時に移行されます。

オペレーティング システムの更新

同じページ（設定 → 更新）には、コンソール サーバーのオペレーティング システムの状態が表示されます。利用可能な更新の数、そのうちセキュリティ修正の数、再起動が必要かどうか、自動セキュリティ更新がオンかどうか。状態は毎日、または今すぐ確認で更新されます。次の操作ができます:

  • 自動セキュリティ更新をオンにする（推奨）。システム自身のツールがセキュリティ修正のみを毎日インストールします。Debian と Ubuntu では unattended-upgrades、AlmaLinux と Rocky Linux では dnf-automatic。
  • すべての更新を今すぐインストール。PostgreSQL などのサービスが一時的に再起動することがあり、コンソールは自動的に再接続します。
  • サーバーを再起動（カーネル更新の後など）。バックアップや復元の実行中はコンソールが拒否します。エージェントはジョブを保持し、コンソールが戻ると結果を報告します。

これらのタスクは、コンソールの更新と同じ root サービスを通じて実行されます。監査ログに記録され、最後のタスクの出力がページに表示されます。

コンソール自体のバックアップ

ストレージ上のバックアップは、復旧シートを使えばコンソールなしでも読み取れます。サーバーを失った後にコンソール自体も取り戻すには、設定 → コンソールのバックアップをオンにしてください。対象にはジョブ、スケジュール、エージェント、ユーザー、設定、実行履歴、保存された資格情報が含まれます。コンソールは毎日、ネットワーク ストレージ ターゲットの backupzit-console フォルダーに自分自身をバックアップします。

コンソールのバックアップには次が含まれます:

  • テーブルごとにエクスポートしたデータベース全体（特定の pg_dump バージョンは不要）。
  • 保存された資格情報を復号するシークレット キー。
  • エージェントが固定しているコンソールの証明書。

ターゲットの回復キーで暗号化され、重複排除されます。最新のバックアップが保持されます（既定は 14 個）。

コンソールの復元

  1. 同じかそれより新しいバージョンの新しいコンソールをインストールします（例: アプライアンス ISO から）。
  2. 新しいサーバーで root として次を実行します。資格情報はストレージ ターゲットの復旧シートのもので、リポジトリのアドレスはコンソールのバックアップ ページに表示されます。 
    systemctl stop backupzit-server
set -a; . /etc/backupzit/server.env; set +a
export BACKUPZIT_PASSWORD='<recovery key>'
export BACKUPZIT_SFTP_PASSWORD='…' BACKUPZIT_SFTP_HOSTKEY='SHA256:…'   # or BACKUPZIT_S3_ACCESS_KEY/_SECRET_KEY, _SMB_PASSWORD, _AZURE_KEY, _HARDENED_KEY/_FINGERPRINT
backupzit-server --restore-console --repo 'sftp://backup@nas:22/backups/backupzit-console'
systemctl start backupzit-server
  3. 新しいサーバーに古いサーバーの IP アドレスまたは DNS 名を割り当てます。エージェントは復元された証明書を信頼し、自動的に再接続します。

復元により、新しいコンソールのデータベースがバックアップのものに置き換えられ、インストール済みのバージョンに合わせて更新されます。--snapshot ID を指定すると、最新ではなく古いバックアップを復元します。

復旧シートと secrets.key のコピーも、パスワード マネージャーなどサーバーの外に保管してください。
