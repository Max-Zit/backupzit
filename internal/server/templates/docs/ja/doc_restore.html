復元

成功したバックアップはすべて復元できます。全体または選択したフォルダーだけを、同じマシン、別のエージェント、または新しい仮想マシンとして復元できます。

復元ウィザード

メニューの 復元をクリックします。ウィザードは 4 つの質問をします:

  1. 何を復元しますか?
    • 仮想マシン全体
    • 仮想マシン内のファイル
    • ファイルとフォルダー
    • ディスク イメージ / ベアメタル
    • ディスク イメージ内のファイル
    • データベース（特定の時点へ）
    • Linux システム全体
    • Microsoft 365 のメールと OneDrive（Microsoft 365 を参照）
    各選択肢には、利用できる復元ポイントの数が表示されます。
  2. ソース: 仮想マシン（すべてのハイパーバイザーとジョブにまたがる）、またはバックアップ ジョブとそのマシン。
  3. 復元ポイント: 復元元のバックアップ。新しい順に、ステータス、ストレージ、サイズとともに表示されます。
    • 疑わしい（ランサムウェアの可能性がある）としてフラグが付いたバックアップには印が付きます。
    • バックアップ コピー ジョブが 2 次ストレージに作成したコピーはコピーとして表示されます（ファイルと VM のバックアップ）。
  4. オプション: 復元先と復元方法。オプションの上に選択内容の概要が表示されます。

上部の各ステップはリンクなので、前のどのステップにも戻れます。各ステップには固有のアドレスがあるため、ブックマークや共有もできます。

オプションはアクティビティのバックアップ ページと同じで、そこから直接復元を開始することもできます。ウィザードが表示されるのは、ロールで復元が許可されているユーザーだけです。

ファイル バックアップからの復元

  1. 復元ウィザードでファイルとフォルダーを選び、ジョブと復元ポイントを選びます。または、アクティビティやジョブ ページでバックアップを開きます。
  2. このバックアップからファイルを復元で、ファイルを受け取るエージェントを選びます。バックアップしたマシンとは別のマシン（たとえば交換用の PC）でも構いません。
  3. 復元先を選びます:
    • フォルダーに復元（推奨）— 例: D:\Restore。その下に元の構造が再作成されます: D:\Restore\C\Users\ana\Documents\…。既存のものには一切触れません。
    • 元の場所に復元 — ファイルを元の場所に書き戻し、現在のバージョンを上書きします。NAS 共有の場合、エージェントは共有を書き込み可能で再接続します。
  4. 必要に応じて次のパスのみに絞り込みます（1 行に 1 つ。例: C:\Users\ana\Documents\Contracts）。またはファイル ブラウザーで選びます（下記）。
  5. 復元したファイルを確認はオンのままにしてください。各ファイルを読み戻し、バックアップ内のチェックサムと比較します。
  6. 復元を開始をクリックします。進行状況と結果は復元実行のページに表示されます。

ファイルの時刻、Windows の属性（隠しファイル、読み取り専用など）、Linux の所有者、アクセス許可（setuid ビットを含む）、ACL、拡張属性（SELinux ラベル、ファイル ケーパビリティ）、シンボリック リンクとハード リンクも復元されます。所有者は、エージェントが root/管理者として実行されている場合にのみ設定されます。

ファイルの参照、ダウンロード、選択

バックアップ実行のファイルを参照では、バックアップしたフォルダーが当時のまま表示されます（NAS 共有や Linux システム バックアップも同様）。フォルダーを開き、ファイルやフォルダーにチェックを付けてから:

  • ダウンロード — 1 つのファイルはそのまま、複数のファイルやフォルダーは ZIP アーカイブとして、ブラウザーで直接ダウンロードされます。ダウンロードは監査ログに記録されます。
  • エージェント上に復元 — 次のパスのみを指定した復元と同様に、フォルダーまたは元の場所へ。

ファイルへのシンボリック リンク（例: /etc/os-release）は、リンク先のファイルがバックアップに含まれていれば、そのファイルとしてダウンロードされます。フォルダーへのリンクは ZIP アーカイブから除外されます。仮想マシンのバックアップ（ext4、XFS）からダウンロードしたファイルも同様です。エージェント上での復元では、リンクはリンクとして再作成されます。

コンソールはストレージから直接バックアップを読み取るため、参照はネットワーク ストレージ（SFTP、S3、SMB、Azure、強化リポジトリ）上のバックアップで動作します。エージェントのローカル ディスクや USB ディスクの場合は、パスを指定して復元してください。復元ロールを持つユーザーは参照とダウンロードができます。

目的のバックアップを探すには: カレンダーでどの日にどのバックアップが実行されたかを確認するか、ジョブ ページの履歴を使います。

ディスク イメージから個別のファイルを復元

イメージ バックアップでは、バックアップ実行のファイルを参照をクリックします。イメージ内の NTFS ファイル システムをコンソールで直接参照し、ファイルやフォルダーにチェックを付けて、ディスク全体を復元せずに任意のエージェントに復元できます。

VM から個別のファイルを復元（Proxmox VE、Hyper-V、VMware）

VM バックアップ実行で、ゲストの横にあるファイルを参照をクリックします。コンソールにはディスクのパーティションと LVM ボリュームが表示され、NTFS、ext4、XFS ファイル システムを参照できます。チェックしたファイルをダウンロードする（複数の場合は ZIP アーカイブ）か、任意のエージェントに復元します。Proxmox VE、Hyper-V、VMware ESXi を参照してください。

マシン全体の復元

  • Windows ディスク イメージ: ディスクまたはベアメタルへ。異なるハードウェアへも — ディスク イメージ。
  • Linux システム: ディスクまたはベアメタルへ、または新しい Proxmox VM として — Linux システム バックアップ。
  • Proxmox の VM とコンテナー: 新しいゲストとして、またはその場に — Proxmox VE。Proxmox VM はバックアップから即座に実行し、実行中にストレージへ移動することもできます（インスタント リカバリ）。
  • データベース（SQL Server、PostgreSQL、MySQL/MariaDB）: 新しい名前で、またはその場に、特定の時点へ — データベース。
  • Hyper-V VM: 新しい VM として、またはその場に（ID と MAC アドレスを保持）— Hyper-V。
  • VMware ESXi VM: 新しい VM として、またはその場に（UUID と MAC アドレスを保持）、任意の ESXi ホストとデータストアへ — VMware ESXi。Linux プロキシ エージェント経由でバックアップから即座に起動し、その後データストアにコピーすることもできます（インスタント リカバリ）。

復旧 ISO

ベアメタル復元では、マシンを復旧 ISO（USB メモリーに書き込むか VM に接続）から起動します。リカバリーメディアを参照してください:

  • Linux 復旧 ISO — 各リリースとともに公開されます（backupzit-recovery-linux.iso）。リカバリーメディア ページから、更新ソース上の ISO にリンクしています。
  • Windows 復旧 ISO — Windows PE は再配布できないため、任意の Windows 10/11 または Server の PC で一度だけ作成します:
    1. Microsoft の無料の Windows ADK（機能 Deployment Tools）と Windows PE アドオンをインストールします。
    2. リリースから build-winpe.ps1 をダウンロードし（エージェント パッケージの隣）、エージェントがインストールされたマシンの C:\Program Files\backupzit Agent から backupzit-agent.exe を取得します。
    3. 管理者の PowerShell で: .\build-winpe.ps1 -AgentExe .\backupzit-agent.exe -Out .\backupzit-recovery.iso。ストレージやネットワークのドライバー（例: Proxmox VM 用の VirtIO）には -DriverDir C:\Drivers を、入力なしで接続させるには -RecoveryJson .\recovery.json を追加します。
    4. 必要に応じて ISO をコンソールの /var/lib/backupzit/dist ディレクトリにコピーします。すると、リカバリーメディア ページで提供されます。

コンソールでのファイル参照は、ネットワーク ストレージ（SFTP、S3、SMB、Azure、強化リポジトリ）上のバックアップで動作します。コンソールが直接読み取ります。エージェントのローカル ディスク上のバックアップには、コマンドラインを使ってください。

コンソールなしでの復元

コンソール自体が失われた場合でも、エージェントがインストールされた任意のマシンで、ストレージ ターゲットの復旧シートを使ってストレージから直接復元できます:

set BACKUPZIT_PASSWORD=<recovery key>
set BACKUPZIT_SFTP_PASSWORD=...           (or the S3/SMB/hardened credentials)
backupzit-agent snapshots --repo sftp://backup@nas:22/backups/pc1_1a2b3c4d
backupzit-agent restore   --repo sftp://backup@nas:22/backups/pc1_1a2b3c4d --target D:\Restore latest

コマンドライン リファレンスを参照してください。

自動復元テスト

BackupZit は、何もしなくてもバックアップを定期的に検証します。毎週（設定 → 復元テストで変更可能）、各ジョブのエージェントが最新のバックアップからランダムなファイルのサンプルを一時フォルダーに復元し、保存されたチェックサムとすべてのバイトを照合してから削除します。ディスク イメージの場合はランダムなブロックを読み取って検証します。これにより、ストレージへのアクセス、資格情報、暗号化キー、データの整合性というチェーン全体が検証されます。

  • 結果はアクティビティとジョブの履歴に復元テストの実行として表示され、ジョブごとにレポート（復元テスト列）にも表示されます。
  • 失敗したテストは他の失敗と同じく扱われ、メール アラートが送信されます。
  • ジョブ ページの復元をテストで、すぐにテストを開始できます。
  • サンプル サイズはストレージから読み取る量を制限します。ダウンロード料金がかかるクラウド ストレージでは小さくしてください。

Proxmox VM の起動テスト

ブロックが読み取れても、VM がまだ起動するとは限りません。Proxmox VM バックアップの起動テストを有効にすると（設定 → 復元テスト）、Proxmox VM ジョブの復元テストでは、最新バックアップのすべての VM をジョブのノード上で 1 台ずつインスタント リカバリで起動します。VM は新しい ID で、ネットワーク カードを切断した状態（元の VM と競合しないように）でバックアップから実行され、直後に削除されます。設定した時間内に VM の QEMU ゲスト エージェントが応答すれば、つまりオペレーティング システムが起動すればテストは合格です。ゲスト エージェントのない VM は、1 分間動作し続ければ合格です。実行ページでは起動済みではなく実行中と表示されます。

  • テスト中、ノードにはもう 1 台分の VM を動かす空きメモリーが必要です。
  • テストで起動を確認できるよう、VM に QEMU ゲスト エージェント（Linux では qemu-guest-agent、Windows では VirtIO ゲスト ツール）をインストールし、VM のオプションで有効にしてください。
  • 実行ページには、各 VM の結果と起動にかかった時間が一覧表示されます。

さらに、ときどき（例: 四半期ごと）実際のフォルダーを手動で復元し、いくつかのファイルを開いてみてください。緊急時に作業を行う人の訓練にもなります。
