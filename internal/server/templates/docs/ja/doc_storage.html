ストレージ ターゲット

ストレージ ターゲットは、エージェントがバックアップを書き込む場所です。各エージェントはターゲットの場所の下にある専用のリポジトリを使います。

ストレージの種類の選択

S3 互換オフサイト / クラウドのコピー: AWS S3、Wasabi、Backblaze B2、MinIO、Ceph、Google Cloud StorageObject Lock による不変性に対応。

SMB 共有Windows ファイル サーバー、Synology/QNAP NASSMB 2/3。エージェントが自分でサインインするため、ドライブの割り当ては不要です。

接続のテスト

ストレージ ターゲットを追加すると、入力された資格情報ですぐにテストされます。小さなファイルを書き込み、読み戻して削除します。不変ストレージ（Object Lock 付き S3、強化リポジトリ）では、テストはサインインと一覧表示のみを行い、ロックされたものが残らないようにします。S3 では、不変性が要求されている場合にバケットで Object Lock が有効かどうかも確認します。ターゲットはどちらの場合も保存され、結果が表示されます。誤ったパスワード、ホスト キー、バケット、共有は、最初のバックアップではなく今の時点でわかります。ストレージ ページの接続をテストでテストを再実行できます。

テストは選択した場所で実行されます。ターゲットを追加するときは接続テストの実行元で、それ以降は接続をテストで開くページで選択します。このコンソールはコンソール自身のネットワークからテストします。エージェントはそのエージェントのネットワークからテストします。コンソールが別の場所（VPS など）で動作し、ストレージが顧客のネットワーク上にある場合に意味を持つのはこちらです（エージェント 0.60.0 以降。リカバリーメディアは除く）。ページには、そのターゲットを最後にバックアップで使用したエージェントが提案されます。エージェントでのテストは同じ手順による短い実行です（アクティビティの接続テスト）。ビジー状態のエージェントはバックアップと並行して実行します。ページはテストの完了を待ち、その後ストレージ ページに結果が表示されます。ローカル ディスクや USB ディスクにはそのエージェントからのみ到達でき、最初のバックアップでテストされます。

失敗したテストは、コンソールとエージェントのどちらで実行されたものでも、ターゲット、その種類、テストの実行場所、エラーとともにコンソールのログにも記録されます（storage connection test failed）。そのため、後から設定 → 診断などで確認できます。

エージェントのみ到達可能なストレージ

顧客のネットワーク上の NAS、SFTP サーバー、強化リポジトリには、その拠点のエージェントからは到達できてもコンソールからは到達できないことがよくあり、インターネットに公開すべきでもありません。そのようなターゲットを追加するときにエージェントのみ到達可能をオンにするか、一覧で既存のターゲットの横にあるエージェントのみ到達可能をクリックします（コンソールの接続を許可で再びオフにできます）。一覧ではそのターゲットにエージェントのみと表示されます。バックアップ、復元、復元テスト、データ確認、保持はこれまでどおりエージェントで実行されます。コンソール自体がストレージに接続しなくなるだけです。

  • 追加時もその後も、コンソールはテストしません。接続をテストではエージェントだけを選択できます。
  • バックアップを検索は、ローカル ディスクや USB ディスクと同様に、エージェント経由で検索します。
  • コンソールのバックアップの保存先としては表示されず、コンソールのバックアップの保存先になっているターゲットにはこのオプションを設定できません。
  • そのバックアップのファイルの参照と個別ファイルのダウンロードは、そのストレージを使うエージェント経由で行われます。バックアップを作成したエージェント、それがオフラインならこのストレージを使ったことのある別のオンラインのエージェントです（エージェント 0.61 以降。エージェントが要求を受け取るまで、最初のページに最大 30 秒ほどかかることがあります）。古いエージェントでは、代わりに 次のパスのみ で復元します（復元 を参照）。
  • エージェントを削除しても、コンソールはそのストレージ上にあるエージェントのバックアップを削除しません。ストレージ側でフォルダーを削除してください。

SFTP

場所: sftp://user@host:22/path（ユーザーのホーム ディレクトリからの相対パスには /~/path を使用）。パスワードまたは秘密キーと、サーバーのホスト キーのフィンガープリントを入力します。フィンガープリントはサーバー上で次のコマンドで取得できます:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

バックアップ フォルダーにのみ書き込める専用ユーザーを作成してください。

S3 互換

エンドポイント（例: s3.eu-central-1.amazonaws.com、s3.wasabisys.com、10.0.0.5:9000）、バケット、任意のフォルダー、そのバケットへの読み書き権限を持つアクセス キーを入力します。平文 HTTP は、証明書のないローカル MinIO の場合にのみオンにしてください。

オブジェクトストレージはときどき応答が遅かったり、一時的なエラーを返したりします。エージェントは応答を最大 5 分待ち、タイムアウト、接続の切断、短い読み取り、サーバーエラー、スロットリング(SlowDown)の場合は、バックアップや復元をあきらめる前に間隔を延ばしながら数回再試行します。一部を再送しても安全で、Object Lock でも問題ありません。 すべてのアップロードにはプロバイダーが検証するチェックサム（Content-MD5）が付き、各アップロードの後にエージェントは保存されたオブジェクトのサイズを確認します。短く届いたものは再アップロードされます（エージェント 0.54.2 以降）。

S3、Azure、強化リポジトリでは、エージェントは最大 4 つのパックを同時にアップロードし、VM とディスクの復元は最大 4 ブロックを先読みします。遠方や低速のプロバイダーで特に効果があります。帯域制限は合計に対して引き続き適用されます。SFTP、SMB、ローカルまたは USB ディスクには 2 つのパックを同時に書き込むため（エージェント 0.62 以降）、1 つを書き込んでいる間に次のパックを準備でき、復元ではそれらから最大 3 ブロックを先読みするため（エージェントと復元メディア 0.61 以降）、ネットワークと復元先ディスクが同時に動きます。ファイルの復元でも大きなファイルの部分を同じように先読みし、全データのチェックは複数のパックを同時に読み取ります（0.62）。大きなリポジトリのインデックスも同時に 8 ファイルずつ読み取られます。その間、エージェントのログには進行状況とともに "loading the repository index" が表示されます。

不変バックアップ（Object Lock）

バケットを Object Lock を有効にして作成し、変更不可のバックアップ … N 日間をオンにします。エージェントが書き込む各ファイルは コンプライアンス モードで N 日間（+1 日の余裕）ロックされます。その間は、キーを持つ攻撃者もバケットの所有者も、誰も削除や上書きができません。各バックアップの後、古いバックアップから再利用されたデータのロックが延長されるため、すべての復元ポイントが全期間保護されます。エージェントは 16 個のオブジェクトを同時に延長し、既知のロック日付を自身のフォルダーに記録するため、再起動や更新のたびにすべてのオブジェクトを確認し直すことはありません。まずエージェントは、ジョブが保持しているバックアップを読み取ります。ツリーとブロック マップは複数を同時に読み取ります（実行には オブジェクト ロックのため保持しているバックアップを読み取り中: N 件読み取り済み と表示）。その後、実行には オブジェクト ロックを延長中 N / M と表示されます。エージェントのログには各ステップにかかった時間が記録されます。

バケットには、コンプライアンス モードで少なくとも N 日の既定の保持期間も設定してください (AWS: Object Lock → Default retention、MinIO: mc retention set --default COMPLIANCE 30d)。これにより、侵害されたコンピューターがロックなしで書き込んだオブジェクトも含め、バケット自身がすべての新しいオブジェクトをロックします。既定の保持期間がない場合や N 日より短い場合は、保存先の接続テストで警告されます。

削除（保持処理または攻撃者による）は「削除マーカー」を追加するだけです。ロックの終了後に領域が解放されるよう、最新でないバージョンを 1 日後に期限切れにするライフサイクル ルールを追加してください。ランサムウェア対策を参照してください。

Backblaze B2

  1. Backblaze で Application Keys を開き、バケットへの読み書き権限を持つアプリケーションキーを作成します。B2 の S3 API はアカウントのマスターキーを受け付けません。その場合 BackupZit は Malformed Access Key Id と表示します。
  2. バケットのページに表示される S3 エンドポイント（例: s3.us-west-004.backblazeb2.com、バケット名は含めない）、バケット名、アクセスキーとしてアプリケーションキーの keyID、シークレットキーとしてその applicationKey、エンドポイントのリージョン（us-west-004）を指定して S3 ターゲットを追加します。

キーと一緒にコピーされた空白や改行は、ターゲットの保存時に取り除かれます。イミュータブルにするには、Object Lock を有効にしてバケットを作成します。

Google Cloud Storage

Google Cloud Storage は、相互運用性 API を通じて S3 互換ターゲットとして動作します:

  1. Google Cloud コンソールで Cloud Storage → Settings → Interoperability を開き、バケットに対して Storage Object Admin ロールを持つサービス アカウントの HMAC キーを作成します。
  2. エンドポイント storage.googleapis.com、バケット名、HMAC のアクセス キーとシークレット、リージョン auto で S3 ターゲットを追加します。

Google Cloud Storage では S3 Object Lock オプションは使えません。不変性が必要な場合は、Google Cloud でバケットの保持ポリシーを設定（してロック）してください。削除されたバックアップは保持期間が終わるまで残ります。

Azure Blob Storage

  1. Azure portal でストレージ アカウント（StorageV2、冗長性は任意）とコンテナー（例: backups）を作成します。
  2. アカウント名、コンテナー、任意のフォルダーで Azure Blob Storage ターゲットを追加します。
  3. アクセス キー（ストレージ アカウント → アクセス キー）で認証するか、より制限するなら、読み取り・書き込み・削除・一覧の権限と適切な有効期限を持つコンテナーの SAS トークンで認証します。

ランサムウェア対策として、コンテナーで時間ベースの保持ポリシーを使ったバージョン レベルの不変性を有効にしてください。削除または上書きされたバックアップは、その期間中は復旧できます。詳細設定のエンドポイント欄は、Azure Government/China、Azure Stack Hub、Azurite エミュレーターの場合にのみ必要です。

ローテーション USB ディスク

取り外してオフサイトに持ち出すディスクは、小規模オフィスにとってランサムウェア、火災、盗難に対する最も簡単な保護です。BackupZit は、Windows が割り当てるドライブ文字に関係なく、ボリューム ラベルでディスクを検出します:

  1. 2 台以上のディスクを NTFS（Linux: ext4）でフォーマットし、BZBACKUP1、BZBACKUP2、… と名前を付けます（Windows: ドライブを右クリック → プロパティ → 名前）。
  2. ラベル BZBACKUP* で ローテーション USB / リムーバブル ディスク タイプのストレージ ターゲットを追加します。
  3. そこへのバックアップ ジョブを作成します。より良いのは、NAS やクラウドのジョブをディスクにコピーするバックアップ コピー ジョブです。
  4. ディスクを定期的に（例: 毎週）交換し、取り外したディスクは安全な場所に保管します。
  • 各ディスクには、独自の保持設定を持つ完全で独立したバックアップが入ります。すべてのディスクはターゲットの回復キーで暗号化されます。
  • 実行には使用したディスクが表示されます（ディスク BZBACKUP2）。復元ではまさにそのディスクを求め、どれが接続されているかを示します。
  • ディスクが接続されていない場合、実行はわかりやすいメッセージとアラートとともに失敗します。ディスクを再接続するためのリマインダーです。
  • 一度に接続するディスクは 1 台だけにしてください。

SMB 共有

サーバー、共有、任意のフォルダー、ユーザー、パスワード、（ドメイン アカウントの場合）ドメイン。エージェントがこの資格情報で自ら接続するため、SYSTEM として実行されるサービスでも動作します。

SMB アカウントには、ファイルの作成・読み取り・削除に加え、一時ファイルの名前変更によって既存のリポジトリファイルを置き換える権限が必要です。これにより、ロックの更新がアトミックに反映されます。置換に失敗した場合は書き込みエラーを報告し、以前のファイルを保持します。 リポジトリのロックを読み取れない場合、ロックが存在しないとは判断せず、メンテナンスを停止します。

強化リポジトリ

専用の Linux サーバーに backupzit-repo パッケージをインストールし、そのサーバーで次を実行します:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

サーバーのアドレス、アクセス キー、フィンガープリントをコンソールに入力します。不変期間はリポジトリ サーバー（/etc/backupzit-repo/repo.env）で設定し、コンソールやエージェントからは変更できません。詳細はランサムウェア対策を参照してください。

アクセス キーはリポジトリの 1 つのパスに限定し、制限を付けられます。侵害されたコンピューターが自分のバックアップにしか届かないよう、コンピューターごとに専用の保存先とキーを用意してください:

backupzit-repo add-key pc-anna --path office/pc-anna --quota 500G --daily 100G --rate 600
backupzit-repo set-key pc-anna --quota 1T     # 制限を変更 (none で解除)
backupzit-repo keys                           # キーとその制限

--path を付けると、そのキーには hardened://server/office/pc-anna 以外のものは存在しません。--quota はパス配下に保存されるデータ (削除されても保持中のファイルを含む)、--daily は 1 日 (UTC) あたりの新しいデータ、--rate は 1 分あたりの書き込み要求を制限します。制限は新しいアップロードを拒否するだけで、バックアップはメッセージ付きで失敗します。何かを削除したり短縮したりすることはなく、読み取りと復元は制限されません。オプションなしのキーには制限がないため、大きな最初のバックアップが誤ってブロックされることはありません。

暗号化と回復キー

バックアップを暗号化（既定）では、リポジトリ内のすべて（ファイルの内容、ファイル名、フォルダー構造、スナップショットの一覧）がエージェントを出る前に AES-256-GCM で暗号化されます。ストレージ プロバイダーにはランダムなデータしか見えません。

暗号化されたターゲットを作成すると、コンソールに回復キーが表示され、復旧シートをダウンロードできます。

復旧シートを印刷するか、バックアップとは別にパスワード マネージャーに保存してください。コンソールを失った場合でも、復元に必要なのは回復キーとストレージの場所および資格情報だけです。キーがなければ、暗号化されたバックアップは誰にも読めません。BackupZit のサポートでも同じです。

後からストレージ一覧のリカバリーキーでキーを再表示できます。この操作はログに記録されます。

既知のキーで以前に作成したバックアップを読むには（コンソールのバックアップなしでコンソールを再インストールした後など）、同じ場所と資格情報でストレージを追加するときに既存の回復キーにキーを入力し、その後バックアップを検索を使います。

ストレージ一覧

一覧には各ターゲットの種類、場所、暗号化（管理者は回復キーにアクセス可能）、不変性（S3 では Object Lock の期間、強化リポジトリではリポジトリサーバーで設定）が表示されます。エージェントのみ到達可能なストレージにはエージェントのみと表示され、一覧の下に注記が表示されます。資格情報は保存後に二度と表示されず、暗号化して保存されます。ターゲットの追加と削除、回復キーの表示ができるのは管理者だけです。

ストレージ上のバックアップを検索する

ストレージ一覧のバックアップを検索は、コンソールが認識していないリポジトリをストレージ上で探します（以前に削除したエージェントのもの、または別のコンソールで作成されたもの。再インストール前など）。各フォルダーについて、コンピューター、ジョブ（バックアップ対象に基づく名前）、バックアップ数と日付を表示します。読み取れないフォルダー（別の回復キーで暗号化されている場合など）にはその旨が表示されます。選択したバックアップを追加すると、コンピューター名の削除済みエージェントの履歴として記録されます。エージェント ページのバックアップを保持している削除済みエージェントとアクティビティ（トリガー: インポート済み）に表示され、任意のエージェントへの復元、そのコンピューターのエージェントへの関連付け、削除ができます（エージェントを参照）。ストレージ上の内容は変更されません。コンソールに既にあるリポジトリは表示されず、2 回追加しても何も追加されません。

ネットワーク ストレージはコンソールが自身のネットワークから検索するため、コンソールから到達できる必要があります。ローカル ディスクや USB ディスクは、それが接続されたコンピューターのエージェントが検索します。検索ページでそのエージェントを選択してください（エージェント 0.44.0 以降）。ローテーションする USB ディスクでは、その時点で接続されているディスクが検索されます。エージェントのみ到達可能なストレージは、選択したエージェントがターゲットの資格情報でサインインして検索します（エージェント 0.60.0 以降）。そのターゲットを最後にバックアップで使用したエージェントが先頭に表示されます。VMware 接続と Microsoft 365 テナントのバックアップは復元できますが、エージェントには関連付けられません。

ストレージ ターゲット上の VM バックアップ

ストレージ一覧の VM バックアップ には、ターゲットに復元ポイントがあるすべての仮想マシンとコンテナーが、その時刻とサイズとともに表示されます。ジョブが削除された、またはジョブで選択されなくなった VM も含まれます。それらには ジョブなし の印が付き、ダッシュボードの 要対応 に表示されます。誰かが削除するまでストレージを使い続けるためです。その VM だけを含む復元ポイントはそこで削除できます。チェックして、パスワードまたは 2 要素認証コードで確認します（4 つの目による承認 がオンの場合は、先に別のユーザーが承認します）。コンソールはその復元ポイントだけが使っていた領域を解放し、結果は監査ログに表示されます。VM ジョブは実行ごとにすべての VM のバックアップを 1 つ書き込むため、他の VM も含む復元ポイントはジョブの保持期間で削除されるまで残ります。他の VM の履歴には一切影響しません。変更不可のストレージ（Object Lock、強化リポジトリ）では、ロックが期限切れになるまで削除は拒否されます。コンソールは自分で到達できるストレージ上で削除します。エージェントのコンピューターのディスク、SSH キーによるサインイン、またはエージェントのみが到達できるストレージでは、ジョブの保持期間によってバックアップが削除されます。

ストレージ使用量と予測

各バックアップ（とその保持処理）の後、エージェントはリポジトリが占める容量を報告し、ローカル ディスク、USB ディスク、SFTP サーバー（OpenSSH の statvfs 拡張）、SMB 共有の場合はストレージのサイズと空き容量も報告します。ストレージ → ストレージ使用量では、各ターゲットについて次を表示します:

  • そのターゲット上のすべてのリポジトリが使用している容量（エージェントごとに 1 つ。ローテーション USB ディスクではディスクごとに集計）。
  • サイズがわかっているストレージでは使用率（75 % から黄色、90 % から赤）。グラフでは容量が赤い破線で表示されます。
  • 過去 90 日間のグラフと、1 週間分のバックアップ後には 1 日あたりの増加量（過去 30 日間の線形トレンド）を 30 日先まで破線で描画し、ストレージがいっぱいになる時期を表示します。サイズが不明な場合は 90 日後の予想使用量を表示します。

ストレージ ターゲットが 90 % に達した場合や 30 日以内にいっぱいになる場合は、ダッシュボードの要対応で警告されます。S3 と Azure には固定のサイズがないため、使用量とその増加のみが表示されます。使用量は保存されたデータ（圧縮・暗号化・重複排除後）であり、ストレージが他の理由で保持しているファイル（オブジェクトのバージョン、他のプログラム）は含まれません。

ターゲットの削除

ジョブがまだ使っているストレージ ターゲットは削除できません。コンソールからストレージ ターゲットを削除しても、ストレージ上のデータは削除されません。ただし、コンソールはその認証情報と回復キーを破棄するため、そのバックアップはコンソールから復元できなくなります。先に復旧シートをダウンロードしてください。4 アイズ承認が有効な場合は、先に 2 人目のユーザーの承認が必要です。
