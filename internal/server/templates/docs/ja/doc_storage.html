ストレージ ターゲット

ストレージ ターゲットは、エージェントがバックアップを書き込む場所です。各エージェントはターゲットの場所の下にある専用のリポジトリを使います。

ストレージの種類の選択

種類適した用途備考
SFTPSSH が使える任意の Linux サーバーまたは NAS暗号化された転送。サーバーのホスト キーが固定されます。
S3 互換オフサイト / クラウドのコピー: AWS S3、Wasabi、Backblaze B2、MinIO、Ceph、Google Cloud StorageObject Lock による不変性に対応。
Azure Blob StorageMicrosoft 中心の企業向けのオフサイト コピーアカウント キーまたは SAS トークン。Azure のバージョン レベルの不変性ポリシーで不変性を実現。
SMB 共有Windows ファイル サーバー、Synology/QNAP NASSMB 2/3。エージェントが自分でサインインするため、ドライブの割り当ては不要です。
強化リポジトリランサムウェアに強いオンプレミス ストレージbackupzit-repo を実行する Linux サーバー。不変期間が終わるまでバックアップは削除できません。
ローテーション USB ディスク小規模オフィス向けのオフライン コピー: 2 台以上のディスクを毎週交換ドライブ文字ではなくボリューム ラベル（BZBACKUP1、BZBACKUP2 …）で検出します。
ローカル / マウント パスUSB ディスク、2 台目のディスク、またはエージェントにマウントされた NFS/iSCSI ボリュームエージェントから見たパス。例: E:\Backups や /mnt/backup。

3-2-1 ルール: データのコピーを 3 つ、2 種類の異なるメディアに、うち 1 つはオフサイトに保管します。たとえば、1 つのジョブはローカル NAS へ、もう 1 つは S3 か別の建物にある強化リポジトリへ。

接続のテスト

ストレージ ターゲットを追加すると、コンソールは入力された資格情報ですぐにテストします。小さなファイルを書き込み、読み戻して削除します。不変ストレージ（Object Lock 付き S3、強化リポジトリ）ではサインインと一覧表示のみを行い、ロックされたものが残らないようにします。S3 では、不変性が要求されている場合にバケットで Object Lock が有効かどうかも確認します。ターゲットはどちらの場合も保存され、結果が表示されます。誤ったパスワード、ホスト キー、バケット、共有は、最初のバックアップではなく今の時点でわかります。ストレージ ページの接続をテストでテストを再実行できます。コンソールは自身のネットワークからテストします。バックアップを書き込むのはエージェントなので、エージェントだけが到達できるターゲット（ローカル ディスクや USB ディスク）は最初のバックアップでテストされます。

SFTP

場所: sftp://user@host:22/path（ユーザーのホーム ディレクトリからの相対パスには /~/path を使用）。パスワードまたは秘密キーと、サーバーのホスト キーのフィンガープリントを入力します。フィンガープリントはサーバー上で次のコマンドで取得できます:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

バックアップ フォルダーにのみ書き込める専用ユーザーを作成してください。

S3 互換

エンドポイント（例: s3.eu-central-1.amazonaws.com、s3.wasabisys.com、10.0.0.5:9000）、バケット、任意のフォルダー、そのバケットへの読み書き権限を持つアクセス キーを入力します。平文 HTTP は、証明書のないローカル MinIO の場合にのみオンにしてください。

不変バックアップ（Object Lock）

バケットを Object Lock を有効にして作成し、変更不可のバックアップ … N 日間をオンにします。エージェントが書き込む各ファイルは コンプライアンス モードで N 日間（+1 日の余裕）ロックされます。その間は、キーを持つ攻撃者もバケットの所有者も、誰も削除や上書きができません。各バックアップの後、古いバックアップから再利用されたデータのロックが延長されるため、すべての復元ポイントが全期間保護されます。

削除（保持処理または攻撃者による）は「削除マーカー」を追加するだけです。ロックの終了後に領域が解放されるよう、最新でないバージョンを 1 日後に期限切れにするライフサイクル ルールを追加してください。ランサムウェア対策を参照してください。

Google Cloud Storage

Google Cloud Storage は、相互運用性 API を通じて S3 互換ターゲットとして動作します:

  1. Google Cloud コンソールで Cloud Storage → Settings → Interoperability を開き、バケットに対して Storage Object Admin ロールを持つサービス アカウントの HMAC キーを作成します。
  2. エンドポイント storage.googleapis.com、バケット名、HMAC のアクセス キーとシークレット、リージョン auto で S3 ターゲットを追加します。

Google Cloud Storage では S3 Object Lock オプションは使えません。不変性が必要な場合は、Google Cloud でバケットの保持ポリシーを設定（してロック）してください。削除されたバックアップは保持期間が終わるまで残ります。

Azure Blob Storage

  1. Azure portal でストレージ アカウント（StorageV2、冗長性は任意）とコンテナー（例: backups）を作成します。
  2. アカウント名、コンテナー、任意のフォルダーで Azure Blob Storage ターゲットを追加します。
  3. アクセス キー（ストレージ アカウント → アクセス キー）で認証するか、より制限するなら、読み取り・書き込み・削除・一覧の権限と適切な有効期限を持つコンテナーの SAS トークンで認証します。

ランサムウェア対策として、コンテナーで時間ベースの保持ポリシーを使ったバージョン レベルの不変性を有効にしてください。削除または上書きされたバックアップは、その期間中は復旧できます。詳細設定のエンドポイント欄は、Azure Government/China、Azure Stack Hub、Azurite エミュレーターの場合にのみ必要です。

ローテーション USB ディスク

取り外してオフサイトに持ち出すディスクは、小規模オフィスにとってランサムウェア、火災、盗難に対する最も簡単な保護です。BackupZit は、Windows が割り当てるドライブ文字に関係なく、ボリューム ラベルでディスクを検出します:

  1. 2 台以上のディスクを NTFS（Linux: ext4）でフォーマットし、BZBACKUP1、BZBACKUP2、… と名前を付けます（Windows: ドライブを右クリック → プロパティ → 名前）。
  2. ラベル BZBACKUP* で ローテーション USB / リムーバブル ディスク タイプのストレージ ターゲットを追加します。
  3. そこへのバックアップ ジョブを作成します。より良いのは、NAS やクラウドのジョブをディスクにコピーするバックアップ コピー ジョブです。
  4. ディスクを定期的に（例: 毎週）交換し、取り外したディスクは安全な場所に保管します。
  • 各ディスクには、独自の保持設定を持つ完全で独立したバックアップが入ります。すべてのディスクはターゲットの回復キーで暗号化されます。
  • 実行には使用したディスクが表示されます（ディスク BZBACKUP2）。復元ではまさにそのディスクを求め、どれが接続されているかを示します。
  • ディスクが接続されていない場合、実行はわかりやすいメッセージとアラートとともに失敗します。ディスクを再接続するためのリマインダーです。
  • 一度に接続するディスクは 1 台だけにしてください。

SMB 共有

サーバー、共有、任意のフォルダー、ユーザー、パスワード、（ドメイン アカウントの場合）ドメイン。エージェントがこの資格情報で自ら接続するため、SYSTEM として実行されるサービスでも動作します。

強化リポジトリ

専用の Linux サーバーに backupzit-repo パッケージをインストールし、そのサーバーで次を実行します:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

サーバーのアドレス、アクセス キー、フィンガープリントをコンソールに入力します。不変期間はリポジトリ サーバー（/etc/backupzit-repo/repo.env）で設定し、コンソールやエージェントからは変更できません。詳細はランサムウェア対策を参照してください。

暗号化と回復キー

バックアップを暗号化（既定）では、リポジトリ内のすべて（ファイルの内容、ファイル名、フォルダー構造、スナップショットの一覧）がエージェントを出る前に AES-256-GCM で暗号化されます。ストレージ プロバイダーにはランダムなデータしか見えません。

暗号化されたターゲットを作成すると、コンソールに回復キーが表示され、復旧シートをダウンロードできます。

復旧シートを印刷するか、バックアップとは別にパスワード マネージャーに保存してください。コンソールを失った場合でも、復元に必要なのは回復キーとストレージの場所および資格情報だけです。キーがなければ、暗号化されたバックアップは誰にも読めません。BackupZit のサポートでも同じです。

後からストレージ一覧のリカバリーキーでキーを再表示できます。この操作はログに記録されます。

ストレージ一覧

一覧には各ターゲットの種類、場所、暗号化（管理者は回復キーにアクセス可能）、不変性（S3 では Object Lock の期間、強化リポジトリではリポジトリサーバーで設定）が表示されます。資格情報は保存後に二度と表示されず、暗号化して保存されます。ターゲットの追加と削除、回復キーの表示ができるのは管理者だけです。

ストレージ使用量と予測

各バックアップ（とその保持処理）の後、エージェントはリポジトリが占める容量を報告し、ローカル ディスク、USB ディスク、SFTP サーバー（OpenSSH の statvfs 拡張）、SMB 共有の場合はストレージのサイズと空き容量も報告します。ストレージ → ストレージ使用量では、各ターゲットについて次を表示します:

  • そのターゲット上のすべてのリポジトリが使用している容量（エージェントごとに 1 つ。ローテーション USB ディスクではディスクごとに集計）。
  • サイズがわかっているストレージでは使用率（75 % から黄色、90 % から赤）。グラフでは容量が赤い破線で表示されます。
  • 過去 90 日間のグラフと、1 週間分のバックアップ後には 1 日あたりの増加量（過去 30 日間の線形トレンド）を 30 日先まで破線で描画し、ストレージがいっぱいになる時期を表示します。サイズが不明な場合は 90 日後の予想使用量を表示します。

ストレージ ターゲットが 90 % に達した場合や 30 日以内にいっぱいになる場合は、ダッシュボードの要対応で警告されます。S3 と Azure には固定のサイズがないため、使用量とその増加のみが表示されます。使用量は保存されたデータ（圧縮・暗号化・重複排除後）であり、ストレージが他の理由で保持しているファイル（オブジェクトのバージョン、他のプログラム）は含まれません。

ターゲットの削除

コンソールからストレージ ターゲットを削除しても、ストレージ上のデータは削除されません。4 アイズ承認が有効な場合は、先に 2 人目のユーザーの承認が必要です。
