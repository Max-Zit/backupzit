ランサムウェア対策

攻撃者は本番データを暗号化する前に、バックアップを削除または暗号化しようとします。BackupZit は、盗まれた資格情報を使われてもバックアップを破壊できないストレージを提供します。

保護の層

層防げるもの
暗号化（AES-256）ストレージ上のバックアップの読み取りや改ざん。あらゆる変更が検出されます。
変更不可の S3（Object Lock、コンプライアンス モード）バックアップの削除や上書き — キーを持つ攻撃者、不正な管理者、操作ミスのいずれによるものも。
強化リポジトリ同じ保護を自社の Linux サーバーで: ファイルは一度だけ書き込まれ、ファイル システムの変更不可フラグが付きます。
オフサイト コピー火災、盗難、拠点の全損。
4 つの目による承認（任意）盗まれた、または悪用された 1 つのコンソール アカウントによるジョブやストレージ先の削除、保持期間の短縮: 2 人目のユーザーの承認が必要になります。ユーザー、ロール、LDAP を参照してください。

不審なバックアップの自動検出

各バックアップはジョブの最近の履歴と比較されます。ランサムウェアや大量削除の痕跡があると 不審 としてマークされます:

  • 通常よりはるかに多くのファイルが変更された（例: 通常の 1 % ではなく 95 %）、
  • 新しいデータが圧縮できなくなった — 暗号化されたファイルはランダムなデータのように見えます、
  • ファイル数が突然 3 分の 1 以上減った、
  • 新しいデータ量が急増した（ディスク イメージ、Linux システム、VM も対象）。

このとき BackupZit はアラート メールを送信し（失敗通知が有効な場合）、ダッシュボードに確認が必要な不審なバックアップとして表示し、ジョブの保持を一時停止します。古いバックアップは削除されないため、破損したバックアップが届き続けても最後の正常なバックアップは復元可能なままです。マシンを確認したら、ジョブのページで 確認済み — 保持を再開 をクリックします。

Object Lock による変更不可の S3

  1. Object Lock を有効にしたバケットを作成します（AWS、Wasabi、Backblaze B2、MinIO: mc mb --with-lock）。
  2. 最新でないバージョン（noncurrent versions）を 1 日後に削除するライフサイクル ルールを追加します（MinIO: mc ilm rule add --noncurrent-expire-days 1 --expire-delete-marker）。
  3. S3 ストレージ先を追加し、N 日間変更不可のバックアップをオンにします。N は保護したい最長の保持期間以上にします（例: 30）。

各復元ポイントは作成後少なくとも N 日間ロックされます。新しいバックアップと共有されるデータのロックは自動的に延長されます。

強化リポジトリ

backupzit-repo を実行する専用の Linux サーバー:

  • エージェントとコンソールはファイルの追加しかできません。既存のファイルが上書きされることはありません。
  • 各ファイルには、そのサーバーで設定した期間 chattr +i 属性が付きます。root でも先にフラグを外さない限り削除できません。
  • クライアントからの削除は、期間が終わるまでファイルを非表示にするだけです。
  • サービスは非特権ユーザーとして動作し、唯一の権限は変更不可フラグの設定です。
apt install ./backupzit-repo_*.deb
vi /etc/backupzit-repo/repo.env        # BACKUPZIT_REPO_LOCK_DAYS=30
systemctl start backupzit-repo
backupzit-repo add-key office-console
backupzit-repo fingerprint

セットアップ後は、リポジトリ サーバーで SSH などのリモート アクセスを無効化し、ローカル コンソール / iDRAC / iLO / ハイパーバイザーへのアクセスを保護してください。保護の強さは、そのマシンの root アカウントの強さで決まります。

攻撃後の復旧

攻撃者がバックアップを削除または上書きした場合は、ストレージを攻撃前の状態で読み取ります — 読み取り専用で、何も変更しません:

backupzit-agent snapshots --repo <リポジトリ> --as-of 2026-10-01T14:30
backupzit-agent restore   --repo <リポジトリ> --as-of 2026-10-01T14:30 --target D:\Restore latest

強化リポジトリでは、管理者が非表示のファイルを元に戻し、バックアップを通常どおり続けることもできます:

backupzit-repo status
backupzit-repo undelete --since 2026-10-01T14:00

推奨事項

  • ストレージには、Windows ドメインに参加していない専用のアカウントを使います。
  • 少なくとも 1 つの変更不可のコピーを保持します（S3 Object Lock または強化リポジトリ）。
  • リカバリーシートはオフライン（印刷して金庫）で保管します。
  • メール アラートを有効にします — 失敗数や送信データ量の急な変化は、攻撃の最初の兆候であることがよくあります。
