ユーザー、ロール、LDAP

各人に、必要な権限だけを持つ専用のアカウントを与えます — ローカル アカウントとして、または Active Directory / LDAP のサインインで。

ローカル ユーザー

ユーザー → 新しいローカル ユーザー で、ユーザー名、ロール、10 文字以上のパスワードを入力します。ユーザーのページでは、ロールの変更、アカウントの無効化（開いているセッションはすぐに終了）、新しいパスワードの設定、ユーザーの削除ができます。

各ユーザーは マイ アカウント（右上の自分の名前をクリック）で自分のパスワードを変更できます。

有効な ローカル管理者 が常に 1 人以上残るため、ディレクトリに到達できないときでもサインインできます。自分自身の降格、無効化、削除はできません。

Active Directory / LDAP でのサインイン

設定 → LDAP / Active Directory で設定します:

  1. サーバー: ldaps://dc1.example.local:636。プレーンな ldap:// は StartTLS 付きでのみ受け付けるため、パスワードが暗号化されずに送られることはありません。
  2. サービス アカウント: ユーザーとグループの検索に使う通常のドメイン アカウント（読み取り権限で十分）。例: CN=svc-backupzit,OU=Service Accounts,DC=example,DC=local。
  3. 検索ベース: 例: DC=example,DC=local。
  4. ユーザーフィルター: Active Directory は (&(objectClass=user)(sAMAccountName={username}))、OpenLDAP は (&(objectClass=inetOrgPerson)(uid={username}))。
  5. グループ → ロール: 使用するロールごとにグループの完全な DN を指定します。例: CN=BackupZit Admins,OU=Groups,DC=example,DC=local。一致する最も高いロールが適用されます。どのグループにも属さないユーザーはサインインできません。サブグループのメンバーも含めるには、Active Directory で 入れ子のグループ をオンにします。
  6. 証明書の信頼: ドメイン コントローラーが社内 CA を使っている場合は CA 証明書を貼り付けます。自己署名証明書の場合はフィンガープリントを入力します。
  7. 実在のユーザーで テスト を使い、接続、パスワード、得られるロールを確認してから 保存 します。

ディレクトリ ユーザーは初回サインイン後にユーザー一覧に表示されます。名前、メール、ロールはサインインのたびにディレクトリから更新されます。ディレクトリ ユーザーをすぐにブロックするには、BackupZit（またはディレクトリ）でアカウントを無効にします。

シングルサインオン（SAML、OpenID Connect）

シングルサインオンでは、ユーザーはサインイン ページで サインイン: … をクリックし、ID プロバイダーでサインインします — Microsoft Entra ID（Azure AD）、Okta、Google Workspace、Keycloak、ADFS、その他の SAML 2.0 または OpenID Connect プロバイダー。設定 → シングルサインオン で設定します:

  1. OpenID Connect（利用できる場合は推奨）または SAML 2.0 を選びます。
  2. OpenID Connect: 設定ページに表示されるリダイレクト URI（https://<コンソール>/login/sso/callback）で ID プロバイダーに Web アプリを登録し、issuer、クライアント ID、クライアント シークレットを入力します。プロバイダーがユーザーのグループを groups クレームに入れるようにします（Entra ID: グループ ID を送る Token configuration → Add groups claim、Keycloak: Group Membership マッパー、Okta: groups クレーム）。
  3. SAML 2.0: コンソールのメタデータ URL（https://<コンソール>/login/sso/metadata、アサーション コンシューマー サービス /login/sso/acs）で ID プロバイダーにコンソールを追加し、グループを属性として送るようにして、ID プロバイダーのメタデータ URL を入力するか、メタデータ XML を貼り付けます。SAML ではコンソールが HTTPS である必要があります。アサーションは署名されている必要があります。コンソールの要求は署名されません。
  4. グループ（名前、Entra ID の場合は ID）を 4 つのロールに対応付けます。一致する最も高いロールが適用されます。どれにも属さないユーザーは、ロールを選ばない限りサインインできません。

HTTPS 証明書が自社 CA の発行または自己署名である ID プロバイダー（オンプレミスの Keycloak や AD FS）には、その CA 証明書を CA 証明書（PEM） に設定する必要があります。パブリックなもの（Entra ID、Okta、Google）は不要です。保存時に ID プロバイダーが応答するかを確認します。ユーザーは初回サインイン時に作成され（ユーザー一覧で SSO と表示）、ディレクトリ ユーザーと同様にサインインのたびにグループからロールを受け取ります。名前とメールは ID プロバイダーから取得されます。2 要素目は ID プロバイダーが担うため、コンソールは SSO ユーザーに独自の 2 要素コードを求めません。ローカル アカウントは引き続き使えるため、ID プロバイダーに到達できないときでも管理者は常にサインインできます。サインインの応答は 1 回しか使えず、ID プロバイダーの署名が必要です。SSO のサインインと拒否はすべて監査ログに記録されます。

セッション

設定 → サインインとセキュリティ で、サインインの有効期間（既定 12 時間）と、何分間操作がなければサインアウトするか（既定 60、0 = しない）を設定します。誤ったパスワードが繰り返されると、そのアドレスはしばらくブロックされます: 既定では 15 分以内に 5 回失敗すると 30 分間。上限は同じページにあります。セキュリティ を参照してください。

2 要素認証

各ユーザーは マイ アカウント → 2 要素 で、サインインを 2 要素目で保護できます: 認証アプリ（Microsoft / Google Authenticator、Authy、1Password、Bitwarden など）で QR コードを読み取り、6 桁のコードを入力します。使い捨ての リカバリー コード が 10 個、一度だけ表示されます — 安全に保管してください。電話を紛失した場合、それぞれ 1 回使えます。シングルサインオン でサインインするユーザーにはコンソールのコードは求められません: 2 要素目は ID プロバイダーが担います。

設定 → サインインとセキュリティ で、管理者 または すべてのユーザー に 2 要素認証を必須にできます。次回のサインイン後に設定を求められます。ユーザーが電話とリカバリー コードの両方を失った場合は、管理者がユーザーのページで 2 要素サインインをリセットします。2 要素認証はディレクトリ（LDAP）アカウントでも使えます。

API トークン

スクリプトや監視ツールは、パスワードの代わりに API トークンを使います。各ユーザーは マイ アカウント → API トークン で自分のトークンを作成・失効させます。トークンのロールはユーザー自身のロールより低くできます。管理者は ユーザー ページですべてのトークンを確認し、失効させることができます。REST API を参照してください。

4 つの目による承認

任意の機能で、既定ではオフです。設定 → サインインとセキュリティ → 4 つの目による承認 でオンにします。有効な管理者が 2 人以上必要です。オンにすると、次の変更は 2 人目のユーザー が承認したときにのみ有効になります:

変更承認できるユーザー
バックアップ ジョブの削除または無効化、ジョブの保持期間の短縮（以前より低いルール、またはすべて保持していた箇所へのルール追加）、不審なバックアップ後の保持の再開ジョブを管理できるユーザー
エージェントまたは ESXi ホストの削除エージェントを管理できるユーザー
ストレージ先の削除ストレージを管理できるユーザー
ユーザーの削除。承認できるユーザー（管理者またはバックアップ オペレーター）の作成。ユーザーへのより多くの権限を持つロールの付与、またはそのようなユーザーの再有効化。そのようなユーザーのパスワードや 2 要素サインインのリセット管理者
LDAP サインインまたはシングルサインオンの変更（ディレクトリ ユーザーのロールを決めるため）管理者
4 つの目による承認のオフ管理者

要求は 承認 に表示され（メニューとダッシュボードにカウンター付き）、通知の受信者にメールが届きます。適切な権限を持つほかのユーザーが承認または却下します。要求者は取り消すことしかできません。承認された変更はすぐに実行されます。要求は 7 日後に期限切れになります。より短い保持期間でジョブを編集した場合、ほかの変更はすぐに保存され、保持だけが承認待ちになります。要求、承認、却下とそのユーザーは監査ログに記録されます。

要求の前から存在していたアカウントだけが、その要求を判断できます。 新しい承認者、パスワードのリセット、ディレクトリ設定の承認と合わせて、1 人の管理者が単独で 2 人目の承認者を得ること — たとえば 2 つ目の管理者アカウントを作る、別の管理者のパスワードを設定する、ディレクトリのグループを管理者ロールに対応付ける — を防ぎます。オプションがオンの間、有効な最後の 2 人の管理者は削除、無効化、降格できないため、要求は常に判断できます。要求内のパスワードはハッシュとしてのみ保存され、LDAP とシングルサインオンの設定はコンソールのシークレット キーで暗号化されます。ディレクトリ自体（Active Directory、Entra ID）でのグループ メンバーシップはコンソールの管理外です。それらの管理者グループはそちらで保護してください。

これにより、盗まれた、または悪用された 1 つのアカウントが構成を削除したり、保持にバックアップを削除させたりすることを防ぎます。変更不可のストレージの代わりにはなりません: それについては ランサムウェア対策 を参照してください。

監査ログ

ユーザー → 監査ログ には、サインイン、失敗したサインイン、変更（ユーザー、ジョブ、ストレージ先、復元、表示されたリカバリー キー、設定）が、時刻、ユーザー、アドレスとともに表示されます。

改ざんからの保護

各エントリは前のエントリと連鎖しています: 自身の内容と前のエントリのハッシュを持ち、サーバーのシークレット ファイル（データベースにはない）の秘密で計算されます。そのため、データベースで直接エントリを変更または削除すると連鎖が壊れます。最新のハッシュはコンソールのデータの横にあるファイルにも保存されるため、最新のエントリの削除も検出されます。

  • コンソールは起動時と 1 日 1 回、連鎖全体を確認します。壊れている場合、監査ログ ページに最初の不正なエントリとともに 監査ログが変更されました と表示され、管理者にメールが届きます。
  • 監査ログ ページの 今すぐ整合性を確認 で、すぐに確認を実行します。
  • バージョン 0.33.3 より前に書き込まれたエントリには連鎖がありません。ページにその件数が表示されます。

連鎖はログが変更されたことを示しますが、変更された内容を取り戻すことはできません — また、シークレット ファイルごとコンソール サーバー自体を乗っ取った者は連鎖を書き換えられます。これに備えて、設定 → サインインとセキュリティ → 監査ログの保護 で、各エントリのコピーを別の syslog サーバーや SIEM に送信します:

  • Syslog サーバー を host:port で指定し、プロトコル を選びます: TLS（推奨、通常ポート 6514）、TCP または UDP（通常 514）。TLS サーバーの証明書はコンソール マシンから信頼されている必要があります。
  • 保存するとテスト メッセージが送信されます。サーバーが受け付けない場合も設定は保存され、エラーが表示されます。
  • メッセージは RFC 5424 形式（facility auth）で、エントリ番号、ユーザー、操作、アドレス、連鎖ハッシュを含みます。1 日 1 回、audit.checkpoint メッセージが最新のハッシュを運ぶため、コピーとコンソールを比較できます。
  • syslog サーバーに到達できない間、エントリはメモリーで待機し（最大 1000 件）、再び応答したときに送信されます。コンソールは動作を続け、エントリはいずれにせよコンソール自身の監査ログに残ります。
