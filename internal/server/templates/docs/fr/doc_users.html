Utilisateurs, rôles et LDAP

Donnez à chaque personne son propre compte avec uniquement les droits dont elle a besoin — en comptes locaux, ou avec sa connexion Active Directory / LDAP.

Usage typique : les administrateurs informatiques sont Administrateurs ; les personnes qui gèrent les sauvegardes au quotidien sont Opérateurs de sauvegarde ; le support qui récupère les fichiers supprimés est Opérateur de restauration ; la direction et les auditeurs sont Lecteurs. Les pages et boutons qu'un rôle ne peut pas utiliser sont masqués, et le serveur les refuse de toute façon. Notez qu'une restauration peut écraser des données — la restauration d'une image disque ou d'un système Linux efface le disque cible, et une restauration de VM avec remplacer supprime la VM existante — ne donnez donc les rôles de restauration qu'aux personnes à qui vous confieriez cela ; chaque restauration figure dans le journal d'audit.

Utilisateurs locaux

Dans Utilisateurs → Nouvel utilisateur local, saisissez un nom d'utilisateur, un rôle et un mot de passe d'au moins 10 caractères. Sur la page de l'utilisateur, vous pouvez changer le rôle, désactiver le compte (les sessions ouvertes se terminent immédiatement), définir un nouveau mot de passe ou supprimer l'utilisateur.

Chaque utilisateur peut changer son propre mot de passe dans Mon compte (cliquez sur votre nom en haut à droite).

Il reste toujours au moins un administrateur local actif, afin que vous puissiez vous connecter même si l'annuaire est injoignable. Vous ne pouvez pas vous rétrograder, vous désactiver ou vous supprimer vous-même.

Connexion avec Active Directory / LDAP

Dans Paramètres → LDAP / Active Directory :

  1. Serveur : ldaps://dc1.example.local:636. Le simple ldap:// n'est accepté qu'avec StartTLS, de sorte que les mots de passe ne circulent jamais en clair.
  2. Compte de service : un compte de domaine normal utilisé pour rechercher utilisateurs et groupes (l'accès en lecture suffit), par ex. CN=svc-backupzit,OU=Service Accounts,DC=example,DC=local.
  3. Base de recherche : par ex. DC=example,DC=local.
  4. Filtre d'utilisateurs : Active Directory (&(objectClass=user)(sAMAccountName={username})), OpenLDAP (&(objectClass=inetOrgPerson)(uid={username})).
  5. Groupes → rôles : le DN complet d'un groupe pour chaque rôle que vous voulez utiliser, par ex. CN=BackupZit Admins,OU=Groups,DC=example,DC=local. Le rôle le plus élevé correspondant l'emporte ; les utilisateurs qui ne sont dans aucun groupe ne peuvent pas se connecter. Cochez groupes imbriqués dans Active Directory pour inclure les membres des sous-groupes.
  6. Confiance du certificat : si les contrôleurs de domaine utilisent une AC interne, collez le certificat de l'AC ; pour un certificat auto-signé, saisissez son empreinte.
  7. Utilisez Test avec un vrai utilisateur pour vérifier la connexion, le mot de passe et le rôle obtenu, puis Enregistrer.

Les utilisateurs de l'annuaire apparaissent dans la liste des utilisateurs après leur première connexion. Leur nom, leur e-mail et leur rôle sont mis à jour depuis l'annuaire à chaque connexion. Pour bloquer immédiatement un utilisateur de l'annuaire, désactivez le compte dans BackupZit (ou dans l'annuaire).

Authentification unique (SAML, OpenID Connect)

Avec l'authentification unique, les utilisateurs cliquent sur Se connecter avec … sur la page de connexion et se connectent auprès de votre fournisseur d'identité — Microsoft Entra ID (Azure AD), Okta, Google Workspace, Keycloak, ADFS ou tout autre fournisseur SAML 2.0 ou OpenID Connect. Configurez-la dans Paramètres → Authentification unique :

  1. Choisissez OpenID Connect (recommandé quand c'est possible) ou SAML 2.0.
  2. OpenID Connect : enregistrez une application web auprès du fournisseur d'identité avec l'URI de redirection affichée sur la page des paramètres (https://<console>/login/sso/callback), et saisissez son émetteur (issuer), son ID client et son secret client. Faites placer par le fournisseur les groupes de l'utilisateur dans une revendication groups (Entra ID : Token configuration → Add groups claim, qui envoie des ID de groupe ; Keycloak : un mappeur Group Membership ; Okta : une revendication groups).
  3. SAML 2.0 : ajoutez la console auprès du fournisseur d'identité avec son URL de métadonnées (https://<console>/login/sso/metadata, service consommateur d'assertions /login/sso/acs), faites-lui envoyer les groupes comme attribut, et saisissez l'URL des métadonnées du fournisseur d'identité ou collez son XML de métadonnées. SAML exige la console en HTTPS. Les assertions doivent être signées ; les requêtes de la console ne le sont pas.
  4. Associez des groupes (noms, ou ID pour Entra ID) aux quatre rôles ; le rôle le plus élevé correspondant l'emporte. Les utilisateurs qui ne sont dans aucun d'eux ne peuvent pas se connecter, sauf si vous choisissez un rôle pour eux.

Un fournisseur d'identité dont le certificat HTTPS provient de votre propre AC ou est auto-signé (un Keycloak ou AD FS sur site) a besoin de ce certificat d'AC dans Certificat de l’AC (PEM) ; les fournisseurs publics (Entra ID, Okta, Google) n'ont besoin de rien. L'enregistrement vérifie que le fournisseur d'identité répond. Les utilisateurs sont créés à leur première connexion (marqués SSO dans Utilisateurs) et reçoivent leur rôle depuis leurs groupes à chaque connexion, comme les utilisateurs de l'annuaire ; leur nom et leur e-mail viennent du fournisseur d'identité. Le second facteur est géré par le fournisseur d'identité, la console ne demande donc pas aux utilisateurs SSO son propre code à deux facteurs. Les comptes locaux continuent de fonctionner, de sorte qu'un administrateur peut toujours se connecter même si le fournisseur d'identité est injoignable. Une réponse de connexion n'est utilisable qu'une seule fois et doit être signée par le fournisseur d'identité ; chaque connexion SSO et chaque refus figurent dans le journal d'audit.

Sessions

Dans Paramètres → Connexion et sécurité, définissez la durée d'une connexion (12 heures par défaut) et après combien de minutes d'inactivité les utilisateurs sont déconnectés (60 par défaut, 0 = jamais). Des mots de passe erronés répétés bloquent l'adresse pendant un moment : par défaut après 5 échecs en 15 minutes, pendant 30 minutes. Les limites se trouvent sur la même page ; voir Sécurité.

Authentification à deux facteurs

Chaque utilisateur peut protéger sa connexion par un second facteur dans Mon compte → Deux facteurs : scannez le code QR avec une application d'authentification (Microsoft ou Google Authenticator, Authy, 1Password, Bitwarden…) et saisissez le code à 6 chiffres. Dix codes de récupération à usage unique sont affichés une fois — conservez-les en lieu sûr ; chacun fonctionne une fois si le téléphone est perdu. Les utilisateurs qui se connectent par authentification unique ne doivent pas saisir le code de la console : leur fournisseur d'identité gère le second facteur.

Dans Paramètres → Connexion et sécurité, vous pouvez exiger l'authentification à deux facteurs pour les administrateurs ou pour tous les utilisateurs ; il leur est demandé de la configurer après leur prochaine connexion. Si un utilisateur perd à la fois son téléphone et ses codes de récupération, un administrateur réinitialise la double authentification sur la page de l'utilisateur. Elle fonctionne aussi pour les comptes de l'annuaire (LDAP).

Jetons API

Les scripts et outils de supervision utilisent des jetons API au lieu de mots de passe. Chaque utilisateur crée et révoque ses propres jetons dans Mon compte → Jetons API ; le rôle d'un jeton peut être inférieur à celui de l'utilisateur. Les administrateurs voient et peuvent révoquer tous les jetons sur la page Utilisateurs. Voir REST API.

Approbation à quatre yeux

Facultative et désactivée par défaut. Activez-la dans Paramètres → Connexion et sécurité → Approbation à quatre yeux ; elle nécessite au moins deux administrateurs actifs. Ces modifications ne prennent alors effet que lorsqu'un second utilisateur les approuve :

ModificationQui peut approuver
Supprimer ou désactiver une tâche de sauvegarde, raccourcir la rétention d'une tâche (toute règle plus basse qu'avant, ou des règles là où tout était conservé), reprendre la rétention après une sauvegarde suspecteLes utilisateurs autorisés à gérer les tâches
Supprimer un agent ou un hôte ESXiLes utilisateurs autorisés à gérer les agents
Supprimer une cible de stockageLes utilisateurs autorisés à gérer le stockage

Modifier la connexion LDAP ou l'authentification unique (elles déterminent les rôles des utilisateurs de l'annuaire)Administrateurs

La demande apparaît dans Approbations (avec un compteur dans le menu et sur le tableau de bord) et les destinataires des notifications reçoivent un e-mail. Tout autre utilisateur disposant de l'autorisation adéquate l'approuve ou la rejette ; le demandeur peut seulement l'annuler. Une modification approuvée est exécutée immédiatement. Les demandes expirent après 7 jours. Lorsqu'une tâche est modifiée avec une rétention plus courte, ses autres modifications sont enregistrées immédiatement et seule la rétention attend. Les demandes, approbations, rejets et leurs utilisateurs figurent dans le journal d'audit.

Seuls les comptes qui existaient avant une demande peuvent en décider. Avec l'approbation des nouveaux approbateurs, des réinitialisations de mot de passe et des paramètres d'annuaire, cela empêche un administrateur seul d'obtenir un second approbateur — par exemple en créant un second compte administrateur, en définissant le mot de passe d'un autre administrateur ou en associant un groupe de l'annuaire au rôle Administrateur. Tant que l'option est active, les deux derniers administrateurs actifs ne peuvent être ni supprimés, ni désactivés, ni rétrogradés, de sorte qu'il est toujours possible de statuer sur les demandes. Les mots de passe contenus dans les demandes ne sont stockés que sous forme de hachage, et les paramètres LDAP et d'authentification unique chiffrés avec la clé des secrets de la console. Les appartenances aux groupes dans l'annuaire lui-même (Active Directory, Entra ID) sont hors de la console ; protégez-y ces groupes d'administrateurs.

Cela protège contre un seul compte volé ou détourné qui supprimerait la configuration ou laisserait la rétention effacer les sauvegardes. Cela ne remplace pas un stockage immuable : pour cela, voir Protection contre les rançongiciels.

Journal d'audit

Utilisateurs → Journal d'audit affiche les connexions, les échecs de connexion et les modifications : utilisateurs, tâches, cibles de stockage, restaurations, clés de récupération affichées et paramètres — avec l'heure, l'utilisateur et l'adresse.

Protection contre les modifications

Chaque entrée est chaînée à la précédente : elle porte un hachage de son propre contenu et de l'entrée précédente, calculé avec un secret du fichier de secrets du serveur (qui n'est pas dans la base de données). Quiconque modifie ou supprime des entrées directement dans la base rompt donc la chaîne. Le hachage le plus récent est aussi conservé dans un fichier à côté des données de la console, de sorte que la suppression des entrées les plus récentes est également détectée.

  • La console vérifie toute la chaîne au démarrage et une fois par jour. Si elle est rompue, la page Journal d'audit affiche Le journal d'audit a été modifié avec la première entrée défectueuse, et les administrateurs reçoivent un e-mail.
  • Vérifier l'intégrité maintenant sur la page Journal d'audit lance la vérification immédiatement.
  • Les entrées écrites avant la version 0.33.3 n'ont pas de chaîne ; la page indique combien il y en a.

La chaîne montre que le journal a été modifié, mais ne peut pas restaurer ce qui l'a été — et quelqu'un qui prend le contrôle du serveur de la console lui-même, avec son fichier de secrets, pourrait réécrire la chaîne. Pour s'en protéger, envoyez une copie de chaque entrée à un serveur syslog ou SIEM séparé dans Paramètres → Connexion et sécurité → Protection du journal d'audit :

  • Serveur syslog sous la forme hôte:port, et le protocole : TLS (recommandé, généralement port 6514), TCP ou UDP (généralement 514). Le certificat d'un serveur TLS doit être approuvé par la machine de la console.
  • L'enregistrement envoie un message de test ; si le serveur ne l'accepte pas, les paramètres sont enregistrés et l'erreur est affichée.
  • Les messages sont au format RFC 5424 (facility auth) avec le numéro d'entrée, l'utilisateur, l'action, l'adresse et le hachage de chaîne. Une fois par jour, un message audit.checkpoint contient le hachage le plus récent, afin que la copie puisse être comparée à la console.
  • Tant que le serveur syslog est injoignable, les entrées attendent en mémoire (jusqu'à 1000) et sont envoyées dès qu'il répond à nouveau ; la console continue de fonctionner, et les entrées restent de toute façon dans son propre journal d'audit.
