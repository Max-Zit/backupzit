Installer le serveur

La console tourne sous Linux (Debian, Ubuntu, AlmaLinux, Rocky Linux) avec PostgreSQL. Chaque organisation exploite sa propre console sur son propre réseau.

Prérequis

  • Une VM ou un serveur Linux : 2 vCPU, 2–4 Go de RAM et 20 Go de disque suffisent pour des centaines d'agents (les données de sauvegarde n'y sont pas stockées).
  • PostgreSQL 13 ou plus récent (local ou sur un autre serveur).
  • Réseau : les agents doivent joindre la console en TCP 8443 (HTTPS). Les agents doivent aussi joindre directement le stockage.

Choisir le mode d'installation

1. Image de VM prête à l'emploi (OVA, qcow2, VHDX)Le plus rapide : importer, démarrer, se connecterVMware, Proxmox/KVM ou Hyper-V ; aucun accès internet nécessaire

1. Image de VM prête à l'emploi

Une appliance terminée (Debian, PostgreSQL, la console, mises à jour de sécurité automatiques) qui démarre en moins d'une minute et ne nécessite aucun accès internet :

HyperviseurComment
VMware ESXiHost Client : Create / Register VM → Deploy a virtual machine from an OVF or OVA file, choisissez backupzit-appliance.ova. vSphere : Deploy OVF Template. Workstation et VirtualBox : File → Open / Import.
Proxmox VECopiez backupzit-appliance.qcow2 sur le nœud, créez une VM sans disque (2 vCPU, 2–4 Go de RAM, réseau VirtIO), puis
qm importdisk <vmid> backupzit-appliance.qcow2 local-lvm
attachez le disque importé en SCSI, faites-en le disque de démarrage et activez l'agent invité QEMU.
Hyper-VDécompressez backupzit-appliance-vhdx.zip, puis Nouveau → Ordinateur virtuel, génération 1, 2–4 Go de RAM, Utiliser un disque dur virtuel existant : le VHDX.

Démarrez la VM. Son écran affiche l'adresse de la console web et le mot de passe initial d'admin (voir Première connexion). Donnez à la VM 2 vCPU et 2–4 Go de RAM ; vous pouvez agrandir le disque de 16 Go à tout moment — l'appliance utilise le nouvel espace à son démarrage suivant (le système de fichiers racine s'agrandit à chaud). Au premier démarrage, chaque copie crée ses propres clés SSH, son mot de passe de base de données et sa clé de secrets, si bien qu'une même image peut être déployée de nombreuses fois. La carte réseau obtient son adresse par DHCP.

2. ISO de l'appliance

L'ISO de l'appliance installe tout sans poser de questions : Debian, PostgreSQL, la console et les mises à jour de sécurité automatiques.

  1. Créez une VM (ou utilisez un serveur) avec 2 vCPU, 2–4 Go de RAM et un disque de 16 Go ou plus. Utilisez VirtIO ou les périphériques par défaut de l'hyperviseur, BIOS ou UEFI.
  2. Démarrez-la sur backupzit-appliance.iso. Après 5 secondes, l'installation démarre d'elle-même, efface le premier disque et installe. Elle télécharge les paquets du système d'exploitation ; le serveur a donc besoin d'un accès internet pendant l'installation. Cela prend environ 10–20 minutes, puis le serveur redémarre.
  3. L'écran du serveur affiche l'adresse de la console web et le mot de passe initial d'admin. Ouvrez l'adresse, connectez-vous et changez le mot de passe.

L'appliance (image ou ISO)

L'appliance a deux comptes distincts :

  • admin dans la console web (https://<address>:8443) pour le travail quotidien. Son mot de passe initial s'affiche sur l'écran du serveur après le premier démarrage ; changez-le sous Mon compte.
  • bzadmin sur le serveur lui-même (son écran dans la console de l'hyperviseur, ou SSH), mot de passe initial backupzit. Vous devez le changer à la première connexion ; l'utilisateur peut utiliser sudo. Root ne peut pas se connecter.

Les mises à jour de BackupZit et du système d'exploitation se gèrent depuis la console (voir ci-dessous). VMware Tools et l'agent invité QEMU sont inclus, si bien que les hyperviseurs affichent l'adresse de l'appliance.

Menu de configuration sur l'écran du serveur

Quand bzadmin se connecte sur l'écran même du serveur (pas en SSH), un menu s'ouvre :

ÉlémentCe qu'il fait
1 NetworkDHCP ou une adresse statique avec longueur de préfixe (p. ex. 192.168.1.20/24), passerelle et jusqu'à trois serveurs DNS.
2 Server nameLe nom d'hôte (lettres, chiffres et -).
3 SSHActive ou désactive le serveur SSH et change son port. Les ports de la console (80, 443, 8443), de PostgreSQL (5432) et de la restauration instantanée (111, 2049) ne peuvent pas être utilisés.
4 Reset the password of "admin"Pour un mot de passe de console web oublié ; lève aussi les blocages de connexion. L'écran cesse ensuite d'afficher le mot de passe initial généré (de même dès le démarrage suivant une fois le mot de passe d'admin changé dans la console web).
5 Lift sign-in blocks and web console limitsQuand trop de connexions échouées ont bloqué une adresse, ou que la console web est limitée à des adresses que vous ne pouvez plus utiliser (voir Sécurité).
6–8Redémarrer la console web, redémarrer ou éteindre le serveur.
9 Time zoneL'appliance démarre en UTC. Définissez votre fuseau, p. ex. Europe/Belgrade : la console y affiche toutes les heures, exécute les planifications et lit les points de restauration (y compris l'instant d'une restauration de base de données). La console redémarre pour l'appliquer.
0 Command lineQuitte le menu. Rouvrez-le avec sudo backupzit-server --setup (aussi en SSH).

Les mêmes réglages de réseau, nom du serveur, SSH et fuseau horaire se trouvent sous Paramètres → Réseau dans la console web (administrateurs uniquement). Là, une adresse statique dont la passerelle ne répond pas dans la demi-minute est annulée automatiquement, si bien qu'une faute de frappe ne peut pas couper l'appliance du réseau ; si la console reste injoignable, utilisez le menu sur l'écran du serveur, qui fonctionne même avec SSH désactivé.

Les agents mémorisent le certificat de la console, pas son adresse. S'ils joignent la console par son adresse IP et que celle-ci change, dirigez-les vers la nouvelle avec backupzit-agent set-server (voir Agents), ou utilisez dès le départ un nom DNS. Avec DHCP, réservez l'adresse de l'appliance dans le serveur DHCP pour qu'elle ne change pas.

Le serveur SSH de l'appliance n'offre que les chiffrements AES-GCM/CTR et les MAC SHA-2 (ni chacha20-poly1305 ni MAC 64 bits, que les scanners de vulnérabilités signalent comme faibles).

3. Script d'installation

Sur un serveur existant avec Debian 12+, Ubuntu 22.04+, AlmaLinux ou Rocky Linux 9+ (x86-64), en root :

curl -fsSL https://github.com/Max-Zit/backupzit/releases/latest/download/install.sh | sudo sh

Le script installe PostgreSQL, télécharge la version la plus récente, vérifie sa signature avec la clé de publication BackupZit ainsi que la somme de contrôle du paquet, installe la console, crée la base de données avec un mot de passe aléatoire, écrit /etc/backupzit/server.env, active les mises à jour de sécurité automatiques, ouvre le port 8443 dans firewalld ou ufw s'ils sont actifs, démarre la console et affiche son adresse et le mot de passe admin initial. Options (après sh -s --) :

OptionEffet
--version 0.32.0installer cette version au lieu de la plus récente
--db postgres://user:pw@host:5432/dbutiliser une base PostgreSQL existante au lieu d'une base locale
--hosts backup.example.local,10.0.0.10noms et adresses pour le certificat de la console (par défaut : l'adresse et le nom du serveur)
--no-auto-updateslaisser les mises à jour de sécurité automatiques telles quelles

Exemple : curl -fsSL …/install.sh | sudo sh -s -- --hosts backup.example.local. Relancer le script sur une console installée met BackupZit à jour en conservant la configuration et les données. Pour lire le script avant de l'exécuter, téléchargez-le d'abord : curl -fsSLO …/install.sh; less install.sh; sudo sh install.sh.

4. Paquets à la main

Debian / Ubuntu

apt install postgresql
apt install ./backupzit-server_*.deb

AlmaLinux / Rocky Linux

dnf install postgresql-server && postgresql-setup --initdb && systemctl enable --now postgresql
dnf install ./backupzit-server-*.rpm

Sous AlmaLinux et Rocky Linux, remplacez ident par scram-sha-256 pour les lignes 127.0.0.1 et ::1 de /var/lib/pgsql/data/pg_hba.conf et redémarrez PostgreSQL, pour que la console puisse se connecter avec un mot de passe.

Créer la base de données

sudo -u postgres psql -c "SET password_encryption = 'scram-sha-256'; CREATE USER backupzit WITH PASSWORD 'choose-a-strong-password'"
sudo -u postgres psql -c "CREATE DATABASE backupzit OWNER backupzit"

Mettez la chaîne de connexion dans /etc/backupzit/server.env :

BACKUPZIT_DB=postgres://backupzit:choose-a-strong-password@localhost:5432/backupzit?sslmode=disable
BACKUPZIT_PUBLIC_URL=https://backup.example.local:8443
BACKUPZIT_TLS_HOSTS=backup.example.local,10.0.0.10
systemctl start backupzit-server

Première connexion

Ouvrez https://<server>:8443. L'administrateur initial est admin ; le mot de passe se trouve dans /var/lib/backupzit/initial-admin-password.txt (ou définissez BACKUPZIT_ADMIN_PASSWORD avant le premier démarrage). Changez-le après la connexion. Pour réinitialiser un mot de passe oublié sur le serveur :

set -a; . /etc/backupzit/server.env; set +a
backupzit-server --set-admin-password 'NEW-PASSWORD'

Le certificat

Au premier démarrage, la console crée un certificat auto-signé. Votre navigateur vous avertira une fois ; les agents ne s'appuient pas du tout sur les autorités de certification — ils épinglent l'empreinte du certificat affichée sur la page Agents lors de leur inscription. Cela protège les agents contre un faux serveur même sur un réseau non fiable.

Ne remplacez pas ce certificat (cert.pem/key.pem dans le répertoire de données) : les agents inscrits auparavant refuseraient de se connecter jusqu'à leur réinscription. Pour les navigateurs, ajoutez plutôt un certificat de confiance comme décrit ci-dessous.

Un certificat de confiance pour les navigateurs

Pour éviter l'avertissement du navigateur, ouvrez Paramètres → Certificat. La console répond alors aussi à un nom DNS, par exemple https://backup.example.com sur le port 443, avec un certificat de confiance. Les agents continuent d'utiliser le port 8443 et le certificat épinglé ; ils ne sont donc pas concernés.

  • Téléverser un certificat de votre CA d'entreprise ou d'une CA publique, y compris un certificat générique comme *.example.com. Collez le certificat (avec ses certificats intermédiaires) et la clé privée au format PEM, ou choisissez les fichiers. La console vérifie que la clé correspond au certificat, qu'il est valide maintenant et qu'il couvre le nom DNS. Sans DNS interne, saisissez plutôt l'adresse IP de la console et utilisez un certificat émis pour cette adresse IP (nom alternatif IP:192.168.1.20) ; donnez alors une adresse fixe à la console. Vous recevez un e-mail 21 jours avant l'expiration.
  • Let's Encrypt : certificats gratuits, renouvelés automatiquement 30 jours avant leur expiration. Let's Encrypt doit vérifier que vous contrôlez le nom, de l'une de deux façons :
    • Vérification DNS via Cloudflare, recommandée pour les consoles non joignables depuis internet. BackupZit crée un enregistrement TXT temporaire avec un jeton API Cloudflare. Dans Cloudflare, allez dans My Profile → API Tokens → Create Token, utilisez le modèle Edit zone DNS et limitez-le à votre zone.
    • Vérification HTTP : le port 80 de la console doit être joignable depuis internet sous le nom DNS. C'est rarement souhaitable pour un serveur de sauvegarde.
    Essayez d'abord la configuration avec Utiliser le système de test de Let's Encrypt. Ses certificats ne sont pas reconnus par les navigateurs, mais il n'a pas de limites de débit.
  • Écouter sur le port 80 redirige http:// vers https://.

Le nom DNS doit pointer vers l'adresse IP de la console, généralement via un enregistrement A dans votre DNS interne. Les fichiers du certificat sont conservés dans /var/lib/backupzit/web, et la clé n'est lisible que par le service. Sous Linux, le service peut utiliser les ports 80 et 443 (CAP_NET_BIND_SERVICE) ; ouvrez-les dans le pare-feu si des navigateurs se connectent depuis d'autres réseaux.

La console se connecte aussi elle-même au stockage pour vous permettre de parcourir les fichiers dans les images disque et les sauvegardes de VM (et de les télécharger) ; elle a donc besoin du même accès au stockage que les agents.

Mettre à jour BackupZit

Par défaut, la console récupère les mises à jour depuis les versions officielles de BackupZit sur GitHub (https://github.com/Max-Zit/backupzit/releases). Sous Paramètres → Mises à jour, vous pouvez saisir une autre source de mise à jour — votre propre miroir HTTPS ou un dossier sur le serveur. Quelle que soit la source, chaque version doit porter une signature BackupZit valide. La console vérifie chaque jour s'il y a de nouvelles versions et envoie un e-mail aux administrateurs quand l'une est disponible. Pour l'installer, cliquez sur Installer :

  1. La console vérifie la signature de la version et la somme de contrôle du paquet, et attend qu'aucune sauvegarde ni restauration ne soit en cours.
  2. Un service système (backupzit-update, exécuté en root) vérifie de nouveau la signature avec les clés de publication intégrées à BackupZit. Même une console compromise ne peut pas faire installer un autre paquet.
  3. Il sauvegarde la base de données (pg_dump), conserve le programme actuel, installe le paquet et redémarre la console.
  4. Si la nouvelle version ne répond pas dans les deux minutes, le programme précédent et la base de données telle qu'elle était sont restaurés automatiquement. Le résultat, avec le journal du démarrage échoué, est affiché sur la page Mises à jour, consigné dans le journal d'audit et envoyé par e-mail.
  5. Après une mise à jour réussie, les agents sont aussi mis à jour : chacun installe la nouvelle version lorsqu'il est inactif. Désactivez cela sur la même page si vous préférez les mettre à jour vous-même.

La console est indisponible pendant environ une minute. Les sauvegardes de base de données et les programmes précédents des trois dernières mises à jour sont conservés dans /var/lib/backupzit-update.

Sans accès internet : téléchargez les fichiers de la version (manifest.json, manifest.json.sig et le paquet serveur) sur un autre ordinateur. Puis téléversez-les sous Installer une mise à jour depuis des fichiers, ou copiez-les dans un dossier du serveur et utilisez ce dossier comme source de mise à jour.

Vous pouvez toujours mettre à jour avec le gestionnaire de paquets (apt install ./backupzit-server_….deb) ; la base de données est migrée au démarrage de la nouvelle version.

Mises à jour du système d'exploitation

La même page (Paramètres → Mises à jour) affiche le système d'exploitation du serveur de la console : combien de mises à jour sont disponibles, combien sont des correctifs de sécurité, si un redémarrage est nécessaire et si les mises à jour de sécurité automatiques sont activées. L'état est actualisé chaque jour, ou avec Vérifier maintenant. Vous pouvez :

  • Activer les mises à jour de sécurité automatiques (recommandé). L'outil propre au système installe uniquement les correctifs de sécurité, chaque jour : unattended-upgrades sous Debian et Ubuntu, dnf-automatic sous AlmaLinux et Rocky Linux.
  • Installer toutes les mises à jour maintenant. Des services comme PostgreSQL peuvent redémarrer brièvement, et la console se reconnecte d'elle-même.
  • Redémarrer le serveur, par exemple après une mise à jour du noyau. La console refuse tant que des sauvegardes ou restaurations sont en cours. Les agents conservent leurs tâches et transmettent les résultats quand la console revient.

Ces opérations passent par le même service root que les mises à jour de la console. Elles sont consignées dans le journal d'audit, et la sortie de la dernière opération est affichée sur la page.

Sauvegarder la console elle-même

Les sauvegardes sur votre stockage restent lisibles sans la console, grâce aux fiches de récupération. Pour récupérer aussi la console elle-même après la perte de son serveur, activez Paramètres → Sauvegarde de la console. Cela comprend les tâches, planifications, agents, utilisateurs, paramètres, l'historique des exécutions et les identifiants enregistrés. La console se sauvegarde alors chaque jour vers une cible de stockage réseau, dans le dossier backupzit-console.

Une sauvegarde de la console contient :

  • toute la base de données, exportée table par table, si bien qu'aucune version particulière de pg_dump n'est nécessaire ;
  • la clé de secrets qui déchiffre les identifiants enregistrés ;
  • le certificat de la console, que les agents épinglent.

Elle est chiffrée avec la clé de récupération de la cible et dédupliquée. Les sauvegardes les plus récentes sont conservées : 14 par défaut.

Restaurer la console

  1. Installez une nouvelle console de même version ou plus récente, par exemple depuis l'ISO de l'appliance.
  2. Sur le nouveau serveur, en root, exécutez ce qui suit. Les identifiants sont ceux de la fiche de récupération de la cible de stockage, et l'adresse du dépôt est affichée sur la page Sauvegarde de la console. 
    systemctl stop backupzit-server
set -a; . /etc/backupzit/server.env; set +a
export BACKUPZIT_PASSWORD='<recovery key>'
export BACKUPZIT_SFTP_PASSWORD='…' BACKUPZIT_SFTP_HOSTKEY='SHA256:…'   # or BACKUPZIT_S3_ACCESS_KEY/_SECRET_KEY, _SMB_PASSWORD, _AZURE_KEY, _HARDENED_KEY/_FINGERPRINT
backupzit-server --restore-console --repo 'sftp://backup@nas:22/backups/backupzit-console'
systemctl start backupzit-server
  3. Donnez au nouveau serveur l'adresse IP ou le nom DNS de l'ancien. Les agents font confiance au certificat restauré et se reconnectent d'eux-mêmes.

La restauration remplace la base de données de la nouvelle console par la sauvegarde et met la base de données au niveau de la version installée. --snapshot ID restaure une sauvegarde plus ancienne au lieu de la plus récente.

Conservez aussi une copie des fiches de récupération et de secrets.key en dehors du serveur, par exemple dans votre gestionnaire de mots de passe.
