Machines virtuelles Proxmox VE

BackupZit sauvegarde les machines virtuelles (QEMU) et les conteneurs (LXC) de Proxmox VE sans rien installer dans les invités. L'agent tourne sur l'hôte Proxmox, prend un instantané de chaque invité, lit ses disques et les stocke dédupliqués sur n'importe quelle cible de stockage.

Mise en place

  1. Installez le paquet Agent Linux — Debian / Ubuntu depuis Agents sur chaque nœud Proxmox (Proxmox VE 7 et 8 sont basés sur Debian) : 
    apt install ./backupzit-agent_*.deb
backupzit-agent enroll --code "BZ1-..."
systemctl enable --now backupzit-agent
  2. En moins d'une minute, le nœud apparaît sur la page Agents avec le badge Proxmox VE · N guests.
  3. Dans Tâches de sauvegarde, sélectionnez cet agent et choisissez Machines virtuelles (Proxmox VE, Hyper-V, VMware). Sauvegardez tous les invités du nœud (les invités créés plus tard sont inclus automatiquement) ou cochez-en certains.

L'agent utilise les outils propres au nœud (qm, pct, pvesm, LVM, ZFS, Ceph) ; aucun jeton d'API ni mot de passe n'est stocké dans la console.

Comment un invité est sauvegardé

  1. Un instantané Proxmox temporaire est pris (backupzit_…, visible sous Snapshots pendant quelques secondes à quelques minutes). L'invité continue de tourner.
  2. Si l'agent invité QEMU tourne dans la VM (et est activé dans les options de la VM), Proxmox gèle les systèmes de fichiers pour l'instantané — la sauvegarde est alors cohérente au niveau applicatif. Sans lui, la sauvegarde est cohérente en cas de crash, comme une coupure de courant. Installez qemu-guest-agent dans les VM Linux et les outils invités VirtIO dans les VM Windows.
  3. Chaque disque est lu depuis l'instantané par blocs de 1 Mio. Les blocs vides ne sont pas stockés et les blocs déjà présents dans le dépôt ne sont pas renvoyés ; après la première sauvegarde, seules les données modifiées sont transférées.
  4. L'instantané est supprimé. La configuration de l'invité (processeur, mémoire, réseau, disques) est stockée avec la sauvegarde.

La page de l'exécution liste chaque invité, ses disques et la façon dont il a été capturé. Les tests de restauration vérifient des blocs aléatoires des sauvegardes de VM comme pour les images disque et, avec le test de démarrage activé, démarrent chaque VM depuis la sauvegarde, isolée du réseau, pour prouver qu'elle démarre.

Les disques marqués Backup: no (backup=0) dans Proxmox, les disques physiques en passthrough et les montages bind sont ignorés et listés comme avertissements. Les lecteurs cloud-init ne sont pas stockés ; ils sont recréés à partir de la configuration lors de la restauration.

Restaurer une VM ou un conteneur

Ouvrez une exécution de sauvegarde de VM (depuis la page de la tâche ou Activité) et utilisez Restaurer une VM ou un conteneur :

  • Invité — l'un des invités de cette sauvegarde.
  • Restaurer sur le nœud Proxmox — tout nœud doté de l'agent BackupZit, y compris un nœud d'un autre cluster.
  • En tant que nouvel invité avec le prochain ID libre (par défaut) ou avec l'ID … — l'original continue de tourner. Comme les deux existent, les cartes réseau de la copie reçoivent de nouvelles adresses MAC.
  • Avec son ID d'origine — après la suppression de l'invité. S'il existe encore, cochez l'arrêter et le supprimer pour le remplacer par la sauvegarde ; l'invité existant et ses disques sont supprimés d'abord.
  • Nom et Stockage pour les disques — par ex. restaurer sur un autre stockage que l'original.
  • Démarrer l'invité après la restauration.

Chaque restauration attribue aux VM un nouvel ID de génération (vmgenid), afin que les contrôleurs de domaine Windows et d'autres logiciels détectent le retour en arrière en toute sécurité. Les disques sont alloués avec pvesm sur le stockage choisi ; sur un stockage de type répertoire, ils sont restaurés en fichiers raw.

Restauration instantanée

Restaurer une grande VM prend autant de temps que copier ses disques. Avec Instantanément, en s’exécutant depuis la sauvegarde dans le formulaire de restauration, la VM tourne au contraire en quelques secondes, alors que ses disques sont encore dans la sauvegarde :

  1. L'agent sert les disques de la VM en lecture seule depuis la sauvegarde (un petit serveur NBD tournant comme unité systemd backupzit-instant-<ID>) et crée une nouvelle VM avec le prochain ID libre dont les disques sont des overlays qcow2 sur le stockage de type répertoire backupzit-instant (/var/lib/backupzit-instant, ajouté automatiquement). Les données sont lues depuis la sauvegarde à la demande ; tout ce que la VM écrit reste dans les overlays. Les variables du micrologiciel (disque EFI) et l'état du TPM sont petits et copiés.
  2. La VM démarre. Vérifiez-la — elle reçoit de nouvelles adresses MAC comme toute copie. Le tableau de bord liste chaque VM qui tourne encore depuis une sauvegarde.
  3. Sur la page de l'exécution, soit Terminer : les disques sont déplacés vers le stockage choisi pendant que la VM tourne (qm disk move), puis la sauvegarde n'est plus utilisée. Soit Abandonner : la VM est arrêtée et supprimée avec ses modifications.

Tant qu'une VM tourne depuis une sauvegarde, la rétention ne supprime jamais cette sauvegarde. La VM est aussi rapide que le stockage de sauvegarde le permet : un dépôt sur un disque local ou un partage réseau rapide fonctionne le mieux ; des lectures via SFTP ou S3 depuis un site éloigné la ralentissent jusqu'à ce qu'elle soit terminée. La restauration instantanée concerne les VM (pas les conteneurs) et crée une nouvelle VM — pour restaurer sur place, utilisez une restauration normale. Le disque EFI ne peut pas être déplacé pendant que la VM tourne ; il reste alors sur backupzit-instant (voir le message de l'exécution) et peut être déplacé après l'arrêt de la VM : qm disk move ID efidisk0 STORAGE --delete 1.

Réplication

Pour les invités qui doivent revenir en quelques minutes, une tâche de VM peut conserver des répliques : sous Avancé dans le formulaire de la tâche, cochez Conserver des répliques des VM et choisissez le nœud (tout nœud doté de l'agent BackupZit, y compris dans un autre cluster) et le stockage. Après chaque sauvegarde, l'agent de ce nœud met à jour une copie arrêtée de chaque invité de la tâche :

  • La première fois, la réplique est restaurée comme un nouvel invité (prochain ID libre, nom original-replica, nouvelles adresses MAC, jamais démarrée avec le nœud).
  • Ensuite, seuls les blocs modifiés depuis la sauvegarde que contient la réplique sont écrits — généralement quelques secondes par sauvegarde.
  • La page de la tâche liste les répliques, la sauvegarde que chacune contient et leur état. Si un invité est perdu, cliquez sur Démarrer le réplica : il tourne avec les données de la dernière sauvegarde, sans restauration. Ne le démarrez que si l'original a vraiment disparu — les deux en même temps sur le réseau peuvent entrer en conflit.
  • Tant qu'une réplique tourne, elle n'est plus mise à jour (l'exécution le signale). Pour répliquer à nouveau, supprimez l'invité réplique dans Proxmox ; la sauvegarde suivante en crée une nouvelle. Les répliques ayant des instantanés Proxmox ne sont pas mises à jour non plus.
  • Les disques ajoutés plus tard à un invité ne sont pas répliqués (supprimez la réplique pour recommencer) ; les disques agrandis le sont aussi sur la réplique. Les modifications de configuration (mémoire, processeurs) sont reprises à la création de la réplique.
  • La réplication lit les sauvegardes comme une restauration : le nœud de réplique doit atteindre le stockage. Désactiver la réplication laisse les répliques en l'état.

Ligne de commande

backupzit-agent pve list
backupzit-agent pve backup  --repo ... [--vmid 100,200] [--exclude 300]
backupzit-agent pve show    --repo ... latest
backupzit-agent pve restore --repo ... --vmid 100 [--new-vmid -1|N] [--name copy] [--storage local-lvm] [--overwrite] [--start] SNAPSHOT|latest
backupzit-agent pve instant --repo ... --vmid 100 [--new-vmid N] [--name X] SNAPSHOT|latest
backupzit-agent pve instant-finish --vmid 101 --storage local-lvm
backupzit-agent pve instant-discard --vmid 101

Les options du dépôt sont les mêmes que pour toutes les commandes (voir Référence de la ligne de commande). La ligne de commande fonctionne sans la console, par exemple pour restaurer un nœud entier après un sinistre.

Clusters

Installez l'agent sur chaque nœud. Une tâche sauvegarde les invités qui tournent sur le nœud de son agent ; un invité listé dans une tâche et migré vers un autre nœud est signalé par un avertissement nommant ce nœud — sauvegardez chaque nœud avec sa propre tâche, ou utilisez tous les invités du nœud sur chaque nœud pour que les invités migrés soient toujours couverts.

Restaurer des fichiers individuels

Dans le tableau des invités d'une exécution de sauvegarde de VM, cliquez sur Parcourir les fichiers. La console lit le disque directement depuis la sauvegarde — rien n'est restauré au préalable — et affiche ses partitions et volumes logiques LVM ; NTFS (Windows), ext2/3/4 et XFS (Linux) peuvent être parcourus, y compris dans LVM. Cochez des fichiers et dossiers, puis :

  • Télécharger — un fichier tel quel, plusieurs fichiers ou dossiers dans une archive ZIP, directement dans votre navigateur ;
  • Restaurer sur l’agent — les copier dans un dossier sur n'importe quel agent, par ex. dans la VM (si elle exécute l'agent BackupZit) ou sur un serveur de fichiers.

En ligne de commande : backupzit-agent pve ls --vmid 100 latest /etc et backupzit-agent pve extract --vmid 100 --target /srv/restore latest /etc/nginx ; --volume sélectionne une partition ou un volume logique (pve ls sans chemin les liste). La navigation dans la console nécessite que la sauvegarde soit sur un stockage réseau (SFTP, S3, SMB, Azure, dépôt renforcé).
