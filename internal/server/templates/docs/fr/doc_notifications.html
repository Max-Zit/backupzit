Notifications : e-mail, Slack, Teams, webhooks

Recevez un e-mail quand une sauvegarde échoue, et un résumé quotidien chaque matin.

Configurer l'e-mail

Dans Paramètres → Notifications par e-mail, cochez Envoyer des notifications par e-mail (sans cela, aucun e-mail n'est envoyé) et remplissez :

ChampExemple
Serveur SMTP / portsmtp.office365.com / 587, smtp.gmail.com / 587, relais interne / 25
SécuritéSTARTTLS (port 587), TLS (port 465) ou Aucune (uniquement pour un relais interne sans authentification : un nom d'utilisateur et un mot de passe ne sont jamais envoyés en clair)
Nom d'utilisateur / Mot de passeLa boîte aux lettres utilisée pour l'envoi ; laissez vide pour un relais sans authentification. Gmail exige un mot de passe d'application ; pour Microsoft 365, où l'authentification SMTP de base est en cours de retrait, un relais ou un connecteur SMTP est le choix le plus sûr.
Debackup@example.com
ÀUne ou plusieurs adresses, séparées par des virgules.

Utilisez Envoyer un e-mail de test pour vérifier les paramètres, puis cliquez sur Enregistrer (le test ne les enregistre pas). Les e-mails, messages de chat et rapports sont rédigés dans la langue choisie dans le même formulaire (par défaut, la langue de la console lors de l'enregistrement).

Ce qui est envoyé

  • Échecs (recommandé) — un e-mail par exécution échouée avec la raison : sauvegardes, copies, restaurations et tests de restauration échoués. Avec cette option, vous recevez aussi une alerte SUSPICIOUS lorsqu'une sauvegarde ressemble à un rançongiciel ou à une suppression massive.
  • Avertissements — exécutions où certains fichiers n'ont pas pu être lus.
  • Réussites — chaque exécution réussie (souvent trop ; préférez le rapport quotidien).
  • Rapport quotidien — à l'heure choisie : exécutions des dernières 24 heures, problèmes et agents hors ligne. L'objet se termine par OK, AVERTISSEMENTS ou ATTENTION (p. ex. [BackupZit] Rapport quotidien 2026-11-17 : OK), afin que les règles de messagerie puissent les trier.

Avec Échecs activé, une tâche qui manque son objectif de point de récupération (RPO) est aussi signalée — une fois, puis à nouveau seulement après l'avoir respecté entre-temps. Les exécutions arrêtées par un utilisateur (statut annulée) n'envoient pas d'e-mail d'échec ; une exécution arrêtée par sa durée maximale, si.

Un e-mail par tâche, et filtres de messagerie

Activez aussi Réussites pour recevoir un e-mail pour chaque exécution terminée de chaque tâche, avec la tâche et l’ordinateur dans l’objet, au lieu du seul résumé quotidien. Pour un résumé par tâche, créez un rapport planifié pour cette tâche. L’objet est rédigé dans la langue des e-mails ; pour les règles de messagerie, chaque e-mail d’exécution porte donc aussi des en-têtes qui ne changent pas avec la langue : X-BackupZit-Status (success, warning ou failed), X-BackupZit-Job, X-BackupZit-Agent (le nom affiché dans la console), X-BackupZit-Host (le nom d’hôte signalé par l’ordinateur), X-BackupZit-Kind et X-BackupZit-Run. Une sauvegarde qui ressemble à un rançongiciel porte aussi X-BackupZit-Suspicious: yes — veillez à ce que les règles qui classent les exécutions réussies ne la cachent pas.

Indépendamment de ces options, les destinataires des notifications reçoivent aussi un e-mail quand :

  • une modification attend l'approbation d'un second utilisateur (principe des quatre yeux) ;
  • deux machines utilisent une même inscription d'agent ;
  • le journal d'audit a été modifié ;
  • la sauvegarde de la console elle-même a échoué ;
  • le renouvellement du certificat HTTPS pour les navigateurs a échoué, ou un certificat importé expire dans les 21 jours ;
  • une nouvelle version de BackupZit est disponible (désactivable dans Paramètres → Mises à jour), ou une mise à jour de la console a échoué ;
  • une adresse a été bloquée après trop de connexions échouées (désactivable dans la protection contre la force brute).

Pour des résumés hebdomadaires ou mensuels, utilisez les rapports planifiés ; ils sont envoyés avec les mêmes paramètres de messagerie et ont leurs propres destinataires. Les objets commencent par [BackupZit] afin que les règles de messagerie puissent les trier. Le mot de passe SMTP est stocké chiffré. Les liens des e-mails, messages de chat et rapports mènent à la console à l'adresse avec laquelle vous l'ouvrez dans le navigateur (ou celle définie avec --public-url).

Quand le port web HTTPS avec un certificat de confiance est activé (Paramètres → Certificat), les liens des e-mails, messages de chat et rapports utilisent son adresse, même quand le port 8443 ne sert que les agents. Sinon, ils utilisent --public-url, ou à défaut l'adresse avec laquelle un utilisateur autorisé à modifier les paramètres a ouvert la console en dernier.

Slack, Microsoft Teams et webhooks

Dans Paramètres → Chat et webhooks, ajoutez autant de canaux que vous voulez ; chacun choisit s'il reçoit les échecs, les avertissements et les réussites. Les sauvegardes inhabituelles (rançongiciel possible) comptent comme des échecs. Envoyer un test vérifie immédiatement un canal.

  • Slack : créez un incoming webhook pour le canal (paramètres de l'application Slack → Incoming Webhooks) et collez son URL (https://hooks.slack.com/services/…).
  • Microsoft Teams : dans le canal, ajoutez le workflow Post to a channel when a webhook request is received et collez son URL. Les messages arrivent sous forme de cartes avec un bouton qui ouvre l'exécution dans la console.
  • Webhook : toute URL qui accepte un POST JSON — système de tickets, supervision ou outil d'automatisation. Avec un secret de signature, chaque requête porte X-BackupZit-Signature: sha256=<hex>, le HMAC-SHA256 du corps, afin que le destinataire puisse vérifier qu'elle vient de votre console. Les redirections ne sont pas suivies (une réponse 3xx compte comme une erreur) et les adresses lien-local (169.254.x.x, comme les services de métadonnées du cloud, et fe80::) sont refusées ; les adresses internes fonctionnent.

Le JSON d'un webhook :

{"event": "run.finished", "run_id": 412, "kind": "vm-backup", "kind_title": "VM backup",
 "status": "failed", "suspicious": "", "job": "Proxmox VMs", "job_id": 7, "agent": "pve1", "agent_id": 3,
 "message": "…", "errors": ["…"], "started_at": "2026-10-04T22:00:03+02:00",
 "finished_at": "2026-10-04T22:04:41+02:00", "duration_s": 278, "files": 4, "bytes": 85899345920,
 "bytes_read": 12884901888, "bytes_stored": 1073741824, "snapshot": "9f3c2a1b",
 "url": "https://backup.example/runs/412"}

duration_s est la durée de l'exécution en secondes. Pour les sauvegardes, files et bytes sont la taille des données sauvegardées, bytes_read ce qui a été lu et bytes_stored ce qui a été envoyé vers le stockage ; snapshot est l'ID de la nouvelle sauvegarde.

Une tâche qui manque son objectif de point de récupération envoie {"event": "rpo.missed", "job_id", "job", "agent", "rpo_hours", "last_good_backup", "url"} ; les champs vides (comme suspicious ou la tâche d'une exécution qui n'en a pas) sont omis. Les URL Slack et Teams doivent utiliser https://. Les messages sont envoyés une fois par exécution, même lorsque l'e-mail est désactivé. Un canal en échec (mauvaise URL, service indisponible) est consigné dans le journal de la console et ne bloque pas les autres. Les URL de webhook sont stockées chiffrées. Une sauvegarde planifiée ignorée parce que l'exécution précédente de la tâche est toujours active, ou qui n'a pas démarré dans la plage de sauvegarde de la tâche, envoie une notification par tâche (e-mail avec les notifications d'échec et {"event": "schedule.skipped"} ou "schedule.window_missed" avec "job_id", "job", "agent", "count", "since"), et la suivante seulement après une sauvegarde réussie de la tâche entre-temps.
