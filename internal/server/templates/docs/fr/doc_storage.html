Cibles de stockage

Une cible de stockage est l'endroit où les agents écrivent leurs sauvegardes. Chaque agent utilise son propre dépôt sous l'emplacement de la cible.

Règle 3-2-1 : conservez 3 copies de vos données, sur 2 supports différents, dont 1 hors site — par exemple une tâche vers un NAS local et une autre vers S3 ou un dépôt renforcé dans un autre bâtiment.

Tester la connexion

Quand une cible de stockage est ajoutée, la console la teste immédiatement avec les identifiants saisis : elle écrit un petit fichier, le relit et le supprime. Sur un stockage immuable (S3 avec Object Lock, dépôt renforcé), elle se contente de se connecter et de lister, pour ne rien laisser de verrouillé ; pour S3, elle vérifie aussi que le bucket a Object Lock lorsque l'immuabilité est demandée. La cible est enregistrée dans tous les cas et le résultat est affiché — un mauvais mot de passe, une mauvaise clé d'hôte, un mauvais bucket ou partage apparaît maintenant et non à la première sauvegarde. Tester la connexion sur la page Stockage refait le test. La console teste depuis son propre réseau ; ce sont les agents qui écrivent les sauvegardes, donc une cible que seuls les agents peuvent atteindre (un disque local ou USB) est testée par la première sauvegarde.

SFTP

Emplacement : sftp://user@host:22/path (utilisez /~/path pour un chemin relatif au répertoire personnel de l'utilisateur). Saisissez un mot de passe ou une clé privée, et l'empreinte de la clé d'hôte du serveur, que vous obtenez sur le serveur avec :

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Créez un utilisateur dédié qui ne peut écrire que dans le dossier de sauvegarde.

Compatible S3

Saisissez le point de terminaison (p. ex. s3.eu-central-1.amazonaws.com, s3.wasabisys.com, 10.0.0.5:9000), le bucket, un dossier facultatif et une clé d'accès avec droits de lecture/écriture sur ce bucket. Cochez HTTP en clair uniquement pour un MinIO local sans certificat.

Sauvegardes immuables (Object Lock)

Créez le bucket avec Object Lock activé et cochez Sauvegardes immuables … pendant N jours. Chaque fichier écrit par les agents est verrouillé en mode conformité pendant N jours (+1 jour de marge) : personne — ni un attaquant possédant les clés, ni le propriétaire du bucket — ne peut le supprimer ou l'écraser avant. Après chaque sauvegarde, le verrou des données réutilisées depuis des sauvegardes plus anciennes est prolongé, si bien que chaque point de restauration est protégé pendant toute la période.

Une suppression (par la rétention ou par un attaquant) ajoute seulement un « marqueur de suppression ». Ajoutez une règle de cycle de vie qui fait expirer les versions non actuelles après un jour, pour libérer l'espace une fois les verrous terminés. Voir Protection contre les rançongiciels.

Google Cloud Storage

Google Cloud Storage fonctionne comme cible compatible S3 via son API d'interopérabilité :

  1. Dans la console Google Cloud, ouvrez Cloud Storage → Settings → Interoperability et créez une clé HMAC pour un compte de service disposant du rôle Storage Object Admin sur le bucket.
  2. Ajoutez une cible S3 avec le point de terminaison storage.googleapis.com, le nom du bucket, la clé d'accès et le secret HMAC, et la région auto.

L'option S3 Object Lock n'est pas disponible sur Google Cloud Storage ; pour l'immuabilité, définissez une règle de conservation du bucket (et verrouillez-la) dans Google Cloud. Les sauvegardes supprimées restent alors jusqu'à la fin de la période de conservation.

Azure Blob Storage

  1. Dans le portail Azure, créez un compte de stockage (StorageV2, toute redondance) et un conteneur, p. ex. backups.
  2. Ajoutez une cible Azure Blob Storage avec le nom du compte, le conteneur et un dossier facultatif.
  3. Authentifiez-vous avec une clé d'accès (Compte de stockage → Clés d'accès) ou, de façon plus restreinte, un jeton SAS pour le conteneur avec les droits lecture, écriture, suppression et liste et une expiration adaptée.

Pour la protection contre les rançongiciels, activez sur le conteneur l'immuabilité au niveau des versions avec une stratégie de rétention temporelle ; les sauvegardes supprimées ou écrasées restent alors récupérables pendant cette durée. Le champ point de terminaison sous Avancé n'est nécessaire que pour Azure Government/China, Azure Stack Hub ou l'émulateur Azurite.

Disques USB en rotation

Des disques déconnectés et emportés hors site sont la protection la plus simple contre les rançongiciels, l'incendie et le vol pour les petits bureaux. BackupZit trouve le disque par son nom de volume, quelle que soit la lettre de lecteur attribuée par Windows :

  1. Formatez deux disques ou plus en NTFS (Linux : ext4) et nommez-les BZBACKUP1, BZBACKUP2, … (Windows : clic droit sur le lecteur → Propriétés → nom).
  2. Ajoutez une cible de stockage de type Disques USB / amovibles en rotation avec le nom BZBACKUP*.
  3. Créez une tâche de sauvegarde vers elle — ou mieux, une tâche de copie de sauvegarde qui copie une tâche NAS ou cloud sur le disque.
  4. Échangez les disques régulièrement (p. ex. chaque semaine) et gardez celui qui est déconnecté en lieu sûr.
  • Chaque disque contient une sauvegarde complète et indépendante avec sa propre rétention ; tous les disques sont chiffrés avec la clé de récupération de la cible.
  • L'exécution indique le disque utilisé (Disque BZBACKUP2). Une restauration demande exactement ce disque et vous indique lequel est connecté.
  • Quand aucun disque n'est connecté, l'exécution échoue avec un message clair et une alerte — un rappel de rebrancher le disque.
  • Ne connectez qu'un seul des disques à la fois.

Partage SMB

Serveur, partage, dossier facultatif, utilisateur, mot de passe et (pour les comptes de domaine) le domaine. Les agents se connectent eux-mêmes avec ces identifiants ; cela fonctionne donc aussi pour les services exécutés en tant que SYSTEM.

Dépôt renforcé

Installez le paquet backupzit-repo sur un serveur Linux dédié, puis sur ce serveur :

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

Saisissez l'adresse du serveur, la clé d'accès et l'empreinte dans la console. La période d'immuabilité se configure sur le serveur de dépôt (/etc/backupzit-repo/repo.env) et ne peut être modifiée ni depuis la console ni depuis les agents. Détails dans Protection contre les rançongiciels.

Chiffrement et clé de récupération

Avec Chiffrer les sauvegardes (par défaut), tout le contenu du dépôt — contenu et noms des fichiers, arborescence, listes d'instantanés — est chiffré en AES-256-GCM avant de quitter l'agent. Le fournisseur de stockage ne voit que des données aléatoires.

Quand vous créez une cible chiffrée, la console affiche une clé de récupération et propose une fiche de récupération à télécharger.

Imprimez la fiche de récupération ou conservez-la dans un gestionnaire de mots de passe, séparément des sauvegardes. Si la console est perdue, la clé de récupération plus l'emplacement et les identifiants du stockage suffisent pour restaurer. Sans la clé, personne ne peut lire les sauvegardes chiffrées — pas même le support BackupZit.

Vous pouvez réafficher la clé plus tard avec Clé de récupération dans la liste des stockages ; cette action est journalisée.

La liste des stockages

La liste montre pour chaque cible le type, l'emplacement, le chiffrement (avec accès à la clé de récupération pour les administrateurs) et l'immuabilité : la période Object Lock pour S3, ou défini sur le serveur de dépôt pour les dépôts renforcés. Les identifiants ne sont plus jamais affichés après l'enregistrement et sont stockés chiffrés. Seuls les administrateurs peuvent ajouter ou supprimer des cibles et voir les clés de récupération.

Utilisation du stockage et prévision

Après chaque sauvegarde (et sa rétention), l'agent indique l'espace occupé par son dépôt et — pour les disques locaux et USB, les serveurs SFTP (extension statvfs d'OpenSSH) et les partages SMB — la taille et l'espace libre du stockage. Sous Stockage → Utilisation du stockage, chaque cible affiche :

  • l'espace utilisé par tous les dépôts qu'elle contient (un par agent ; pour les disques USB en rotation, chaque disque compte) ;
  • pour un stockage de taille connue, son taux de remplissage (jaune dès 75 %, rouge dès 90 %), avec la capacité en ligne rouge pointillée dans le graphique ;
  • un graphique des 90 derniers jours et, après une semaine de sauvegardes, la croissance par jour (tendance linéaire des 30 derniers jours), tracée 30 jours à l'avance en pointillé, et la date où le stockage sera plein — ou, sans taille connue, l'utilisation attendue dans 90 jours.

Nécessite votre attention sur le tableau de bord avertit quand une cible de stockage est pleine à 90 % ou le sera dans les 30 jours. S3 et Azure n'ont pas de taille fixe ; seuls l'espace utilisé et sa croissance y sont affichés. L'espace utilisé correspond aux données stockées (compressées, chiffrées, dédupliquées) ; les fichiers que le stockage conserve pour d'autres raisons (versions d'objets, autres programmes) ne sont pas comptés.

Supprimer une cible

Supprimer une cible de stockage de la console n'efface aucune donnée sur le stockage. Avec l'approbation à quatre yeux activée, un second utilisateur doit d'abord l'approuver.
