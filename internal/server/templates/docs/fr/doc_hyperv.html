Machines virtuelles Hyper-V

BackupZit sauvegarde les machines virtuelles Hyper-V depuis l'agent installé sur l'hôte Hyper-V ; rien n'est installé dans les VM. Les invités Windows et Linux sont capturés sans être arrêtés. Vous pouvez les restaurer en tant que nouvelle VM ou à la place de l'original.

Mise en place

  1. Installez le MSI de l'Agent Windows depuis Agents sur l'hôte Hyper-V et inscrivez-le. Hôtes pris en charge : Windows Server 2016 ou plus récent avec le rôle Hyper-V, ou Windows 10/11 avec Hyper-V. Dans un cluster, installez l'agent sur chaque hôte.
  2. En moins d'une minute, l'hôte apparaît sur la page Agents avec le badge Hyper-V · N VMs.
  3. Dans Tâches de sauvegarde, sélectionnez cet agent et choisissez Machines virtuelles (Proxmox VE, Hyper-V, VMware). Choisissez ensuite :
    • Toutes les VM (et conteneurs) de l’hôte, ce qui couvre aussi les VM créées plus tard ;
    • des VM individuelles, en les cochant.

L'agent passe par les interfaces propres à Hyper-V : le module PowerShell Hyper-V et l'API Virtual Disk de Windows. La console ne stocke aucun identifiant Hyper-V.

Comment une VM est sauvegardée

  1. Un point de contrôle de récupération temporaire (backupzit_…) est créé. C'est le type de point de contrôle qu'Hyper-V fournit aux applications de sauvegarde. Hyper-V demande à l'invité de s'y préparer :
    • Les invités Windows vident les tampons de leurs applications via VSS.
    • Les invités Linux gèlent leurs systèmes de fichiers, si les démons Hyper-V sont installés (hyperv-daemons / hv-vss-daemon).
    Si l'invité ne peut faire ni l'un ni l'autre, le point de contrôle est pris en cohérence de crash. La page de l'exécution indique le type utilisé.
  2. Le point de contrôle de récupération active le Resilient Change Tracking (RCT) pour les disques de la VM ; vous verrez des fichiers .rct et .mrt à côté d'eux. La première sauvegarde lit les disques entiers. Ensuite, RCT indique quels blocs ont changé depuis la sauvegarde précédente, et seuls ceux-ci sont lus.
  3. Les disques sont lus dans l'état du point de contrôle, via l'API Virtual Disk, par blocs de 1 Mio. Cela couvre les fichiers VHDX et VHD, y compris les chaînes de points de contrôle antérieurs. Les blocs vides ne sont pas stockés, et les blocs déjà présents dans le dépôt ne sont pas renvoyés.
  4. Le point de contrôle est supprimé et Hyper-V le fusionne en arrière-plan.
  5. La configuration de la VM est stockée avec la sauvegarde : génération, processeur, mémoire, cartes réseau (commutateur, VLAN, adresse MAC), contrôleurs de disque, démarrage sécurisé et TPM.

Les VM éteintes sont lues directement, sans point de contrôle. Sur les hôtes antérieurs à Windows Server 2016 (sans points de contrôle de récupération), un point de contrôle de production est utilisé et chaque sauvegarde lit les disques entiers.

Sur chaque hôte, les sauvegardes simultanées d’une même VM attendent leur tour, depuis le service comme en ligne de commande. Une sauvegarde ne supprime que son propre point de contrôle temporaire. L’agent supprime un point de contrôle resté en place dès que sa sauvegarde s’est terminée sur un autre nœud (après une migration dynamique), ou lorsqu’il a plus de 48 heures (sauvegarde interrompue par un crash ou une coupure de courant). Tous les processus de sauvegarde simultanés doivent utiliser les binaires mis à jour.

Uniquement cohérent avec les applications. Pour Active Directory, SQL Server, Exchange et d'autres bases de données, cochez Exiger des points de contrôle cohérents avec les applications dans la tâche (aussi dans une tâche pour un cluster). Une VM en cours d'exécution n'est alors sauvegardée qu'à partir d'un point de contrôle que l'invité a préparé avec VSS ; en cas d'échec, la VM n'est pas sauvegardée et l'exécution échoue (avec une notification) au lieu de prendre un point de contrôle cohérent en cas d'arrêt brutal. Les autres VM de la tâche sont tout de même sauvegardées et peuvent être restaurées depuis cette exécution. Vérifiez le service d'intégration Backup (volume shadow copy) dans les paramètres de la VM et VSS dans l'invité (vssadmin list writers). Nécessite des agents 0.48.0 ou plus récents ; avec des agents plus anciens, l'exécution échoue en demandant de les mettre à jour.

vTPM et BitLocker. Pour les VM de génération 2 avec un TPM virtuel, la sauvegarde conserve aussi le vTPM (le fichier d'état de l'invité et son protecteur de clé). Restaurée comme nouvelle VM sur le même hôte, ou sur un hôte disposant du certificat gardien de l'hôte d'origine, la VM retrouve son vTPM et BitLocker ne demande pas la clé de récupération. Sur d'autres hôtes, la VM reçoit un vTPM neuf et vide, et la restauration le signale ; pour l'éviter, importez d'abord le certificat UntrustedGuardian de l'hôte d'origine. Une restauration par-dessus la VM existante conserve son vTPM. Les VM protégées (Host Guardian Service) ne sont pas prises en charge. Conservez malgré tout les clés de récupération BitLocker.

Le contrôle d’intégrité du dépôt vérifie aussi l’état sauvegardé de l’invité. Après la mise à jour, vérifiez les dépôts et copies existants ; une mise à jour ne peut pas récupérer un état de l’invité déjà supprimé. S’il manque, utilisez une copie intacte ou effectuez une nouvelle sauvegarde.

Exemple du laboratoire de test : une VM Linux avec un disque de 3 Go. La première sauvegarde a lu 3 Go. La suivante, après 64 Mo de nouvelles données, a lu 96 Mo.

Sous Windows 10/11, Hyper-V crée un point de contrôle automatique au démarrage d'une VM, sauf si cette option est désactivée dans les paramètres de la VM. BackupZit gère ces points de contrôle, mais pour des serveurs vous voudrez désactiver les points de contrôle automatiques (paramètres de la VM → Points de contrôle).

Restaurer une VM

Ouvrez l'exécution de la sauvegarde de VM (depuis la page de la tâche ou Activité) et utilisez Restaurer une VM Hyper-V.

En tant que nouvelle VM à côté de l'original

Crée une seconde VM avec de nouvelles adresses MAC, afin qu'elle puisse tourner sur le même réseau que l'original. Par défaut, elle porte le nom de l'original suivi de « restored » et de la date. Les points de contrôle automatiques y sont désactivés (Windows les active pour les nouvelles VM), donc son démarrage ne laisse pas de fichiers de point de contrôle. Si la copie tourne à côté de l'original et contient l'agent BackupZit, voir Deux machines utilisant un même agent.

Les paramètres réseau de l'invité liés à une adresse MAC ne s'appliquent pas aux nouvelles cartes. Un exemple est match: macaddress de netplan, utilisé par les images cloud Linux.

À la place de la VM d'origine

Cochez l'arrêter et remplacer ses disques. BackupZit alors :

  • éteint la VM existante ;
  • fusionne ses points de contrôle ;
  • remplace ses disques par les disques restaurés.

La VM conserve son ID, ses cartes réseau et ses adresses MAC, donc les tâches, la supervision et le réseau de l'invité continuent de fonctionner.

Avant d’arrêter la VM d’origine ou de fusionner ses points de contrôle, BackupZit reconstruit tous les disques dans un sous-dossier unique backupzit-restore-* du dossier choisi (celui des disques d’origine par défaut). Un échec de préparation laisse la VM inchangée. Après le remplacement, les anciens fichiers gardent leur chemin ; ne les supprimez qu’après avoir vérifié la VM restaurée. Après le début de la bascule, une erreur peut nécessiter une récupération manuelle : les disques reconstruits sont conservés, leur dossier figure dans l’erreur, et les paramètres et points de contrôle ne sont pas rétablis automatiquement.

Si la VM d'origine n'existe plus, elle est recréée, avec un nouvel ID Hyper-V.

Options

  • Dossier des disques virtuels : le dossier par défaut de l'hôte ou tout dossier contenant des disques de VM. Une restauration sur place met les nouveaux disques à côté des originaux.
  • Démarrer la VM après la restauration.

Ce que reçoit une VM restaurée

  • Les commutateurs virtuels sont connectés par leur nom. Si un commutateur n'existe pas sur l'hôte, la carte reste déconnectée.
  • Chaque VM restaurée reçoit un nouvel ID de génération, afin que les contrôleurs de domaine Active Directory détectent la restauration en toute sécurité.

Clusters de basculement

Les VM d'un cluster de basculement Hyper-V sont sauvegardées par une seule tâche pour tout le cluster. Trois étapes :

1. Installer l'agent sur chaque nœud

Installez l'agent Windows sur chaque nœud du cluster (pas dans les VM). Une VM est toujours sauvegardée par l'agent du nœud sur lequel elle tourne à ce moment : les points de contrôle et le suivi des modifications de Hyper-V ne fonctionnent que là. Tant qu'une VM tourne sur un nœud sans agent, elle n'est pas sauvegardée ; elle l'est de nouveau dès qu'elle passe sur un nœud avec l'agent.

2. La console reconnaît le cluster d'elle-même

Rien n'est à configurer pour le cluster, ni dans BackupZit ni dans Windows. Chaque agent (version 0.47.0 ou plus récente) signale le cluster de basculement de son nœud et les VM qui sont en cluster. Environ une minute après l'installation ou la mise à jour des agents :

  • la page Agents indique cluster NOM pour chaque nœud ;
  • le cluster apparaît dans le formulaire de tâche (étape suivante), avec le nombre de ses nœuds.

Les nœuds ajoutés plus tard au cluster sont reconnus de la même façon et rejoignent la tâche automatiquement dès que leur agent est installé.

3. Créer la tâche pour le cluster

  1. Ouvrez Backup jobs et le formulaire New backup job.
  2. Ouvrez la liste Agent et allez à sa fin : sous Hyper-V failover clusters (virtual machines), choisissez le cluster, par ex. HVC01 — 2 nodes. Choisissez le cluster, pas un seul nœud.
  3. Le type est réglé sur Virtual machines. Choisissez All clustered VMs (y compris les VM ajoutées plus tard au cluster) ou Only these ; chaque VM indique le nœud sur lequel elle tourne.
  4. Choisissez le stockage, la planification et le nombre de sauvegardes à conserver, puis cliquez sur Create job.

La page de la tâche montre chaque nœud avec son dernier résultat ; Run backup now on all agents les lance tous. Un nœud qui n'exécute à ce moment aucune VM de la tâche indique None of the job's VMs runs on this node now, ce qui est une réussite.

Tâches de VM créées auparavant pour des nœuds isolés : désactivez-les ou supprimez-les après la première sauvegarde de la tâche du cluster, sinon les VM du cluster sont sauvegardées deux fois ; leurs sauvegardes restent sur le stockage. Les VM hors cluster (propres à un nœud) ne font pas partie de la tâche du cluster ; sauvegardez-les avec une tâche de ce nœud.

Fonctionnement

  • Chaque nœud sauvegarde les VM du cluster qu'il exécute à ce moment, toutes dans un même dépôt du cluster sur le stockage.
  • Quand une VM passe sur un autre nœud (migration à chaud ou basculement), son historique continue là-bas et Resilient Change Tracking ne lit toujours que les blocs modifiés : pas de nouvelle sauvegarde complète.
  • Une VM déplacée pendant sa sauvegarde est tout de même sauvegardée entièrement. Le nœud vers lequel elle a été déplacée supprime le point de contrôle de la sauvegarde en quelques minutes, une fois la lecture terminée ; l'exécution indique que la VM a été déplacée.

Restauration

  • À la place de l'original s'exécute sur le nœud qui possède la VM à ce moment (la console le choisit). La VM est arrêtée et démarrée par le cluster, pour qu'il ne prenne pas l'arrêt pour une panne.
  • Comme nouvelle VM : choisissez un dossier sur un Cluster Shared Volume (C:\ClusterStorage\…). La configuration de la VM y va aussi et la VM est ajoutée au cluster comme rôle.

Restaurer des fichiers individuels

Dans le tableau des VM de l'exécution, cliquez sur Parcourir les fichiers pour voir les partitions et volumes des disques de la VM. Vous pouvez parcourir NTFS, ext2/3/4 et XFS, y compris dans LVM. De là, vous pouvez télécharger des fichiers ou les restaurer sur n'importe quel agent. Cela fonctionne exactement comme pour Proxmox VE.

Ligne de commande

Exécutez ces commandes sur l'hôte Hyper-V, en tant qu'administrateur :

La restauration Hyper-V en ligne de commande prend un verrou partagé du dépôt avant de sélectionner le point de restauration et le conserve jusqu’à la fin. Elle attend la fin des opérations de maintenance exclusives incompatibles ; si elle ne peut pas obtenir le verrou, elle échoue sans modifier la VM.

backupzit-agent hyperv list
backupzit-agent hyperv backup  --repo ... [--vmid N,N]
backupzit-agent hyperv restore --repo ... --vmid N [--new] [--name NAME] [--folder D:\VMs] [--overwrite] [--start] SNAPSHOT|latest
  • --vmid est le numéro affiché par hyperv list. BackupZit le dérive du GUID de la VM.
  • Sans --new, la VM est restaurée sur place.
  • --overwrite confirme que les disques d'une VM existante doivent être remplacés.

Les options du dépôt sont les mêmes que pour toutes les commandes ; voir Référence de la ligne de commande.

Pas encore inclus

  • Certains types de disques. Les VHDX partagés, les ensembles VHD (VHD Set) et les disques pass-through ne sont pas sauvegardés.

Diagnostiquer les lectures complètes

Le journal de l’agent (Agents → Obtenir le journal) et la sortie CLI indiquent hyperv disk read pour chaque disque, avec vm_id, disk, mode (full ou incremental), reason et disk_bytes. Après une lecture réussie, hyperv disk read complete ajoute bytes_read : les octets lus à la source par blocs entiers, pas les octets transférés après déduplication. Une première sauvegarde, une VM arrêtée ou un suivi indisponible peuvent normalement exiger une lecture complète. Une erreur de l’API RCT figure dans error et entraîne un repli sûr vers une lecture complète ; ce repli seul ne fait pas échouer la sauvegarde et n’ajoute pas d’avertissement. Un disque remplacé peut provoquer une erreur de requête RCT, sans que cette erreur prouve le remplacement. Codes de raison :

rct_not_requested · rct_state_failed · rct_disabled · no_previous_backup · disk_size_changed · previous_id_missing · rct_query_failed · rct_changes
