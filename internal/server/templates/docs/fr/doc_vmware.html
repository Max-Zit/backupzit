Machines virtuelles VMware ESXi

BackupZit sauvegarde les machines virtuelles des hôtes VMware ESXi sans rien installer sur ESXi ni dans les VM. Un agent BackupZit sur n'importe quelle machine du réseau sert de proxy à l'hôte. Il prend des instantanés, lit uniquement les blocs modifiés des disques virtuels et les écrit sur votre stockage.

Prérequis

  • ESXi 6.7, 7 ou 8 connecté directement, ou vCenter Server 7 ou 8 avec ses hôtes ESXi (voir vCenter Server).
  • Un utilisateur disposant des droits d'administrateur sur l'hôte, généralement root.
  • SSH activé sur les hôtes sous licence gratuite : Host → Actions → Services → Enable Secure Shell. La licence ESXi gratuite rend l'API en lecture seule, donc les instantanés et les restaurations passent par SSH. Les hôtes sous licence sont modifiés via l'API vSphere et n'ont pas besoin de SSH.
  • Un agent proxy : tout agent Windows ou Linux qui atteint l'hôte sur le port 443 (et 22 quand SSH est utilisé). Les données de sauvegarde passent par lui ; placez-le donc sur un réseau rapide, proche de l'hôte et du stockage.
  • De l'espace libre sur le datastore de la VM pendant la sauvegarde d'une VM en marche. BackupZit y copie brièvement le disque (voir ci-dessous). La copie est thin, elle a donc besoin d'autant d'espace que le disque en utilise réellement. Avec le hot-add, aucune copie n'est faite.

Ajouter un hôte

  1. Ouvrez Agents → Hôtes VMware ESXi → Ajouter un hôte ESXi ou vCenter Server.
  2. Saisissez l'adresse, l'utilisateur, le mot de passe et l'agent proxy.
  3. La console se connecte une fois pour les vérifier. Elle lit la liste des VM et la licence, et épingle le certificat HTTPS et la clé d'hôte SSH de l'hôte. Si l'hôte est plus tard remplacé par une autre machine à la même adresse, BackupZit refuse de se connecter au lieu de lui envoyer le mot de passe. Si le certificat change pour une raison connue — l'hôte a été réinstallé, a reçu un nouveau certificat ou a été ajouté à vCenter (qui remplace les certificats de ses hôtes) —, l'hôte affiche la nouvelle empreinte avec un bouton Accepter le nouveau certificat sur la page Agents. Comparez l'empreinte avec celle de l'hôte avant de l'accepter.

Le mot de passe est stocké chiffré, comme tous les autres secrets. La console elle-même se connecte à l'hôte (HTTPS 443, et SSH 22 avec la licence gratuite) lors de son ajout, sur Actualiser et toutes les 10 minutes pour actualiser la liste des VM, sauf si l'hôte est joint via l'agent proxy. Supprimer retire l'hôte avec ses tâches de sauvegarde ; les sauvegardes restent sur le stockage. Le tableau indique le mode de chaque hôte :

  • API vSphere (hôte sous licence, SSH inutile) : les instantanés, copies de disques, restaurations et restaurations instantanées passent par l'API.
  • vCenter Server (API vSphere) : un vCenter avec ses hôtes ESXi ; tout passe par l'API vCenter.
  • licence gratuite : instantanés et restaurations via SSH : l'API de l'hôte est en lecture seule, donc ces étapes passent par SSH.
  • SSH (choisi pour cet hôte) : l'hôte est modifié via SSH même si son API pourrait le faire (Toujours SSH lors de l'ajout de l'hôte).

Via l'agent proxy (agent 0.56 ou plus récent) : cochez Se connecter via l'agent proxy lors de l'ajout de l'hôte, ou Se connecter via le proxy dans sa ligne, et la console ne se connecte jamais elle-même à l'hôte. L'agent proxy vérifie l'adresse et le mot de passe, lit la liste des VM, la version et la licence, et signale le certificat HTTPS et la clé d'hôte SSH qu'il a vus ; la console les épingle la première fois, comme pour une connexion directe, et dès lors l'agent proxy refuse un hôte qui présente un autre certificat (la ligne de l'hôte propose alors Accepter le nouveau certificat). Actualiser et la liste des VM toutes les 10 minutes passent aussi par l'agent proxy ; ces vérifications n'apparaissent pas dans Activité. Seul l'agent proxy doit pouvoir joindre l'hôte, exactement comme pour les sauvegardes et les restaurations : la console peut donc se trouver sur un autre réseau, derrière un NAT ou dans une plage d'adresses qui se chevauche. Une adresse ou un mot de passe erroné apparaît comme erreur de l'hôte après la première vérification de l'agent proxy : supprimez l'hôte et ajoutez-le de nouveau. Tant que l'agent proxy est hors ligne ou occupé, la dernière liste des VM reste affichée.

Avec Automatique, la console choisit elle-même : un hôte qui reçoit plus tard une licence passe à l'API sans autre configuration. Comment l'hôte est modifié, dans la ligne de l'hôte (et à l'ajout), peut imposer Toujours SSH ou Toujours l'API vSphere ; le changement est vérifié aussitôt. Les sauvegardes antérieures et leurs points de restauration ne dépendent pas de la méthode.

vCenter Server

Ajoutez un vCenter Server comme un hôte : son adresse, administrator@vsphere.local (ou un utilisateur ayant le rôle Administrator) et un agent proxy. BackupZit voit alors les VM de tous les hôtes ESXi et clusters du datacenter par cette seule connexion ; rien n'est modifié via SSH et aucun mot de passe d'hôte n'est nécessaire.

  • Une VM déplacée vers un autre hôte avec vMotion continue d'être sauvegardée : les VM sont reconnues par leur UUID d'instance, pas par leur hôte.
  • Une restauration peut choisir l'hôte ESXi qui exécute la VM (par défaut : l'hôte de la VM d'origine) et le datastore.
  • La restauration instantanée démarre la VM sur l'hôte choisi ; Terminer la déplace vers un datastore avec Storage vMotion pendant qu'elle tourne, sans interruption.
  • Un vCenter comportant plusieurs datacenters ne peut pas encore être ajouté ; ajoutez directement les hôtes des autres datacenters.

N'ajoutez pas le même hôte ESXi à la fois directement et via vCenter : chaque connexion a son propre dépôt, ses VM seraient donc sauvegardées deux fois. Si un hôte que BackupZit sauvegarde directement est ensuite ajouté à vCenter, acceptez son nouveau certificat sur la page Agents ; ses tâches continuent de fonctionner — vCenter attribue un nouvel ID aux VM créées sur l'hôte autonome, et BackupZit y bascule les tâches à la prochaine actualisation.

Tâches de sauvegarde

Dans Tâches de sauvegarde, choisissez l'hôte ESXi (listé sous Hôtes VMware ESXi dans la liste des agents) et Machines virtuelles. Sauvegardez toutes les VM de l'hôte (les VM créées plus tard sont incluses automatiquement) ou cochez-en certaines. La tâche s'exécute sur l'agent proxy de l'hôte. Si vous changez de proxy, les tâches existantes suivent.

Pour exclure certaines VM, p. ex. la VM de la console BackupZit, choisissez Toutes les VM (et conteneurs) de l’hôte sauf celles cochées et cochez-les.

Comment une VM est sauvegardée

  1. Le suivi des blocs modifiés (CBT) est activé pour la VM s'il est désactivé.
    • Sur les hôtes sous licence, cela se fait automatiquement.
    • Sur les hôtes gratuits, le CBT ne peut être activé que lorsque la VM est éteinte. BackupZit le fait lors de la première sauvegarde qui trouve la VM éteinte. D'ici là, chaque sauvegarde lit les disques entiers et l'exécution affiche un avertissement.
  2. Un instantané backupzit_… est pris. Lorsque les VMware Tools tournent dans l'invité, l'instantané est suspendu (quiesced) : les applications et systèmes de fichiers sont vidés d'abord, ce qui rend la sauvegarde cohérente au niveau applicatif. Sans VMware Tools, elle est cohérente en cas de crash. Installez open-vm-tools dans les VM Linux et VMware Tools dans les VM Windows. Pour un invité dont la suspension échoue ou se comporte mal, cochez Instantanés cohérents en cas de crash (sans suspension par VMware Tools) dans la tâche : ses sauvegardes sont alors cohérentes en cas de crash, comme après une coupure de courant (agent 0.58). Sur certains hôtes (ESXi 6.7), le disque d'un instantané suspendu est un petit delta écrit par la suspension elle-même ; l'agent le lit avec l'instantané (agent 0.58 ; les agents plus anciens le refusaient comme disque delta d'instantané).
  3. Le CBT indique quels blocs lire :
    • pour la première sauvegarde, uniquement les blocs utilisés ;
    • ensuite, uniquement les blocs modifiés depuis la sauvegarde précédente.
  4. Une VM en marche garde ses disques verrouillés. Ses disques sont donc copiés sur le datastore (thin) et l'instantané est supprimé aussitôt, généralement après quelques secondes. La copie est ensuite lue via HTTPS et supprimée. Les VM éteintes sont lues directement. Avec le hot-add, les disques des VM en marche sont plutôt lus via la propre VM du proxy, sans copie.
  5. La configuration de la VM (.vmx) et la NVRAM sont stockées avec la sauvegarde.

Exemple du laboratoire de test : une VM Debian avec un disque de 8 Go, dont 1,6 Go utilisés. La première sauvegarde a lu 1,6 Go. La suivante, après 50 Mo de nouvelles données, a lu 70 Mo et a duré 23 secondes.

Hot-add : aucune copie sur le datastore

Copier les disques d'une VM en marche coûte du temps et des E/S sur le datastore de production à chaque sauvegarde, y compris les incrémentales, et demande de l'espace libre pour les blocs utilisés des disques. Avec de grosses VM sur des disques lents, cela compte. Avec le Hot-add (Agents → Hôtes VMware ESXi, la case à cocher sous l'agent proxy), le proxy les lit plutôt sur place :

  • Prérequis : le proxy est un agent Linux dans une VM qui voit les datastores de la VM (sur le même hôte, ou sur un hôte du même vCenter qui y a accès), et l'hôte est modifié via l'API vSphere (vCenter ou hôte sous licence). Le proxy trouve sa propre VM grâce à son BIOS UUID.
  • Fonctionnement : tant que l'instantané existe, chaque disque est attaché à la VM du proxy en mode independent-nonpersistent. Le proxy l'ouvre en lecture seule ; tout ce qui y serait écrit irait dans un redo log que vSphere abandonne au détachement du disque, le disque de la VM n'est donc jamais modifié. Le proxy lit uniquement les blocs signalés par le CBT, détache le disque, puis l'instantané est supprimé.
  • Ce que cela économise : aucune copie temporaire et aucun espace supplémentaire sur le datastore. Une sauvegarde incrémentale d'une VM de 2 To avec 20 Go de modifications lit 20 Go. L'instantané reste en place tant que les disques sont lus (au lieu de seulement pendant la copie), la VM écrit donc un peu plus longtemps dans l'instantané.
  • Solution de repli : si le proxy n'est pas une VM de l'hôte, ou si l'attachement ou la lecture d'un disque échoue, ce disque est copié sur le datastore comme avant, et l'exécution affiche un avertissement avec la raison. Le Hot-add est désactivé par défaut ; les agents antérieurs à 0.54 l'ignorent. La page de l'exécution indique combien de disques ont été lus par hot-add.
  • Sur la VM du proxy : empêchez LVM d'activer les volumes des disques attachés, avec le fichier de périphériques de LVM (use_devicesfile = 1 dans /etc/lvm/lvm.conf, les disques propres du proxy enregistrés avec lvmdevices). Les volumes que LVM active malgré tout sont retirés avant le détachement du disque. N'attachez pas à la main des disques d'autres VM au proxy : un disque independent-nonpersistent provenant du dossier d'une autre VM est pris pour un disque laissé par une sauvegarde interrompue, et détaché.

Plusieurs agents proxy (vCenter)

Un agent proxy lit un disque après l'autre, et via le hot-add uniquement sur les hôtes dont il voit les datastores. Avec une connexion vCenter, ajoutez un agent Linux dans une VM sur chaque hôte ESXi comme agent proxy supplémentaire (Agents → Hôtes VMware ESXi, Agents proxy supplémentaires sous l'agent proxy ; agents 0.55 ou plus récents) :

  • Répartition par hôte : chaque sauvegarde de la tâche est répartie. Chaque VM va à l'agent proxy de l'hôte ESXi sur lequel elle tourne (selon la dernière liste des VM), toute autre VM à l'agent proxy de la connexion. Chaque agent proxy sauvegarde sa part dans une exécution distincte, en même temps que les autres, via le hot-add sur son propre hôte. Seuls les agents proxy en ligne participent : les VM d'un agent proxy éteint vont à l'agent proxy de la connexion. La première sauvegarde dans un nouveau dépôt et les sauvegardes vers une cible locale ou USB ne sont pas réparties.
  • Un démarrage : la tâche présente les parties d'un démarrage comme un tout : en cours tant qu'une partie tourne, en échec si une partie a échoué. Les alertes RPO et le tableau de bord ne comptent une sauvegarde qu'une fois toutes les parties réussies ; une tâche enchaînée ou une copie « après chaque sauvegarde » démarre une seule fois, après la dernière partie.
  • Pas de chevauchement : les sauvegardes et restaurations de la connexion sur des agents proxy différents ne tournent pas en même temps (seules les parties d'un même démarrage le font), ainsi une VM déplacée entre hôtes n'est jamais traitée par deux agents proxy à la fois.
  • Rétention par agent proxy : chaque partie conserve le nombre de sauvegardes de la tâche pour ses VM, et les tâches de copie les copient et les conservent aussi par partie. Les sauvegardes d'avant la répartition de la tâche et celles d'un agent proxy retiré restent telles quelles : elles restent des points de restauration de leurs VM. Une VM déplacée sur un autre hôte (vMotion) passe à l'agent proxy de cet hôte dès la prochaine actualisation de la liste des VM.
  • BackupZit trouve l'hôte d'un agent proxy grâce au BIOS UUID que son agent signale ; la page Agents l'affiche à côté de chaque agent. Hôte ESXi introuvable : l'agent n'est pas une VM de ce vCenter, ou la liste des VM est plus ancienne que l'agent (cliquez sur Actualiser).

Annuler une sauvegarde VMware (Activité → Annuler) arrête aussi une copie de disque en cours sur le datastore et supprime la copie partielle ; l'instantané est supprimé comme après chaque sauvegarde. Un instantané encore en cours de création au moment de l'annulation est attendu (jusqu'à cinq minutes), puis supprimé lui aussi.

Instantanés restés en place. L'agent proxy enregistre chaque instantané et chaque copie temporaire de disque avant de les créer, et n'efface l'enregistrement qu'une fois qu'il constate que l'objet a disparu : après la suppression, il liste à nouveau les instantanés de la VM, essaie jusqu'à trois fois en une dizaine de minutes, se reconnecte lorsque la session vSphere a pris fin (aussi avant chaque VM, de sorte qu'une session perdue ne fait pas échouer les VM suivantes) et consolide les disques lorsque vSphere indique qu'ils en ont besoin ; une VM sans instantanés dont les disques ont encore besoin d'une consolidation après une suppression antérieure est consolidée avant sa prochaine sauvegarde. Si l'agent s'arrête en cours de route (crash, coupure de courant) ou si la suppression échoue à répétition, l'enregistrement reste :

  • La console met en file d'attente une exécution de nettoyage sur l'agent proxy (lui seul possède les identifiants de l'hôte), et l'agent proxy supprime aussi ces restes après chaque sauvegarde de la connexion. Les VM sur lesquelles travaille une sauvegarde ou une restauration de l'agent proxy ne sont pas touchées.
  • Le tableau de bord liste chaque reste sous Nécessite votre attention (VM, depuis quand, pourquoi) avec Supprimer maintenant, et une notification (e-mail, chat) part une seule fois pour chaque reste qui subsiste.
  • La console recherche aussi les instantanés backupzit_… de plus de six heures dans la liste des VM qu'elle actualise toutes les 10 minutes, tant qu'aucune sauvegarde de la connexion ne tourne, si bien que les restes d'agents plus anciens apparaissent aussi. Seuls les instantanés nommés backupzit_… sont supprimés ; les instantanés propres à la VM ne sont jamais touchés.

Restaurer une VM

Utilisez l'assistant de restauration (Machine virtuelle complète) ou la page de la sauvegarde dans Activité. Choisissez :

  • En tant que nouvelle VM à côté de l'original : une copie avec un nouveau nom, un nouvel UUID et de nouvelles adresses MAC. Le nom par défaut est celui de l'original suivi de -restored- et de la date. Les paramètres réseau de l'invité liés aux anciennes adresses MAC, comme netplan match: macaddress dans les images cloud, ne s'appliquent pas à la copie.
  • À la place de la VM d'origine : avec l'arrêter et remplacer ses disques, BackupZit :
    • éteint la VM et supprime ses instantanés ;
    • renomme les disques actuels en ….replaced-DATE.vmdk (supprimez-les une fois que la VM restaurée fonctionne) ;
    • écrit la sauvegarde dans de nouveaux disques portant les noms d'origine, et règle le processeur et la mémoire comme dans la sauvegarde.
    La VM conserve son UUID, ses cartes réseau et ses adresses MAC. Si la VM a été supprimée, elle est recréée avec son identité d'origine.
  • Hôte ESXi et datastore : un autre hôte, ou un autre datastore du même hôte.
  • Démarrer la VM après la restauration.

Les disques sont restaurés en thin, et seuls les blocs contenant des données sont écrits. Les images ISO connectées aux lecteurs CD/DVD ne font pas partie de la sauvegarde ; ces lecteurs restent donc vides.

Restauration instantanée

Choisissez Instantanément, en s’exécutant depuis la sauvegarde pour démarrer une VM en quelques secondes, sans copier d'abord ses disques. L'agent proxy de l'hôte — il doit s'agir d'un agent Linux — sert les disques de la VM directement depuis la sauvegarde via NFS ; l'hôte les monte comme datastore backupzit-<agent> et exécute la VM depuis celui-ci. Les modifications faites par la VM sont conservées sur l'agent (/var/lib/backupzit/instant-esxi, qui a donc besoin d'espace libre) ; la sauvegarde elle-même n'est jamais modifiée, et la rétention la conserve tant que la VM tourne depuis elle. Si la VM d'origine existe encore, la VM instantanée reçoit un nouvel UUID et de nouvelles adresses MAC.

Sur la page de l'exécution, lorsque la VM fonctionne comme prévu :

  • Terminer la copie sur un datastore de l'hôte : la VM est arrêtée (via VMware Tools s'ils tournent), ses disques sont copiés en thin (via l'API sur les hôtes sous licence, avec vmkfstools via SSH sous licence gratuite), elle est enregistrée depuis le datastore et redémarrée. Un hôte autonome n'a pas de Storage vMotion, cela nécessite donc une courte interruption qui augmente avec la taille des disques. Si la copie échoue, la VM continue de tourner depuis la sauvegarde.
  • Abandonner arrête et supprime la VM avec toutes ses modifications.

L'agent répond en NFS sur le port 2049 (et l'enregistre auprès du rpcbind de la machine sur le port 111, ou répond lui-même sur le port 111) uniquement pour l'adresse de l'hôte ESXi ; ouvrez ces ports de l'hôte vers l'agent si un pare-feu se trouve entre les deux. Lorsque la dernière VM instantanée est terminée ou abandonnée, le datastore est supprimé et le serveur NFS s'arrête.

Fichiers individuels

Parcourir les fichiers sur la page de la sauvegarde (ou Fichiers d’une machine virtuelle dans l'assistant de restauration) ouvre les disques de la VM. Vous pouvez parcourir NTFS, ext2/3/4 et XFS, y compris sur LVM, et télécharger des fichiers ou les restaurer sur n'importe quel agent.

Ligne de commande

Ces commandes s'exécutent sur n'importe quel agent. Définissez le mot de passe ESXi dans BACKUPZIT_VMWARE_PASSWORD :

backupzit-agent vmware list    --host 192.168.1.20 [--user root]
backupzit-agent vmware backup  --host … --repo … [--vmid N,N]
backupzit-agent vmware restore --host … --repo … --vmid N [--new] [--name NAME] [--datastore DS] [--overwrite] [--start] SNAPSHOT|latest

vmware list affiche les empreintes du certificat et de la clé SSH de l'hôte. Passez-les avec --thumbprint et --ssh-host-key pour les épingler aussi en ligne de commande.

Pas encore inclus

  • vCenter avec plusieurs datacenters. Seul un vCenter avec un datacenter peut être ajouté ; ajoutez directement les hôtes des autres.
  • Les VM ayant leurs propres instantanés. Leurs disques sont des deltas ; supprimez ou consolidez d'abord les instantanés. (Le petit delta qu'écrit un instantané suspendu appartient à la sauvegarde elle-même et est lu avec elle.)
  • Certains types de disques. Les mappages de périphériques bruts (RDM) et les disques indépendants.
  • La restauration instantanée via un agent proxy Windows. La restauration instantanée nécessite un agent proxy Linux.
