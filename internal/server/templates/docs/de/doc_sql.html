Datenbanken: SQL Server, PostgreSQL, MySQL

BackupZit sichert Datenbanken mit den eigenen Werkzeugen des Datenbankservers, über den Agenten auf der Datenbankmaschine: Microsoft SQL Server unter Windows, PostgreSQL und MySQL/MariaDB unter Linux. Vollsicherungen laufen nach dem Zeitplan des Auftrags; Log-Sicherungen alle paar Minuten ermöglichen es, eine einzelne Datenbank auf einen beliebigen Zeitpunkt wiederherzustellen — zum Beispiel auf eine Minute vor einem falschen DELETE.

Einen Auftrag erstellen

Erstellen Sie unter Sicherungsaufträge einen Auftrag der Art Datenbanken auf dem Agenten der Datenbankmaschine und wählen Sie:

  • Datenbankserver: Microsoft SQL Server, PostgreSQL oder MySQL/MariaDB. Kann später nicht geändert werden.
  • Instanz oder Port: die SQL-Server-Instanz (leer für die Standardinstanz, z. B. SQLEXPRESS) oder der PostgreSQL-Port (leer für 5432). MySQL/MariaDB wird über den lokalen Socket erreicht.
  • Datenbanken: ein Name pro Zeile, oder leer für alle Benutzerdatenbanken — später erstellte Datenbanken werden automatisch einbezogen.
  • Logs alle … Minuten sichern: z. B. 15 — Transaktionslogs (SQL Server), archiviertes WAL (PostgreSQL) oder Binärlogs (MySQL). Leer lassen, wenn die Wiederherstellung auf den Zeitpunkt einer Vollsicherung genügt.
  • Der Zeitplan ist der der Vollsicherungen, z. B. täglich um 22:00.

Sicherungen werden dedupliziert — unveränderte Daten werden nicht erneut hochgeladen — und wie jede Sicherung verschlüsselt. Die Aufbewahrung zählt die Vollsicherungen; Log-Sicherungen werden so lange behalten wie die Vollsicherung, auf der sie aufbauen. Die Laufseite listet auf, was jede Sicherung enthält.

Microsoft SQL Server

  1. Installieren Sie den Agenten auf der Windows-Maschine, auf der SQL Server läuft (jede Edition ab 2012, einschließlich Express).
  2. Der Agent läuft als NT AUTHORITY\SYSTEM und verbindet sich mit Windows-Authentifizierung. Geben Sie diesem Konto einmal pro Instanz die Rolle sysadmin: 
    sqlcmd -S .\SQLEXPRESS -E -Q "ALTER SERVER ROLE sysadmin ADD MEMBER [NT AUTHORITY\SYSTEM]"
  • Jeder Lauf schreibt eine Sicherungsdatei pro Datenbank (BACKUP DATABASE / BACKUP LOG … WITH CHECKSUM) in den Standard-Sicherungsordner der Instanz, speichert die Dateien und löscht sie. Der Ordner braucht während des Laufs freien Platz für die größte Datenbank.
  • Mit aktivierten Log-Sicherungen beginnen die Vollsicherungen die Log-Kette. Ohne sie werden Vollsicherungen als COPY_ONLY erstellt, sodass sie andere Sicherungs- oder Wartungspläne nicht stören.
  • Log-Sicherungen werden für Datenbanken im Wiederherstellungsmodell full oder bulk-logged erstellt; Datenbanken im Modell simple erhalten nur Vollsicherungen. Aktivieren Sie Systemdatenbanken, um master, model und msdb hinzuzufügen.

PostgreSQL

Der Agent arbeitet als Konto postgres über den lokalen Socket — für Sicherungen ist nichts zu konfigurieren. Eine Vollsicherung speichert den ganzen Cluster (pg_basebackup), die Rollen (pg_dumpall --globals-only) und einen pg_dump jeder Datenbank.

Point-in-Time-Recovery braucht WAL-Archivierung. Mit aktivierten Log-Sicherungen richtet die erste Vollsicherung sie mit ALTER SYSTEM ein: archive_mode = on und ein archive_command, der abgeschlossene WAL-Segmente nach /var/lib/backupzit-pg/wal kopiert; die Log-Sicherungen speichern und entfernen sie dort. archive_mode wird nach einem Neustart von PostgreSQL wirksam (systemctl restart postgresql) — der Lauf weist darauf hin. Verwendet bereits ein anderes Werkzeug archive_command, lässt BackupZit es unverändert und sichert ohne Point-in-Time-Recovery. Hören die Log-Sicherungen auf (Auftrag deaktiviert oder gelöscht), schalten Sie die Archivierung wieder aus (ALTER SYSTEM RESET archive_mode, Neustart), damit der Ordner nicht vollläuft.

  • Eine Datenbank wiederherstellen im Stand der Vollsicherung: aus ihrem pg_dump in den laufenden Server, unter neuem Namen oder anstelle der Datenbank.
  • Zu einem Zeitpunkt (oder neuester Stand): Der Agent entpackt die Cluster-Sicherung in eine temporäre Instanz auf einem freien Port (nur Socket, kein Netzwerk, keine Archivierung), spielt das WAL bis zu diesem Zeitpunkt ein, erstellt daraus einen Dump der Datenbank in den laufenden Server und entfernt die temporäre Instanz. Die Maschine braucht eine Weile freien Platz für den Cluster.
  • Ganzer Cluster: wird auf dieselbe Weise als separate Instanz wiederhergestellt, die auf einem freien Port weiterläuft; der Lauf nennt ihren Port und ihr Datenverzeichnis (unter /var/lib/backupzit-pg) sowie, wie man sich verbindet und sie stoppt.

MySQL und MariaDB

Der Agent verbindet sich als root über den lokalen Socket (Socket-Authentifizierung, Standard unter Debian und Ubuntu) oder mit den Zugangsdaten aus /root/.my.cnf. Eine Vollsicherung speichert einen mysqldump jeder Datenbank (konsistent, mit Routinen, Events und Triggern) zusammen mit der zugehörigen Binärlog-Position.

Point-in-Time-Recovery braucht das Binärlog. Aktivieren Sie es einmal in der Serverkonfiguration und starten Sie den Server neu, z. B. /etc/mysql/mariadb.conf.d/60-binlog.cnf:

[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin
binlog_format = ROW
expire_logs_days = 7

(legen Sie den Ordner für das Log an, mit dem Konto mysql als Besitzer). Die Log-Sicherungen speichern dann jedes geschlossene Binärlog. Halten Sie die eigene Ablaufzeit des Servers länger als das Intervall der Log-Sicherungen; eine Lücke wird gemeldet, und Wiederherstellungen können sie nicht überbrücken.

  • Eine Datenbank wiederherstellen: Ihr Dump wird in eine neue Datenbank geladen (oder ersetzt eine vorhandene). Zu einem Zeitpunkt oder neuester Stand: Die nach dem Dump in den Binärlogs aufgezeichneten Änderungen dieser Datenbank werden bis zu diesem Zeitpunkt eingespielt — auch wenn die Datenbank einen neuen Namen erhält. Das Einspielen wird nicht in das Binärlog des Servers geschrieben.
  • Benutzer und Rechte (die Systemdatenbank mysql) sind nicht Teil der Dumps.

Wiederherstellen

Öffnen Sie einen Lauf einer Vollsicherung (oder verwenden Sie den Wiederherstellungsassistenten → Datenbank) und wählen Sie die Datenbank, die Maschine für die Wiederherstellung (derselbe Server oder ein anderer mit demselben Datenbankserver) und:

  • Als neue Datenbank mit z. B. dem Namen sales_restored — das Original bleibt unberührt, und Sie können Zeilen zurückkopieren — oder unter ihrem ursprünglichen Namen; aktivieren Sie ersetzen, um eine vorhandene Datenbank zu überschreiben (ihre Benutzer werden zuerst getrennt).
  • Zustand: Stand der Vollsicherung; der neueste Stand (die Vollsicherung und jede Log-Sicherung danach); oder ein Zeitpunkt zwischen der Vollsicherung und der neuesten verwendbaren Log-Sicherung, wie die Tabelle zeigt. Geben Sie die Zeit so ein, wie die Konsole sie anzeigt, in der Zeitzone des Konsolenservers (siehe Zeitzone); der Agent rechnet sie in die Zeitzone des Datenbankservers um.

Befehlszeile

backupzit-agent sql list    [--instance SQLEXPRESS]
backupzit-agent sql backup  --repo ... [--instance I] [--db a,b] [--system] [--log] [--copy-only]
backupzit-agent sql restore --repo ... [--instance I] --db NAME [--as NEW] [--replace] [--at "2026-10-04 14:59:00"] SNAPSHOT|latest
backupzit-agent pg list     [--port 5432]
backupzit-agent pg backup   --repo ... [--port P] [--db a,b] [--pitr | --wal]
backupzit-agent pg restore  --repo ... --db NAME|"(cluster)" [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest
backupzit-agent mysql list
backupzit-agent mysql backup  --repo ... [--db a,b] [--binlog]
backupzit-agent mysql restore --repo ... --db NAME [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest

Nicht enthalten

  • Differenzielle SQL-Server-Sicherungen und Always-On-Verfügbarkeitsgruppen; entfernte Datenbankserver — der Agent sichert Server auf seiner eigenen Maschine.
  • Wiederherstellung einzelner Tabellen: Stellen Sie die Datenbank unter neuem Namen wieder her und kopieren Sie die Zeilen.
