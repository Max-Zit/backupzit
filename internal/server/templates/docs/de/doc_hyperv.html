Virtuelle Hyper-V-Maschinen

BackupZit sichert virtuelle Hyper-V-Maschinen über den Agenten auf dem Hyper-V-Host; in den VMs wird nichts installiert. Windows- und Linux-Gäste werden erfasst, während sie weiterlaufen. Sie können sie als neue VM oder anstelle des Originals wiederherstellen.

Einrichtung

  1. Installieren Sie das MSI des Windows-Agent von Agenten auf dem Hyper-V-Host und registrieren Sie ihn. Unterstützte Hosts: Windows Server 2016 oder neuer mit der Hyper-V-Rolle oder Windows 10/11 mit Hyper-V. In einem Cluster installieren Sie den Agenten auf jedem Host.
  2. Innerhalb einer Minute erscheint der Host auf der Seite Agenten mit dem Kennzeichen Hyper-V · N VMs.
  3. Wählen Sie unter Sicherungsaufträge diesen Agenten und Virtuelle Maschinen (Proxmox VE, Hyper-V, VMware). Wählen Sie dann eines:
    • Alle VMs (und Container) auf dem Host, was auch später erstellte VMs abdeckt;
    • Alle VMs auf dem Host außer den angehakten, z. B. ohne die VM der BackupZit-Konsole; später erstellte VMs sind ebenfalls enthalten;
    • einzelne VMs, indem Sie sie markieren.

Der Agent arbeitet über die eigenen Schnittstellen von Hyper-V: das Hyper-V-PowerShell-Modul und die Windows Virtual Disk API. Die Konsole speichert keine Hyper-V-Zugangsdaten.

Wie eine VM gesichert wird

  1. Ein temporärer Wiederherstellungsprüfpunkt (recovery checkpoint, backupzit_…) wird erstellt. Das ist der Prüfpunkttyp, den Hyper-V für Sicherungsanwendungen bereitstellt. Hyper-V bittet den Gast, sich darauf vorzubereiten:
    • Windows-Gäste leeren ihre Anwendungspuffer über VSS.
    • Linux-Gäste frieren ihre Dateisysteme ein, wenn die Hyper-V-Daemons installiert sind (hyperv-daemons / hv-vss-daemon).
    Kann der Gast keines von beiden, wird der Prüfpunkt absturzkonsistent erstellt. Die Laufseite zeigt, welche Art verwendet wurde.
  2. Der Wiederherstellungsprüfpunkt schaltet Resilient Change Tracking (RCT) für die Festplatten der VM ein; daneben sehen Sie .rct- und .mrt-Dateien. Die erste Sicherung liest die ganzen Festplatten. Danach meldet RCT, welche Blöcke sich seit der vorigen Sicherung geändert haben, und nur diese werden gelesen. Eine vergrößerte Festplatte (zum Beispiel mit Resize-VHD) wird genauso gelesen: die geänderten Blöcke und der neue Bereich. Eine verkleinerte Festplatte wird einmal ganz gelesen.
  3. Die Festplatten werden im Stand des Prüfpunkts über die Virtual Disk API in Blöcken zu 1 MiB gelesen. Das umfasst VHDX- und VHD-Dateien, einschließlich Ketten früherer Prüfpunkte. Leere Blöcke werden nicht gespeichert, und Blöcke, die bereits im Repository liegen, werden nicht erneut hochgeladen. Das ist die Standard-Blockgröße; ein Job kann stattdessen 256 oder 512 KiB verwenden (siehe Jobs).
  4. Der Prüfpunkt wird entfernt, und Hyper-V führt ihn im Hintergrund zusammen.
  5. Die Konfiguration der VM wird mit der Sicherung gespeichert: Generation, CPU, Arbeitsspeicher, Netzwerkadapter (Switch, VLAN, MAC-Adresse), Festplattencontroller, Secure Boot und TPM.

Auch ausgeschaltete VMs erhalten einen Wiederherstellungsprüfpunkt (Agent 0.58), sodass die Änderungsverfolgung nur liest, was sich seit ihrer vorherigen Sicherung geändert hat, auch solange sie ausgeschaltet bleiben; wo Hyper-V keinen erstellen kann (zum Beispiel bei Replica-VMs), werden ihre Festplatten direkt gelesen. Auf Hosts ohne Wiederherstellungsprüfpunkte wird ein gewöhnlicher Prüfpunkt erstellt (wenn möglich ein Produktionsprüfpunkt, sonst absturzkonsistent), und jede Sicherung liest die ganzen Festplatten.

Überlappende Sicherungen derselben VM warten auf jedem Host aufeinander, auch Dienst und Befehlszeile. Eine Sicherung entfernt nur ihren eigenen temporären Prüfpunkt. Der Agent entfernt einen zurückgebliebenen Prüfpunkt, sobald seine Sicherung auf einem anderen Knoten beendet ist (nach einer Livemigration), oder wenn er älter als 48 Stunden ist (eine durch Absturz oder Stromausfall unterbrochene Sicherung). Alle überlappenden Sicherungsprozesse müssen aktualisierte Programme verwenden.

Zurückgebliebene Prüfpunkte. Der Agent vermerkt jeden Sicherungsprüfpunkt, bevor er ihn erstellt, und löscht den Vermerk erst, wenn der Prüfpunkt weg ist (nach dem Entfernen listet er die Prüfpunkte der VM erneut auf, bis zu drei Versuche über etwa zehn Minuten). Vermerkte Prüfpunkte werden nach einem Absturz oder einem fehlgeschlagenen Entfernen gleich entfernt, beim Start des Agenten und alle 15 Minuten, nicht erst nach 48 Stunden; eine VM, die eine Sicherung gerade verwendet, bleibt unberührt. Wurde die VM auf einen anderen Knoten verschoben, entfernt der Agent dort den Prüfpunkt. Wird eine Sicherung abgebrochen, während Hyper-V ihren Prüfpunkt noch erstellt, und dauert das länger als fünf Minuten, legt Hyper-V ihn möglicherweise unter seinem Standardnamen an (Name der VM und Datum): Der Agent entfernt diesen einen Wiederherstellungsprüfpunkt, sobald er erscheint. Was sich nicht entfernen lässt, steht im Dashboard unter Benötigt Aufmerksamkeit mit Jetzt entfernen und wird einmal gemeldet.

Nur anwendungskonsistent. Für Active Directory, SQL Server, Exchange und andere Datenbanken aktivieren Sie im Job Anwendungskonsistente Prüfpunkte verlangen (auch im Job für einen Cluster). Eine laufende VM wird dann nur aus einem Prüfpunkt gesichert, den der Gast mit VSS vorbereitet hat; schlägt das fehl, wird die VM nicht gesichert und der Lauf schlägt fehl (mit Benachrichtigung), statt einen absturzkonsistenten Prüfpunkt zu nehmen. Die anderen VMs des Jobs werden weiter gesichert und lassen sich aus diesem Lauf wiederherstellen. Prüfen Sie den Integrationsdienst Backup (volume shadow copy) in den VM-Einstellungen und VSS im Gast (vssadmin list writers). Benötigt Agenten 0.48.0 oder neuer; bei älteren Agenten schlägt der Lauf mit der Aufforderung zur Aktualisierung fehl.

Erwartet absturzkonsistent. Gäste, die selbst keinen Prüfpunkt vorbereiten können (zum Beispiel ein altes Linux ohne die Hyper-V-Daemons), lassen sich im Job unter VMs, bei denen absturzkonsistent genügt eintragen, mit Namen oder Muster (legacy-*): Ihr absturzkonsistenter Prüfpunkt ist dann keine Warnung, und die Laufseite zeigt weiterhin, dass er absturzkonsistent war. Anwendungskonsistente Prüfpunkte verlangen hat Vorrang. Benötigt Agenten ab 0.53.0; ältere Agenten warnen weiter.

vTPM und BitLocker. Bei VMs der Generation 2 mit virtuellem TPM speichert die Sicherung auch das vTPM (die Gaststatusdatei und die Schlüsselschutzvorrichtung). Als neue VM auf demselben Host wiederhergestellt, oder auf einem Host mit dem Guardian-Zertifikat des ursprünglichen Hosts, erhält die VM ihr vTPM zurück und BitLocker fragt nicht nach dem Wiederherstellungsschlüssel. Auf anderen Hosts erhält die VM ein neues, leeres vTPM, und die Wiederherstellung meldet das; importieren Sie dort vorher das Zertifikat UntrustedGuardian des ursprünglichen Hosts. Eine Wiederherstellung über die vorhandene VM behält deren vTPM. Abgeschirmte VMs (Host Guardian Service) werden nicht unterstützt. Bewahren Sie die BitLocker-Wiederherstellungsschlüssel trotzdem auf.

Die Integritätsprüfung des Repositorys prüft auch den gespeicherten Gastzustand. Prüfen Sie nach dem Update vorhandene Repositorys und Kopien; ein Update kann bereits gelöschten Gastzustand nicht wiederherstellen. Verwenden Sie bei fehlendem Zustand eine intakte Kopie oder erstellen Sie eine neue Sicherung.

Beispiel aus dem Testlabor: eine Linux-VM mit einer 3-GB-Festplatte. Die erste Sicherung las 3 GB. Die nächste, nach 64 MB neuen Daten, las 96 MB.

Unter Windows 10/11 erstellt Hyper-V beim Start einer VM einen automatischen Prüfpunkt, sofern diese Option in den VM-Einstellungen nicht ausgeschaltet ist. BackupZit kommt mit solchen Prüfpunkten zurecht, aber bei Servern sollten Sie automatische Prüfpunkte ausschalten (VM-Einstellungen → Prüfpunkte).

Datenträger auslassen

Datenträger mit Daten, die anders gesichert werden, können ausgelassen werden: Tragen Sie sie im Auftrag unter Datenträger ausschließen ein, einen pro Zeile, als Dateinamenmuster (*-data.vhdx) oder vollständigen Pfad (D:\VMs\SQL01\data.vhdx); Groß- und Kleinschreibung spielt keine Rolle. Die Seite des Laufs zeigt die ausgeschlossenen Datenträger jeder VM. Eine als neue VM wiederhergestellte VM erhält nur die gesicherten Datenträger; eine Wiederherstellung am ursprünglichen Ort lässt die ausgeschlossenen Datenträger unverändert angeschlossen. Eine VM, deren Datenträger alle ausgeschlossen sind, wird nicht gesichert. Agenten älter als 0.49 können keine Datenträger ausschließen; die Konsole startet einen solchen Auftrag daher nicht auf ihnen.

Eine VM wiederherstellen

Öffnen Sie den Lauf der VM-Sicherung (über die Auftragsseite oder Aktivität) und verwenden Sie Eine Hyper-V-VM wiederherstellen.

Als neue VM neben dem Original

Erstellt eine zweite VM mit neuen MAC-Adressen, sodass sie im selben Netz wie das Original laufen kann. Standardmäßig wird sie nach dem Original plus „restored“ und dem Datum benannt. Automatische Prüfpunkte werden bei ihr ausgeschaltet (Windows schaltet sie für neue VMs ein), sodass ihr Start keine Prüfpunktdateien hinterlässt. Läuft die Kopie neben dem Original und enthält sie den BackupZit-Agenten, siehe Zwei Maschinen mit einem Agenten.

Netzwerkeinstellungen im Gast, die an eine MAC-Adresse gebunden sind, gelten nicht für die neuen Adapter. Ein Beispiel ist match: macaddress von netplan, das Linux-Cloud-Images verwenden.

Anstelle der Original-VM

Aktivieren Sie ausschalten und ihre Datenträger ersetzen. BackupZit dann:

  • schaltet die vorhandene VM aus;
  • führt ihre Prüfpunkte zusammen;
  • tauscht ihre Festplatten gegen die wiederhergestellten.

Die VM behält ihre ID, Netzwerkadapter und MAC-Adressen, sodass Aufträge, Überwachung und das Netzwerk des Gasts weiter funktionieren.

Vor dem Stoppen der ursprünglichen VM oder dem Zusammenführen ihrer Prüfpunkte stellt BackupZit alle Datenträger in einem eindeutigen Unterordner backupzit-restore-* des gewählten Datenträgerordners wieder her (standardmäßig des ursprünglichen Ordners). Fehler bei der Vorbereitung lassen die VM unverändert. Alte Datenträger behalten ihre Pfade; löschen Sie sie erst nach Prüfung der wiederhergestellten VM. Fehler nach Beginn der Umschaltung können manuelle Wiederherstellung erfordern: Neue Datenträger bleiben erhalten, ihr Ordner steht in der Fehlermeldung, und Einstellungen sowie Prüfpunkte werden nicht automatisch zurückgesetzt.

Existiert die Original-VM nicht mehr, wird sie neu erstellt, mit einer neuen Hyper-V-ID.

Optionen

  • Ordner für die virtuellen Festplatten: der Standardordner des Hosts oder ein beliebiger Ordner mit VM-Festplatten. Eine Wiederherstellung an Ort und Stelle legt die neuen Festplatten in einen neuen Unterordner backupzit-restore-… und lässt die alten, wo sie waren. Seit 0.59 kommen die Datenträger in einen Ordner, den nur das System, Administratoren und Hyper-V-Administratoren ändern dürfen (auf einer SMB-Freigabe behält er die Berechtigungen der Freigabe), und kein Ordner auf dem Weg kann während der Wiederherstellung umbenannt oder ersetzt werden; einer Verknüpfung auf dem Weg wird nur gefolgt, wenn sie dem System gehört, etwa C:\ClusterStorage\Volume1. Gibt es schon einen Ordner mit dem Namen der VM, den andere Benutzer ändern dürfen, kommen die Datenträger in einen neuen Ordner backupzit-restore-… darin.
  • VM nach der Wiederherstellung starten.

Was eine wiederhergestellte VM erhält

  • Virtuelle Switches werden nach Namen verbunden. Gibt es einen Switch auf dem Host nicht, bleibt der Adapter getrennt.
  • Jede wiederhergestellte VM erhält eine neue Generations-ID, sodass Active-Directory-Domänencontroller die Wiederherstellung sicher erkennen.

Failovercluster

Die VMs eines Hyper-V-Failoverclusters werden mit einem Job für den ganzen Cluster gesichert. Drei Schritte:

1. Den Agenten auf jedem Knoten installieren

Installieren Sie den Windows-Agenten auf jedem Knoten des Clusters (nicht in den VMs). Eine VM sichert immer der Agent des Knotens, auf dem sie gerade läuft: Nur dort funktionieren die Prüfpunkte und die Änderungsverfolgung von Hyper-V. Solange eine VM auf einem Knoten ohne Agenten läuft, wird sie nicht gesichert; sobald sie auf einen Knoten mit Agenten wechselt, wieder.

2. Die Konsole erkennt den Cluster selbst

Für den Cluster muss weder in BackupZit noch in Windows etwas eingerichtet werden. Jeder Agent (Version 0.47.0 oder neuer) meldet den Failovercluster seines Knotens und welche VMs geclustert sind. Etwa eine Minute nach der Installation oder Aktualisierung der Agenten:

  • kennzeichnet die Seite Agents jeden Knoten mit cluster NAME;
  • erscheint der Cluster im Job-Formular (nächster Schritt), mit der Zahl seiner Knoten.

Später zum Cluster hinzugefügte Knoten werden ebenso erkannt und kommen automatisch zum Job, sobald ihr Agent installiert ist.

3. Den Job für den Cluster anlegen

  1. Öffnen Sie Backup jobs und das Formular New backup job.
  2. Öffnen Sie die Liste Agent und gehen Sie an ihr Ende: Wählen Sie unter Hyper-V failover clusters (virtual machines) den Cluster, z. B. HVC01 — 2 nodes. Wählen Sie den Cluster, nicht einen einzelnen Knoten.
  3. Die Art ist auf Virtual machines gesetzt. Wählen Sie All clustered VMs (auch später zum Cluster hinzugefügte VMs), All clustered VMs except the ticked ones oder Only these; bei jeder VM steht der Knoten, auf dem sie gerade läuft.
  4. Wählen Sie das Speicherziel, den Zeitplan und wie viele Sicherungen bleiben, und klicken Sie auf Create job.

Die Seite des Jobs zeigt jeden Knoten mit seinem letzten Ergebnis; Run backup now on all agents startet alle. Ein Knoten, auf dem gerade keine VM des Jobs läuft, meldet None of the job's VMs runs on this node now – das ist ein Erfolg.

Früher angelegte VM-Jobs einzelner Knoten: Deaktivieren oder löschen Sie sie nach der ersten Sicherung des Cluster-Jobs, sonst werden die geclusterten VMs doppelt gesichert; ihre Sicherungen bleiben auf dem Speicher. Nicht geclusterte VMs (sie gehören zu einem Knoten) gehören nicht zum Cluster-Job; sichern Sie sie mit einem Job dieses Knotens.

Wie es funktioniert

  • Jeder Knoten sichert die geclusterten VMs, die gerade auf ihm laufen, alle in ein Repository des Clusters auf dem Speicher.
  • Wechselt eine VM auf einen anderen Knoten (Live-Migration oder Failover), läuft ihr Verlauf dort weiter, und Resilient Change Tracking liest weiterhin nur die geänderten Blöcke: Es gibt keine neue Vollsicherung.
  • Eine VM, die während ihrer Sicherung verschoben wird, wird trotzdem vollständig gesichert. Der Knoten, auf den sie gewechselt ist, entfernt den Prüfpunkt der Sicherung innerhalb weniger Minuten, sobald die Sicherung fertig gelesen hat; der Lauf meldet, dass die VM verschoben wurde.

Wiederherstellen

  • Anstelle des Originals läuft auf dem Knoten, dem die VM gerade gehört (die Konsole wählt ihn). Die VM wird über den Cluster gestoppt und gestartet, damit der Cluster das Stoppen nicht für einen Ausfall hält.
  • Als neue VM: Wählen Sie einen Ordner auf einem Cluster Shared Volume (C:\ClusterStorage\…). Auch die Konfiguration der VM kommt dorthin, und die VM wird dem Cluster als Rolle hinzugefügt.

Einzelne Dateien wiederherstellen

Klicken Sie in der VM-Tabelle des Laufs auf Dateien durchsuchen, um die Partitionen und Volumes auf den Festplatten der VM zu sehen. Sie können NTFS, ext2/3/4 und XFS durchsuchen, auch innerhalb von LVM. Von dort laden Sie Dateien herunter oder stellen sie auf einem beliebigen Agenten wieder her. Es funktioniert genau wie bei Proxmox VE.

Befehlszeile

Führen Sie dies auf dem Hyper-V-Host als Administrator aus:

Die Hyper-V-Wiederherstellung über die Befehlszeile erwirbt vor der Auswahl des Snapshots eine gemeinsame Repository-Sperre und hält sie bis zum Ende der Wiederherstellung. Sie wartet auf kollidierende Wartungsarbeiten mit exklusiver Sperre. Kann die Sperre nicht erworben werden, schlägt sie fehl, ohne die VM zu verändern.

backupzit-agent hyperv list
backupzit-agent hyperv backup  --repo ... [--vmid N,N]
backupzit-agent hyperv restore --repo ... --vmid N [--new] [--name NAME] [--folder D:\VMs] [--overwrite] [--start] SNAPSHOT|latest
  • --vmid ist die von hyperv list angezeigte Nummer. BackupZit leitet sie aus der GUID der VM ab.
  • Ohne --new wird die VM an Ort und Stelle wiederhergestellt.
  • --overwrite bestätigt, dass die Festplatten einer vorhandenen VM ersetzt werden sollen.

Die Repository-Optionen sind dieselben wie bei allen Befehlen; siehe Befehlszeilenreferenz.

Noch nicht enthalten

  • Einige Festplattentypen. Freigegebene VHDX (Shared VHDX), VHD-Sets und Pass-Through-Festplatten werden nicht gesichert. Der Lauf warnt bei jedem davon, und eine Wiederherstellung am ursprünglichen Ort lässt sie unverändert angehängt.

Vollständige Datenträgerlesevorgänge untersuchen

Das Agentenprotokoll (Agenten → Protokoll abrufen) und die CLI-Ausgabe melden je Datenträger hyperv disk read mit vm_id, disk, mode (full oder incremental), reason und disk_bytes. Nach erfolgreichem Lesen ergänzt hyperv disk read complete den Wert bytes_read: gelesene Quelldaten in ganzen Sicherungsblöcken, nicht übertragene Daten nach Deduplizierung. Die erste Sicherung oder fehlende Änderungsverfolgung können vollständiges Lesen erfordern; eine ausgeschaltete VM wird ab Agent 0.58 inkrementell gelesen (vorher las jede Sicherung erneut alles, was sich geändert hatte, seit die VM zuletzt lief). RCT-API-Fehler erscheinen als error und führen sicher zum vollständigen Lesen; allein dadurch scheitert die Sicherung nicht und erhält keine Warnung. Ein ersetzter Datenträger kann einen RCT-Abfragefehler verursachen, aber dieser Fehler beweist keinen Austausch. Grundcodes:

rct_not_requested · rct_state_failed · rct_disabled · no_previous_backup · disk_size_changed · previous_id_missing · rct_query_failed · rct_changes
