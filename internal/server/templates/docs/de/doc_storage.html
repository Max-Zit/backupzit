Speicherziele

Ein Speicherziel ist der Ort, an den Agenten ihre Sicherungen schreiben. Jeder Agent verwendet sein eigenes Repository unterhalb des Speicherorts des Ziels.

Einen Speichertyp wählen

SFTPJeden Linux-Server oder NAS mit SSHVerschlüsselte Übertragung; der Host-Schlüssel des Servers wird gepinnt.
S3-kompatibelExterne / Cloud-Kopien: AWS S3, Wasabi, Backblaze B2, MinIO, Ceph, Google Cloud StorageUnterstützt Unveränderlichkeit mit Object Lock.
Azure Blob StorageExterne Kopien für Microsoft-orientierte UnternehmenKontoschlüssel oder SAS-Token; Unveränderlichkeit über Azures Unveränderlichkeitsrichtlinien auf Versionsebene.

3-2-1-Regel: Halten Sie 3 Kopien Ihrer Daten auf 2 verschiedenen Medien, davon 1 außer Haus — zum Beispiel ein Auftrag auf ein lokales NAS und ein weiterer auf S3 oder ein gehärtetes Repository in einem anderen Gebäude.

Die Verbindung testen

Beim Hinzufügen eines Speicherziels testet die Konsole es sofort mit den eingegebenen Zugangsdaten: Sie schreibt eine kleine Datei, liest sie zurück und entfernt sie. Auf unveränderlichem Speicher (S3 mit Object Lock, gehärtetes Repository) meldet sie sich nur an und listet auf, damit nichts Gesperrtes zurückbleibt; bei S3 prüft sie außerdem, ob der Bucket Object Lock hat, wenn Unveränderlichkeit gewünscht ist. Das Ziel wird in jedem Fall gespeichert, und das Ergebnis wird angezeigt — ein falsches Passwort, Host-Schlüssel, Bucket oder eine falsche Freigabe zeigt sich jetzt und nicht erst bei der ersten Sicherung. Verbindung testen auf der Seite Speicher wiederholt den Test. Die Konsole testet aus ihrem eigenen Netzwerk; die Sicherungen schreiben die Agenten, daher wird ein Ziel, das nur die Agenten erreichen (eine lokale oder USB-Festplatte), von der ersten Sicherung getestet.

SFTP

Ort: sftp://user@host:22/path (verwenden Sie /~/path für einen Pfad relativ zum Home-Verzeichnis des Benutzers). Geben Sie ein Passwort oder einen privaten Schlüssel ein und den Fingerabdruck des Host-Schlüssels des Servers, den Sie auf dem Server erhalten mit:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Legen Sie einen eigenen Benutzer an, der nur in den Sicherungsordner schreiben kann.

S3-kompatibel

Geben Sie den Endpunkt (z. B. s3.eu-central-1.amazonaws.com, s3.wasabisys.com, 10.0.0.5:9000), den Bucket, einen optionalen Ordner und einen Zugriffsschlüssel mit Lese-/Schreibzugriff auf diesen Bucket ein. Aktivieren Sie Unverschlüsseltes HTTP nur für ein lokales MinIO ohne Zertifikat.

Unveränderliche Sicherungen (Object Lock)

Erstellen Sie den Bucket mit aktiviertem Object Lock und aktivieren Sie Unveränderliche Sicherungen … für N Tage. Jede Datei, die die Agenten schreiben, wird für N Tage (+1 Tag Puffer) im Compliance-Modus gesperrt: Niemand — weder ein Angreifer mit den Schlüsseln noch der Bucket-Eigentümer — kann sie vorher löschen oder überschreiben. Nach jeder Sicherung wird die Sperre von Daten, die aus älteren Sicherungen wiederverwendet werden, verlängert, sodass jeder Wiederherstellungspunkt für die volle Frist geschützt ist.

Löschen (durch Aufbewahrung oder durch einen Angreifer) fügt nur eine „Löschmarkierung“ hinzu. Fügen Sie eine Lebenszyklusregel hinzu, die nicht aktuelle Versionen nach einem Tag ablaufen lässt, damit Platz frei wird, sobald die Sperren enden. Siehe Ransomware-Schutz.

Google Cloud Storage

Google Cloud Storage funktioniert über seine Interoperabilitäts-API als S3-kompatibles Ziel:

  1. Öffnen Sie in der Google Cloud Console Cloud Storage → Settings → Interoperability und erstellen Sie einen HMAC-Schlüssel für ein Dienstkonto mit der Rolle Storage Object Admin auf dem Bucket.
  2. Fügen Sie ein S3-Ziel mit dem Endpunkt storage.googleapis.com, dem Bucket-Namen, dem HMAC-Zugriffsschlüssel und -Geheimnis und der Region auto hinzu.

Die S3-Option Object Lock ist auf Google Cloud Storage nicht verfügbar; für Unveränderlichkeit legen Sie in Google Cloud eine Bucket-Aufbewahrungsrichtlinie fest (und sperren Sie sie). Gelöschte Sicherungen bleiben dann bis zum Ende der Aufbewahrungsfrist erhalten.

Azure Blob Storage

  1. Erstellen Sie im Azure-Portal ein Speicherkonto (StorageV2, beliebige Redundanz) und einen Container, z. B. backups.
  2. Fügen Sie ein Ziel vom Typ Azure Blob Storage mit Kontoname, Container und optionalem Ordner hinzu.
  3. Authentifizieren Sie sich mit einem Zugriffsschlüssel (Speicherkonto → Zugriffsschlüssel) oder, stärker eingeschränkt, einem SAS-Token für den Container mit Lese-, Schreib-, Lösch- und Auflistungsrechten und passendem Ablaufdatum.

Für Ransomware-Schutz aktivieren Sie auf dem Container die Unveränderlichkeit auf Versionsebene mit einer zeitbasierten Aufbewahrungsrichtlinie; gelöschte oder überschriebene Sicherungen bleiben dann für diese Zeit wiederherstellbar. Das Feld Endpunkt unter Erweitert wird nur für Azure Government/China, Azure Stack Hub oder den Azurite-Emulator benötigt.

Wechselnde USB-Festplatten

Festplatten, die getrennt und außer Haus gebracht werden, sind für kleine Büros der einfachste Schutz gegen Ransomware, Feuer und Diebstahl. BackupZit findet die Festplatte über ihre Volumebezeichnung, egal welchen Laufwerksbuchstaben Windows vergibt:

  1. Formatieren Sie zwei oder mehr Festplatten mit NTFS (Linux: ext4) und benennen Sie sie BZBACKUP1, BZBACKUP2, … (Windows: Rechtsklick auf das Laufwerk → Eigenschaften → Name).
  2. Fügen Sie ein Speicherziel vom Typ Wechselnde USB- / Wechseldatenträger mit der Bezeichnung BZBACKUP* hinzu.
  3. Erstellen Sie einen Sicherungsauftrag dorthin — oder besser einen Sicherungskopie-Auftrag, der einen NAS- oder Cloud-Auftrag auf die Festplatte kopiert.
  4. Tauschen Sie die Festplatten regelmäßig (z. B. wöchentlich) und bewahren Sie die getrennte an einem sicheren Ort auf.
  • Jede Festplatte enthält eine vollständige, unabhängige Sicherung mit eigener Aufbewahrung; alle Festplatten sind mit dem Wiederherstellungsschlüssel des Ziels verschlüsselt.
  • Der Lauf zeigt, welche Festplatte verwendet wurde (Festplatte BZBACKUP2). Eine Wiederherstellung fragt genau nach dieser Festplatte und sagt Ihnen, welche angeschlossen ist.
  • Ist keine Festplatte angeschlossen, schlägt der Lauf mit einer klaren Meldung und einer Warnung fehl — eine Erinnerung, die Festplatte wieder anzuschließen.
  • Schließen Sie immer nur eine der Festplatten an.

SMB-Freigabe

Server, Freigabe, optionaler Ordner, Benutzer, Passwort und (bei Domänenkonten) die Domäne. Agenten verbinden sich selbst mit diesen Zugangsdaten, daher funktioniert es auch für Dienste, die als SYSTEM laufen.

Gehärtetes Repository

Installieren Sie das Paket backupzit-repo auf einem dedizierten Linux-Server und führen Sie dann auf diesem Server aus:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

Geben Sie die Serveradresse, den Zugriffsschlüssel und den Fingerabdruck in der Konsole ein. Die Unveränderlichkeitsfrist wird auf dem Repository-Server konfiguriert (/etc/backupzit-repo/repo.env) und kann weder von der Konsole noch von Agenten geändert werden. Details unter Ransomware-Schutz.

Verschlüsselung und der Wiederherstellungsschlüssel

Mit Sicherungen verschlüsseln (Standard) wird alles im Repository — Dateiinhalte, Dateinamen, Ordnerstruktur, Snapshot-Listen — mit AES-256-GCM verschlüsselt, bevor es den Agenten verlässt. Der Speicheranbieter sieht nur Zufallsdaten.

Wenn Sie ein verschlüsseltes Ziel erstellen, zeigt die Konsole einen Wiederherstellungsschlüssel und bietet ein Wiederherstellungsblatt zum Download an.

Drucken Sie das Wiederherstellungsblatt aus oder speichern Sie es in einem Passwortmanager, getrennt von den Sicherungen. Geht die Konsole verloren, brauchen Sie zur Wiederherstellung nur den Wiederherstellungsschlüssel sowie Speicherort und Zugangsdaten. Ohne den Schlüssel kann niemand verschlüsselte Sicherungen lesen — auch nicht der BackupZit-Support.

Sie können den Schlüssel später mit Wiederherstellungsschlüssel in der Speicherliste erneut anzeigen; das wird protokolliert.

Die Speicherliste

Die Liste zeigt für jedes Ziel Typ, Ort, Verschlüsselung (mit Zugriff auf den Wiederherstellungsschlüssel für Administratoren) und Unveränderlichkeit: die Object-Lock-Frist bei S3 oder auf dem Repository-Server festgelegt bei gehärteten Repositories. Zugangsdaten werden nach dem Speichern nie wieder angezeigt und verschlüsselt gespeichert. Nur Administratoren können Ziele hinzufügen oder entfernen und Wiederherstellungsschlüssel sehen.

Speichernutzung und Prognose

Nach jeder Sicherung (und ihrer Aufbewahrung) meldet der Agent, wie viel Platz sein Repository belegt, und — bei lokalen und USB-Festplatten, SFTP-Servern (OpenSSH-Erweiterung statvfs) und SMB-Freigaben — Größe und freien Platz des Speichers. Unter Speicher → Speichernutzung zeigt jedes Ziel:

  • den von allen Repositories darauf belegten Platz (eines pro Agent; bei wechselnden USB-Festplatten zählt jede Festplatte);
  • bei Speicher mit bekannter Größe, wie voll er ist (gelb ab 75 %, rot ab 90 %), mit der Kapazität als gestrichelte rote Linie im Diagramm;
  • ein Diagramm der letzten 90 Tage und, nach einer Woche Sicherungen, das Wachstum pro Tag (linearer Trend der letzten 30 Tage), 30 Tage im Voraus als gestrichelte Linie gezeichnet, und wann der Speicher voll sein wird — oder, ohne bekannte Größe, die erwartete Nutzung in 90 Tagen.

Benötigt Aufmerksamkeit im Dashboard warnt, wenn ein Speicherziel zu 90 % voll ist oder innerhalb von 30 Tagen voll sein wird. S3 und Azure haben keine feste Größe; dort werden nur der belegte Platz und sein Wachstum angezeigt. Der belegte Platz sind die gespeicherten (komprimierten, verschlüsselten, deduplizierten) Daten; Dateien, die der Speicher aus anderen Gründen aufbewahrt (Objektversionen, andere Programme), werden nicht gezählt.

Ein Ziel entfernen

Das Entfernen eines Speicherziels aus der Konsole löscht keine Daten auf dem Speicher. Mit eingeschalteter Vier-Augen-Freigabe muss ein zweiter Benutzer zuerst zustimmen.
