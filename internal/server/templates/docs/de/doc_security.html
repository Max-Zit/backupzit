Sicherheit & Empfehlungen

Wie BackupZit Ihre Daten und die Konsole schützt und was Sie auf Ihrer Seite tun sollten.

Eingebauter Schutz

  • Verschlüsselung an der Quelle — AES-256-GCM im Agenten; der Speicher sieht nur verschlüsselte Daten. Schlüssel werden mit Argon2id abgeleitet.
  • Gepinnte Verbindungen — Agenten pinnen das Konsolenzertifikat; SFTP-Hostschlüssel und Zertifikate gehärteter Repositories werden ebenfalls gepinnt. Keine Zertifizierungsstelle kann missbraucht werden, um sich als sie auszugeben.
  • Vertrauenswürdiges Zertifikat für Browser — optional ein hochgeladenes oder Let's-Encrypt-Zertifikat (TLS 1.2+) auf einer eigenen Adresse, automatisch erneuert; siehe Server installieren.
  • Geheimnisse im Ruhezustand — Speicherpasswörter und -schlüssel, Wiederherstellungsschlüssel, SMTP-/LDAP-Passwörter und Zwei-Faktor-Geheimnisse werden in der Datenbank mit einem außerhalb gehaltenen Schlüssel (secrets.key) verschlüsselt.
  • Agentengeheimnisse — jeder Agent hat ein eigenes Geheimnis, auf der Konsole nur als Hash gespeichert und auf dem Agenten in einer Datei, die nur Administratoren lesen können.
  • Webkonsole — HttpOnly-, SameSite=Strict-Sitzungscookies; Schutz vor Cross-Site-Anfragen und Clickjacking; strikte Content-Security-Policy; Passwörter mit bcrypt gehasht; sensible Seiten werden nie zwischengespeichert.
  • Schutz vor Brute-Force — Adressen, deren Anmeldung zu oft fehlschlägt, werden gesperrt: Passwörter, Zwei-Faktor-Codes und API-Token. Sperren überdauern Neustarts, Wiederholungstäter werden länger gesperrt, und Administratoren erhalten eine E-Mail. Siehe unten.
  • Konten — Rollen mit minimalen Rechten, optionale Zwei-Faktor-Authentifizierung (TOTP) und LDAPS-Anmeldung; API-Token mit eigener, niedrigerer Rolle und Ablaufdatum.
  • Vier-Augen-Freigabe (optional) — das Löschen oder Deaktivieren von Aufträgen, das Löschen von Agenten, ESXi-Hosts, Speicherzielen und Benutzern, das Verkürzen der Aufbewahrung, das Ausschalten der Freigabe und alles, was einem Administrator einen zweiten Freigebenden verschaffen könnte (neue Freigebende, mehr Rechte, Rücksetzen von Passwort und Zwei-Faktor, Änderungen an LDAP und SSO), brauchen die Freigabe eines zweiten Benutzers. Siehe Benutzer, Rollen & LDAP.
  • Prüfpfad — Anmeldungen, fehlgeschlagene Anmeldungen, Benutzer- und Rollenänderungen, Aufträge, Speicherziele, Wiederherstellungen, angezeigte Wiederherstellungsschlüssel, Einstellungsänderungen und API-Aktionen werden im Prüfprotokoll erfasst; Einträge sind verkettet, sodass Änderungen und Löschungen in der Datenbank erkannt werden, und können an einen Syslog-Server oder ein SIEM kopiert werden (Schutz vor Änderungen); Löschungen auf einem gehärteten Repository werden auf diesem Server protokolliert.
  • Konsolen-Updates — Releases sind mit dem BackupZit-Releaseschlüssel (Ed25519) signiert. Die Konsole und der root-Dienst, der sie installiert, prüfen beide die Signatur, die Datenbank wird vorher gesichert, und ein fehlgeschlagenes Update wird zurückgerollt.
  • Agenten-Updates — Agenten laden neue Versionen nur von ihrer Konsole über die gepinnte Verbindung und installieren sie nur, wenn die SHA-256-Prüfsumme stimmt.
  • Lokaler Statuskanal — die Tray-App spricht mit dem Agentendienst über eine lokale Named Pipe (Windows) bzw. einen nur für root zugänglichen Socket (Linux). Angemeldete Benutzer der Maschine können den Status lesen und die Sicherungsaufträge der eigenen Maschine starten; sonst nichts (Aufträge, Zeitpläne, Speicher und Wiederherstellungen werden nur in der Konsole verwaltet).
  • Hypervisor-Sicherungen — der Agent auf einem Proxmox- oder Hyper-V-Host nutzt die eigenen Werkzeuge des Hosts; dafür werden keine Hypervisor-Passwörter gespeichert. Für VMware ESXi speichert die Konsole das Passwort des Hosts verschlüsselt, pinnt sein HTTPS-Zertifikat und seinen SSH-Hostschlüssel und gibt die Verbindung nur an den Proxy-Agenten des Hosts für dessen Läufe weiter.
  • Integrität der Sicherungen — jeder Block wird bei der Wiederherstellung über seinen SHA-256-Hash geprüft; automatische Wiederherstellungstests und die Ransomware-Erkennung überwachen die Sicherungen fortlaufend.

Schutz vor Brute-Force

Konfiguriert unter Einstellungen → Anmeldung & Sicherheit. Die Standardwerte sind für die meisten Installationen sicher:

EinstellungStandardBedeutung
Fehlversuche pro Adresse5Fehlgeschlagene Anmeldungen von einer IP-Adresse innerhalb des Zählzeitraums sperren diese Adresse. Gezählt werden falsche Passwörter, falsche Zwei-Faktor-Codes und ungültige API-Token.
Zählzeitraum15 MinutenÄltere Fehlversuche werden vergessen.
Sperren für30 MinutenEine gesperrte Adresse kann sich nicht anmelden, auch nicht mit dem richtigen Passwort. Die Anmeldeseite antwortet „Zu viele fehlgeschlagene Anmeldungen“ und die API mit HTTP 429.
Wiederholungstäter länger sperrenanJede weitere Sperre einer Adresse innerhalb eines Tages dauert doppelt so lange: 30 Minuten, 1 Stunde, 2 Stunden, … bis zu 7 Tage.
Fehlversuche pro Benutzername20Fehlversuche für einen Benutzernamen, von beliebigen Adressen, pausieren die Anmeldung für diesen Benutzernamen, bis der Zählzeitraum vorbei ist. Das stoppt Rateversuche, die über viele Adressen verteilt sind. Konten werden nie dauerhaft gesperrt, sodass ein Angreifer den Administrator nicht aussperren kann.
Diese Netzwerke nie sperrenkeineOptionale Netzwerke, z. B. das Subnetz der Administratoren, die nie gesperrt werden. Das Limit pro Benutzername gilt für sie trotzdem.
Reverse-ProxyskeineLäuft die Konsole hinter nginx, Traefik oder einem anderen Proxy, geben Sie dessen Adresse ein: Die Client-Adresse wird dann aus X-Forwarded-For übernommen (sonst sähen alle Clients wie der Proxy aus), und wenn der Proxy X-Forwarded-Proto: https sendet, werden die Anmelde-Cookies als Secure markiert. Beide Header werden von jeder anderen Adresse ignoriert, sodass sie nicht gefälscht werden können.
E-Mail, wenn eine Adresse gesperrt wirdanWird an die Empfänger aus den E-Mail-Einstellungen gesendet.

Dieselbe Seite listet die gesperrten Adressen mit Grund und Dauer jeder Sperre auf und erlaubt, eine Sperre aufzuheben. Sperren und Aufhebungen werden im Prüfprotokoll erfasst.

Haben Sie sich selbst ausgesperrt, melden Sie sich von einer anderen Adresse an, oder führen Sie dies auf dem Server mit denselben Datenbankoptionen wie der Dienst aus:

backupzit-server --unblock-ip all

Um eine einzelne Sperre aufzuheben, geben Sie statt all die Adresse an.

Zugriff auf die Webkonsole (öffentliche Adresse)

Agenten verbinden sich auf Port 8443 mit der Konsole. Um die Konsole unter einer öffentlichen Adresse anzubieten — für Agenten an anderen Standorten oder bei Kunden —, während nur Ihre Administratoren die Webkonsole öffnen können, verwenden Sie Einstellungen → Anmeldung & Sicherheit → Zugriff auf die Webkonsole:

EinstellungWirkung
Erlaubte AdressenIP-Adressen oder Netzwerke (z. B. 203.0.113.10, 10.0.0.0/24). Webkonsole, REST API und jede Seite antworten nur diesen Adressen; andere erhalten „not found“, als gäbe es keine Konsole. Agenten erreichen ihre API immer (Registrierung, Abfragen, Ergebnisse, Downloads, Push-Installation). Leer: alle. Die Konsole lehnt eine Liste ab, die Ihre eigene Adresse nicht enthält.
Port 8443 nur für AgentenDie Webkonsole ist dann nur auf dem Webport mit dem vertrauenswürdigen Zertifikat erreichbar (Einstellungen → Zertifikat, meist 443), sodass eine Firewall 8443 für alle und 443 nur für Ihre Adressen öffnen kann. Verfügbar, sobald der Webport läuft; ändern Sie es über den Webport, nicht über 8443.

Eine typische Firewall für eine öffentliche Konsole: 8443 offen für alle (Agenten), 443 und 80 (Let's-Encrypt-HTTP-Prüfung) nur von Ihren Adressen, SSH nur von Ihren Adressen oder aus, alles andere geschlossen.

Ausgesperrt? Auf dem Server selbst (localhost) antwortet die Konsole immer. Auf der Appliance hebt Punkt 5 des Setup-Menüs auf ihrem Bildschirm Anmeldesperren und diese Beschränkungen auf.

Empfehlungen

Konsole

  • Betreiben Sie die Konsole in einem internen Netz; veröffentlichen Sie Port 8443 nicht im Internet. Nutzen Sie für die Fernverwaltung ein VPN.
  • Verwenden Sie ein langes, eindeutiges Administratorpasswort und ändern Sie das ursprüngliche.
  • Verlangen Sie Zwei-Faktor-Authentifizierung für Administratoren (Einstellungen → Anmeldung & Sicherheit).
  • Geben Sie jeder Person ein eigenes Konto mit der niedrigsten funktionierenden Rolle; verwenden Sie für die Überwachung API-Token mit der Rolle Betrachter.
  • Sichern Sie secrets.key getrennt von der Datenbank (Server installieren).
  • Wählen Sie unter Einstellungen → Anmeldung & Sicherheit eine passende Sitzungsdauer (kürzer ist sicherer).
  • Halten Sie den Server aktuell (apt upgrade / dnf upgrade), einschließlich PostgreSQL.

Speicher

  • Geben Sie jedem Speicherziel ein eigenes Konto mit Zugriff nur auf den Sicherungsordner bzw. Bucket.
  • Nehmen Sie den Sicherungsspeicher nicht in die Windows-Domäne auf; verwenden Sie Zugangsdaten, die nirgends sonst verwendet werden.
  • Halten Sie mindestens eine unveränderliche Kopie (S3 Object Lock oder gehärtetes Repository) und eine externe Kopie vor.

Schlüssel

  • Bewahren Sie Wiederherstellungsblätter offline auf. Ohne sie können verschlüsselte Sicherungen bei Verlust der Konsole nicht wiederhergestellt werden.
  • Testen Sie einmal eine Wiederherstellung über die Befehlszeile nur mit dem Wiederherstellungsblatt, damit Sie wissen, dass das Verfahren funktioniert.
  • Behandeln Sie einen USB-Stick mit recovery.json wie einen Schlüssel: Bis der Wiederherstellungscode abläuft (30 Tage), lässt er eine Maschine als Wiederherstellungsagent der Konsole beitreten. Erstellen Sie bei Bedarf einen neuen Code, statt alte Sticks aufzubewahren.
  • Wiederherstellungs-ISOs geben jedem, der davon bootet, eine root-/Administrator-Befehlszeile — wie jedes Bootmedium. Schützen Sie Server mit einem Firmware-Passwort (BIOS/UEFI) und sicheren Booteinstellungen.

Agenten und Hypervisoren

  • Die Konsole kann Software auf Agenten installieren (Agenten-Updates) und Daten auf sie zurückspielen. Schützen Sie die Administratorkonten entsprechend: Zwei-Faktor-Authentifizierung, wenige Administratoren.
  • Dateien von VM-Festplatten werden beim Durchsuchen von Konsole und Agenten geparst; beschädigte oder bösartige Dateisystemdaten erzeugen einen Fehler, keinen Absturz.

Sicherheitsproblem melden

Bitte melden Sie Schwachstellen vertraulich an die BackupZit-Maintainer, statt ein öffentliches Issue zu eröffnen.
