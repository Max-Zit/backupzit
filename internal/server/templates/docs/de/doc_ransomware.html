Schutz vor Ransomware

Angreifer versuchen, Sicherungen zu löschen oder zu verschlüsseln, bevor sie die Produktivdaten verschlüsseln. BackupZit bietet Speicher, auf dem Sicherungen nicht zerstört werden können — auch nicht mit gestohlenen Zugangsdaten.

Die Schutzschichten

SchichtSchützt vor
Verschlüsselung (AES-256)Lesen oder Manipulieren von Sicherungen auf dem Speicher. Jede Änderung wird erkannt.
Unveränderlicher S3 (Object Lock, Compliance-Modus)Löschen oder Überschreiben von Sicherungen — durch einen Angreifer mit den Schlüsseln, einen böswilligen Administrator oder einen Fehler.
Gehärtetes RepositoryDasselbe auf Ihrem eigenen Linux-Server: Dateien werden nur einmal geschrieben und erhalten das Unveränderlich-Flag des Dateisystems.
Externe KopieBrand, Diebstahl, Totalverlust des Standorts.
Vier-Augen-Freigabe (optional)Ein gestohlenes oder missbrauchtes Konsolenkonto, das Aufträge und Speicherziele löscht oder die Aufbewahrung verkürzt: Ein zweiter Benutzer muss zustimmen. Siehe Benutzer, Rollen & LDAP.

Automatische Erkennung verdächtiger Sicherungen

Jede Sicherung wird mit dem jüngsten Verlauf ihres Auftrags verglichen. Sie wird als verdächtig markiert, wenn sie Spuren von Ransomware oder Massenlöschung zeigt:

  • weit mehr Dateien geändert als üblich (z. B. 95 % statt der üblichen 1 %),
  • die neuen Daten lassen sich nicht mehr komprimieren — verschlüsselte Dateien sehen wie Zufallsdaten aus,
  • die Zahl der Dateien ist plötzlich um ein Drittel oder mehr gesunken,
  • ein plötzlicher Sprung in der Menge neuer Daten (auch bei Festplattenabbildern, Linux-Systemen und VMs).

Dann sendet BackupZit eine Warn-E-Mail (bei aktivierten Fehlerbenachrichtigungen), zeigt die Sicherung im Dashboard unter zu prüfende verdächtige Sicherungen an und pausiert die Aufbewahrung des Auftrags: Keine ältere Sicherung wird gelöscht, sodass die letzten sauberen Sicherungen wiederherstellbar bleiben, auch wenn weiter beschädigte Sicherungen kommen. Nachdem Sie die Maschine geprüft haben, klicken Sie auf der Auftragsseite auf Geprüft – Aufbewahrung fortsetzen.

Unveränderlicher S3 mit Object Lock

  1. Erstellen Sie einen Bucket mit aktiviertem Object Lock (AWS, Wasabi, Backblaze B2, MinIO: mc mb --with-lock).
  2. Fügen Sie eine Lifecycle-Regel hinzu, die nicht aktuelle Versionen (noncurrent versions) nach 1 Tag löscht (MinIO: mc ilm rule add --noncurrent-expire-days 1 --expire-delete-marker).
  3. Fügen Sie das S3-Ziel hinzu und aktivieren Sie Unveränderliche Sicherungen für N Tage. Wählen Sie N mindestens so lang wie die längste Aufbewahrung, die geschützt sein soll, z. B. 30.

Jeder Wiederherstellungspunkt bleibt mindestens N Tage nach seiner Erstellung gesperrt; Daten, die mit neueren Sicherungen geteilt werden, werden automatisch verlängert.

Gehärtetes Repository

Ein eigener Linux-Server mit backupzit-repo:

  • Agenten und Konsole können Dateien nur hinzufügen; vorhandene Dateien werden nie überschrieben.
  • Jede Datei erhält das Attribut chattr +i für den auf diesem Server eingestellten Zeitraum. Nicht einmal root kann sie löschen, ohne vorher das Flag zu entfernen.
  • Löschungen durch Clients verbergen Dateien nur, bis ihr Zeitraum abgelaufen ist.
  • Der Dienst läuft als nicht privilegierter Benutzer; sein einziges Recht ist das Setzen des Unveränderlich-Flags.
apt install ./backupzit-repo_*.deb
vi /etc/backupzit-repo/repo.env        # BACKUPZIT_REPO_LOCK_DAYS=30
systemctl start backupzit-repo
backupzit-repo add-key office-console
backupzit-repo fingerprint

Nach der Einrichtung deaktivieren Sie SSH und anderen Fernzugriff auf dem Repository-Server und schützen Sie den Zugang zu seiner lokalen Konsole / iDRAC / iLO / zum Hypervisor. Der Schutz ist nur so stark wie das root-Konto dieser Maschine.

Wiederherstellung nach einem Angriff

Hat ein Angreifer Sicherungen gelöscht oder überschrieben, lesen Sie den Speicher so, wie er vor dem Angriff war — das ist nur lesend und ändert nichts:

backupzit-agent snapshots --repo <repository> --as-of 2026-10-01T14:30
backupzit-agent restore   --repo <repository> --as-of 2026-10-01T14:30 --target D:\Restore latest

Auf einem gehärteten Repository kann der Administrator verborgene Dateien auch zurückholen, damit die Sicherungen normal weiterlaufen:

backupzit-repo status
backupzit-repo undelete --since 2026-10-01T14:00

Empfehlungen

  • Verwenden Sie für den Speicher ein eigenes Konto, das nicht Teil Ihrer Windows-Domäne ist.
  • Halten Sie mindestens eine unveränderliche Kopie vor (S3 Object Lock oder gehärtetes Repository).
  • Bewahren Sie die Wiederherstellungsblätter offline auf (ausgedruckt, im Tresor).
  • Aktivieren Sie E-Mail-Warnungen — eine plötzliche Änderung bei Fehlern oder beim hochgeladenen Datenvolumen ist oft das erste Anzeichen eines Angriffs.
