Benutzer, Rollen & LDAP

Geben Sie jeder Person ein eigenes Konto mit genau den Rechten, die sie braucht — als lokale Konten oder mit ihrer Anmeldung aus Active Directory / LDAP.

Typische Verteilung: IT-Administratoren sind Administratoren; wer die täglichen Sicherungen betreut, ist Sicherungsoperator; der Helpdesk, der gelöschte Dateien zurückholt, ist Wiederherstellungsoperator; Geschäftsleitung und Prüfer sind Betrachter. Seiten und Schaltflächen, die eine Rolle nicht verwenden darf, werden ausgeblendet, und der Server lehnt sie ohnehin ab. Beachten Sie, dass eine Wiederherstellung Daten überschreiben kann — eine Wiederherstellung eines Festplattenabbilds oder Linux-Systems löscht die Zielfestplatte, und eine VM-Wiederherstellung mit ersetzen löscht die vorhandene VM —, geben Sie die Wiederherstellungsrollen also nur Personen, denen Sie das anvertrauen würden; jede Wiederherstellung steht im Prüfprotokoll.

Lokale Benutzer

Geben Sie unter Benutzer → Neuer lokaler Benutzer einen Benutzernamen, eine Rolle und ein Passwort mit mindestens 10 Zeichen ein. Auf der Seite des Benutzers können Sie die Rolle ändern, das Konto deaktivieren (offene Sitzungen enden sofort), ein neues Passwort setzen oder den Benutzer löschen.

Jeder Benutzer kann sein eigenes Passwort unter Mein Konto ändern (klicken Sie oben rechts auf Ihren Namen).

Es bleibt immer mindestens ein aktivierter lokaler Administrator, sodass Sie sich auch anmelden können, wenn das Verzeichnis nicht erreichbar ist. Sie können sich nicht selbst herabstufen, deaktivieren oder löschen.

Anmeldung mit Active Directory / LDAP

Unter Einstellungen → LDAP / Active Directory:

  1. Server: ldaps://dc1.example.local:636. Einfaches ldap:// wird nur mit StartTLS akzeptiert, sodass Passwörter nie unverschlüsselt übertragen werden.
  2. Dienstkonto: ein normales Domänenkonto, mit dem Benutzer und Gruppen gesucht werden (Lesezugriff genügt), z. B. CN=svc-backupzit,OU=Service Accounts,DC=example,DC=local.
  3. Suchbasis: z. B. DC=example,DC=local.
  4. Benutzerfilter: Active Directory (&(objectClass=user)(sAMAccountName={username})), OpenLDAP (&(objectClass=inetOrgPerson)(uid={username})).
  5. Gruppen → Rollen: der vollständige DN einer Gruppe für jede Rolle, die Sie verwenden möchten, z. B. CN=BackupZit Admins,OU=Groups,DC=example,DC=local. Die höchste passende Rolle gewinnt; Benutzer in keiner der Gruppen können sich nicht anmelden. Aktivieren Sie in Active Directory verschachtelte Gruppen, um Mitglieder von Untergruppen einzuschließen.
  6. Zertifikatsvertrauen: Verwenden die Domänencontroller eine interne Zertifizierungsstelle, fügen Sie das CA-Zertifikat ein; für ein selbstsigniertes Zertifikat geben Sie seinen Fingerabdruck ein.
  7. Prüfen Sie mit Test und einem echten Benutzer die Verbindung, das Passwort und die resultierende Rolle, dann Speichern.

Verzeichnisbenutzer erscheinen nach ihrer ersten Anmeldung in der Benutzerliste. Name, E-Mail und Rolle werden bei jeder Anmeldung aus dem Verzeichnis aktualisiert. Um einen Verzeichnisbenutzer sofort zu sperren, deaktivieren Sie das Konto in BackupZit (oder im Verzeichnis).

Single Sign-On (SAML, OpenID Connect)

Mit Single Sign-On klicken Benutzer auf der Anmeldeseite auf Anmelden mit … und melden sich bei Ihrem Identitätsanbieter an — Microsoft Entra ID (Azure AD), Okta, Google Workspace, Keycloak, ADFS oder jedem anderen SAML-2.0- oder OpenID-Connect-Anbieter. Eingerichtet wird es unter Einstellungen → Single Sign-On:

  1. Wählen Sie OpenID Connect (empfohlen, wo verfügbar) oder SAML 2.0.
  2. OpenID Connect: Registrieren Sie beim Identitätsanbieter eine Webanwendung mit der auf der Einstellungsseite angezeigten Umleitungs-URI (https://<konsole>/login/sso/callback) und geben Sie deren Issuer, Client-ID und Client-Secret ein. Lassen Sie den Anbieter die Gruppen des Benutzers in einen Claim groups schreiben (Entra ID: Token configuration → Add groups claim, das Gruppen-IDs sendet; Keycloak: ein Mapper Group Membership; Okta: ein Groups-Claim).
  3. SAML 2.0: Fügen Sie die Konsole beim Identitätsanbieter mit ihrer Metadaten-URL hinzu (https://<konsole>/login/sso/metadata, Assertion Consumer Service /login/sso/acs), lassen Sie die Gruppen als Attribut senden, und geben Sie die Metadaten-URL des Identitätsanbieters ein oder fügen Sie dessen Metadaten-XML ein. SAML erfordert die Konsole unter HTTPS. Assertions müssen signiert sein; die Anfragen der Konsole sind nicht signiert.
  4. Ordnen Sie Gruppen (Namen, bei Entra ID IDs) den vier Rollen zu; die höchste passende Rolle gewinnt. Benutzer in keiner davon können sich nicht anmelden, es sei denn, Sie wählen eine Rolle für sie.

Ein Identitätsanbieter, dessen HTTPS-Zertifikat von Ihrer eigenen CA stammt oder selbstsigniert ist (ein lokales Keycloak oder AD FS), braucht dieses CA-Zertifikat in CA-Zertifikat (PEM); öffentliche (Entra ID, Okta, Google) brauchen nichts. Beim Speichern wird geprüft, ob der Identitätsanbieter antwortet. Benutzer werden bei ihrer ersten Anmeldung angelegt (unter Benutzer mit SSO markiert) und erhalten ihre Rolle bei jeder Anmeldung aus ihren Gruppen, wie Verzeichnisbenutzer; Name und E-Mail kommen vom Identitätsanbieter. Den zweiten Faktor übernimmt der Identitätsanbieter, daher fragt die Konsole SSO-Benutzer nicht nach ihrem eigenen Zwei-Faktor-Code. Lokale Konten funktionieren weiter, sodass sich ein Administrator immer anmelden kann, auch wenn der Identitätsanbieter nicht erreichbar ist. Eine Anmeldeantwort kann nur einmal verwendet werden und muss vom Identitätsanbieter signiert sein; jede SSO-Anmeldung und -Ablehnung steht im Prüfprotokoll.

Sitzungen

Unter Einstellungen → Anmeldung & Sicherheit legen Sie fest, wie lange eine Anmeldung gilt (Standard 12 Stunden) und nach wie vielen Minuten Inaktivität Benutzer abgemeldet werden (Standard 60, 0 = nie). Wiederholt falsche Passwörter sperren die Adresse eine Zeit lang: standardmäßig nach 5 Fehlversuchen innerhalb von 15 Minuten für 30 Minuten. Die Grenzen stehen auf derselben Seite; siehe Sicherheit.

Zwei-Faktor-Authentifizierung

Jeder Benutzer kann seine Anmeldung unter Mein Konto → Zwei-Faktor mit einem zweiten Faktor schützen: Scannen Sie den QR-Code mit einer Authentifizierungs-App (Microsoft oder Google Authenticator, Authy, 1Password, Bitwarden …) und geben Sie den 6-stelligen Code ein. Zehn einmalige Wiederherstellungscodes werden einmal angezeigt — bewahren Sie sie sicher auf; jeder funktioniert einmal, falls das Telefon verloren geht. Benutzer, die sich per Single Sign-On anmelden, werden nicht nach dem Code der Konsole gefragt: Den zweiten Faktor übernimmt ihr Identitätsanbieter.

Unter Einstellungen → Anmeldung & Sicherheit können Sie die Zwei-Faktor-Authentifizierung für Administratoren oder für alle Benutzer verlangen; sie werden nach ihrer nächsten Anmeldung zur Einrichtung aufgefordert. Verliert ein Benutzer Telefon und Wiederherstellungscodes, setzt ein Administrator die Zwei-Faktor-Anmeldung auf der Seite des Benutzers zurück. Zwei-Faktor funktioniert auch für Verzeichniskonten (LDAP).

API-Token

Skripte und Überwachungswerkzeuge verwenden API-Token statt Passwörtern. Jeder Benutzer erstellt und widerruft seine eigenen Token unter Mein Konto → API-Token; die Rolle eines Tokens kann niedriger sein als die des Benutzers. Administratoren sehen alle Token auf der Seite Benutzer und können sie widerrufen. Siehe REST API.

Vier-Augen-Freigabe

Optional und standardmäßig aus. Schalten Sie sie unter Einstellungen → Anmeldung & Sicherheit → Vier-Augen-Freigabe ein; sie erfordert mindestens zwei aktivierte Administratoren. Dann werden diese Änderungen erst wirksam, wenn ein zweiter Benutzer sie freigibt:

Die Anfrage erscheint unter Freigaben (mit einem Zähler im Menü und im Dashboard), und die Empfänger der Benachrichtigungen erhalten eine E-Mail. Jeder andere Benutzer mit der passenden Berechtigung gibt sie frei oder lehnt sie ab; der Antragsteller kann sie nur zurückziehen. Eine freigegebene Änderung wird sofort ausgeführt. Anfragen verfallen nach 7 Tagen. Wird ein Auftrag mit kürzerer Aufbewahrung bearbeitet, werden seine anderen Änderungen sofort gespeichert und nur die Aufbewahrung wartet. Anfragen, Freigaben, Ablehnungen und ihre Benutzer stehen im Prüfprotokoll.

Nur Konten, die vor einer Anfrage existierten, können über sie entscheiden. Zusammen mit der Freigabepflicht für neue Freigebende, Passwortrücksetzungen und Verzeichniseinstellungen verhindert das, dass ein einzelner Administrator sich allein einen zweiten Freigebenden verschafft — etwa durch Anlegen eines zweiten Administratorkontos, durch Setzen des Passworts eines anderen Administrators oder durch Zuordnen einer Verzeichnisgruppe zur Rolle Administrator. Solange die Option eingeschaltet ist, können die letzten zwei aktivierten Administratoren nicht gelöscht, deaktiviert oder herabgestuft werden, sodass über Anfragen immer entschieden werden kann. Passwörter in Anfragen werden nur als Hashes gespeichert, LDAP- und Single-Sign-On-Einstellungen mit dem Geheimnisschlüssel der Konsole verschlüsselt. Gruppenmitgliedschaften im Verzeichnis selbst (Active Directory, Entra ID) liegen außerhalb der Konsole; schützen Sie diese Administratorgruppen dort.

Das schützt davor, dass ein einzelnes gestohlenes oder missbrauchtes Konto die Konfiguration entfernt oder die Aufbewahrung die Sicherungen löschen lässt. Es ersetzt keinen unveränderlichen Speicher: Dafür siehe Schutz vor Ransomware.

Prüfprotokoll

Benutzer → Prüfprotokoll zeigt Anmeldungen, fehlgeschlagene Anmeldungen und Änderungen: Benutzer, Aufträge, Speicherziele, Wiederherstellungen, angezeigte Wiederherstellungsschlüssel und Einstellungen — mit Zeit, Benutzer und Adresse.

Schutz vor Änderungen

Jeder Eintrag ist mit dem vorherigen verkettet: Er trägt einen Hash seines eigenen Inhalts und des vorherigen Eintrags, verschlüsselt mit einem Geheimnis aus der Geheimnisdatei des Servers (die nicht in der Datenbank liegt). Wer Einträge direkt in der Datenbank ändert oder löscht, unterbricht daher die Kette. Der neueste Hash wird außerdem in einer Datei neben den Konsolendaten gehalten, sodass auch das Löschen der neuesten Einträge erkannt wird.

  • Die Konsole prüft die ganze Kette beim Start und einmal täglich. Ist sie unterbrochen, zeigt die Seite Prüfprotokoll Das Audit-Protokoll wurde geändert mit dem ersten fehlerhaften Eintrag, und die Administratoren erhalten eine E-Mail.
  • Integrität jetzt prüfen auf der Seite Prüfprotokoll führt die Prüfung sofort aus.
  • Einträge, die vor Version 0.33.3 geschrieben wurden, haben keine Kette; die Seite zeigt, wie viele es sind.

Die Kette zeigt, dass das Protokoll geändert wurde, kann das Geänderte aber nicht zurückholen — und wer den Konsolenserver selbst mit seiner Geheimnisdatei übernimmt, könnte die Kette neu schreiben. Dagegen senden Sie eine Kopie jedes Eintrags an einen separaten Syslog-Server oder ein SIEM unter Einstellungen → Anmeldung & Sicherheit → Schutz des Audit-Protokolls:

  • Syslog-Server als host:port und das Protokoll: TLS (empfohlen, meist Port 6514), TCP oder UDP (meist 514). Dem Zertifikat eines TLS-Servers muss die Konsolenmaschine vertrauen.
  • Beim Speichern wird eine Testnachricht gesendet; nimmt der Server sie nicht an, werden die Einstellungen trotzdem gespeichert und der Fehler angezeigt.
  • Die Nachrichten sind RFC 5424 (Facility auth) mit Eintragsnummer, Benutzer, Aktion, Adresse und Ketten-Hash. Einmal täglich trägt eine Nachricht audit.checkpoint den neuesten Hash, sodass die Kopie mit der Konsole verglichen werden kann.
  • Solange der Syslog-Server nicht erreichbar ist, warten Einträge im Speicher (bis zu 1000) und werden gesendet, sobald er wieder antwortet; die Konsole arbeitet weiter, und die Einträge bleiben in jedem Fall in ihrem eigenen Prüfprotokoll.
