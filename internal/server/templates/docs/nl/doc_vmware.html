Virtuele machines in VMware ESXi

BackupZit maakt back-ups van de virtuele machines van VMware ESXi-hosts zonder iets op ESXi of in de VM's te installeren. Een BackupZit-agent op een willekeurige machine in het netwerk werkt als proxy van de host. Hij maakt snapshots, leest alleen de gewijzigde blokken van de virtuele schijven en schrijft ze naar uw opslag.

Vereisten

  • ESXi 6.7, 7 of 8 rechtstreeks verbonden, of vCenter Server 7 of 8 met zijn ESXi-hosts (zie vCenter Server).
  • Een gebruiker met beheerdersrechten op de host, meestal root.
  • SSH ingeschakeld op hosts met de gratis licentie: Host → Actions → Services → Enable Secure Shell. De gratis ESXi-licentie maakt de API alleen-lezen, dus snapshots en herstelbewerkingen lopen via SSH. Gelicentieerde hosts worden via de vSphere-API gewijzigd en hebben geen SSH nodig.
  • Een proxy-agent: een willekeurige Windows- of Linux-agent die de host bereikt op poort 443 (en 22 als SSH wordt gebruikt). De back-upgegevens lopen erdoorheen, zet hem dus op een snel netwerk dicht bij de host en de opslag.
  • Vrije ruimte op de datastore van de VM terwijl een draaiende VM wordt geback-upt. BackupZit kopieert de schijf daar even (zie hieronder). De kopie is thin, dus hij heeft zoveel ruimte nodig als de schijf werkelijk gebruikt. Met hot-add wordt geen kopie gemaakt.

Een host toevoegen

  1. Open Agents → VMware ESXi-hosts → Een ESXi-host of vCenter Server toevoegen.
  2. Voer het adres, de gebruiker, het wachtwoord en de proxy-agent in.
  3. De console maakt één keer verbinding om ze te controleren. Hij leest de VM-lijst en de licentie, en pint het HTTPS-certificaat en de SSH-hostsleutel van de host. Als de host later wordt vervangen door een andere machine met hetzelfde adres, weigert BackupZit verbinding te maken in plaats van die het wachtwoord te sturen. Wijzigt het certificaat om een bekende reden — de host is opnieuw geïnstalleerd, heeft een nieuw certificaat gekregen of is aan vCenter toegevoegd (dat de certificaten van zijn hosts vervangt) —, dan toont de host op de pagina Agents de nieuwe vingerafdruk met een knop Nieuw certificaat accepteren. Vergelijk de vingerafdruk met de host voordat u hem accepteert.

Het wachtwoord wordt versleuteld opgeslagen, zoals alle andere geheimen. De console maakt zelf verbinding met de host (HTTPS 443, en SSH 22 bij de gratis licentie) bij het toevoegen, bij Vernieuwen en elke 10 minuten om de VM-lijst te vernieuwen, tenzij de host via de proxyagent wordt bereikt. Verwijderen verwijdert de host samen met zijn back-uptaken; de back-ups blijven op de opslag. De tabel toont de modus van elke host:

  • vSphere-API (gelicentieerde host, geen SSH nodig): snapshots, schijfkopieën, herstel en direct herstel lopen via de API.
  • vCenter Server (vSphere-API): een vCenter met zijn ESXi-hosts; alles loopt via de API van vCenter.
  • gratis licentie: snapshots en herstel via SSH: de API van de host is alleen-lezen, dus deze stappen lopen via SSH.
  • SSH (gekozen voor deze host): de host wordt via SSH gewijzigd, ook al zou zijn API dat kunnen (Altijd SSH bij het toevoegen van de host).

Via de proxyagent (agent 0.56 of nieuwer): vink bij het toevoegen van de host Verbinden via de proxyagent aan, of Verbinden via de proxy in zijn rij, en de console maakt nooit zelf verbinding met de host. De proxyagent controleert het adres en het wachtwoord, leest de VM-lijst, de versie en de licentie, en meldt het HTTPS-certificaat en de SSH-hostsleutel die hij zag; de console pint ze de eerste keer, net als bij een directe verbinding, en vanaf dan weigert de proxyagent een host die een ander certificaat toont (de rij van de host biedt dan Nieuw certificaat accepteren). Vernieuwen en de VM-lijst elke 10 minuten komen ook van de proxyagent; deze controles verschijnen niet in Activiteit. Alleen de proxyagent moet de host kunnen bereiken, precies zoals voor back-ups en herstel, dus de console kan in een ander netwerk, achter NAT of in een overlappend adresbereik staan. Een verkeerd adres of wachtwoord verschijnt na de eerste controle van de proxyagent als fout van de host: verwijder de host en voeg hem opnieuw toe. Zolang de proxyagent offline of bezig is, blijft de laatste VM-lijst staan.

Met Automatisch kiest de console zelf, dus een host die later een licentie krijgt, schakelt zonder verdere instellingen over op de API. Hoe de host wordt gewijzigd in de rij van de host (en bij het toevoegen) kan Altijd SSH of Altijd de vSphere-API afdwingen; de wijziging wordt meteen gecontroleerd. Eerdere back-ups en hun herstelpunten hangen niet af van de methode.

vCenter Server

Voeg een vCenter Server toe zoals een host: het adres, administrator@vsphere.local (of een gebruiker met de rol Administrator) en een proxy-agent. BackupZit ziet dan de VM's van alle ESXi-hosts en clusters van het datacenter via deze ene verbinding; er wordt niets via SSH gewijzigd en geen hostwachtwoord is nodig.

  • Een VM die met vMotion naar een andere host is verplaatst, wordt verder geback-upt: VM's worden herkend aan hun instance-UUID, niet aan hun host.
  • Bij herstel kunt u de ESXi-host kiezen waarop de VM draait (standaard: de host van de oorspronkelijke VM) en de datastore.
  • Direct herstel start de VM op de gekozen host; Voltooien verplaatst hem met Storage vMotion terwijl hij blijft draaien naar een datastore, zonder onderbreking.
  • Een vCenter met meerdere datacenters kan nog niet worden toegevoegd; voeg de hosts van de andere datacenters rechtstreeks toe.

Voeg dezelfde ESXi-host niet zowel rechtstreeks als via vCenter toe: elke verbinding heeft een eigen repository, dus zijn VM's zouden twee keer worden geback-upt. Wordt een host waarvan BackupZit rechtstreeks back-ups maakt later aan vCenter toegevoegd, accepteer dan zijn nieuwe certificaat op de pagina Agents; zijn taken blijven werken — vCenter geeft VM's die op de zelfstandige host zijn gemaakt een nieuwe ID, en BackupZit zet de taken bij de volgende vernieuwing daarop over.

Back-uptaken

Kies in Back-uptaken de ESXi-host (vermeld onder VMware ESXi-hosts in de agentlijst) en Virtuele machines. Maak een back-up van alle VM's van de host (later gemaakte VM's worden automatisch opgenomen) of vink er enkele aan. De taak draait op de proxy-agent van de host. Als u de proxy wijzigt, volgen de bestaande taken.

Om losse VM's weg te laten, bijv. de VM van de BackupZit-console, kiest u Alle VM's (en containers) op de host behalve de aangevinkte en vinkt u ze aan.

Hoe een VM wordt geback-upt

  1. Changed block tracking (CBT) wordt voor de VM ingeschakeld als het uit staat.
    • Op gelicentieerde hosts gebeurt dat automatisch.
    • Op gratis hosts kan CBT alleen worden ingeschakeld terwijl de VM uit staat. BackupZit doet het bij de eerste back-up die de VM uitgeschakeld aantreft. Tot dan leest elke back-up de volledige schijven en toont de run een waarschuwing.
  2. Er wordt een snapshot backupzit_… gemaakt. Als VMware Tools in de gast draaien, wordt de snapshot gequiesced: toepassingen en bestandssystemen worden eerst geleegd, wat de back-up applicatieconsistent maakt. Zonder VMware Tools is hij crash-consistent. Installeer open-vm-tools in Linux-VM's en VMware Tools in Windows-VM's.
  3. CBT meldt welke blokken gelezen moeten worden:
    • bij de eerste back-up alleen de gebruikte blokken;
    • daarna alleen de blokken die sinds de vorige back-up zijn gewijzigd.
  4. Een draaiende VM houdt zijn schijven vergrendeld. Zijn schijven worden daarom op de datastore gekopieerd (thin) en de snapshot wordt meteen verwijderd, meestal na enkele seconden. De kopie wordt daarna via HTTPS gelezen en verwijderd. Uitgeschakelde VM's worden direct gelezen. Met hot-add worden de schijven van draaiende VM's in plaats daarvan via de eigen VM van de proxy gelezen, zonder kopie.
  5. De configuratie van de VM (.vmx) en de NVRAM worden met de back-up opgeslagen.

Voorbeeld uit het testlab: een Debian-VM met een schijf van 8 GB, waarvan 1,6 GB in gebruik. De eerste back-up las 1,6 GB. De volgende, na 50 MB nieuwe gegevens, las 70 MB en duurde 23 seconden.

Hot-add: geen kopie op de datastore

Het kopiëren van de schijven van een draaiende VM kost bij elke back-up, ook bij incrementele, tijd en I/O op de productiedatastore en vraagt vrije ruimte voor de gebruikte blokken van de schijven. Bij grote VM's op trage schijven telt dat. Met Hot-add (Agents → VMware ESXi-hosts, het selectievakje onder de proxyagent) leest de proxy ze in plaats daarvan ter plekke:

  • Vereisten: de proxy is een Linux-agent in een VM die de datastores van de VM ziet (op dezelfde host, of op een host van hetzelfde vCenter met toegang ertoe), en de host wordt via de vSphere-API gewijzigd (vCenter of een gelicentieerde host). De proxy vindt zijn eigen VM aan de hand van de BIOS-UUID.
  • Hoe: zolang de snapshot bestaat, wordt elke schijf independent-nonpersistent aan de VM van de proxy gekoppeld. De proxy opent hem alleen-lezen; alles wat ernaar geschreven zou worden, gaat naar een redo log die vSphere weggooit wanneer de schijf wordt ontkoppeld, dus de schijf van de VM wordt nooit gewijzigd. De proxy leest alleen de blokken die CBT meldt, ontkoppelt de schijf en daarna wordt de snapshot verwijderd.
  • Wat het bespaart: geen tijdelijke kopie en geen extra ruimte op de datastore. Een incrementele back-up van een VM van 2 TB met 20 GB aan wijzigingen leest 20 GB. De snapshot blijft bestaan zolang de schijven worden gelezen (in plaats van alleen tijdens het kopiëren), dus de VM schrijft iets langer in de snapshot.
  • Terugval: als de proxy geen VM van de host is, of het koppelen of lezen van een schijf mislukt, wordt die schijf zoals voorheen op de datastore gekopieerd en toont de run een waarschuwing met de reden. Hot-add staat standaard uit; agents ouder dan 0.54 negeren het. De pagina van de run toont hoeveel schijven via hot-add zijn gelezen.
  • Op de proxy-VM: voorkom met het devices-bestand van LVM dat LVM volumes van de gekoppelde schijven activeert (use_devicesfile = 1 in /etc/lvm/lvm.conf, met de eigen schijven van de proxy geregistreerd via lvmdevices). Volumes die LVM toch activeert, worden verwijderd voordat de schijf wordt ontkoppeld. Koppel niet met de hand schijven van andere VM's aan de proxy: een independent-nonpersistent schijf uit de map van een andere VM wordt aangezien voor een schijf die een onderbroken back-up heeft achtergelaten, en ontkoppeld.

Meerdere proxyagents (vCenter)

Eén proxyagent leest de ene schijf na de andere, en via hot-add alleen op de hosts waarvan hij de datastores ziet. Voeg bij een vCenter-verbinding een Linux-agent in een VM op elke ESXi-host toe als extra proxyagent (Agents → VMware ESXi-hosts, Extra proxyagents onder de proxyagent; agents 0.55 of nieuwer):

  • Verdeling per host: elke back-up van de taak wordt verdeeld. Elke VM gaat naar de proxyagent op de ESXi-host waarop hij draait (volgens de laatste VM-lijst), elke andere VM naar de proxyagent van de verbinding. Elke proxyagent maakt een back-up van zijn deel als eigen uitvoering, tegelijk met de andere, via hot-add op zijn eigen host. Alleen proxyagents die online zijn doen mee: de VM's van een uitgeschakelde proxyagent gaan naar de proxyagent van de verbinding. De eerste back-up in een nieuwe repository en back-ups naar een lokaal of USB-doel worden niet verdeeld.
  • Eén start: de taak toont de delen van een start als geheel: bezig zolang een deel loopt, mislukt als een deel mislukte. RPO-meldingen en het dashboard tellen een back-up pas als alle delen geslaagd zijn; een gekoppelde taak of een kopie "na elke back-up" start één keer, na het laatste deel.
  • Geen overlap: back-ups en herstelacties van de verbinding op verschillende proxyagents lopen niet tegelijk (alleen de delen van één start), dus een VM die tussen hosts is verplaatst, wordt nooit door twee proxyagents tegelijk behandeld.
  • Bewaring per proxyagent: elk deel bewaart het ingestelde aantal back-ups van zijn VM's, en kopieertaken kopiëren en bewaren ze ook per deel. Back-ups van voordat de taak werd verdeeld en die van een verwijderde proxyagent blijven zoals ze zijn: ze blijven herstelpunten van hun VM's. Een VM die naar een andere host is verplaatst (vMotion) gaat vanaf de volgende vernieuwing van de VM-lijst naar de proxyagent van die host.
  • BackupZit vindt de host van een proxyagent via de BIOS-UUID die zijn agent meldt; de pagina Agents toont hem naast elke agent. ESXi-host niet gevonden: de agent is geen VM van dit vCenter, of de VM-lijst is ouder dan de agent (klik op Vernieuwen).

Annuleren van een VMware-back-up (Activiteit → Annuleren) stopt ook een lopende schijfkopie op de datastore en verwijdert de onvolledige kopie; de snapshot wordt verwijderd zoals na elke back-up. Een snapshot die nog wordt gemaakt op het moment dat de back-up wordt geannuleerd, wordt afgewacht (tot vijf minuten) en eveneens verwijderd.

Achtergebleven snapshots. De proxyagent legt elke snapshot en tijdelijke schijfkopie vast voordat hij die maakt, en wist de vastlegging pas als hij ziet dat het object weg is: na het verwijderen vraagt hij de snapshots van de VM opnieuw op, probeert het tot drie keer in ongeveer tien minuten en consolideert de schijven wanneer vSphere meldt dat dat nodig is. Stopt de agent halverwege (crash, stroomuitval) of blijft het verwijderen mislukken, dan blijft de vastlegging staan:

  • De console zet een opschoonrun op de proxyagent in de wachtrij (alleen de proxyagent heeft de aanmeldgegevens van de host), en de proxyagent verwijdert zulke restanten ook na elke back-up van de verbinding. VM's waaraan een back-up of herstel van de proxyagent werkt, blijven ongemoeid.
  • Het dashboard toont elk restant onder Vraagt aandacht (VM, sinds wanneer, waarom) met Nu verwijderen, en voor elk restant dat blijft, gaat één keer een melding (e-mail, chat) uit.
  • De console zoekt ook naar backupzit_…-snapshots ouder dan zes uur in de VM-lijst die ze elke 10 minuten vernieuwt, zolang er geen back-up van de verbinding loopt, zodat ook restanten van oudere agents verschijnen. Alleen snapshots met de naam backupzit_… worden ooit verwijderd; de eigen snapshots van de VM blijven altijd onaangeroerd.

Een VM herstellen

Gebruik de herstelwizard (Volledige virtuele machine) of de pagina van de back-up in Activiteit. Kies:

  • Als nieuwe VM naast het origineel: een kopie met een nieuwe naam, UUID en MAC-adressen. De standaardnaam is die van het origineel plus -restored- en de datum. Netwerkinstellingen in de gast die aan de oude MAC-adressen gebonden zijn, zoals netplan match: macaddress in cloud-images, gelden niet voor de kopie.
  • In plaats van de originele VM: met uitschakelen en de schijven vervangen zal BackupZit:
    • de VM uitschakelen en de snapshots verwijderen;
    • de huidige schijven hernoemen naar ….replaced-DATE.vmdk (verwijder ze zodra de herstelde VM werkt);
    • de back-up naar nieuwe schijven met de oorspronkelijke namen schrijven, en CPU en geheugen instellen zoals in de back-up.
    De VM behoudt zijn UUID, netwerkadapters en MAC-adressen. Als de VM was verwijderd, wordt hij opnieuw gemaakt met zijn oorspronkelijke identiteit.
  • ESXi-host en datastore: een andere host, of een andere datastore van dezelfde host.
  • De VM na het herstel starten.

Schijven worden thin hersteld en alleen blokken met gegevens worden geschreven. ISO-images die aan cd/dvd-stations gekoppeld waren, maken geen deel uit van de back-up, dus die stations blijven leeg.

Direct herstel

Kies Direct, draaiend vanuit de back-up om een VM binnen enkele seconden te starten, zonder eerst zijn schijven te kopiëren. De proxy-agent van de host — dat moet een Linux-agent zijn — biedt de schijven van de VM rechtstreeks vanuit de back-up aan via NFS; de host koppelt dat als datastore backupzit-<agent> en draait de VM daarvandaan. Wijzigingen die de VM maakt, worden op de agent bewaard (/var/lib/backupzit/instant-esxi, die daarvoor vrije ruimte nodig heeft); de back-up zelf wordt nooit gewijzigd, en het bewaarbeleid houdt hem vast zolang de VM ervan draait. Als de originele VM nog bestaat, krijgt de directe VM een nieuwe UUID en nieuwe MAC-adressen.

Op de runpagina, wanneer de VM werkt zoals het hoort:

  • Voltooien kopieert hem naar een datastore van de host: de VM wordt afgesloten (via VMware Tools als die draaien), zijn schijven worden thin gekopieerd (via de API op gelicentieerde hosts, met vmkfstools via SSH bij de gratis licentie), hij wordt vanaf de datastore geregistreerd en weer gestart. Een losse host heeft geen Storage vMotion, dus dit vraagt een korte onderbreking die met de schijfgrootte toeneemt. Mislukt het kopiëren, dan blijft de VM vanuit de back-up draaien.
  • Verwerpen stopt en verwijdert de VM met al zijn wijzigingen.

De agent beantwoordt NFS op poort 2049 (en registreert het bij de rpcbind van de machine op poort 111, of beantwoordt poort 111 zelf) alleen voor het adres van de ESXi-host; open deze poorten van de host naar de agent als er een firewall tussen zit. Wanneer de laatste directe VM is voltooid of verworpen, wordt de datastore verwijderd en stopt de NFS-server.

Losse bestanden

Bestanden bladeren op de pagina van de back-up (of Bestanden uit een virtuele machine in de herstelwizard) opent de schijven van de VM. U kunt NTFS, ext2/3/4 en XFS bladeren, ook op LVM, en bestanden downloaden of naar elke agent herstellen.

Opdrachtregel

Deze opdrachten draaien op elke agent. Zet het ESXi-wachtwoord in BACKUPZIT_VMWARE_PASSWORD:

backupzit-agent vmware list    --host 192.168.1.20 [--user root]
backupzit-agent vmware backup  --host … --repo … [--vmid N,N]
backupzit-agent vmware restore --host … --repo … --vmid N [--new] [--name NAME] [--datastore DS] [--overwrite] [--start] SNAPSHOT|latest

vmware list toont de vingerafdrukken van het certificaat en de SSH-sleutel van de host. Geef ze mee met --thumbprint en --ssh-host-key om ze ook op de opdrachtregel te pinnen.

Nog niet inbegrepen

  • vCenter met meerdere datacenters. Alleen een vCenter met één datacenter kan worden toegevoegd; voeg de hosts van de andere rechtstreeks toe.
  • VM's met eigen snapshots. Hun schijven zijn delta's; verwijder of consolideer de snapshots eerst.
  • Sommige schijftypen. Raw device mappings (RDM) en onafhankelijke schijven.
  • Direct herstel via een Windows-proxy-agent. Direct herstel vereist een Linux-proxy-agent.
