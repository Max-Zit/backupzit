Usuários, funções e LDAP

Dê a cada pessoa sua própria conta, só com os direitos de que ela precisa — como contas locais ou com o login do Active Directory / LDAP.

Uso típico: administradores de TI são Administradores; quem cuida dos backups do dia a dia é Operador de backup; o suporte que recupera arquivos excluídos é Operador de restauração; diretoria e auditores são Visualizadores. Páginas e botões que uma função não pode usar ficam ocultos, e o servidor os recusa de qualquer forma. Lembre-se de que restaurar pode sobrescrever dados — restaurar uma imagem de disco ou um sistema Linux apaga o disco de destino, e restaurar uma VM com substituir exclui a VM existente — então dê as funções de restauração só a pessoas a quem você confiaria isso; toda restauração fica no log de auditoria.

Usuários locais

Em Usuários → Novo usuário local informe um nome de usuário, uma função e uma senha de pelo menos 10 caracteres. Na página do usuário você pode alterar a função, desativar a conta (sessões abertas terminam na hora), definir uma nova senha ou excluir o usuário.

Todo usuário pode alterar a própria senha em Minha conta (clique no seu nome no canto superior direito).

Sempre resta pelo menos um administrador local ativo, para que você possa entrar mesmo quando o diretório estiver inacessível. Você não pode rebaixar, desativar ou excluir a si mesmo.

Login com Active Directory / LDAP

Em Configurações → LDAP / Active Directory:

  1. Servidor: ldaps://dc1.example.local:636. O ldap:// simples só é aceito com StartTLS, então as senhas nunca trafegam sem criptografia.
  2. Conta de serviço: uma conta de domínio comum usada para buscar usuários e grupos (acesso de leitura basta), por ex. CN=svc-backupzit,OU=Service Accounts,DC=example,DC=local.
  3. Base de pesquisa: por ex. DC=example,DC=local.
  4. Filtro de usuários: Active Directory (&(objectClass=user)(sAMAccountName={username})), OpenLDAP (&(objectClass=inetOrgPerson)(uid={username})).
  5. Grupos → funções: o DN completo de um grupo para cada função que você quer usar, por ex. CN=BackupZit Admins,OU=Groups,DC=example,DC=local. Vale a função mais alta correspondente; usuários que não estão em nenhum grupo não conseguem entrar. Marque grupos aninhados no Active Directory para incluir membros de subgrupos.
  6. Confiança no certificado: se os controladores de domínio usam uma CA interna, cole o certificado da CA; para um certificado autoassinado, informe a impressão digital dele.
  7. Use Teste com um usuário real para verificar a conexão, a senha e a função resultante, depois Salvar.

Usuários do diretório aparecem na lista de usuários após o primeiro login. Nome, e-mail e função são atualizados a partir do diretório a cada login. Para bloquear um usuário do diretório na hora, desative a conta no BackupZit (ou no diretório).

Login único (SAML, OpenID Connect)

Com o login único, os usuários clicam em Entrar com … na página de login e se autenticam no seu provedor de identidade — Microsoft Entra ID (Azure AD), Okta, Google Workspace, Keycloak, ADFS ou qualquer outro provedor SAML 2.0 ou OpenID Connect. Configure em Configurações → Login único:

  1. Escolha OpenID Connect (recomendado quando disponível) ou SAML 2.0.
  2. OpenID Connect: registre um aplicativo web no provedor de identidade com a URI de redirecionamento mostrada na página de configurações (https://<console>/login/sso/callback) e informe o emissor (issuer), o ID do cliente e o segredo do cliente. Faça o provedor colocar os grupos do usuário em uma declaração groups (Entra ID: Token configuration → Add groups claim, que envia IDs de grupo; Keycloak: um mapper Group Membership; Okta: uma declaração groups).
  3. SAML 2.0: adicione o console no provedor de identidade com a URL de metadados dele (https://<console>/login/sso/metadata, serviço consumidor de asserções /login/sso/acs), faça-o enviar os grupos como atributo e informe a URL de metadados do provedor de identidade ou cole o XML de metadados dele. O SAML exige o console em HTTPS. As asserções precisam ser assinadas; as requisições do console não são assinadas.
  4. Associe grupos (nomes, ou IDs no Entra ID) às quatro funções; vale a função mais alta correspondente. Usuários que não estão em nenhum deles não conseguem entrar, a menos que você escolha uma função para eles.

Um provedor de identidade cujo certificado HTTPS vem da sua própria CA ou é autoassinado (um Keycloak ou AD FS local) precisa desse certificado de CA em Certificado da CA (PEM); os públicos (Entra ID, Okta, Google) não precisam de nada. Ao salvar, verifica-se se o provedor de identidade responde. Os usuários são criados no primeiro login (marcados como SSO em Usuários) e recebem a função a partir dos grupos a cada login, como os usuários do diretório; nome e e-mail vêm do provedor de identidade. O segundo fator fica a cargo do provedor de identidade, então o console não pede aos usuários SSO o próprio código de dois fatores. As contas locais continuam funcionando, então um administrador sempre consegue entrar mesmo quando o provedor de identidade está inacessível. Uma resposta de login só pode ser usada uma vez e precisa ser assinada pelo provedor de identidade; todo login e toda recusa SSO ficam no log de auditoria.

Sessões

Em Configurações → Login e segurança defina quanto tempo dura um login (padrão 12 horas) e após quantos minutos de inatividade os usuários são desconectados (padrão 60, 0 = nunca). Senhas erradas repetidas bloqueiam o endereço por um tempo: por padrão após 5 falhas em 15 minutos, por 30 minutos. Os limites ficam na mesma página; veja Segurança.

Autenticação de dois fatores

Todo usuário pode proteger o login com um segundo fator em Minha conta → Dois fatores: escaneie o código QR com um aplicativo autenticador (Microsoft ou Google Authenticator, Authy, 1Password, Bitwarden…) e digite o código de 6 dígitos. Dez códigos de recuperação de uso único são mostrados uma vez — guarde-os em local seguro; cada um funciona uma vez se o telefone for perdido. Usuários que entram com login único não precisam do código do console: o segundo fator fica a cargo do provedor de identidade deles.

Em Configurações → Login e segurança você pode exigir autenticação de dois fatores para administradores ou para todos os usuários; eles são solicitados a configurá-la após o próximo login. Se um usuário perder o telefone e os códigos de recuperação, um administrador redefine os dois fatores na página do usuário. Ela também funciona para contas do diretório (LDAP).

Tokens de API

Scripts e ferramentas de monitoramento usam tokens de API em vez de senhas. Cada usuário cria e revoga os próprios tokens em Minha conta → Tokens de API; a função de um token pode ser inferior à do usuário. Administradores veem e podem revogar todos os tokens na página Usuários. Veja REST API.

Aprovação a quatro olhos

Opcional e desligada por padrão. Ligue-a em Configurações → Login e segurança → Aprovação a quatro olhos; ela exige pelo menos dois administradores ativos. A partir daí, estas alterações só valem quando um segundo usuário as aprova:

Excluir ou desativar uma tarefa de backup, encurtar a retenção de uma tarefa (qualquer regra menor que antes, ou regras onde antes tudo era mantido), retomar a retenção após um backup suspeitoUsuários que podem gerenciar tarefas
Remover um agente ou um host ESXiUsuários que podem gerenciar agentes

Excluir um usuário; criar um usuário que pode aprovar (Administrador ou Operador de backup); dar a um usuário uma função com mais direitos, ou reativar esse usuário; redefinir a senha ou os dois fatores desse usuárioAdministradores

A solicitação aparece em Aprovações (com um contador no menu e no painel) e os destinatários das notificações recebem um e-mail. Qualquer outro usuário com a permissão adequada a aprova ou rejeita; o solicitante só pode cancelá-la. Uma alteração aprovada é executada na hora. As solicitações expiram após 7 dias. Quando uma tarefa é editada com retenção mais curta, as demais alterações dela são salvas na hora e só a retenção fica aguardando. Solicitações, aprovações, rejeições e seus usuários ficam no log de auditoria.

Só contas que existiam antes de uma solicitação podem decidir sobre ela. Junto com a aprovação de novos aprovadores, redefinições de senha e configurações de diretório, isso impede que um único administrador obtenha sozinho um segundo aprovador — por exemplo criando uma segunda conta de administrador, definindo a senha de outro administrador ou associando um grupo do diretório à função Administrador. Enquanto a opção está ligada, os dois últimos administradores ativos não podem ser excluídos, desativados nem rebaixados, então sempre é possível decidir sobre as solicitações. As senhas nas solicitações são armazenadas apenas como hash, e as configurações de LDAP e login único criptografadas com a chave de segredos do console. Associações a grupos no próprio diretório (Active Directory, Entra ID) ficam fora do console; proteja esses grupos de administradores lá.

Isso protege contra uma única conta roubada ou mal usada que remova a configuração ou deixe a retenção apagar os backups. Não substitui o armazenamento imutável: para isso, veja Proteção contra ransomware.

Log de auditoria

Usuários → Log de auditoria mostra logins, logins com falha e alterações: usuários, tarefas, destinos de armazenamento, restaurações, chaves de recuperação exibidas e configurações — com hora, usuário e endereço.

Proteção contra alterações

Cada entrada é encadeada à anterior: ela traz um hash do próprio conteúdo e da entrada anterior, calculado com um segredo do arquivo de segredos do servidor (que não está no banco de dados). Quem altera ou exclui entradas diretamente no banco de dados, portanto, quebra a corrente. O hash mais recente também fica em um arquivo ao lado dos dados do console, então a exclusão das entradas mais recentes também é detectada.

  • O console verifica toda a corrente ao iniciar e uma vez por dia. Se ela estiver quebrada, a página Log de auditoria mostra O registro de auditoria foi alterado com a primeira entrada ruim, e os administradores recebem um e-mail.
  • Verificar integridade agora na página Log de auditoria executa a verificação na hora.
  • Entradas gravadas antes da versão 0.33.3 não têm corrente; a página mostra quantas são.

A corrente mostra que o log foi alterado, mas não consegue recuperar o que foi alterado — e alguém que tome o próprio servidor do console, com seu arquivo de segredos, poderia reescrever a corrente. Contra isso, envie uma cópia de cada entrada para um servidor syslog ou SIEM separado em Configurações → Login e segurança → Proteção do registro de auditoria:

  • Servidor syslog como host:porta, e o protocolo: TLS (recomendado, normalmente porta 6514), TCP ou UDP (normalmente 514). O certificado de um servidor TLS precisa ser confiável para a máquina do console.
  • Ao salvar, uma mensagem de teste é enviada; se o servidor não a aceitar, as configurações são salvas e o erro é exibido.
  • As mensagens são RFC 5424 (facility auth) com número da entrada, usuário, ação, endereço e hash da corrente. Uma vez por dia uma mensagem audit.checkpoint leva o hash mais recente, para que a cópia possa ser comparada com o console.
  • Enquanto o servidor syslog estiver inacessível, as entradas aguardam na memória (até 1000) e são enviadas quando ele voltar a responder; o console continua funcionando, e as entradas permanecem de qualquer forma no próprio log de auditoria.
