Destinos de armazenamento

Um destino de armazenamento é onde os agentes gravam os seus backups. Cada agente usa o seu próprio repositório sob o local do destino.

Regra 3-2-1: mantenha 3 cópias dos seus dados, em 2 mídias diferentes, 1 delas fora do local — por exemplo, uma tarefa para um NAS local e outra para S3 ou um repositório protegido noutro edifício.

Testar a conexão

Quando um destino de armazenamento é adicionado, a console testa-o logo com as credenciais informadas: grava um pequeno arquivo, lê-o de volta e remove-o. Em armazenamento imutável (S3 com Object Lock, repositório protegido) apenas faz login e lista, para não deixar nada bloqueado; no S3 também verifica se o bucket tem Object Lock quando a imutabilidade é pedida. O destino é salvo de qualquer forma e o resultado é mostrado — uma senha, chave de host, bucket ou compartilhamento errado aparece agora e não no primeiro backup. Testar conexão na página Armazenamento repete o teste. A console testa a partir da sua própria rede; quem grava os backups são os agentes, por isso um destino que só os agentes alcançam (um disco local ou USB) é testado pelo primeiro backup.

SFTP

Local: sftp://user@host:22/path (use /~/path para um caminho relativo à pasta pessoal do usuário). Informe uma senha ou uma chave privada, e a impressão digital da chave de host do servidor, que obtém no servidor com:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Crie um usuário dedicado que só possa gravar na pasta de backups.

Compatível com S3

Informe o endpoint (p. ex. s3.eu-central-1.amazonaws.com, s3.wasabisys.com, 10.0.0.5:9000), o bucket, uma pasta opcional e uma chave de acesso com leitura/gravação nesse bucket. Marque HTTP sem criptografia apenas para um MinIO local sem certificado.

Backups imutáveis (Object Lock)

Crie o bucket com Object Lock ativado e marque Backups imutáveis … por N dias. Cada arquivo gravado pelos agentes fica bloqueado em modo de conformidade por N dias (+1 dia de margem): ninguém — nem um invasor com as chaves, nem o proprietário do bucket — pode excluí-lo ou sobrescrevê-lo antes disso. Após cada backup, o bloqueio dos dados reutilizados de backups mais antigos é prolongado, de modo que cada ponto de restauração fica protegido durante todo o período.

Excluir (pela retenção ou por um invasor) só adiciona um «marcador de exclusão». Adicione uma regra de ciclo de vida que expire as versões não atuais após um dia, para liberar espaço quando os bloqueios terminarem. Veja Proteção contra ransomware.

Google Cloud Storage

O Google Cloud Storage funciona como destino compatível com S3 através da sua API de interoperabilidade:

  1. No console do Google Cloud abra Cloud Storage → Settings → Interoperability e crie uma chave HMAC para uma conta de serviço com o papel Storage Object Admin no bucket.
  2. Adicione um destino S3 com o endpoint storage.googleapis.com, o nome do bucket, a chave de acesso e o segredo HMAC e a região auto.

A opção S3 Object Lock não está disponível no Google Cloud Storage; para imutabilidade, defina uma política de retenção do bucket (e bloqueie-a) no Google Cloud. Os backups excluídos permanecem então até ao fim do período de retenção.

Azure Blob Storage

  1. No portal do Azure crie uma conta de armazenamento (StorageV2, qualquer redundância) e um contêiner, p. ex. backups.
  2. Adicione um destino Azure Blob Storage com o nome da conta, o contêiner e uma pasta opcional.
  3. Autentique-se com uma chave de acesso (Conta de armazenamento → Chaves de acesso) ou, de forma mais restrita, um token SAS para o contêiner com permissões de leitura, gravação, exclusão e listagem e uma validade adequada.

Para proteção contra ransomware, ative no contêiner a imutabilidade em nível de versão com uma política de retenção baseada em tempo; os backups excluídos ou sobrescritos continuam recuperáveis durante esse tempo. O campo endpoint em Avançado só é necessário para Azure Government/China, Azure Stack Hub ou o emulador Azurite.

Discos USB em rotação

Discos desconectados e levados para fora do local são a proteção mais simples contra ransomware, incêndio e roubo para pequenos escritórios. O BackupZit encontra o disco pelo seu rótulo de volume, qualquer que seja a letra de unidade atribuída pelo Windows:

  1. Formate dois ou mais discos com NTFS (Linux: ext4) e chame-os BZBACKUP1, BZBACKUP2, … (Windows: clique com o botão direito na unidade → Propriedades → nome).
  2. Adicione um destino de armazenamento do tipo Discos USB / removíveis em rotação com o rótulo BZBACKUP*.
  3. Crie uma tarefa de backup para ele — ou melhor, uma tarefa de cópia de backup que copia uma tarefa de NAS ou nuvem para o disco.
  4. Troque os discos regularmente (p. ex. semanalmente) e guarde o desconectado num lugar seguro.
  • Cada disco contém um backup completo e independente com a sua própria retenção; todos os discos são criptografados com a chave de recuperação do destino.
  • A execução mostra qual disco foi usado (Disco BZBACKUP2). Uma restauração pede exatamente esse disco e diz qual está conectado.
  • Quando nenhum disco está conectado, a execução falha com uma mensagem clara e um alerta — um lembrete para voltar a ligar o disco.
  • Conecte apenas um dos discos de cada vez.

Compartilhamento SMB

Servidor, compartilhamento, pasta opcional, usuário, senha e (para contas de domínio) o domínio. Os agentes conectam-se por conta própria com estas credenciais, por isso funciona também para serviços executados como SYSTEM.

Repositório protegido

Instale o pacote backupzit-repo num servidor Linux dedicado e depois, nesse servidor:

backupzit-repo add-key office-console     # shows the access key once
backupzit-repo fingerprint                # certificate fingerprint

Informe na console o endereço do servidor, a chave de acesso e a impressão digital. O período de imutabilidade é configurado no servidor do repositório (/etc/backupzit-repo/repo.env) e não pode ser alterado pela console nem pelos agentes. Detalhes em Proteção contra ransomware.

Criptografia e a chave de recuperação

Com Criptografar backups (o padrão), tudo no repositório — conteúdo e nomes dos arquivos, estrutura de pastas, listas de snapshots — é criptografado com AES-256-GCM antes de sair do agente. O provedor de armazenamento só vê dados aleatórios.

Quando cria um destino criptografado, a console mostra uma chave de recuperação e oferece uma ficha de recuperação para baixar.

Imprima a ficha de recuperação ou guarde-a num gerenciador de senhas, separada dos backups. Se a console se perder, a chave de recuperação mais o local e as credenciais do armazenamento são tudo o que precisa para restaurar. Sem a chave, ninguém consegue ler os backups criptografados — nem o suporte do BackupZit.

Pode voltar a mostrar a chave mais tarde com Chave de recuperação na lista de armazenamento; isto fica registrado.

A lista de armazenamento

A lista mostra para cada destino o tipo, o local, a criptografia (com acesso à chave de recuperação para administradores) e a imutabilidade: o período de Object Lock no S3, ou definido no servidor do repositório nos repositórios protegidos. As credenciais nunca mais são mostradas depois de salvas e são guardadas criptografadas. Só administradores podem adicionar ou remover destinos e ver chaves de recuperação.

Uso do armazenamento e previsão

Após cada backup (e a sua retenção), o agente informa quanto espaço o seu repositório ocupa e — para discos locais e USB, servidores SFTP (extensão statvfs do OpenSSH) e compartilhamentos SMB — o tamanho e o espaço livre do armazenamento. Em Armazenamento → Uso do armazenamento cada destino mostra:

  • o espaço usado por todos os repositórios nele (um por agente; em discos USB em rotação, cada disco conta);
  • em armazenamento de tamanho conhecido, o quanto está cheio (amarelo a partir de 75 %, vermelho a partir de 90 %), com a capacidade como linha vermelha tracejada no gráfico;
  • um gráfico dos últimos 90 dias e, após uma semana de backups, o crescimento por dia (tendência linear dos últimos 30 dias), desenhado 30 dias à frente como linha tracejada, e quando o armazenamento ficará cheio — ou, sem tamanho conhecido, o uso esperado em 90 dias.

Requer atenção no painel avisa quando um destino de armazenamento está 90 % cheio ou ficará cheio em 30 dias. S3 e Azure não têm tamanho fixo; ali só são mostrados o espaço usado e o seu crescimento. O espaço usado são os dados armazenados (comprimidos, criptografados, desduplicados); arquivos que o armazenamento mantém por outras razões (versões de objetos, outros programas) não são contados.

Remover um destino

Remover um destino de armazenamento da console não exclui nenhum dado no armazenamento. Com a aprovação de quatro olhos ativada, um segundo usuário tem de aprovar primeiro.
