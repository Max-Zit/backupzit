Bancos de dados: SQL Server, PostgreSQL, MySQL

O BackupZit faz backup de bancos de dados com as ferramentas do próprio servidor de banco de dados, a partir do agente na máquina do banco: Microsoft SQL Server no Windows, PostgreSQL e MySQL/MariaDB no Linux. Backups completos seguem o agendamento da tarefa; backups de log a cada poucos minutos permitem restaurar um único banco em qualquer momento — por exemplo um minuto antes de um DELETE errado.

Criar uma tarefa

Em Tarefas de backup crie uma tarefa do tipo Bancos de dados, no agente da máquina do banco, e escolha:

  • Servidor de banco de dados: Microsoft SQL Server, PostgreSQL ou MySQL/MariaDB. Não pode ser alterado depois.
  • Instância ou porta: a instância do SQL Server (vazio para a instância padrão, por ex. SQLEXPRESS) ou a porta do PostgreSQL (vazio para 5432). O MySQL/MariaDB é acessado pelo socket local.
  • Bancos de dados: um nome por linha, ou vazio para todos os bancos de usuário — bancos criados depois são incluídos automaticamente.
  • Fazer backup dos logs a cada … minutos: por ex. 15 — logs de transação (SQL Server), WAL arquivado (PostgreSQL) ou logs binários (MySQL). Deixe vazio se restaurar no horário de um backup completo for suficiente.
  • O agendamento é o dos backups completos, por ex. diariamente às 22:00.

Os backups são deduplicados — dados inalterados não são enviados de novo — e criptografados como qualquer backup. A retenção conta os backups completos; backups de log são mantidos enquanto existir o backup completo em que se baseiam. A página da execução lista o que cada backup contém.

Microsoft SQL Server

  1. Instale o agente na máquina Windows que roda o SQL Server (qualquer edição a partir de 2012, inclusive Express).
  2. O agente roda como NT AUTHORITY\SYSTEM e se conecta com autenticação do Windows. Dê a essa conta a função sysadmin, uma vez por instância: 
    sqlcmd -S .\SQLEXPRESS -E -Q "ALTER SERVER ROLE sysadmin ADD MEMBER [NT AUTHORITY\SYSTEM]"
  • Cada execução grava um arquivo de backup por banco (BACKUP DATABASE / BACKUP LOG … WITH CHECKSUM) na pasta de backup padrão da instância, armazena os arquivos e os exclui. Enquanto a execução dura, a pasta precisa de espaço livre para o maior banco.
  • Com backups de log ligados, os backups completos iniciam a cadeia de logs. Sem eles, os backups completos são feitos como COPY_ONLY, para não atrapalhar outros planos de backup ou manutenção.
  • Backups de log são feitos para bancos no modelo de recuperação full ou bulk-logged; bancos no modelo simple recebem só backups completos. Marque bancos do sistema para incluir master, model e msdb.

PostgreSQL

O agente trabalha como a conta postgres pelo socket local — nada a configurar para backups. Um backup completo armazena o cluster inteiro (pg_basebackup), as funções (pg_dumpall --globals-only) e um pg_dump de cada banco.

A recuperação para um momento específico precisa de arquivamento de WAL. Com backups de log ligados, o primeiro backup completo o configura com ALTER SYSTEM: archive_mode = on e um archive_command que copia os segmentos WAL concluídos para /var/lib/backupzit-pg/wal; os backups de log os armazenam e removem dali. O archive_mode passa a valer após uma reinicialização do PostgreSQL (systemctl restart postgresql) — a execução avisa. Se outra ferramenta já usa archive_command, o BackupZit não mexe nele e faz backup sem recuperação para um momento específico. Se os backups de log pararem (tarefa desativada ou excluída), desligue o arquivamento de novo (ALTER SYSTEM RESET archive_mode, reinicialização) para a pasta não encher.

  • Restaurar um banco de dados no estado do backup completo: a partir do pg_dump dele no servidor em execução, com um novo nome ou substituindo o banco.
  • Em um momento específico (ou o mais recente): o agente descompacta o backup do cluster em uma instância temporária em uma porta livre (só socket, sem rede, sem arquivamento), reaplica o WAL até esse momento, exporta o banco dela para o servidor em execução e remove a instância temporária. A máquina precisa de espaço livre para o cluster por um tempo.
  • Cluster inteiro: restaurado da mesma forma como uma instância separada que continua rodando em uma porta livre; a execução informa a porta e o diretório de dados (em /var/lib/backupzit-pg) e como conectar e pará-la.

MySQL e MariaDB

O agente se conecta como root pelo socket local (autenticação por socket, padrão no Debian e Ubuntu), ou com as credenciais de /root/.my.cnf. Um backup completo armazena um mysqldump de cada banco (consistente, com rotinas, eventos e triggers) junto com a posição do log binário correspondente.

A recuperação para um momento específico precisa do log binário. Ative-o uma vez na configuração do servidor e reinicie o servidor, por ex. /etc/mysql/mariadb.conf.d/60-binlog.cnf:

[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin
binlog_format = ROW
expire_logs_days = 7

(crie a pasta do log, tendo a conta mysql como dona). Os backups de log então armazenam cada log binário fechado. Mantenha a expiração própria do servidor maior que o intervalo dos backups de log; uma lacuna é informada, e as restaurações não conseguem atravessá-la.

  • Restaurar um banco de dados: o dump dele é carregado em um banco novo (ou substitui um existente). Em um momento específico ou o mais recente, as alterações desse banco registradas nos logs binários após o dump são reaplicadas até esse momento — também quando o banco recebe um novo nome. A reaplicação não é gravada no log binário do servidor.
  • Usuários e privilégios (o banco de sistema mysql) não fazem parte dos dumps.

Restauração

Abra uma execução de backup completo (ou use o assistente de restauração → Banco de dados) e escolha o banco, a máquina onde restaurar (o mesmo servidor ou outro com o mesmo servidor de banco de dados) e:

  • Como novo banco de dados chamado por ex. sales_restored — o original fica intacto e você pode copiar linhas de volta — ou com o nome original; marque substituí-lo para sobrescrever um banco existente (os usuários dele são desconectados antes).
  • Estado: o do backup completo; o estado mais recente (o backup completo e todo backup de log depois dele); ou um momento específico entre o backup completo e o backup de log utilizável mais recente, como a tabela mostra. Digite o horário como o console mostra, no fuso horário do servidor do console (veja Fuso horário); o agente o converte para o fuso horário do servidor de banco de dados.

Linha de comando

backupzit-agent sql list    [--instance SQLEXPRESS]
backupzit-agent sql backup  --repo ... [--instance I] [--db a,b] [--system] [--log] [--copy-only]
backupzit-agent sql restore --repo ... [--instance I] --db NAME [--as NEW] [--replace] [--at "2026-10-04 14:59:00"] SNAPSHOT|latest
backupzit-agent pg list     [--port 5432]
backupzit-agent pg backup   --repo ... [--port P] [--db a,b] [--pitr | --wal]
backupzit-agent pg restore  --repo ... --db NAME|"(cluster)" [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest
backupzit-agent mysql list
backupzit-agent mysql backup  --repo ... [--db a,b] [--binlog]
backupzit-agent mysql restore --repo ... --db NAME [--as NEW] [--replace] [--at TIME | --latest] SNAPSHOT|latest

Não incluído

  • Backups diferenciais do SQL Server e grupos de disponibilidade Always On; servidores de banco de dados remotos — o agente faz backup de servidores na própria máquina.
  • Restaurar tabelas avulsas: restaure o banco com um novo nome e copie as linhas.
