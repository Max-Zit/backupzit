Segurança e boas práticas

Como o BackupZit protege seus dados e o console, e o que você deve fazer do seu lado.

Proteções embutidas

  • Criptografia na origem — AES-256-GCM no agente; o armazenamento só vê dados criptografados. As chaves são derivadas com Argon2id.
  • Conexões fixadas — os agentes fixam o certificado do console; chaves de host SFTP e certificados de repositórios protegidos também são fixados. Nenhuma autoridade certificadora pode ser usada para se passar por eles.
  • Certificado confiável para navegadores — opcionalmente um certificado enviado ou do Let's Encrypt (TLS 1.2+) em um endereço separado, renovado automaticamente; veja Instalar o servidor.
  • Segredos em repouso — senhas e chaves de armazenamento, chaves de recuperação, senhas SMTP/LDAP e segredos de dois fatores são criptografados no banco de dados com uma chave mantida fora dele (secrets.key).
  • Segredos dos agentes — cada agente tem seu próprio segredo, armazenado só como hash no console e, no agente, em um arquivo que só administradores podem ler.
  • Console web — cookies de sessão HttpOnly e SameSite=Strict; proteção contra requisições entre sites e clickjacking; Content-Security-Policy rígida; senhas com hash bcrypt; páginas sensíveis nunca ficam em cache.
  • Proteção contra força bruta — endereços que falham no login vezes demais são bloqueados: senhas, códigos de dois fatores e tokens de API. Os bloqueios sobrevivem a reinicializações, reincidentes ficam bloqueados por mais tempo e os administradores recebem um e-mail. Veja abaixo.
  • Contas — funções com privilégio mínimo, autenticação de dois fatores opcional (TOTP) e login LDAPS; tokens de API com função própria, mais baixa, e validade.
  • Aprovação a quatro olhos (opcional) — excluir ou desativar tarefas, excluir agentes, hosts ESXi, destinos de armazenamento e usuários, encurtar a retenção, desligar a aprovação e tudo o que poderia dar a um administrador um segundo aprovador (novos aprovadores, mais direitos, redefinição de senha e dois fatores, mudanças em LDAP e SSO) exigem a aprovação de um segundo usuário. Veja Usuários, funções e LDAP.
  • Trilha de auditoria — logins, logins com falha, alterações de usuários e funções, tarefas, destinos de armazenamento, restaurações, chaves de recuperação exibidas, alterações de configuração e ações de API são registrados no log de auditoria; as entradas são encadeadas para que alterações e exclusões no banco sejam detectadas, e podem ser copiadas para um servidor syslog ou SIEM (Proteção contra alterações); exclusões em um repositório protegido são registradas naquele servidor.
  • Atualizações do console — as versões são assinadas com a chave de release do BackupZit (Ed25519). O console e o serviço root que as instala verificam a assinatura, o banco de dados é copiado antes e uma atualização com falha é revertida.
  • Atualizações dos agentes — os agentes só baixam novas versões do próprio console pela conexão fixada e só as instalam se o checksum SHA-256 conferir.
  • Canal de status local — o aplicativo da bandeja fala com o serviço do agente por um named pipe local (Windows) ou um socket só para root (Linux). Usuários conectados à máquina podem ler o status e iniciar as tarefas de backup da própria máquina; nada mais (tarefas, agendamentos, armazenamento e restaurações só são gerenciados no console).
  • Backups de hipervisores — o agente em um host Proxmox ou Hyper-V usa as ferramentas do próprio host; nenhuma senha de hipervisor é armazenada para eles. Para o VMware ESXi o console armazena a senha do host criptografada, fixa o certificado HTTPS e a chave de host SSH dele, e só entrega a conexão ao agente proxy do host para as execuções dele.
  • Integridade dos backups — cada bloco é verificado pelo hash SHA-256 na restauração; testes de restauração automáticos e a detecção de ransomware vigiam os backups continuamente.

Proteção contra força bruta

Configure em Configurações → Login e segurança. Os padrões são seguros para a maioria das instalações:

ConfiguraçãoPadrãoSignificado
Tentativas falhas por endereço5Logins com falha de um endereço IP dentro do período de contagem bloqueiam esse endereço. Contam senhas erradas, códigos de dois fatores errados e tokens de API inválidos.
Período de contagem15 minutosFalhas mais antigas são esquecidas.
Bloquear por30 minutosUm endereço bloqueado não consegue entrar, nem com a senha certa. A página de login responde "Muitas tentativas de login com falha" e a API responde HTTP 429.
Bloquear reincidentes por mais tempoligadoCada novo bloqueio de um endereço no mesmo dia dura o dobro: 30 minutos, 1 hora, 2 horas, … até 7 dias.
Tentativas falhas por nome de usuário20Falhas para um nome de usuário, de quaisquer endereços, pausam o login desse nome até passar o período de contagem. Isso barra tentativas espalhadas por muitos endereços. As contas nunca são bloqueadas permanentemente, então um atacante não consegue trancar o administrador do lado de fora.
Nunca bloquear estas redesnenhumaRedes opcionais, por ex. a sub-rede dos administradores, que nunca são bloqueadas. O limite por nome de usuário continua valendo para elas.
Proxies reversosnenhumSe o console roda atrás de nginx, Traefik ou outro proxy, informe o endereço dele: o endereço do cliente passa a ser lido de X-Forwarded-For (senão todos os clientes pareceriam ser o proxy) e, quando o proxy envia X-Forwarded-Proto: https, os cookies de login são marcados como Secure. Os dois cabeçalhos são ignorados vindos de qualquer outro endereço, então não podem ser falsificados.
E-mail quando um endereço é bloqueadoligadoEnviado aos destinatários das configurações de e-mail.

A mesma página lista os endereços bloqueados, com o motivo e a duração de cada bloqueio, e permite remover um bloqueio. Bloqueios e desbloqueios ficam registrados no log de auditoria.

Se você se trancou do lado de fora, entre por outro endereço ou execute isto no servidor com as mesmas opções de banco de dados do serviço:

backupzit-server --unblock-ip all

Para remover um único bloqueio, informe o endereço em vez de all.

Acesso ao console web (endereço público)

Os agentes se conectam ao console na porta 8443. Para oferecer o console em um endereço público — para agentes em outros locais ou clientes — deixando só seus administradores abrirem o console web, use Configurações → Login e segurança → Acesso ao console web:

ConfiguraçãoEfeito
Endereços permitidosEndereços IP ou redes (por ex. 203.0.113.10, 10.0.0.0/24). O console web, a REST API e todas as páginas só respondem a esses endereços; os demais recebem "not found", como se não houvesse console. Os agentes sempre alcançam a API deles (registro, consultas, resultados, downloads, instalação remota). Vazio: todos. O console recusa uma lista que não contenha o seu próprio endereço.
Porta 8443 só para agentesO console web fica então só na porta web com o certificado confiável (Configurações → Certificado, normalmente 443), de modo que um firewall pode abrir a 8443 para todos e a 443 só para seus endereços. Disponível quando a porta web estiver ativa; altere-a pela porta web, não pela 8443.

Um firewall típico para um console público: 8443 aberta para todos (agentes), 443 e 80 (verificação HTTP do Let's Encrypt) só a partir dos seus endereços, SSH só a partir dos seus endereços ou desligado, todo o resto fechado.

Ficou trancado do lado de fora? No próprio servidor (localhost) o console sempre responde. No appliance, o item 5 do menu de configuração na tela dele remove bloqueios de login e essas restrições.

Recomendações

Console

  • Mantenha o console em uma rede interna; não publique a porta 8443 na internet. Use VPN para administração remota.
  • Use uma senha de administrador longa e única e troque a inicial.
  • Exija autenticação de dois fatores para administradores (Configurações → Login e segurança).
  • Dê a cada pessoa sua própria conta com a função mais baixa que funcione; use tokens de API com a função Visualizador para monitoramento.
  • Faça backup do secrets.key separado do banco de dados (Instalar o servidor).
  • Escolha em Configurações → Login e segurança uma duração de sessão adequada (mais curta é mais segura).
  • Mantenha o servidor atualizado (apt upgrade / dnf upgrade), incluindo o PostgreSQL.

Armazenamento

  • Dê a cada destino de armazenamento sua própria conta, com acesso só à pasta ou bucket de backup.
  • Não coloque o armazenamento de backup no domínio Windows; use credenciais que não sejam usadas em nenhum outro lugar.
  • Mantenha pelo menos uma cópia imutável (S3 Object Lock ou repositório protegido) e uma cópia externa.

Chaves

  • Guarde as folhas de recuperação offline. Sem elas, backups criptografados não podem ser restaurados se o console for perdido.
  • Teste uma vez uma restauração pela linha de comando só com a folha de recuperação, para saber que o procedimento funciona.
  • Trate um pendrive com recovery.json como uma chave: até o código de recuperação expirar (30 dias), ele permite que uma máquina entre no console como agente de recuperação. Crie um novo código quando precisar, em vez de guardar pendrives antigos.
  • As ISOs de recuperação dão uma linha de comando de root / administrador a quem der boot nelas — como qualquer mídia de boot. Proteja os servidores com senha de firmware (BIOS/UEFI) e configurações de boot seguro.

Agentes e hipervisores

  • O console pode instalar software nos agentes (atualizações de agentes) e restaurar dados neles. Proteja as contas de administrador de acordo: autenticação de dois fatores, poucos administradores.
  • Arquivos de discos de VM são analisados pelo console e pelos agentes quando você navega neles; dados de sistema de arquivos danificados ou hostis geram um erro, não uma falha.

Relatar um problema de segurança

Relate vulnerabilidades em particular aos mantenedores do BackupZit, em vez de abrir uma issue pública.
