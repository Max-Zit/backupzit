Máquinas virtuais do Proxmox VE

O BackupZit faz backup de máquinas virtuais (QEMU) e contêineres (LXC) do Proxmox VE sem instalar nada dentro dos convidados. O agente roda no host Proxmox, tira um snapshot de cada convidado, lê seus discos e os armazena deduplicados em qualquer destino de armazenamento. Os discos das VMs são guardados como imagens de disco; contêineres em ZFS têm backup arquivo por arquivo (veja Contêineres (LXC) em ZFS).

Configuração

  1. Instale o pacote Agente Linux — Debian / Ubuntu a partir de Agentes em cada nó Proxmox (Proxmox VE 7, 8 e 9 são baseados em Debian): 
    apt install ./backupzit-agent_*.deb
backupzit-agent enroll --code "BZ1-..."
systemctl enable --now backupzit-agent
  2. Em até um minuto o nó aparece na página Agentes com o selo Proxmox VE · N guests.
  3. Em Tarefas de backup selecione esse agente e escolha Máquinas virtuais (Proxmox VE, Hyper-V, VMware). Depois escolha Todas as VMs (e contêineres) do host (convidados criados depois são incluídos automaticamente) ou marque alguns.

Para deixar de fora convidados individuais, p. ex. a VM da consola BackupZit, escolha Todas as VMs (e contentores) do host exceto as marcadas e marque-os.

O agente usa as ferramentas do próprio nó (qm, pct, pvesm, LVM, ZFS, Ceph); nenhum token de API ou senha é armazenado no console.

Como um convidado é copiado

  1. Um snapshot temporário do Proxmox é criado (backupzit_…, visível em Snapshots por alguns segundos a minutos). O convidado continua rodando.
  2. Se o QEMU guest agent roda na VM (e está ativado nas opções da VM), o Proxmox congela os sistemas de arquivos para o snapshot — o backup fica então consistente com as aplicações. Sem ele, o backup tem consistência de falha, como uma queda de energia. Instale qemu-guest-agent nas VMs Linux e as ferramentas de convidado VirtIO nas VMs Windows.
  3. Cada disco é lido do snapshot em blocos de 1 MiB. Blocos vazios não são armazenados e blocos que já estão no repositório não são enviados de novo, então após o primeiro backup só os dados alterados são transferidos. VMs em execução com discos em LVM-thin, ZFS, Ceph RBD ou arquivos qcow2 também têm rastreamento de blocos alterados (dirty bitmaps do QEMU): a partir do segundo backup, só as áreas gravadas desde o backup anterior são lidas, o que leva segundos em vez de minutos. Depois que a VM foi parada, reiniciada ou movida para outro nó, ou que um disco foi redimensionado, o backup seguinte lê os discos completos uma vez; a página da execução mostra quais discos foram lidos somente como blocos alterados. Este é o tamanho de bloco padrão; uma tarefa pode usar 256 ou 512 KiB em vez disso (veja Tarefas).
  4. O snapshot é removido. A configuração do convidado (CPU, memória, rede, discos) é armazenada com o backup.

A página da execução lista cada convidado, seus discos e como foi capturado. Testes de restauração verificam blocos aleatórios dos backups de VM como nas imagens de disco e, com o teste de boot ligado, iniciam cada VM a partir do backup, isolada da rede, para provar que ela inicia. Contêineres em ZFS são testados restaurando arquivos aleatórios.

Ceph RBDsim, snapshotsim
Diretório, NFS, CIFS com discos qcow2sim, snapshotsim
Diretório, NFS, CIFS com discos raw, LVM thicknão — pare o convidado ou mova o discosim
Subvolumes ZFS de contêineres (LXC)sim, snapshot, arquivo por arquivosim, arquivo por arquivo

Discos marcados como Backup: no (backup=0) no Proxmox, discos físicos em passthrough e bind mounts são ignorados e listados como avisos. Drives cloud-init não são armazenados; eles são recriados a partir da configuração na restauração. Um convidado parado cujos discos são lidos sem snapshot fica enquanto isso com o bloqueio de backup do Proxmox VE, como no vzdump: não pode ser iniciado (nem pelo HA) até que seus discos sejam lidos.

Snapshots e bloqueios que ficam para trás. O agente registra cada snapshot de backup antes de criá-lo, e o bloqueio de backup de um convidado parado assim que ele é definido, e só apaga o registro quando a configuração do convidado mostra que ele sumiu (um snapshot é removido com --force quando a remoção normal falha, até três tentativas em cerca de dez minutos). Após uma falha do agente ou uma queda de energia, o próprio agente os remove, ao iniciar e a cada 15 minutos:

  • Convidados em que um backup ou uma restauração do agente está trabalhando, e convidados para os quais o Proxmox VE executa uma tarefa (um backup vzdump, uma migração), não são tocados.
  • Um bloqueio de snapshot (lock: snapshot) deixado por uma criação interrompida é removido junto com o snapshot; antes, os dispositivos Ceph RBD do snapshot são desmapeados (unmap).
  • Snapshots backupzit_… com mais de um dia dos quais o agente não tem registro (por exemplo, de versões mais antigas) também são removidos. Seus próprios snapshots nunca são tocados.
  • Um bloqueio de backup só é removido quando o registro mostra que o BackupZit o definiu. Um bloqueio que ele não definiu é informado com o comando que o remove (qm unlock, pct unlock), porque o vzdump usa o mesmo bloqueio.
  • O que não pode ser removido aparece no painel em Requer atenção com Remover agora e é notificado uma vez.

Contêineres (LXC) em ZFS

Em um armazenamento ZFS, o Proxmox guarda os volumes de um contêiner (LXC) como datasets (subvol-<ID>-disk-N): sistemas de arquivos, não discos virtuais como os zvols de uma VM (QEMU). Por isso o BackupZit faz o backup desses contêineres arquivo por arquivo:

  • O snapshot temporário é o mesmo; o agente lê os arquivos do snapshot ZFS de cada subvolume (.zfs/snapshot, mesmo oculto) enquanto o contêiner continua rodando.
  • Proprietários (inclusive os IDs deslocados de contêineres sem privilégios), permissões, datas, atributos estendidos e ACLs, links físicos e simbólicos e arquivos de dispositivo são mantidos. Sockets ficam de fora, como no vzdump; os serviços do contêiner os recriam.
  • A partir do segundo backup, só são lidos os arquivos cujo tamanho ou data de modificação mudou; os outros vêm do backup anterior.
  • Um contêiner assim é restaurado em um armazenamento ZFS, como novos subvolumes com o tamanho (cota) dos volumes originais.

Contêineres em LVM-thin ou Ceph RBD têm discos virtuais e têm backup bloco a bloco, como as VMs. A página da execução lista as VMs (QEMU) e os contêineres (LXC) em tabelas separadas e mostra como cada contêiner foi guardado. Requer agentes 0.53 ou mais recentes.

Restaurar uma VM ou contêiner

Abra uma execução de backup de VM (pela página da tarefa ou Atividade) e use Restaurar uma VM ou contêiner:

  • Convidado — um dos convidados desse backup.
  • Restaurar no nó do Proxmox — qualquer nó com o agente BackupZit, inclusive um nó de outro cluster.
  • Como novo convidado com o próximo ID livre (padrão) ou com o ID … — o original continua rodando. Como os dois existem, as placas de rede da cópia recebem novos endereços MAC.
  • Com o ID original — depois que o convidado foi excluído. Se ele ainda existir, marque pará-lo e excluí-lo para substituí-lo pelo backup. Desde a 0.59 o convidado existente continua em execução enquanto os discos do backup são gravados, e só é parado e excluído com seus discos quando todos estiverem restaurados: se a restauração falhar antes (armazenamento cheio, dados ausentes), o convidado fica como estava e os discos novos são removidos. Por isso é preciso, por um tempo, espaço para os dois; com Excluí-lo antes de gravar os discos o convidado é excluído primeiro, como antes da 0.59 (agentes anteriores à 0.59 sempre fazem assim; para eles o console só aceita a substituição com esta opção marcada). Antes de gravar, a restauração verifica se o armazenamento tem espaço para os discos novos e ainda deixa 5 % (pelo menos 1 GiB) livres, para que um pool thin não encha; caso contrário, ela para com uma mensagem e o convidado não é alterado.
  • Nome e Armazenamento para os discos — por ex. restaurar em um armazenamento diferente do original.
  • Iniciar o convidado após a restauração.
  • Manter as configurações que agem no host também em outro nó — configurações que executam código no host ou chegam ao seu hardware (script hook, argumentos brutos do QEMU args, dispositivos PCI e USB repassados, chaves lxc.* brutas e dispositivos de contêineres) são mantidas quando o convidado volta ao nó em que teve backup, e citadas nas notas da execução. Em outro nó elas são deixadas de fora, a menos que isto esteja marcado (agentes 0.62 e mais novos; os mais antigos as mantêm), para que um backup de outro host, ou de um comprometido, não possa adicioná-las sem ser notado.

Toda restauração dá às VMs um novo ID de geração (vmgenid), para que controladores de domínio Windows e outros softwares detectem a reversão com segurança. Os discos são alocados com pvesm no armazenamento escolhido; em armazenamento do tipo diretório eles são restaurados como arquivos raw. A lista de armazenamentos só oferece os adequados ao convidado escolhido: discos de VM para uma VM, volumes de contêiner para um contêiner e ZFS para um contêiner com backup arquivo por arquivo.

Recuperação instantânea

Restaurar uma VM grande leva tanto tempo quanto copiar seus discos. Com Instantaneamente, rodando a partir do backup no formulário de restauração, a VM roda em segundos, enquanto seus discos ainda estão no backup:

  1. O agente serve os discos da VM somente leitura a partir do backup (um pequeno servidor NBD rodando como a unidade systemd backupzit-instant-<ID>) e cria uma nova VM com o próximo ID livre cujos discos são overlays qcow2 no armazenamento de diretório backupzit-instant (/var/lib/backupzit-instant, adicionado automaticamente). Os dados são lidos do backup sob demanda; tudo o que a VM grava fica nos overlays. Variáveis de firmware (disco EFI) e estado do TPM são pequenos e copiados.
  2. A VM inicia. Verifique-a — ela recebe novos endereços MAC como qualquer cópia. O painel lista toda VM que ainda roda a partir de um backup.
  3. Na página da execução, ou Concluir: os discos são movidos para o armazenamento escolhido enquanto a VM continua rodando (qm disk move), e então o backup não é mais usado. Ou Descartar: a VM é parada e excluída junto com suas alterações.

Enquanto uma VM roda a partir de um backup, a retenção nunca remove esse backup. A VM é tão rápida quanto o armazenamento de backup permite: um repositório em disco local ou em um compartilhamento de rede rápido funciona melhor; leituras via SFTP ou S3 de longe a deixam lenta até ser concluída. A recuperação instantânea é para VMs (não contêineres) e cria uma nova VM — para restaurar no local use uma restauração normal. O disco EFI não pode ser movido com a VM rodando; ele fica então em backupzit-instant (veja a mensagem da execução) e pode ser movido após desligar a VM: qm disk move ID efidisk0 STORAGE --delete 1.

Replicação

Para convidados que precisam voltar em minutos, uma tarefa de VM pode manter réplicas: em Avançado no formulário da tarefa marque Manter réplicas das VMs e escolha o nó (qualquer nó com o agente BackupZit, inclusive em outro cluster) e o armazenamento. Após cada backup, o agente nesse nó atualiza uma cópia parada de cada convidado da tarefa:

  • Na primeira vez, a réplica é restaurada como um novo convidado (próximo ID livre, nome original-replica, novos endereços MAC, nunca iniciada com o nó).
  • Depois só são gravados os blocos que mudaram desde o backup que a réplica contém — normalmente alguns segundos por backup.
  • A página da tarefa lista as réplicas, o backup que cada uma contém e seu estado. Se um convidado for perdido, clique em Iniciar réplica: ela roda com os dados do último backup, sem restauração. Inicie-a somente quando o original realmente não existir mais — os dois na rede ao mesmo tempo podem entrar em conflito. Depois que uma réplica foi iniciada (também na interface do Proxmox VE, por exemplo para um teste de failover), a próxima atualização compara cada bloco em vez de gravar só as alterações, para que a réplica volte a corresponder ao backup. O mesmo acontece após uma atualização interrompida (falha do agente ou do nó) e quando o log de tarefas do Proxmox VE não pode ser lido para saber se a réplica foi iniciada.
  • Enquanto uma réplica roda, ela não é mais atualizada (a execução informa). Para replicar de novo, exclua o convidado réplica no Proxmox; o próximo backup cria um novo. Réplicas com snapshots do Proxmox também não são atualizadas.
  • Discos adicionados depois a um convidado não são replicados (exclua a réplica para recomeçar); discos que cresceram também crescem na réplica. Alterações de configuração (memória, CPUs) são aplicadas quando a réplica é criada.
  • A replicação lê os backups como uma restauração: o nó da réplica precisa alcançar o armazenamento. Desligar a replicação deixa as réplicas como estão.

Linha de comando

backupzit-agent pve list
backupzit-agent pve backup  --repo ... [--vmid 100,200] [--exclude 300]
backupzit-agent pve show    --repo ... latest
backupzit-agent pve restore --repo ... --vmid 100 [--new-vmid -1|N] [--name copy] [--storage local-lvm] [--overwrite [--remove-first]] [--start] SNAPSHOT|latest
backupzit-agent pve instant --repo ... --vmid 100 [--new-vmid N] [--name X] SNAPSHOT|latest
backupzit-agent pve instant-finish --vmid 101 --storage local-lvm
backupzit-agent pve instant-discard --vmid 101

As opções de repositório são as mesmas de todos os comandos (veja Referência da linha de comando). A linha de comando funciona sem o console, por exemplo para restaurar um nó inteiro após um desastre.

Clusters

Instale o agente em cada nó. Uma tarefa faz backup dos convidados que rodam no nó do seu agente; um convidado listado em uma tarefa e migrado para outro nó é informado como aviso com o nome desse nó — faça backup de cada nó com sua própria tarefa, ou use Todas as VMs (e contêineres) do host em cada nó para que convidados migrados estejam sempre cobertos.

Restaurar arquivos avulsos

Na tabela de convidados de uma execução de backup de VM, clique em Navegar pelos arquivos. O console lê o disco diretamente do backup — nada é restaurado antes — e mostra suas partições e volumes lógicos LVM; NTFS (Windows), ext2/3/4, XFS e btrfs (Linux) podem ser navegados, também dentro de LVM. Marque arquivos e pastas e:

  • Baixar — um arquivo como está, vários arquivos ou pastas como arquivo ZIP, direto para o navegador;
  • Restaurar no agente — copiá-los para uma pasta em qualquer agente, por ex. de volta à VM (se ela roda o agente BackupZit) ou para um servidor de arquivos.

Na linha de comando: backupzit-agent pve ls --vmid 100 latest /etc e backupzit-agent pve extract --vmid 100 --target /srv/restore latest /etc/nginx; --volume seleciona uma partição ou volume lógico (pve ls sem caminho os lista). Navegar no console exige o backup em armazenamento de rede (SFTP, S3, SMB, Azure, repositório protegido).

Para contêineres (LXC) em ZFS, Navegar pelos arquivos abre diretamente seus arquivos, como os de um backup de arquivos; as pastas rootfs, mp0, mp1… são os volumes do contêiner. Arquivos restaurados em um agente mantêm proprietários e permissões. Eles são restaurados em uma pasta, não no local original: os caminhos do backup são os de dentro do contêiner, não do host. Um link simbólico só é seguido dentro do seu volume. Réplicas de contêineres copiados arquivo por arquivo ainda não são suportadas; restaure-os em vez disso.

Backup da configuração do host

Os convidados são só metade de um nó Proxmox: definições de armazenamento, rede, usuários, firewall, certificados e as configurações de cada VM e contêiner estão na configuração dele. Faça o backup dela com uma tarefa de arquivos comum no agente do nó: em Tarefas de backup, escolha o agente do nó e Arquivos e pastas e clique em Preencher a configuração do host. Isso preenche os caminhos /etc (com /etc/pve, a rede e /etc/hosts), /var/lib/pve-cluster (o banco de dados de configuração config.db) e /root; execute a tarefa, por exemplo, diariamente. O banco de dados muda enquanto o nó funciona, então o agente primeiro faz uma cópia consistente dele, que o backup contém como /var/lib/backupzit/pve-config/config.db; não são necessários pacotes adicionais.

Para reconstruir um nó com falha: instale a mesma versão do Proxmox VE com o mesmo nome de host e endereço, instale o agente, restaure /etc/network/interfaces e /etc/hosts no lugar, depois pare o serviço do cluster (systemctl stop pve-cluster), exclua config.db-wal e config.db-shm em /var/lib/pve-cluster se existirem, restaure a cópia consistente de /var/lib/backupzit/pve-config em /var/lib/pve-cluster (config.db, e config.db-wal se o backup tiver um), inicie o serviço de novo e restaure os convidados. Em um cluster, adicione um nó reinstalado ao cluster de novo em vez de restaurar config.db.
