Linux system backup & P2V

A Linux system job backs up a whole Linux machine so it can be recreated on an empty disk — the same machine after a disk failure, new hardware, or a virtual machine in Proxmox VE (physical-to-virtual, P2V).

What is backed up

  • Every local file system (ext2/3/4, xfs, vfat), also on LVM, file by file with owners, permissions, setuid bits, ACLs, extended attributes (SELinux labels, file capabilities), hard links and device files. Each file system is backed up separately; network shares and virtual file systems (/proc, /sys, /run) are skipped.
  • The disk layout: GPT or MBR partition tables with their IDs, LVM volume groups (vgcfgbackup), file system UUIDs, labels and on-disk features, and the boot code (MBR and the BIOS boot partition of GRUB).

Like Relax-and-Recover, BackupZit does not copy the running disk block by block: Linux has no built-in snapshot of a running disk, so a raw copy would be inconsistent. Each file is read whole, and the layout makes the restored disk bootable again. Databases should be dumped before the backup or backed up with their own tools.

Single files and folders are restored from a system backup like from any file backup (Restore files from this backup on the run page).

Not supported yet

Encrypted disks (LUKS), software RAID (mdadm), btrfs and systems spread over several disks. The job reports these clearly instead of creating an incomplete backup.

Restoring the whole system

Open the system backup run (job page or Activity) and use Restore the whole system:

As a new Proxmox VM

Choose the Proxmox node (its BackupZit agent does the work), storage, VM ID, name, memory and cores. BackupZit creates the VM with the same firmware as the original (UEFI/OVMF or BIOS), a VirtIO SCSI disk and network card, recreates the disk, restores all files and can start the VM. Because the VM is a copy that may run next to the original:

  • network settings bound to the old MAC addresses (common in cloud images: netplan match: macaddress) are changed to apply to any wired interface,
  • the BackupZit agent inside the copy is unenrolled, so it does not report as the original machine.

Onto a disk

Restore onto an empty disk of a Linux agent, e.g. a second disk (/dev/sdb), or onto the new machine itself (bare metal):

  1. On Recovery download the Linux recovery ISO and create a recovery code. Write the ISO to a USB stick (Rufus, balenaEtcher) or attach it to a VM. It boots on BIOS and UEFI machines.
  2. Boot the machine from it. The recovery system starts the agent, which connects to the console with backupzit/recovery.json from any other USB stick or disk, or asks for the server address and recovery code.
  3. The machine appears as a recovery agent. In the system backup run choose Onto a disk, that agent and its disk (usually /dev/sda, /dev/nvme0n1 or /dev/vda).

Any Linux live system works as well: start the agent there with sudo backupzit-agent recovery --server https://console:8443 --token CODE; the tools it needs (gdisk, LVM, mkfs) are named if missing. Tick Different hardware when the machine is not the original one.

The target may be larger or smaller than the original disk: the last partition grows to fill it, or shrinks as long as its data fits. The file system UUIDs and partition IDs stay the same, so /etc/fstab and the boot loader need no changes. For UEFI systems the boot loader is also installed at the removable-media path \EFI\BOOT\BOOTX64.EFI, which every UEFI firmware starts without a boot entry. RHEL-like systems (dracut) get a new initramfs with all drivers when moved to different hardware.

Command line

backupzit-agent system-backup  --repo ... [--exclude PATTERN]
backupzit-agent system-show    --repo ... latest
backupzit-agent system-restore --repo ... --target /dev/sdb [--new-hardware] --yes-erase-target latest
